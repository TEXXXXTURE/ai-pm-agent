# 发布计划技能（launch-plan）

把发布当成一个**协调问题**来规划：用分层让投入与场面匹配，让每条工作线都有且仅有一个具名责任人，并用一份真正的 go/no-go 清单把发布日"门控"起来——不达标就不放行，而不是靠心情决定上不上。

## 一、何时使用 / 先问用户什么

### 适用场景
- 用户说"帮我做发布计划 / 上线计划 / GTM 计划 / 发布清单 / 这个功能准备怎么发 / release plan / launch checklist"。
- 新产品、新功能、新版本、新套餐档位即将推向客户，需要协调产品、文档、客服、销售、市场、法务、数据、灰度发布等多条线。
- 发布前需要回答："这是多大场面的发布、谁负责什么、什么时候做什么、什么条件下才能发、发完谁盯着、出问题怎么撤。"

### 不适用
- 纯内部技术重构、不面向客户的改动——没有用户可感知的发布，不需要 GTM 机器，走发布说明即可。
- 还没想清楚"做什么、为谁做"的早期想法——发布计划是需求成熟后的协调工具；需求本身没理清时，先做需求澄清 / 路线图，不要拿发布计划倒推产品。
- 发布结束后的总结反思——那是复盘技能（retro）的活，本技能只在"Day1-7 安排首次复盘"处与其衔接。

### 先问用户什么（最多 3 个问题，信息不足先澄清）
1. **发布的是什么、目前处于什么阶段？**（全新产品 / 重要功能 / 小改进；规划中 / 即将发布 / 已发布要补计划）——这是分层的输入，决定投入规格。
2. **日期驱动还是范围驱动？**——是有硬性日期（展会、合同、合规截止），还是范围必须完整、日期可让？**两者不能同时被悄悄固定**，否则计划必崩，必须让用户显式选一个。
3. **"发布成功"在第 7 天和第 30 天分别用什么数字衡量？**（采纳率、功能激活、产生的商机 / 收入、留存等）——Tier1/2 没有数字化目标就不发布：没有目标的发布无法失败，也就无法成功。

规则：用户指令里已给出的信息直接采用、不重复问；**3 个问题问完或用户不回应，就带着【假设】标签继续推进，并在计划开头标注所采用的假设**（含建议的分层及理由）。

可选：动手前先查本地知识库中的历史发布、既有承诺与定位口径，避免新计划与既往结论冲突：
```bash
bash scripts/run-tool.sh scripts/kb_query.py --query "发布 上线 GTM 定位 承诺" --type decision,case --top-k 3
```
- `--query`：查询词（必填）；`--type`：`decision|eval|case`，可逗号分隔多类型；`--top-k`：返回条数，默认 3。
- 输出 JSON：`{"status": "ok/empty", "query": ..., "archives": [...]}`，无结果时 status 为 empty，不算错误。

## 二、工作流步骤

### 第 0 步：先分层，并请用户确认

大多数发布失败是**分层错配**——Tier3 的小修小补搞了一波公关推送，或 Tier1 的战略级赌注悄无声息地溜上线。先给出带理由的分层建议，**请用户确认后再展开计划**：

- **Tier 1（大发布）**：新产品或重大能力；公司级叙事；全套 GTM 机器（市场、公关、销售赋能、活动等全上）。
- **Tier 2（中等发布）**：面向已知细分人群的重要功能；定向宣告（博客、邮件、应用内通知）。
- **Tier 3（小发布）**：改进 / 修复；只出发布说明与文档更新。

计划的"重量"必须与层级匹配：Tier3 配十行清单就是浪费，Tier1 缺公关与赋能就是事故。层级确认后，按层级裁剪后续工作流，不需要的线直接砍掉。

### 第 1 步：定位一句话先于一切

先写定位句：**对于【目标受众】中饱受【痛点】困扰的人，【功能/产品】能带来【结果】，与【现有替代方案】不同的是【差异点】。**
- 如果这句话写不利索，说明发布话术还没准备好——**明确向用户标红旗**，不要带病进入物料制作。
- 定位句是所有受众话术、物料、销售口径的唯一源头。

### 第 2 步：搭工作流矩阵，每条线有且仅有一个具名责任人

按层级裁剪候选工作线：产品就绪度、文档 / 帮助中心、客服赋能（话术宏、已知问题清单）、销售 / 客户成功赋能、定价 / 套餐变更、市场物料、对外沟通 / 公关、法务 / 合规审查、数据埋点、灰度发布机制（开关、放量比例、回滚）。
- 每条工作线**有且仅有一个具名责任人**——"某团队""客服那边"不算责任人，必须落到一个人名。
- 每条线写清关键交付物与截止时间。

### 第 3 步：从发布日倒排时间线（T-minus），标出关键路径

- 以发布日为 T0 倒排（T-30、T-14、T-7……），每行挂里程碑与责任人。
- **显式标出关键路径**（决定发布日能否成立的最长依赖链，如合规审查、应用商店审核）。
- Tier 1–2 必须排入**发布演练 / Bug Bash（全员找茬）**时段。

### 第 4 步：明确灰度机制与回滚方案

- 写清开关策略与放量阶段：**internal（内部）→ beta（内测）→ X%（百分比放量）→ GA（全量）**，每阶段带日期或进入条件。
- **每个阶段写明观测指标与通过阈值**，达标才进下一阶段。"我们会盯着的"不是计划。
- **回滚触发条件必须是一个数字，不是心情**（如：错误率 > 2%、核心流程转化率下降 > 10%）；并写明回滚操作步骤与回滚责任人。

### 第 5 步：写 go/no-go 检查清单，并安排 T-2/T-3 会议

- 检查项**只允许二元判断**（能明确回答"是 / 否"）："文档基本好了"不合格，"帮助文章已发布并完成评审"合格。
- 每项都有 owner。
- **go/no-go 会议安排在发布前 T-2 或 T-3 天**，逐项过清单，任一项不过即 no-go。

### 第 6 步：发布后 Day1–7 值班安排与首次复盘

- 谁盯哪个数据看板、反馈从哪几个渠道汇到哪里、谁负责分流响应。
- 排定 Day1–7 值班表，并**确定首次复盘时间**（届时调用 retro 技能，对照本计划里的 D7 目标做上线后复盘）。

### 第 7 步：Top 3 风险

列出最值得防范的 3 个风险，每个都带**缓解措施**与**早期预警信号**（可观察的数字或事件，而不是"感觉不对"）。

### Tier1 扩展检查（仅 Tier 1 大发布必做，浓缩版）

Tier 1 在上述骨架之上，再补四件事；Tier2/3 不做，避免臃肿：

1. **滩头市场（beachhead）**：不面向"所有人"。按四个标准选一个最该先拿下的细分人群——痛点够不够痛、愿不愿且能不能付钱、打不打得赢（够得着、拿得下）、会不会转介绍；给出推荐与理由，并顺手标出拿下滩头后的相邻扩张人群。
2. **ICP（理想客户画像）**：公司规模 / 行业 / 地域等属性、决策人角色、他们雇佣本产品完成的具体任务（JTBD）、今天用什么替代方案、30 秒内可识别的资格信号。
3. **分受众信息**：购买者、使用者、影响者各看什么信息，用客户的语言而非内部术语写，每条信息配一个证据点（proof point）。
4. **渠道按预期 ROI 排序**：列出触达 ICP 的渠道（可达量、成本、优先级），pre-launch（等待名单 / beta / 抢先体验）与发布日、发布后动作同等重要，别只规划发布当天。

## 三、markdown 输出模板

```markdown
# 发布计划 — [功能/产品]，Tier [N]
**发布日期**：[日期]（驱动方式：固定日期 / 固定范围） · **总责任人（DRI）**：[人名]
**定位一句话**：[对于谁……与……不同的是……]
**成功定义**：D7 [数字目标] · D30 [数字目标]
**假设**：[用户未回答而采用的假设；没有则写"无"]

## 工作流矩阵
| 工作线 | 具名责任人 | 关键交付物 | 截止时间 | 状态 |
|---|---|---|---|---|
|        |            |            |          |      |

## 倒排时间线（关键路径以【CP】标注）
| T-minus | 里程碑 | 责任人 |
|---|---|---|
|         |         |        |

## 灰度与回滚
放量阶段：internal → beta → [X]% → GA（[各阶段日期 / 进入条件]）
各阶段观测指标：[指标 + 通过阈值]
**回滚触发条件**：[具体数字条件] → **操作步骤**：[步骤、责任人]

## Go/No-Go 检查清单（会议：T-[2/3]）
- [ ] [二元判断项] — [owner]

## Day1–7 值班与首次复盘
[看板盯守人 · 反馈汇集渠道与分流人 · 值班表 · 首次复盘日期（届时做 retro）]

## Top 3 风险
| 风险 | 缓解措施 | 早期预警信号 |
|---|---|---|
|    |         |              |

## Tier1 扩展（仅 Tier 1 填写）
- **滩头市场**：[人群 + 选择理由（痛点/付费/可赢/转介绍）+ 相邻扩张人群]
- **ICP**：[关键属性、决策人、JTBD、现用替代、资格信号]
- **分受众信息**：[购买者 / 使用者 / 影响者：信息 + 证据点]

```

落盘建议：发布计划可保存为 `output/发布计划-<产品或功能>-<日期>.md`。需要做成 PPT 汇报、发布时间线图、作战看板等演示物时，不自制 HTML，按项目规矩产出《演示需求交接单》（五要素：演示什么、受众、核心结论、数据素材、期望形式），交外置工具包处理。

## 四、呈现前质量自检清单

- [ ] 分层有明确理由且经用户确认；计划的工作线数量与场面重量与 Tier 匹配（Tier1 做了扩展检查，Tier3 没有被过度编排）
- [ ] 固定日期与固定范围只锁定了一个，没有双固定；定位一句话写得出来，写不出时已向用户标红旗
- [ ] D7、D30 成功指标是具体数字（Tier1/2 无数字目标不发布）
- [ ] 每条工作线都有且仅有一个**具名**责任人（"某团队"不算），且有关键交付物与截止时间
- [ ] 时间线按 T-minus 倒排、关键路径已标注；Tier1–2 排入了发布演练 / Bug Bash
- [ ] 灰度阶段 internal→beta→%→GA 完整，每阶段有观测指标与阈值；**回滚触发条件是数字而非心情**，且有操作步骤与责任人
- [ ] go/no-go 项全部可二元判断、每项有 owner；会议排在 T-2 或 T-3
- [ ] Day1–7 看板 / 反馈分流 / 值班 / 首次复盘时间已排定；Top3 风险各带缓解措施与预警信号
- [ ] 采用的假设已在开头标注；产物为 markdown；未自制 HTML / PPT 等演示物
