# 复盘技能（retro）

复盘不是表彰会也不是批斗会，而是一次**以改进为目的的结构化回看**：先拿当初定下的目标和数据对账，再从团队反馈里收敛出少数几条**有人领、有期限、能量化**的行动项。复盘对象不限于冲刺——迭代、版本发布、项目里程碑、增长实验、上线后观察期都适用。

## 一、何时使用 / 先问用户什么

### 适用场景
- 用户说"做个复盘 / 回顾 / retro / retrospective / 冲刺复盘 / 迭代回顾会 / 版本发布复盘 / 上线复盘 / 增长实验复盘 / 项目里程碑总结"。
- 一个有明确起点与终点、且**当初定过目标**的工作段刚结束，需要回答："目标达成没有、数据怎么说、什么有效什么无效、下次改什么。"
- 收到一批原始反馈（便利贴、问卷、群聊记录），需要聚类成主题并转成改进行动。
- 发布刚结束的 Day1–7：与发布计划技能衔接——发布计划里排定的首次复盘时间到了，就用本技能对照 D7 成功指标做上线后复盘。

### 不适用
- 工作段还没结束、目标尚未到检验时点——复盘会变成空谈；等节点到了再做。
- 当初没有任何目标 / 成功指标可对照（如一次从未定义成功的实验）：先如实说明"无基线可对账"，本次只能做经验梳理，并建议下次做事前先定成功指标（呼应"成功指标先于发布"原则）。
- 绩效评估 / 追责定性——复盘对事不对人，不产出针对个人的评价结论。

### 先问用户什么（最多 3 个问题，信息不足先澄清）
1. **复盘对象是什么、覆盖哪个时间段？**（冲刺 / 迭代 / 版本发布 / 项目里程碑 / 增长实验 / 上线后观察期）——对象决定看什么数据、用什么节奏。
2. **当初定的目标与成功指标是什么？有没有现成数据或材料？**（冲刺目标与 velocity、发布或实验前预设的成功指标与实际值、埋点报表、团队反馈、上次复盘记录）——先有对账依据，复盘才不凭印象。
3. **复盘格式有偏好吗？**——Start/Stop/Continue、4L、帆船三选一；没偏好就由我按上下文推荐（见工作流第 2 步）。

规则：用户指令里已给出的信息直接采用、不重复问；**3 个问题问完或用户不回应，就带着【假设】标签继续推进，并在复盘记录开头标注所采用的假设**。用户提供了文件（数据、图表、反馈、上次复盘记录）时，先读完再开始。

可选：动手前先查本地知识库中的历史决策、上次复盘行动项与发布时定下的成功指标，便于对账与结转：
```bash
bash scripts/run-tool.sh scripts/kb_query.py --query "复盘 改进 行动项 成功指标 发布目标" --type eval,decision --top-k 3
```
- `--query`：查询词（必填）；`--type`：`decision|eval|case`，可逗号分隔多类型；`--top-k`：返回条数，默认 3。
- 输出 JSON：`{"status": "ok/empty", "query": ..., "archives": [...]}`，无结果时 status 为 empty，不算错误。

## 二、工作流步骤

1. **先对账：目标达成与数据，再谈感受。**
   - **冲刺 / 迭代**：冲刺目标是否达成；承诺点数与完成点数（velocity 对比承诺，是过度承诺还是承诺不足）；遇到的阻塞及如何解除；协作模式上什么有效、什么无效。
   - **版本发布 / 上线后**：对照发布前预设的 D7 / D30 成功指标看实际值（没有预设指标就如实标注"无法判定成败"，不归罪于团队）；灰度各阶段是否达标、有没有触发回滚。
   - **增长实验**：对照实验前定的主指标与判定阈值，结论是成立、不成立还是数据不足；样本与周期是否够。
   - **项目里程碑**：对照里程碑验收标准与原定时间 / 范围 / 质量约束。
2. **选一种复盘格式**（按上下文推荐，或让用户指定）：
   - **格式 A — Start / Stop / Continue**：开始做什么 / 停止做什么 / 哪些有效要继续。最通用，适合迭代与发布复盘的默认选择。
   - **格式 B — 4L（Liked / Learned / Lacked / Longed For）**：喜欢的 / 学到的 / 缺失的 / 渴望拥有的。适合学习密度高、新事物多的项目里程碑或首次上线。
   - **格式 C — 帆船（Sailboat）**：风（什么在推动我们）/ 锚（什么在拖慢我们）/ 礁石（前方风险）/ 岛屿（目标在哪）。适合需要兼顾前瞻风险的增长实验与长周期项目。
3. **有原始反馈时做聚类分析**（便利贴、问卷、群聊等）：把相似条目归并成主题；标出被提及频次最高的话题；记录情绪模式（挫败、兴奋、困惑），情绪集中的地方往往是最该改的地方。
4. **生成优先级行动项**（核心产出）：

   | 优先级 | 行动项 | 责任人 | 截止日 | 成功度量 |
   |---|---|---|---|---|
   | 1 | [具体、可执行的改进] | [人名 / 角色] | [日期] | [怎么知道它生效了] |

   - **只留 2–3 条**——行动项多了等于没有，不会被执行。
   - 每条必须**具体、可指派给某个人、可度量**；"加强沟通"不合格，"每周三站会同步阻塞清单，由张三负责，连续 4 周阻塞平均解决时长下降 30%"合格。
5. **结转检查**：如果有上期复盘行动项，逐条核对状态（已完成 / 进行中 / 未启动）；未完成的要给出处置结论（继续挂账、改写、放弃），不许悄悄消失。
6. **基调把控**：全程建设性、对事不对人——目标是改进系统与流程，不是追责；归因指向机制与条件，陈述用事实和数据，不给人贴标签。

## 四、呈现前质量自检清单

- [ ] 先对账后谈感受：目标与数据在前，主题与感受在后；冲刺看了 velocity，发布 / 实验对照了**事前预设**的成功指标（没有预设指标时已如实标注无法判定，未编造结论）
- [ ] 复盘对象明确（迭代 / 发布 / 里程碑 / 实验 / 上线后），格式选择有推荐理由或经用户指定
- [ ] 有原始反馈时完成了主题聚类、高频话题与情绪模式识别，而非逐条罗列
- [ ] 行动项只有 2–3 条，每条具体、可指派到具名责任人、有截止日、有可验证的成功度量
- [ ] 上期行动项逐条核对了结转状态，未完成项有处置结论，没有悄悄消失
- [ ] 全文对事不对人：归因指向机制与事实，无追责定性、无人身评价
- [ ] 与发布场景衔接时，对照的是 launch-plan 中 D7/D30 既定目标；采用的假设已在开头标注
- [ ] 产物为 markdown；未自制 HTML / PPT 等演示物
