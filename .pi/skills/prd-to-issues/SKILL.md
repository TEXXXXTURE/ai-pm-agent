# 拆工单技能（prd-to-issues）

把一份成形的 PRD 变成研发可以直接领取的工单 backlog。灵魂原则是**纵切（vertical slice）**：每张工单交付一条窄但完整、端到端可演示、可验收的用户价值路径——"用户能完成某件事并看到结果"，而不是"做前端页面 / 写后端接口 / 补测试"这种横向 layer 票。

**确认门**：默认只产出工单清单草案；用户明确确认粒度、依赖和优先级后，才进入发布。

## 一、何时使用 / 先问用户什么

### 适用场景
- 用户说"把这个 PRD 拆成工单 / 拆成 issue / 排一下研发任务 / 开发要做哪几单 / 按 vertical slice 拆"。
- PRD 已经过评审或基本成形，目标、主流程、验收口径清楚，需要变成可分配的开发任务。

### 不适用
- 只有想法、还没有 PRD → 先走需求澄清 / PRD 流水线。
- PRD 缺口严重到无法判断"做完什么样算对"（目标、主流程、验收口径缺失，或需求间互相冲突）→ **先建议用 `prd-review` 技能评审**，不硬拆；硬拆等于把产品决策偷偷塞给研发。
- 要文件级实现计划、技术方案设计、提交节奏 → 那是研发侧的技术计划，本技能只交付产品口径的工单。

### 先问用户什么（最多 3 个问题，信息不足先澄清）
1. **PRD 在哪？**——文件路径、对话中的内容，或外部文档；读不到就请用户提供正文。
2. **工单给谁用、用什么系统承接？**——研发小组内部分配 / GitHub Issues / 其他工单系统；决定输出格式与标签建议。
3. **要不要按版本（V1/V2/V3）切？**——大需求先出版本地图再拆单；小需求直接纵切即可。

规则：用户已给的信息不重复问；问题问完或用户不回应，带着【假设】标签继续，并在工单清单开头标注假设。

## 二、工作流步骤

1. **定位输入。** 读取 PRD（`prd.md` / 文件路径 / 对话内容），记录来源。
2. **过 Readiness 门禁。** 快速核对：目标用户、要解决的问题、非目标、主流程、验收口径、关键约束、未决问题是否齐备。
   - 齐备 → 继续拆。
   - 缺到无法判断通过/失败，或需求间冲突 → 停下来，列出最少的待澄清问题，并建议先走 `prd-review`；**不把 PRD 的未决产品问题包装成工单**。
3. **按纵切拆工单。** 每张工单是一条端到端用户价值路径：
   - 拆完问一句："这单单独做完，能给用户演示一件完整的事吗？"——不能，就是切错了（横切了或粒度不对）。
   - 每张工单标注类型：**AFK**（away-from-keyboard，研发可直接动手，决策已定）/ **HITL**（human-in-the-loop，内含架构决策、设计确认、产品取舍或人工审查，必须先有人拍板）。未确认的决策绝不标 AFK。
   - 大需求先切版本（V1/V2/V3）：每个版本有独立的用户结果、范围、非目标、依赖、验收、风险与回滚点；版本内再纵切。不允许只按时间或前后端层级切版本。
4. **建覆盖矩阵核对无遗漏。** PRD 里每个功能点、user story、验收标准，要么被某张工单覆盖，要么明确标注"排除 + 原因"。发现 PRD 缺口时不硬拆，标为"待澄清（HITL）"或建议 `prd-review`。
5. **出工单清单草案。** 每张工单至少包含：标题、类型（AFK/HITL）、优先级/建议标签、来源章节、**用户价值**、做什么（端到端行为描述）、**验收标准**（可勾验的 checklist）、验证方式、**依赖**（blocked by 哪单）、开放问题。
6. **交用户确认。** 请用户核对：粒度是否过粗/过细、依赖顺序对不对、AFK/HITL 标注对不对、要不要合并/拆分/调优先级。**用户没点头，不发布。**
7. **确认后发布。**
   - 默认方式：输出每张工单**可直接粘贴的 issue markdown**（标题 + 正文代码块），由用户自行粘贴到工单系统。
   - 若用户环境有 `gh` 命令，可提示用法（如 `gh issue create --title "标题" --body-file 工单.md`，按依赖顺序先建被依赖的单），但**只提示、不擅自执行**；创建后回填编号/链接，不关闭、不改写原始 PRD。

## 三、markdown 输出模板

### 工单清单草案（确认前）

```markdown
# 工单拆解草案 — [PRD 名称]，[日期]
- **来源 PRD**：[文件 / 对话 / 链接]
- **模式**：草案（待用户确认后才发布）
- **Readiness**：通过 / 需澄清（见下）/ 阻塞（建议先 prd-review）
- **假设**：[用户未回答而采用的假设；没有则写"无"]

## 版本地图（大需求才需要；小需求删去本节）
| 版本 | 独立交付的用户结果 | 范围 | 非目标 | 依赖 | 验收/回滚要点 |
|---|---|---|---|---|---|
| V1 |  |  |  |  |  |

## 工单清单
### 工单 1：[标题——一句话说清端到端价值，如"用户可用邮箱注册并收到欢迎邮件"]
- **类型**：AFK / HITL（HITL 需写明：待谁拍板什么决策）
- **优先级 / 建议标签**：
- **来源**：[PRD 章节 / user story]
- **用户价值**：[这单做完，用户能完成什么、得到什么]
- **做什么**：[端到端行为，从用户触发到可见结果]
- **验收标准**：
  - [ ] 给定……当……则……（可测试、可勾验）
  - [ ]
- **验证方式**：[怎么演示/测试这单]
- **依赖**：无 / 被工单 X 阻塞
- **开放问题**：无 / ……

### 工单 2：……

## 覆盖矩阵
| PRD 功能点 / 验收标准 | 覆盖工单 | 状态 | 备注 |
|---|---|---|---|
|  | 工单 X | 已覆盖 |  |
|  | — | 排除 | [原因，如"V2 再做"] |

## 请确认
- [ ] 粒度是否合适（过粗/过细？）
- [ ] 依赖顺序是否正确
- [ ] AFK / HITL 标注是否正确
- [ ] 是否需要合并、拆分、调优先级或标签
- [ ] 确认后：输出可直接粘贴的 issue markdown（默认）/ 需要 gh 发布命令提示
```

### 发布结果（用户确认并发布后）

```markdown
## 发布结果
- **来源 PRD**：[引用]
- **已创建工单**：[编号 / 链接 / 或"已输出 N 份可粘贴 markdown"]
- **未创建**：[项及原因，如待澄清的 HITL 项]
- **覆盖缺口**：[仍未解决的 PRD 项]
- **后续建议**：[如 先 prd-review 补缺口 / 工单 X 解锁后再开工单 Y]
```

落盘建议：工单清单可保存为 `output/工单拆解-<名称>-<日期>.md`。需要做成看板 / 图表汇报时，不自制 HTML，按项目规矩产出《演示需求交接单》。

## 四、呈现前质量自检清单

- [ ] 没有"前端票 / 后端票 / 测试票"这类横切票；每张工单单独做完都能端到端演示一件完整的事
- [ ] 每张工单四要素齐全：标题 / 用户价值 / 验收标准 / 依赖（另含类型、来源、验证方式、开放问题）
- [ ] 验收标准可测试、可勾验（给定……当……则……），不是"做好 / 支持"类虚词
- [ ] 覆盖矩阵覆盖 PRD 全部功能点与验收标准；排除项有理由，缺口项标"待澄清"而非硬拆
- [ ] AFK / HITL 标注正确；未决产品决策没有被包装成研发可直接动手的票
- [ ] Readiness 门禁已过；PRD 缺口严重时已建议先走 `prd-review`，没有静默跳过
- [ ] 大需求先有版本地图（V1/V2/V3 各自独立可交付），不是按时间或前后端分层
- [ ] 依赖关系成图、顺序正确（被依赖的单先建）；无循环依赖
- [ ] 用户确认前没有任何发布动作；`gh` 只提示用法、未擅自执行
- [ ] 产物为 markdown；未自制 HTML / PPT 等演示物
