# 反馈分类技能（feedback-triage）

把一堆原始反馈变成一张**按痛点排序、可精确计数、带用户原话凭证**的图——让团队看清真正在伤害用户的是什么。

## 一、何时使用 / 先问用户什么

### 适用场景
- 用户说"帮我分类这批反馈 / 评论 / 工单""分析下这些差评 / NPS 留言""用户都在抱怨什么"。
- 用户贴来反馈文本，或给出反馈导出文件（CSV、Excel、文本 dump）。
- 需要从批量反馈中识别主题、频次、严重度，产出可排优先级的行动清单。

### 不适用
- 单条反馈的深度解读、单场用户访谈的纪要整理（不是批量分类场景）。
- 需要专业 NLP 平台 / 情感分析 API 的重型统计（本技能靠逐条判读打标 + 代码精确计数完成）。

### 先问用户什么（最多 3 个问题，信息不足先澄清）
1. **反馈来源与时间窗口？**——应用商店评论偏愤怒、销售笔记偏成单、NPS 留言偏极端；来源偏差必须在报告开头点名。
2. **业务背景？**——什么产品、哪个版本 / 平台、这批反馈对应什么事件（发版 / 活动 / 故障）。
3. **输出用途与切分维度？**——报告给谁看、要支撑什么决定；有无值得切分的字段（套餐档位、平台、用户任期）——40% 企业客户的投诉和 40% 免费用户的投诉，优先级完全不同。

用户不回答就带着合理【假设】继续推进，并在报告"方法说明"里标注所采用的假设。

## 二、工作流步骤

1. **通读 / 解析全部反馈**。结构化导出文件（CSV / Excel）用代码（Python）加载处理，不要凭眼睛看；同一用户的明显重复条目去重，并记录去重前后条数。**大批量（>200 条）必须用代码精确计数，不凭印象估数**（可在 Git Bash 中用项目 venv 的 Python 跑临时统计）。
2. **逐条打标**，每条三个标签：
   - **主题**：分类法从数据里自下而上归纳，不硬塞进预设桶；主题上限约 10 个，超出就合并相近主题或归入"其他"；
   - **严重度**：四档——**阻塞**（无法使用 / 数据丢失）/ **重大摩擦**（主要流程受阻）/ **轻微**（体验瑕疵）/ **需求**（新功能诉求）；
   - **分群**（如有字段）：套餐 / 平台 / 任期等。
3. **诚实计数**：同时报原始条数和占总数百分比。**数字是 7 就不许写"很多用户"**。
4. **按痛点排序，不只看音量**：排序 = f(条数, 严重度, 分群价值, 趋势)。付费客户的低频阻塞问题，可以排在高频外观吐槽前面；当痛点排序与原始条数排序不一致时，必须写出理由。
5. **每个头部主题摘 2-3 条用户原话**（逐字引用，不改写），并标注可追溯的来源 ID（行号 / 工单号 / 评论链接）。原话在组织里比数字传得更远。
6. **每个头部主题给一条行动建议**：立即修复 / 深挖调查 / 进 backlog（注明位置）/ 公告 workaround / 不行动（写明理由）。**对所有主题都建议行动等于分类失败——"不行动"要敢于使用**。
7. 专门记录两类边角信息：
   - **排序分歧**：痛点排序与音量排序不一致的地方及理由；
   - **观察名单**：量小但新增 / 快速增长的信号。

## 三、markdown 输出模板

```markdown
# 反馈分类报告：[来源]，[时间窗口]
**总量**：[N] 条（从 [M] 条去重而来） · **已知偏差**：[来源偏差，如：应用商店评论偏愤怒]
**分群维度**：[套餐 / 平台 / 任期，或"无"]

## 一句话结论
[这批数据说出的、最重要的一件事]

## 主题痛点排序表
| # | 主题 | 条数 | 占比 | 严重度 | 分群集中情况 | 趋势 |
|---|------|------|------|--------|--------------|------|
| 1 |      |      |      |        |              |      |
| 2 |      |      |      |        |              |      |

## 头部主题详情
### 1. [主题]
- **计数**：[n 条，占 x%]；严重度：[阻塞 / 重大摩擦 / 轻微 / 需求]
- **用户原话**：
  > "[原话 1]" —— [来源 ID，如：工单 #1234 / 评论第 7 行]
  > "[原话 2]" —— [来源 ID]
- **为什么排这里**：[与条数排序不一致时必须写明理由]
- **建议行动**：[立即修复 / 深挖调查 / 进 backlog / 公告 workaround / 不行动 + 理由]
- **建议负责方**：[如：客户端组 / 客服 / 产品]

### 2. [主题]
- ……

## 排序分歧
[痛点排序 ≠ 音量排序的地方，及理由；没有则写"无"]

## 观察名单
[量小但新增 / 快速增长的信号；没有则写"暂无"]

## 方法说明
```

落盘建议：报告可保存为 `output/反馈分类-<来源>-<日期>.md`。需要做成网页 / PPT / 图表汇报时，不自制 HTML，按项目规矩产出《演示需求交接单》。

## 四、呈现前质量自检清单

- [ ] 结构化输入的每个计数都是精确值（代码统计），不是估计；条数与占比齐全，总量行写明去重前后数字
- [ ] 原话逐字未改写，每条带可追溯的来源 ID
- [ ] 报告开头已点名来源偏差（评论偏愤怒 / NPS 偏极端 / 销售笔记偏成单）
- [ ] 主题 ≤10 个，分类法从数据自下而上归纳，未硬套预设桶
- [ ] 严重度四档判定标准一致；每条反馈都有主题标签
- [ ] 痛点排序与音量排序不一致处均已写明理由，没有悄悄换位
- [ ] 每个头部主题都有明确行动建议，且"不行动"在该用的地方用了（附理由）
- [ ] 排序分歧、观察名单、方法说明（含去重规则与假设）齐全
- [ ] 产物为 markdown；未自制 HTML / PPT 等演示物
