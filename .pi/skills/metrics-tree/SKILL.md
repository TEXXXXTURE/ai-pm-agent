# 指标树技能（metrics-tree）

定义衡量**交付了多少价值**的指标，拆成团队能撬动的驱动因素，并落实到计算这些指标所需的事件——让指标活在数据看板里，而不只是幻灯片上。

## 一、何时使用 / 先问用户什么

### 适用场景
- 用户说"帮我们定义指标 / 指标体系怎么建 / 北极星指标是什么 / 建个指标树 / KPI 框架 / 我们该衡量什么 / 数据看板要看什么 / 出一份埋点方案（埋点规范）"。
- 产品方向已定，需要把"成功"翻译成可测量、可拆解、可埋点的指标体系。
- 需要区分**虚荣指标**（数字好看但不能指导行动，如注册数、浏览量）与**可行动指标**（团队能撬动、与价值交付算术相连）。

### 不适用
- 单次取数、做报表、分析某份已有数据（那是数据查询，不是指标体系设计）。
- 产品价值时刻本身还没定义清楚就要定指标——先澄清"产品对用户生效的瞬间是什么"。

### 先问用户什么（最多 3 个问题，信息不足先澄清）
1. **产品的核心价值时刻是什么？**——用户做了什么动作时，说明产品对他真正生效了？北极星数的应该是这个动作，而不是它周围的热闹（注册、打开、浏览）。
2. **商业模式与当前阶段？**——广告、SaaS 席位、按量计费、交易市场的指标树结构完全不同；0→1 验证期、增长期、成熟变现期关注的指标也不同。
3. **现在已经埋了哪些点 / 有哪些数据？**——建在缺失事件之上的漂亮指标树是小说；每个叶子指标都要能从真实事件算出。

规则：用户指令里已给出的信息直接采用、不重复问；**3 个问题问完或用户不回应，就带着【假设】标签继续推进，并在文档中标注所采用的假设**。

可选：动手前先查本地知识库中的历史决策 / 评测（既往可能已讨论过指标取舍或埋点现状）：
```bash
bash scripts/run-tool.sh scripts/kb_query.py --query "北极星 指标 埋点" --type decision,eval --top-k 3
```
- `--query`：查询词（必填）；`--type`：`decision|eval|case`，可逗号分隔多类型；`--top-k`：返回条数，默认 3。
- 输出 JSON：`{"status": "ok/empty", "query": ..., "archives": [...]}`，无结果时 status 为 empty，不算错误。

## 二、工作流步骤

1. **提出北极星指标**，并给出 2 个考虑过但否决的备选（写明否决理由——否决理由教会团队这个指标在防什么）。每个候选必须过**作弊测试**：*如果我们用一种赚钱但让产品变差的方式做事情，这个数字会涨吗？* 会涨就是可被博弈的虚荣指标——修正它或给它配护栏。
2. **拆成驱动因素树，2–3 层深**。每个节点必须同时满足三条：团队能撬动、能从真实事件算出来、与父节点有明确算术关系（写明关系：求和 / 乘积 / 漏斗转化率）。
3. **标注输入指标 vs 输出指标**：团队拥有输入指标（驱动因素，自己能动手改善）；管理层盯输出指标（结果）。逐个节点标明归属。
4. **配护栏指标**：为每个驱动因素命名一个"抓住丑陋做法"的指标——例：驱动因素是"人均会话数"，护栏就是"任务完成率"，防止靠骚扰用户刷会话量。
5. **写埋点规范**：每个叶子节点写清事件名、触发时机、事件属性、当前状态（已有 / 需新增）。事件名统一使用 `对象_动作`（object_action）命名，产出工程师不需要再开会追问就能直接实施。

## 三、markdown 输出模板

```markdown
# 指标体系 — [产品]，[日期]
**假设**：[用户未回答而采用的假设；没有则写"无"]

## 北极星指标
**[指标名]** — [精确定义：计数规则 + 时间窗口，如"每个自然周内至少完成 1 次 X 动作的去重用户数"]
*为什么是它*：[与核心价值时刻的关系]
*已否决备选*：[备选 1 — 否决理由] · [备选 2 — 否决理由]
*作弊测试*：[它可能怎么被刷上去，以及对应护栏]

## 驱动因素树
[缩进树；每个节点标注：指标名、与父节点的算术关系、输入/输出标签、负责团队]

北极星
├── 驱动 A（乘积关系：A = B × C）[输出]
│   ├── 驱动 B [输入 — X 团队]
│   └── 驱动 C [输入 — Y 团队]
└── ……

## 护栏指标
| 驱动因素 | 丑陋的撬动方式 | 护栏指标 |
|---|---|---|
|          |                |          |

## 埋点规范
| 指标 | 事件名（对象_动作） | 触发时机 | 事件属性 | 状态（已有/需新增） |
|---|---|---|---|---|
|    |                    |          |          |                     |

## 基线与复盘
[已知当前基线值（不知道就写"待埋点后采集"）；建议的复盘节奏；指标文档负责人]
```

落盘建议：指标体系可保存为 `output/指标体系-<产品>-<日期>.md`。需要做成网页看板 / PPT 汇报时，不自制 HTML，按项目规矩产出《演示需求交接单》。

## 四、呈现前质量自检清单

- [ ] 北极星数的是价值而非活跃——注册数、会话数、浏览量一律不合格，除非产品价值本身就是注意力
- [ ] 每个定义都精确："活跃用户"必须写清定义"活跃"的动作 + 时间窗口，否则不合格
- [ ] 树的算术成立：父节点 = 子节点按明示关系（求和 / 乘积 / 漏斗率）算出；没有孤立的虚荣指标
- [ ] 每个驱动因素都配了护栏指标，且护栏能抓住对应"丑陋做法"
- [ ] 埋点规范照文即可实施：事件名、触发时机、属性齐全，工程师不需要再开会追问
- [ ] 事件名统一 `对象_动作` 命名；每个叶子指标标注了"已有 / 需新增"状态
- [ ] 2 个否决备选及否决理由、作弊测试结论齐全
- [ ] 输入 / 输出标签、负责团队标注齐全；商业模式与产品阶段已在分析中考虑
- [ ] 产物为 markdown；未自制 HTML / PPT 等演示物
