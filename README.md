# AI PM Agent

**AI PM Agent 把 "AI 产品需求" 跑成一条确定性流水线：一句需求进去，PRD、评审结论、研发工单、发布计划按固定顺序出来，8 个节点停下来等你拍板。**

它是给产品经理用的工作流助手，不是编程助手。写代码、修 bug、搭工程不归它管。

## 它解决什么问题

AI 产品从想法到上线，麻烦不在 "写文档慢"，在四个说不清：

1. 这需求算不算 AI 需求、值不值得做 —— 靠拍脑袋
2. 模型到底能不能做到 —— 信榜单、凭感觉
3. 什么算 "做对了"—— 开发前没人定义
4. 上线后质量、成本谁来负责 —— 没人接

这个项目的做法：把每一件说不清的事，变成可测量、可接管、可控成本的事。产物带实测证据，判断留给人。

## 它怎么工作

需求进来先判定走哪条轨：AI 核心需求走完整 12 段，普通需求跳过 AI 专项段，两条路都能从开头跑到收尾。

| 段 | 干什么 | 产什么 |
| --- | --- | --- |
| 0–0.5 | 接收需求、修订整合 | 需求草案（等你确认） |
| 1 | 挖需求、判断是否 AI 核心 | 用户洞察、初始考题 |
| 2 | 判断需求与 AI 的边界 | 三方对照 + 探针实测证据 |
| 3 | 写 PRD | ai-native PRD |
| 4 | 评审 PRD | 五维评审报告，一票否决 |
| 5 | 设计评测体系 | 四层考题 + 双及格线 |
| 6 | 对比选型模型 | 候选各跑一遍，代码硬判推荐 |
| 7 | 拆研发工单 | 工单 + 覆盖矩阵 |
| 8 | 构建期跑评测 | 真跑结果，不达线不放行 |
| 9 | 写发布计划 | 7 步计划 + 灰度 / 回滚 / go-no-go |
| 收尾 | 产物写成文件 | 全部落 output/ |

全程 8 处 HITL（Human-in-the-Loop）停下来等人：需求确认、草案确认、可行性确认、评测体系确认、对比选型、工单确认、发布计划确认、评测执行。你回一句话或一个决定，它接着走；你不答，它停着等，不替你拍板。

## 和主流 AI 工具不一样的地方

**结论由代码判，不由模型说。** 模型只出草案：打分、JSON、清单。评审过不过、评测达不达标、选哪个模型、就绪度几档，全部由代码按数值算。换模型不影响结论，同一份输入跑两遍结果一样。

**模型能力靠实测，不信榜单。** 第 2 段拿真实样例真跑探针：能做什么、做不到什么、需要什么工具兜底，用证据说话，证据不齐不放行。

**评测先于开发。** 需求一确认就开始建考题（典型 / 边界 / 对抗 / 回放四层），开发前先定 "什么算对"；构建期真跑评测，不达及格线不放行。

**结论带证据等级。** 关键结论标 [T1]-[T5] 来源等级（实测 / 用户 / 分析 / 口述 / 直觉），低等级驱动的决策显式标出；发布前做 11 维就绪度打分 + 阻断项检查。

## 跑一遍是什么样

```bash
PYTHONPATH=src python scripts/run_prd_workflow.py \
  --requirement "客服回复建议助手：客服与用户聊天时，AI 根据上下文生成 1-3 条回复建议供一键采用；识别到情绪激烈或涉及投诉赔付时不给建议，提示转人工组长。" \
  --name 客服回复建议助手
```

跑起来它先复述需求、给出一个 "这算不算 AI 需求" 的判断，然后停下来等你回话：

```
STATUS: HITL
THREAD_ID: 4461143c-6ed5-4de8-9e51-981a3c45312e
NODE: requirement_confirm
QUESTION: 节点「requirement_confirm」进入需求确认门。请审阅下方需求理解与 AI 适用性分流建议，确认无误后回复 confirmed，或回复「非AI」改判普通轨、「AI核心」改判 AI 全轨；其他文本作为需求修订意见处理（分流沿用模型建议，不二次中断）。
---
[中断载荷]
requirement_name: 客服回复建议助手
raw_requirement: 客服回复建议助手：客服与用户聊天时，AI 根据上下文生成 1-3 条回复建议……
---
END HITL
```

你回一句 "确认"（或 `confirmed`），它接着往下走。全程有 8 处会这样停下来等你。跑到一半想歇会儿也行：记下 THREAD_ID，回头 `--resume <THREAD_ID> --answer "确认"` 从上次停的地方接着跑。

跑完的产物是文件：

```
output/客服回复建议助手/
├── 需求文档/   客服回复建议助手-prd.md
├── 需求洞察/   客服回复建议助手-insights.md
├── review/     客服回复建议助手-review.md      五维评分 + AI 维度专项检查
├── 研发工单/   客服回复建议助手-issues.md      按「用户能做完一件事」切的工单
├── 发布计划/   客服回复建议助手-launch_plan.md  7 步发布计划
└── 评测/       eval_report.md、bakeoff_report.md、results.json
```

## 装起来

需要 Python 3.11 以上。

```bash
pip install -r requirements.txt
cp .env.example .env        # 填一个模型密钥，默认读 DEEPSEEK_API_KEY
```

测试不用密钥，全跑本地假模型，不花钱：

```bash
pip install -r requirements-dev.txt
PYTHONPATH=src python -m pytest tests/ -q        # 819 passed
```

模型默认走 DeepSeek；Anthropic、Gemini、Ollama 等按 `config.yaml` 里 `llm.providers` 的注释模板取消注释就能接入。密钥只从环境变量读，不写进文件。

项目有一条红线：工作日 09-12 / 14-18 峰时不调 DeepSeek，真机与重活排谷时。

## 项目怎么组织的：判定留内核，执行放外面

架构刻意不做创新，12 项选型逐一对到业界官方文档（见 `docs/技术选型与架构对位报告.md`）。项目自己定的是三层边界：

- **内核**（`src/`）：判定与契约。路由由代码决定，模型不决定走向；结论一律代码硬判。
- **SOP 层**（`AGENTS.md`、`references/`、`docs/`）：规则与清单。告诉 Agent 去哪调什么。
- **外置层**（`scripts/`、`.pi/skills/`、外置工具包、`domain_kb/`）：可替换的执行件与内容。工具随时换，结论不动。

一句话：执行可外置，判定留内核；内容可外置，契约留内核。

```
src/            流水线本体：节点、判定、状态机、提示词、校验
tests/          819 个测试（跑本地假模型，零 API 费）
scripts/        入口脚本与工具脚本
artifacts/      产物模板
.pi/skills/     常驻对话 Agent 的 11 个 PM 技能与操作手册
references/     工具路由表、模型候选清单、流水线拓扑
docs/           PRD、技术设计、工作流设计、职能标准调研、选型对位报告
AGENTS.md       给运行本产品的 Agent 读的人设与纪律
config.yaml     模型、知识库、阈值等配置
```

仓库里只有产品本体。会话记录、任务书、调研草稿这些过程文档留在本地，不上仓库。

## 还没做的

- 上线后的灰度监控和数据回流只有接口，没实现
- 演示类产物（PPT、图表、原型）依赖外置工具；工具没装，这一段只能给出 "要做什么" 的说明
- 领域知识库要自己建库；没有语料时，那一段的检索会直接跳过
- 人工确认点的周边设施（通知、超时、升级、审计）还没做全
