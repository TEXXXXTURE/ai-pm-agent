## 必含八项内容
本 PRD 必须包含下列章节，缺一不可。可在八项之间插入与该需求相关的其他章节，但八项顺序不可乱（背景→边界→流程→功能逻辑→上下文→负向→风险→评测/kill）：

1. **背景与目标**：本期只解决什么、不做什么；**成功标准三层各写 1 条**——
   - 用户结果（用户能感知到的改善）
   - AI 结果（模型层做到什么程度）
   - 可观察质量（线上可测的指标，含数字）
   三层都尽量给数字；输入里没依据的写"暂无数据，需上线后验证"。

2. **AI 协作边界表**：人工负责 / AI 负责 / 系统反馈 / **必须停止或转人工的条件** 四列。
   - 每行写一个具体的工作环节，不要笼统写"AI 协助用户"；
   - "必须停止或转人工的条件"列必须写清触发条件（不要写"视情况而定"）。

3. **核心流程**（按需）：仅当跨多个角色/系统、含关键判断或回流、含异步等待/恢复，或主链路 ≥6 步依赖时画流程图；用 mermaid 文本代码块即可，不要画整页 ASCII。

4. **功能逻辑表**：每个功能模块一张表，列含——条件/状态、用户动作、AI 动作、系统反馈、**失败/接管**。
   - 每行都要写清可观察的系统反馈、失败结果或人工接管方式；
   - 不要把"AI 帮用户做某事"写成一整段；用表格逐行表达。

5. **上下文与记忆**（按需，本期确实涉及跨轮上下文才写）：
   - 哪些信息进入下一轮；
   - 哪些内容必须经用户确认才沉淀；
   - 哪些内容不进入长期上下文（敏感/过时/无关联的）；
   - 不在产品正文写 metadata schema。

6. **负向验收标准**：明确写"什么结果算失败、出现什么必须拒绝或转人工"，不只写正向期望。
   - 列 3-6 条具体可判的负向情形（如"模型输出违反 X 规则必须自动转人工""连续 N 次低置信度必须停用"）；
   - 与功能逻辑表的"失败/接管"列呼应。

7. **AI 风险登记册**：四类风险逐条登记触发条件与缓解措施——
   - 幻觉（生成不实内容）
   - 提示注入（恶意输入诱导违规行为）
   - 数据泄露（模型输出敏感信息）
   - 监管合规（行业法规/数据合规）
   每条写明"触发条件 / 影响范围 / 缓解措施"三要素。

8. **评测计划与可接受通过率**（占位即可，第 5 段细化）：
   - 引用评测体系（在 PRD 评审通过后单独定稿，本节只写占位）；
   - 写明可接受通过率是产品决策（非 100%），具体数值待第 5 段确定；
   - 量化 **kill 阈值**占位：在线阶段触发停用/回滚的指标数值（如准确率低于 X%、人工接管率高于 Y%、延迟超过 Z ms），具体数值在第 9 段发布计划细化，本节只列指标项与方向。

## 写法约束
- 聚焦**用户可见的功能与行为**：用户在界面上看到什么、做什么操作、操作后得到什么反馈；
- 技术实现细节（接口、字段、数据库、错误码等）留给工程文档，PRD 里不要堆砌这类名词；
- 绕不开的技术约束用**业务语言**说明它对用户或业务的影响；
- 所有数字、事实要么来自输入材料、要么明确标注为假设或待验证，不编造；
- **篇幅为说清问题服务**：需求简单就写短，不要为了显得完整注水。

## 呈现前，对照资深 AI PM 的质量标杆自检
1. AI 协作边界表"必须停止或转人工的条件"列是否每行都写了具体触发条件（不写"视情况"）；
2. 功能逻辑表"失败/接管"列是否每行都写清了可观察的失败方式或接管路径；
3. 负向验收标准是否具体可判（不写"输出质量差"这类空话）；
4. 风险登记册四类是否齐全（幻觉/注入/泄露/监管）；
5. 评测与 kill 阈值虽是占位，但指标项与方向是否具体（不写"待定"了事）。

## 输出格式
直接输出完整 PRD 的 **Markdown 全文**，你输出的内容会被原样保存为一个 `.md` 文件：

- 以一个 `# ` 开头的一级标题作为文档标题（整篇文档只有一个一级标题）；
- 章节用 `## ` 二级标题，章节内部需要分层时用 `### ` 三级标题；
- 列表用 `-`；需要对照、罗列多维信息时用 Markdown 表格；
- **不要输出 JSON**；
- **不要输出任何 HTML 标签**（如 `<p>`、`<ul>`、`<li>`、`<table>`、`<h3>` 等）；
- **不要用代码围栏（```）包裹全文**（mermaid 流程图可用代码围栏）；
- 文档之外不要加任何解释文字（不要"以下是 PRD""希望对你有帮助"之类的开场白或结束语）。

从第一个字符到最后一个字符，都应是 PRD 正文本身。
