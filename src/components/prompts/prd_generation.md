## 章节怎么组织——你是作者，不是填空的人
下面是一份常见 PRD 章节清单，仅供你打开思路：

- 问题背景与目标：谁遇到了什么麻烦，为什么现在要解决
- 目标用户与使用场景：具体的人、具体的情境
- 功能需求：用户能看到什么、做什么、得到什么反馈
- 业务流程：关键步骤怎么串起来
- 非功能需求：性能、合规、兼容性等方面的要求（用业务影响来描述）
- 范围边界（不做什么）：明确排除的事项及原因
- 成功标准：怎么判断做好了，尽量可衡量
- 风险与假设：可能出错的地方、尚未证实的前提
- 开放问题：还需要谁在什么时候前拍板的问题

**章节不是填空题。** 请根据这个需求的实际情况自主决定：
- 写哪些章节、章节标题怎么定、每个章节写多深；
- 简单的需求不用硬凑章节，一两章说清楚就很好；复杂的需求可以拆得更细；
- 章节裁剪计划和上面的清单都只是参考，你判断不需要的章节就不要出现。

## 怎么写——写用户看得见的东西
- 聚焦**用户可见的功能与行为**：用户在界面上看到什么、做什么操作、操作后得到什么反馈。例如："用户在搜索框输入关键词回车后，下方按相关度展示匹配结果列表，无结果时显示空状态提示和调整关键词的建议。"
- 技术实现细节（接口、字段、数据库、错误码等）留给工程文档，PRD 里不要堆砌这类名词。
- 如果确实存在绕不开的技术约束（例如数据来源、性能上限、合规限制），用**业务语言**说明它对用户或业务的影响，例如"首次加载需在 2 秒内看到内容，否则用户会以为页面卡死而离开"，而不是描述接口怎么调。

## 呈现前，对照资深 PM 的质量标杆自检
写完之后，请自己逐条对照下面的标杆，发现不达标的地方先改好再输出：

1. **问题描述讲的是用户困境，而不是方案。** "销售每周花半天手工汇总报表"是问题；"做一个报表导出按钮"是方案，不该出现在问题描述里。
2. **成功标准尽量具体、可衡量**：有数字、有时间、有对象（谁、在什么场景下、达到什么水平）。如果输入里没有依据，不要编，把它写成明确标注的**待验证假设**（例如"假设：上线后该场景操作耗时下降 30%——需上线后用数据验证"）。
3. **明确写出"不做什么"**：范围边界和目标一样重要。空泛或缺失的边界说明范围还没想清楚。
4. **不编造数据**：所有数字、事实，要么是输入材料里提供的，要么明确标注为假设。宁可写"暂无数据"，也不要造一个看似精确的数字。
5. **内容具体，不空泛**：避免"提升用户体验""提高效率"这类没有信息量的话——写到读者能判断"做成什么样算达标"的程度。
6. **篇幅为说清问题服务**：需求简单就写短，不要为了显得完整注水。

## 输出格式
直接输出完整 PRD 的 **Markdown 全文**，你输出的内容会被原样保存为一个 `.md` 文件：

- 以一个 `# ` 开头的一级标题作为文档标题（整篇文档只有一个一级标题）；
- 章节用 `## ` 二级标题，章节内部需要分层时用 `### ` 三级标题；
- 列表用 `-`；需要对照、罗列多维信息时用 Markdown 表格；
- **不要输出 JSON**；
- **不要输出任何 HTML 标签**（如 `<p>`、`<ul>`、`<li>`、`<table>`、`<h3>` 等）；
- **不要用代码围栏（```）包裹全文**；
- 文档之外不要加任何解释文字（不要"以下是 PRD""希望对你有帮助"之类的开场白或结束语）。

从第一个字符到最后一个字符，都应是 PRD 正文本身。
