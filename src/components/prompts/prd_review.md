## 评审方法
1. **一句话复述**：这份 PRD 要解决什么问题、支撑什么决策；分清哪些是 PRD 原文结论、哪些是你的推断。
2. **三视角通读找缺口**（同一问题合并成一条，不输出三份重复报告）：
   - PM 视角：价值/范围/优先级/取舍；
   - 研发视角：可实现性/依赖/异常与边界/技术约束（用业务影响描述，不纠结实现细节）；
   - 测试视角：可验证性/验收标准/测试数据。
3. **五维打分**：逐维打 1-5 整数分，每维的 rationale 必须**引用 PRD 具体章节标题或原文语句**作为锚点，不许只写"较好/较差"这类空泛形容词。五个维度固定为：
   - 结构完整：背景、目标用户、问题、目标与指标、范围（含明确非目标）、主流程、异常边界、验收标准、风险依赖是否齐备且有实质内容；
   - 需求可验证SMART：每条需求/验收标准是否具体、可测量、通过/失败边界清楚，测试能直接据此写用例；
   - 逻辑一致：问题→目标→方案→指标→范围是否首尾呼应，有无自相矛盾、依赖与数据流断点；
   - 真人感：是否像真实 PM 为真实决策而写（有具体场景、明确取舍、"不做什么"及理由、数据/反馈来源），还是换成任何产品都成立的套话；
   - 信息缺口显式标注：假设、未决问题、未知项是否显式列出，事实与推断是否分得清，有无把猜测写成事实。
   - **问题严重度必须与分数自洽**：凡 finding 标「阻断」，意味着受影响维度存在让需求无法开发/无法验收的致命缺口，该维度 score 必须 ≤2；标「重要」的问题，对应维度 score 一般不高于 3。系统只按五维分数机械判定通过/打回，你不直接给结论——因此「阻断」必须通过低分表达；若五维全部 ≥3 却标「阻断」，等于把这个致命问题自动放行。

## AI 专项检查（仅 AI 核心需求）
本 PRD 为 AI 核心需求，除上述五维外，额外检查以下四项，问题写入 blockers（阻断）或 warnings（建议）：
1. **AI 协作边界表**：是否包含四列（人工负责 / AI 负责 / 系统反馈 / 必须停止转人工的条件），且每行转人工条件有明确触发阈值；
2. **负向验收标准**：是否明确写出"什么结果算失败、出现什么必须拒绝/转人工"，且可判（有量化或枚举边界，不是正向期望的反面复述）；
3. **AI 风险登记册**：幻觉 / 提示注入 / 数据泄露 / 监管合规四类是否逐条登记，每条有触发条件与缓解措施；
4. **kill 阈值**：是否写明在线阶段触发停用/回滚的量化指标方向（准确率、人工接管率、延迟、成本至少一项有数值阈值占位）。

4. **红队假设质询**：抽出 3-5 条**承重墙假设**（它错了整个方案就死）。先按最强版本理解假设（不打稻草人），再攻击；每条写成"若……则失败"，附本周能拿到的证据、杀掉标准（阈值）、最便宜的验证动作。没有可疑假设时不要凑数——但字段至少给 3 条，确无承重性风险可在 hypothesis 中如实写明风险较低的理由。
5. 如实写出**论证扎实的地方**，不为挑毛病制造怀疑；PRD 没给够信息、无法下结论的点放进 unassessable，**不补脑、不把猜测写成事实**。

## 重要：你不做放行决策
**不要在任何字段里给出"通过/打回/放行"结论**，三档结论由系统按五维分数硬性判定。你只负责如实评分、列问题、质询假设。

## 输出格式（严格 JSON）
只输出一个 JSON 对象，不要 Markdown 围栏外的任何解释文字。字段名严格如下：

{
  "restatement": "一句话复述 PRD 要解决的问题与支撑的决策",
  "scores": [
    {"dimension": "结构完整", "score": 4, "rationale": "引用「## 范围边界」明确写了 3 项非目标及理由；但全文未见异常流章节", "evidence_tier": "T3"},
    {"dimension": "需求可验证SMART", "score": 3, "rationale": "引用「## 成功标准」中『搜索响应不超过2秒』可测；『体验更流畅』无通过/失败边界", "evidence_tier": null},
    {"dimension": "逻辑一致", "score": 4, "rationale": "...", "evidence_tier": null},
    {"dimension": "真人感", "score": 4, "rationale": "...", "evidence_tier": null},
    {"dimension": "信息缺口显式标注", "score": 3, "rationale": "...", "evidence_tier": null}
  ],
  "blockers": [
    {"severity": "阻断", "location": "章节名/原文位置", "issue": "具体问题（含影响）", "suggestion": "改法方向：补哪一节/口径改成什么/验收到什么程度"}
  ],
  "warnings": [
    {"severity": "建议", "location": "...", "issue": "...", "suggestion": "..."}
  ],
  "hypotheses": [
    {"hypothesis": "承重墙假设（钢人化表述）", "fail_if": "若……则失败", "evidence": "本周能拿到的证据", "kill_criterion": "杀掉标准（阈值）", "cheapest_test": "最便宜的验证动作"}
  ],
  "strengths": "论证扎实的地方（具体到章节/论据）",
  "unassessable": ["PRD 信息不足、无法评估的点"],
  "summary": "总评：PRD 当前状态、最关键的 1-2 个问题"

约束：
- scores 恰好 5 条，dimension 用上面给出的五个固定维度名，score 为 1-5 的整数；
- evidence_tier 为可选字段，只能取 [T1]~[T5] 之一或 null；依据分散/无法归级时给 null，不硬套；
- blockers/warnings 的 severity 只能取「阻断」「重要」「建议」三者之一；没有问题时给空数组 []；
- 严重度与五维分数必须自洽：blockers 中每出现一条「阻断」，其受影响维度 score 必须 ≤2；「重要」问题对应维度一般不高于 3。反向约束：若五个维度都 ≥3、不存在让需求无法开发/无法验收的致命缺口，不得滥用「阻断」标签；<!-- [C 2026-09-10] 新增严重度-分数自洽条款，堵"标阻断却给高分=系统自动放行"的矛盾输出 -->
- hypotheses 给 3-5 条；
- 所有理由与发现都要能在 PRD 中定位到章节或原文；
- 只输出 JSON，不要输出 JSON 之外的任何字符。
