# AI PM Agent 技术选型与架构对位报告

> 目的：说明这个项目的每一项技术选择，相对业界标准做法是什么位置——**哪些是直接采用业界标准，哪些是在标准基础上改的、为什么改**。每条业界标准都附权威来源。
> 一句话结论：**本项目的架构不是原创，而是业界标准模式的「确定性一端」的系统化组合——每一条都有权威出处背书；真正的差异化不在架构，而在产品流程设计与「不替用户做决定」的取舍。**

---

## 一、工作流编排：为什么用「确定性流水线」而不是「自主 Agent」

### 业界标准是什么

- Anthropic《Building effective agents》把 LLM 应用分成两类：**workflow（工作流）**= 用预定义代码路径编排 LLM 与工具，可预测；**agent（智能体）**= LLM 动态决定自己的流程与工具调用，灵活。又细分五大模式：prompt chaining / routing / parallelization / orchestrator-workers / evaluator-optimizer。
  （https://www.anthropic.com/engineering/building-effective-agents）
- **状态机/图编排是当前业界主流推荐**：LangChain 官方推荐 LangGraph，v1 起废弃 AgentExecutor、把它换成构建在 LangGraph 上的统一抽象（https://docs.langchain.com/oss/python/migrate/langchain-v1）。学术证据（StateFlow 论文）：状态机相比纯 ReAct 自循环，任务成功率 +13~28%、推理成本降为 1/3~1/5（https://arxiv.org/html/2403.11322v3）。
- **业界对「确定性 vs 自主」的共识是：按任务性质选，不是哪个更好**。生产环境多数「agent」其实是固定序列工作流（Menlo 调研：仅约 16% 是真自主 agent）。确定性工作流提供可预测性、一致性、可审计；自主 agent 提供灵活性但以延迟和成本为代价。
  （https://www.langchain.com/state-of-agent-engineering）

### 我们用了什么

LangGraph 20 节点确定性状态机流水线：想法 → 需求分析 → 方案 → 评审 → 评测设计 → 选型 → 拆工单 → 评测 → 发布计划 → 落盘。

### 相对业界标准改了什么 / 为什么

- **采用的**：状态机图编排 = LangGraph 官方主推形态、Anthropic 五大工作流里的 prompt chaining。
- **改的 / 为什么**：把「判定逻辑」从「模型决定」收紧成**代码硬判——模型只给分/出 JSON，结论由纯函数硬算**。这是业界 Anthropic「hook not prompt」原则的延伸（涉及钱/合规/安全的判断用确定性 hook 而不是 prompt 建议，https://www.anthropic.com/engineering/building-effective-agents）+ StateFlow「过程锚定」的实践。为什么：AI PM 的判断要**可复现、可测试、可追责**——"结论由代码算"保证换模型不影响流程判断，这是产品可信度的地基。

## 二、人在回路（HITL）：8 处停下等真人确认

### 业界标准是什么

- **interrupt/resume（中断/恢复）+ 状态持久化** 是四大框架（LangGraph、OpenAI Agents SDK、Claude Code、Microsoft Agent Framework）全部收敛到同一模式：在不可逆/高风险动作前暂停 → 持久化状态 → 用唯一标识在精确中断点恢复，而不是重跑整个流程。
  （https://docs.langchain.com/oss/python/langgraph/interrupts 、https://openai.github.io/openai-agents-python/human_in_the_loop/ 、https://code.claude.com/docs/en/permission-modes 、https://learn.microsoft.com/en-us/agent-framework/workflows/human-in-the-loop）
- 业界注意点：①框架只负责暂停恢复，**通知/超时/升级/审计要自建**；②**不要到处中断**——只在「人类判断会改变结果」的点中断，否则审批疲劳（Claude Code 实测 93% 审批被无脑接受）。
  （https://jacar.es/en/human-in-the-loop-in-ai-agents/ 、https://www.anthropic.com/engineering/claude-code-auto-mode）

### 我们用了什么

LangGraph `interrupt` 原生能力 + checkpointer（SQLite）+ thread_id，共 8 处中断点（需求确认/整合/边界判断/评测确认/工单确认/发布确认等），全部「空答复继续等、明确答复按字面执行」。

### 相对业界标准改了什么 / 为什么

- **采用的**：interrupt/resume 模式 = LangGraph 一等公民能力，与其他三家框架实现同构。
- **改的 / 为什么**：业界多数实现是「工具级逐次审批」（Claude Code 那种每步问一次）；我们把中断**收敛到 8 个「产品决策点」**（走哪条轨、方案过不过、评测及不及格、要不要发布）——这些正是「人类判断改变结果」的点，不是每一步都问。比「处处审批」更符合业界「只在关键点中断」的建议，也避免了审批疲劳。**「不替用户做决定」是产品主张**：空答复就继续等，绝不偷偷放行或改写用户意见。
- **待补强（诚实说明）**：通知/超时/升级/审计这些 HITL 周边设施我们还没做全（业界也提示要自建）。

## 三、评测：先设计考题再开发（Eval-Driven Development）

### 业界标准是什么

- Promptfoo 的主流用法 = 声明式配置 + CI 回归评测 + LLM-as-judge + 模型对比（https://github.com/promptfoo/promptfoo）。
- **「先设计考题再开发」在业界被明确提倡**，叫 Eval-Driven Development（EDD）：把 TDD 搬到 LLM，先写评测集定义计划中的能力，再开发，迭代到通过，评测进 CI 做回归门禁。DeepEval、Google web.dev、Red Hat 等都倡导。
  （https://deepeval.com/blog/eval-driven-development 、https://web.dev/learn/ai/evaluation-driven-development 、https://developers.redhat.com/articles/2026/03/23/eval-driven-development-build-evaluate-ai-agents）

### 我们用了什么

Promptfoo 外置评测 + 流水线第 5 段「设计评测体系」（四层考题、双及格线）+ 第 8 段「构建期跑评测」（真跑+硬判）。

### 相对业界标准改了什么 / 为什么

- **采用的**：Promptfoo = 业界标准评测工具；「考题先于开发」= EDD 主流做法。
- **改的 / 为什么**：业界 EDD 一般是「开发团队自己写考题」；我们把考题设计**做成流水线里的一个正式环节**（第 5 段，AI PM 起草 + 真人确认），把「及格线硬判」写成代码（不是模型自评）。为什么：让「什么算对」在写代码前就被人确认，且评测结论不依赖模型自我感觉——这比「事后补评测」更符合 EDD 精神，也走得更前置。
- **一次有据的取舍**：真机评测未达标时，先查是不是考题缺陷，**不改考题凑达标**（业界「别信榜单/别为通过而凑」同精神）。

## 四、模型选型：候选池前置到 PRD 之前

### 业界标准是什么

- 业界一致推荐 **requirements-first / 候选池 + 自家数据实测**，反对先拍板一个模型：①先定需求与 KPI → ②按部署约束过滤出候选池 → ③用基准榜粗筛 2-3 个 → ④用你自己的数据实测打分 → ⑤决策。「榜单排名不是决策依据，自家评测才是」。
  （https://www.anaconda.com/blog/choose-open-source-ai-model-6-step-guide 、https://huggingface.co/blog/MichielBontenbal/how-to-choose-your-ai-model）
- AI PM 的选型职责业界共识：**PM 负责候选、判据与评估框架，人拍板**；PRD 写「模型能力要求 + primary/fallback/switch trigger」，不写死模型名。
  （https://www.ideaplan.io/blog/how-to-write-ai-product-prd 、https://aiforproduct.substack.com/p/agent-to-solve-the-model-selection）

### 我们用了什么

候选池前置到第 2 段（PRD 之前）：产 2-5 个候选 + 实时单价 + 接入状态；第 3 段 PRD 写「模型要求与切换条件」；第 6 段读候选池、用户点选、只跑已接入的、硬判推荐。

### 相对业界标准改了什么 / 为什么

- **采用的**：requirements-first + 候选池 + 自测 = 业界标准范式；LiteLLM 统一模型层 = 业界 LLM gateway/model routing 的事实标准实现。
- **改的 / 为什么**：业界多数是「候选池作为开发前的独立环节」；我们把它**前置到 PRD 之前**（第 2 段就产候选池，方案里写模型要求）。为什么：先搞清楚「有哪些模型、什么价、能不能调用」再写方案，方案才不会空谈——这比业界多数做法更早实践 requirements-first。**「AI 给候选与判据、人拍板」**是产品主张，直接对应业界 Three-Gate Framework「agent 输出带推理的推荐、人确认」。

## 五、工具外置：判断留内核、执行交给外面

### 业界标准是什么

- 「模型提议、代码执行」是**所有主流厂商统一的安全范式**：模型永不执行代码，只返回结构化调用请求，真实操作由宿主代码执行（Anthropic 原话："the model never executes anything on its own"）。https://docs.anthropic.com/docs/en/agents-and-tools/tool-use/how-tool-use-works
- **工具经注册表/路由表登记**是业界常规做法，且正被协议化（MCP 的 `tools/list` 就是工具目录发现标准）。https://modelcontextprotocol.io/docs

### 我们用了什么

「判断内嵌、执行外置」：需要判断的留流水线代码硬算，跑评测（Promptfoo）、画图（mermaid）、做演示（PPT 工具包）这类「谁做都一样」的动作交给外面现成工具，工具经 `references/外置工具路由.md` 登记。

### 相对业界标准改了什么 / 为什么

- **采用的**：判断内嵌+执行外置 = function calling 的基础安全模型；路由表登记 = MCP tools/list 同构的自管实现。
- **改的 / 为什么**：我们给「外置」加了两条自己的规则——**执行可外置、判定留内核；内容可外置、契约留内核**。为什么：工具要能随时升级替换（工作随经验积累变化），但「过不过、推不推荐」的判断必须稳定在代码里，不交给外面。这条规则把「外置」从「怎么调用」上升到「什么能外置」的边界，比业界纯工具注册更进一步。

## 六、结构化输出 + Pydantic 校验

### 业界标准是什么

- 「模型只产数据、校验与判定交给代码」是平台级标准：OpenAI/Anthropic 的 Structured Outputs 用 constrained decoding 保证输出合法 JSON，**判定逻辑仍在代码里**。https://developers.openai.com/api/docs/guides/structured-outputs
- **Pydantic 校验 LLM 输出是 Python 生态标准**，OpenAI 官方 SDK 原生路径就是 pydantic.BaseModel。https://pydantic.dev/articles/llm-intro

### 我们用了什么

模型节点出 JSON → Pydantic schema 校验 → 代码硬判结论。819 个测试里大量是「校验模型输出的纯函数测试」。

### 相对业界标准改了什么 / 为什么

- **采用的**：完全就是官方推荐路径（Pydantic 校验 + 代码判定），零创新，但正确地踩在标准上。
- **为什么值得说**：把「模型只给分、校验判定交给代码」这条范式用到了**每一个判定节点**（评审打分、就绪度 11 维度、评测双及格线、kill 阈值）——这是 819 测试全绿、可复现可追责的基础。

## 七、记忆管理

### 业界标准是什么

- LangGraph 官方把记忆分两层：**checkpointer（短期，线程内）+ store（长期，跨线程）**。https://docs.langchain.com/oss/python/langgraph/persistence
- **产物落盘成文件**是 Anthropic 官方 Memory tool 的「文件即记忆」模式（multisession 开发模式：新会话开场读记忆文件恢复状态）。https://docs.anthropic.com/en/docs/agents-and-tools/tool-use/memory-tool

### 我们用了什么

「记忆索引 + 内容仓两层」（开场只读约 3KB 索引，8 个话题按需展开）+ 产物一律 Markdown 落盘成文件 + RAG 知识库检索。

### 相对业界标准改了什么 / 为什么

- **采用的**：两层记忆 ≈ LangGraph checkpointer/store 分层；文件化产物 ≈ Anthropic Memory tool；RAG ≈ 标准知识层。完全对齐。
- **改的 / 为什么**：我们用「索引（结构化元数据）+ 内容仓」而不是向量语义检索做长期记忆。为什么：这是给 Agent 读的**项目记忆**，按主题组织比语义检索更精确可控；产物落盘成文件让「复盘不需要靠记忆」——每开一次会写会话记录，改动留档，素材自动积累。这是比业界「记忆靠向量检索」更适合「项目复盘」场景的简化。

## 八、PM 能力组织：职能清单 + 确定性流水线的合流

### 业界标准是什么

- 主流 AI PM 项目（deanpeters 77 skills、pm-skills 68 skills、borghei 368 skills 等）按**职能清单/技能库**组织原子能力；少数派（pm-workflow-plugin）用**固定流水线**，卖点恰恰是「确定性 + 多层审核」。业界普遍内嵌人工门（Human Gate）。
  （https://github.com/deanpeters/Product-Manager-Skills 、https://github.com/product-on-purpose/pm-skills 、https://github.com/derricktang/pm-workflow-plugin）
- 产品流程「需求→方案→评审→拆单→发布」与 PMI Disciplined Agile、Pendo 生命周期、**Stage-Gate**（评审=阶段间 gate）、中国需求管理实践（阿里云效评审卡点）同构。
  （https://www.pmi.org/disciplined-agile 、https://www.pendo.io/pendo-blog/how-to-use-the-product-management-life-cycle-to-drive-better-business-outcomes/ 、https://help.aliyun.com/zh/yunxiao/use-cases/how-to-develop-scientific-and-effective-requirements-process-specification）

### 我们用了什么

14 项 AI PM 职能标准（对应业界技能库）+ 确定性流水线（对应业界固定工作流）+ 8 处人工确认点。

### 相对业界标准改了什么 / 为什么

- **采用的**：两种范式的交集——职能标准界定了「PM 要会什么」，流水线界定了「干活按什么顺序」。
- **改的 / 为什么**：业界主流是「技能库让 agent 按需调用」（灵活但流程不定）；我们选了「固定流水线」这一少数派，**为了确定性**——AI PM 的交付要有章法、可审计、可复现，这正是 pm-workflow-plugin 这类少数派项目的卖点。而我们比它更进一步：**流水线只做判断、不替用户拍板**，8 处人工确认点对应业界 Stage-Gate 的「评审=gate」。

## 九、AI 需求评审维度

### 业界标准是什么

- 业界对「AI 需求要评审什么」共识高度一致，**五维**：①质量与评测（eval bar）②数据底座 ③幻觉与失败模式 ④内容安全合规 ⑤成本与延迟预算。
  （https://github.com/ombharatiya/AI-for-Product-Managers/blob/main/03-product-craft/prd-template-ai-feature.md 、https://www.ideaplan.io/blog/how-to-write-ai-product-prd）

### 我们用了什么

评审纳入**四维**：数据底座 / 幻觉风险 / 内容安全 / 成本（第 2 段 Pi 评估 + 第 4 段评审），另有一整套评测体系环节（对应「质量评测」维）。

### 相对业界标准改了什么 / 为什么

- **采用的**：四维全部是业界共识项，方向完全一致。
- **改的 / 为什么**：我们把「质量评测（eval bar）」单独做成流水线的一个**正式环节**（第 5 段设计评测 + 第 8 段跑评测），而不是塞进评审维度里——因为「什么算对、怎么测」值得独立确认，这正是 EDD 的精神。诚实说明：业界五维里的「延迟预算」我们覆盖较弱（在发布计划里留了 kill 阈值/cohort 但没单独成维）。

## 十、总对位表

| 技术选择 | 业界对应标准 | 定性 |
|---|---|---|
| LangGraph 20 节点确定性流水线 | Anthropic 五大工作流·prompt chaining；LangGraph 官方主推形态 | 常规、官方推荐 |
| 判定逻辑代码硬判（模型只给分） | Anthropic「hook not prompt」+ StateFlow 过程锚定 | 采用标准且更严格 |
| 8 处 HITL 中断 | LangGraph interrupt/resume（四大框架统一模式） | 采用标准，收敛到关键决策点 |
| Promptfoo 外置评测 + 考题前置 | EDD（Eval-Driven Development） | 采用标准且更前置 |
| 候选池前置到 PRD 前 | requirements-first + 候选池 + 自测 | 采用标准且走得更前 |
| LiteLLM 统一模型层 | LLM gateway / model routing | 采用业界事实标准 |
| 判断内嵌、执行外置 | function calling「模型提议、代码执行」 | 采用基础安全范式 |
| 工具路由表登记 | MCP tools/list 工具目录 | 采用标准，自管实现 |
| 结构化输出 + Pydantic | OpenAI/Anthropic Structured Outputs + Pydantic | 官方背书标准 |
| 记忆两层 + 产物落盘 | LangGraph checkpoint/store + Anthropic Memory tool | 采用标准 |
| 职能清单 + 固定流水线 | 技能库范式 + pm-workflow-plugin 少数派 | 两种范式的交集 |
| 评审四维（数据/幻觉/安全/成本） | 业界 AI PRD 五维共识的子集 | 采用共识 |

## 结论

**架构层：零创新，全部踩在业界标准上。** 每个技术选择都能指到 Anthropic / OpenAI / LangChain / MCP 的官方文档——这是好事，说明设计经得起同行审视。

**真正的差异化在业务层三件事：**
1. **「不替用户做决定」**：8 处确认点只挡明显不合格，空答复继续等、明确答复按字面执行——业界多数 AI 工具是「替你做决定再让你确认」，我们反过来。
2. **「AI 给候选与判据、人拍板」**：选型、评审、评测全按这个——AI 是 PM 不是决策者。
3. **「判断内嵌、执行外置」落地成边界规则**：什么能外置（执行/内容）、什么必须留内核（判定/契约），比业界「工具注册」更进一步。
