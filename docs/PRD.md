## 一、项目定位

### 1.1 一句话定位

AI 产品经理工作流 Agent——把优秀 AI PM 的职能做成**可执行的确定性流水线**：需求进来，一路产出洞察、边界判定、PRD、评审结论、评测体系、选型结论、研发工单、评测结果与发布计划；判断留给人，产出交给流程。

### 1.2 立项依据（为什么按职能标准做，而不是按功能清单做）

市面上的 PM 工具解决「写文档快不快」，AI PM 的真实门槛是四件事：把模糊机会翻译成可判定的任务、在开发前定义「什么算对」、设计人机边界、对上线后的质量与成本负责。这四件事对应 14 项职能（5 项通用底座 + 6 项 AI 专属 + 3 项运行层），每项都有可判定的达标证据。

本项目的产品主张一句话：**不做「帮你写得更快」，做「帮你把不确定的事变成可测量、可接管、可控成本的事」。**

### 1.3 能力等级与产品目标

每项职能分四级：L1 能说清概念 / L2 能独立产出产物 / L3 产物有实测证据支撑 / L4 有上线数据与持续闭环。

- 本项目的目标：**把用户从 L1-L2 顶到 L3**（每一份产物都带实测证据与出处）；
- L4 依赖上线数据，本期只建载体（可观测计划落盘、坏例回流接口），数据回流属二期。

### 1.4 不做什么（明确边界）

1. **不做演示物本身**：PPT、网页幻灯片、图表、流程图、可交互原型不是 Markdown，不假装能做；只产出《演示需求交接单》，交外置工具包制作。
2. **不做多 Agent 管道**：单 Agent（确定性流水线 + 技能），不搞 Agent 之间互相派活。
3. **不做在线监控平台**：第 10/11 段（Langfuse 在线监控、数据飞轮）二期；本期只产监控计划与接口。
4. **不替用户做判断**：所有关键决策（需求确认、改判、工单、发布口径、横跑是否执行）停在 HITL 门等用户答复，流水线不代替用户拍板。

## 二、目标用户

专业产品经理——懂 PM 术语，产物可直接进内部评审，追求规范性与可追溯性。次要用例：想转 AI PM 的传统 PM（用流水线的产物当「作品集级证据」）、需要评审 AI 需求的技术负责人（看证据等级与风险册）。

## 三、核心场景：12 段融合工作流

需求确认后先判定是否 AI 核心（`ai_core`），再分两轨：AI 全轨走全部 12 段，普通轨跳过 AI 专项段（2/5/6/8 段），行为与既有流水线完全一致。

| 段 | 名称 | 承担方 | 产出 | 状态 |
|---|---|---|---|---|
| 0 | 接收需求 | 流水线 | 需求录入、知识库查家底（kb_lookup） | ✅ 已建 |
| 0.5 | 需求修订整合 | 流水线 + HITL | 原需求与修订意见整合成新草案（不设次数上限，每次重整合都要真人回话） | ✅ 已建 |
| 1 | 挖需求并判断是否 AI 核心 | 流水线 + HITL | 用户洞察、`ai_core` 判定与理由、初始考题集 | ✅ 已建 |
| 2 | 判断需求与 AI 的边界 | 流水线 + HITL | 三方对照表（需求 × 模型 × 工具）+ **探针真跑证据** + 能力边界结论 | ✅ 已建（探针自动真跑） |
| 3 | 写 PRD | 流水线 | ai-native PRD（三层成功标准/协作边界表/失败接管列/负向验收/风险册/评测占位）或普通模板 | ✅ 已建 |
| 4 | 评审 PRD | 流水线（模型打分 + 代码硬判） | 五维 + AI 维度评审报告，一票否决，reject 回炉限次 | ✅ 已建 |
| 5 | 设计评测体系 | 流水线 + HITL | 四层考题（典型/边界/对抗/回放）、rubric、双及格线、YAML | ✅ 已建 |
| 6 | 对比选型模型 | 外置工具（Promptfoo）+ 流水线 | 候选横跑，质量/成本/P50/P95 三维，代码硬判推荐 | ✅ 已建 |
| 7 | 拆研发工单 | 流水线 + HITL | 纵切工单 + 覆盖矩阵 + AI 四类特殊项（trace/兜底/评测接入/风险册） | ✅ 已建 |
| 8 | 构建期跑评测 | 外置工具 + 代码硬判 | Promptfoo 真跑结果、双及格线判定、评测报告 | ✅ 已建 |
| 9 | 写发布计划 | 流水线 + HITL | 7 步骨架 + Tier1 扩展 + kill 阈值 + cohort 灰度 + 回滚 + go/no-go + 值班 | ✅ 已建 |
| 10 | 灰度发布与监控 | 人工 + 外置工具 | 监控计划（在线数据二期） | ⬜ 二期接口 |
| 11 | 运营数据回流 | 人工 + 流水线 | 坏例回收进考题集、月度复评 | ⬜ 二期接口 |
| 收尾 | 产物落盘 | 流水线 | 全部产物并入清单落 `output/<需求名>/` | ✅ 已建 |

**人机分工**：模型只出结构化草案（打分、JSON、清单），**结论一律代码硬判**（judge 纯函数 + 条件边），人的判断只出现在 HITL 门。

## 四、职能标准与流水线的对应（本项目的验收依据）

14 项职能 → 12 条硬要求（完整推导见 `docs/AI-PM职能标准与能力模型调研.md` 第四节）。**这份表就是本项目的验收清单**：

| # | 要求 | 落点 | 状态 |
|---|---|---|---|
| R1 | 每段产物可判定：代码硬判，或显式标注「需人工判断」 | 全段 judge + HITL 四态协议 | ✅ |
| R2 | 评测先于开发：需求确认后建初始考题集，随需求生长 | 第 1 段 → 第 5 段 → 第 8 段 | ✅ |
| R3 | 模型能力实测判定，不吃榜单 | 第 2 段探针真跑 + 证据回填 | ✅ |
| R4 | 交付前给出人机边界并写进 PRD | 第 2 段 → 第 3 段协作边界表 | ✅ |
| R5 | 失败与兜底是 PRD 必备章 | 第 3 段 ai-native 模板 | ✅ |
| R6 | 四层考题 + rubric + 双及格线 + 用户确认 | 第 5 段 | ✅ |
| R7 | 同一批考题横跑选型，报三维，硬判推荐 | 第 6 段 | ✅ |
| R8 | 构建期真评测，不达线不放行 | 第 8 段 | ✅ |
| R9 | 发布计划含量化 kill 阈值、灰度、回滚、go/no-go、值班 | 第 9 段 | ✅ |
| R10 | **证据分级**：关键结论标来源等级（实测/用户/分析/口述/直觉），低等级驱动的决策显式标记 | 第 3/4/9 段产物 | ✅ 已做（[T1]-[T5] 等级与 R11 同源：第 3 段 ai-native PRD prompt 要求关键事实/取舍标等级；第 4 段评审五维评分表加证据等级列；第 9 段发布计划 D7/D30 成功定义与 Top3 风险标等级，schema 均可选字段向后兼容） |
| R11 | **就绪度打分**：发布前多维打分 + 三级阻断条件（试点/生产/扩量） | 第 9 段 | ✅ 已做（11 维度 0-5 分 + 加权均分 + 6 档结论 + 阻断项，`readiness_assessment` 节点） |
| R12 | 上线后可观测 + 坏例回流考题集 | 第 10/11 段 | ⬜ 二期接口 |
| R13 | 行业动态追踪：主动跟踪前沿并定期出技术洞察 | 新增通道（可复用 RAG 库 + 定时任务） | ⚠️ 未做 |
| R14 | 产物表述像 PM（业务语言、取舍说明、证据出处），不是技术堆料 | 模板与 prompt 校准 | ⚠️ 未做（内容打磨，留待有数据迭代） |

**优先级**：R10 → R11 → R13（能判定优先），R14 属内容打磨后置。

## 四·五、载体边界：内核 / 外置 / 不接

产品里的每一项能力只有三个去处，不允许"顺手写进内核"：

| 去处 | 放什么 | 载体 | 判据 |
|---|---|---|---|
| **内核（循环）** | 每次跑图都要经过的**判定与门**、契约、状态机 | `src/`（12 段 + judge 纯函数 + HITL + schemas） | 每次都要用，且是判定/契约 |
| **SOP 层** | 规则、路由、清单、清单式指引——**写了 Agent 就会照着调** | `AGENTS.md`、`.trae/rules/`、`references/`（含 `外置工具路由.md`）、`docs/` | 偶尔要用，或属"告诉 Agent 去哪调" |
| **外置实体** | 可替换的执行件与内容 | `scripts/`（通用执行器）、`工具与参考/Agent外置工具包/`（产物能力 + 评测执行器）、`.pi/skills/`（PM 技能）、`domain_kb/`（语料） | 属执行、属内容、领域相关 |
| **不接** | 某个被服务产品自身的领域功能（如某客户的合同条款切分、风险定级） | 无 | 换个领域就废，不是本项目的能力缺口 |

**判断序（四问，新增能力前先过）**：①每次循环都要用吗 ②换个需求/领域还成立吗 ③是判定还是执行 ④是契约还是内容。
**一句话口径**：**执行可外置，判定留内核；内容可外置，契约留内核；偶尔用放 SOP，每次用才进循环。**

**当前盘点**：已登记的外置实体见 `references/外置工具路由.md`（产物能力、评测执行器、通用执行器、文字改写）；仍长在内核需剥离的候选与优先级见 `docs/S046-外置候选清单.md`。

## 五、技术架构

> 节点级设计见 `docs/workflow-design.md`（权威）；详细技术方案见 `docs/technical-design.md`。

### 5.1 选型结论

| 组件 | 选型 | 理由 |
|---|---|---|
| 流水线内核 | Python + LangGraph 确定性状态图 | 路由权在 state 字段 + 条件边纯函数，模型不决定走向 |
| 节点执行 | 统一 NodeRunner：装配上下文 → Pydantic 结构化输出 → 校验自检 → 写回 state | 每节点一个模式，产物稳定可测 |
| 轻活内核 | Pi（终端 ReAct，技能=SKILL.md） | 判断、创意、调研类任务按需加载技能 |
| 图内工具调用 | 节点内 ReAct（LangChain bind_tools + 裸 ChatLiteLLM） | 「节点内 ReAct、节点外不变」：契约与 HITL 门不动 |
| HITL | `interrupt()` + SQLite Checkpointer | 门暂停等人决策，进程退出可断点续跑 |
| 模型 | DeepSeek 直连（OpenAI 兼容），config 多 provider | 密钥只在 `.env`；跑模型前必须清空代理变量 |
| 外置重工具 | Promptfoo（评测/横跑），经工具路由表调度 | 批量真实模型调用类外置，流水线只负责启用与验收 |
| 知识库 | ChromaDB + 中文嵌入（两层接入：流水线 kb_lookup 节点、Pi domain-kb-query 技能） | 检索增强固定节点，不做 Agentic 循环 |
| 产物模板 | Jinja2 → Markdown | 文档一律 Markdown；模板在 `artifacts/templates/` |
| 组件载体 | 文件式自动发现：`src/components/` 下 .md prompt / .py schema / .py guard | 新节点一律配假 LLM 零 API 测试 |

### 5.2 核心机制

| 机制 | 解决什么 | 载体 |
|---|---|---|
| 通路 = 确定性状态图 | 走向由代码决定，不由模型决定 | LangGraph StateGraph + 条件边纯函数 |
| 思考 = 节点内统一执行器 | 上下文装配、结构化输出、自检、写回 | NodeRunner + 组件目录 |
| 门 = HITL 原生中断 | 人决策点可暂停、可续跑、答复协议固定 | interrupt() + SQLite + 四态答复协议 |
| 判定 = 代码硬判 | 模型只出草案，通过/打回由代码判 | judge 纯函数 + 单节点自检（错 1 次不阻断，错误随产物展示） |

### 5.3 分层职责

| 层 | 技术 | 职责 |
|---|---|---|
| 交互层 | CLI（本期）；桌面 UI 为未来项 | 门材料渲染、答复采集、断点续跑入口 |
| 节点层 | LangGraph 节点 + 组件目录 | 各段业务逻辑（prompt/schema/guard 文件式） |
| 模型层 | LangChain / LiteLLM | 统一调用各 provider |
| 工具层 | 节点内工具 + 外置工具包 | 探针、检索、评测、横跑 |
| 知识层 | RAG 库 + 参考库路由 | 查家底、写回、上游技能路由 |

### 5.4 关键设计原则

1. **路由确定性**：模型不决定走向，条件边是读 state 的纯函数。
2. **宽松优先**：闸门只挡退化情形（空答复、证据缺失），显式答复即放行；文案与内容打磨留到有数据再迭代。
3. **结论硬判**：任何「是否达标」「是否通过」「选谁」的结论都由代码按数值判，模型不参与判定。
4. **业务零侵入内核**：PM 方法论全在组件（prompt/schema/guard），内核无业务知识。
5. **产物可追溯**：每份产物带来源材料、判定依据、证据；证据等级 [T1]-[T5]（R10 已落地，第 3/4/9 段产物按等级标记关键结论）。
6. **不做运行时跨节点协调 Agent**：节点内部可多步思考与调工具，节点之间的契约与门不变。

## 六、功能需求

### 6.1 CLI 交互

- 命令行启动（`scripts/run_prd_workflow.py --requirement/--resume`）
- HITL 门输出四要素：`STATUS: HITL` / `NODE` / `QUESTION` / 中断材料（载荷白名单渲染）
- 断点续跑：同一 `thread_id` 逐门推进
- 产物落盘通知与路径回显

### 6.2 重活（辅助模式）

- 需求描述进 → 12 段流水线推进 → 逐门确认 → 产物落 `output/<需求名>/<中文目录>/`
- 人工确认节点必须如实转达给用户，不得代替用户答复（详见 `AGENTS.md` 各门协助协议）

### 6.3 轻活（自主模式）

- 问答、咨询、调研分析、单篇文档、会议纪要等由 Pi 加载技能直接完成
- 11 个 Pi 技能（research-investigation / feedback-triage / roadmap / metrics-tree / stakeholder-comms / experiment-design / retro / demo-handover / domain-kb-query / model-selection / agent-manual）+ RAG 查询技能（domain-kb-query，已并入上表）
- **单一载体规则**：与流水线段重复的技能已删（prd-review↔第 4 段、prd-to-issues↔第 7 段、launch-plan↔第 9 段），同一职能只留一个载体——有进度、有判定的走流水线段，无状态的轻量问答才留技能

### 6.4 演示类需求

- 先产出《演示需求交接单》五要素（演示什么/受众/核心结论/数据素材/期望形式），再按工具路由表调度外置工具包（已装：网页幻灯片/图表/图表绘制/PPTX）；未装则如实说明并给出选项

### 6.5 产物纪律

- 文档产物一律 Markdown，落 `output/`，附文件路径
- 演示类产物不由本项目用 Markdown 拼凑
- 工具脚本产出视为信息素材，消化后转述，不原样甩给用户

## 七、贯穿约束

1. **中文沟通**，专有名词可保留英文。
2. **信息不足先提问**，不靠假设硬写。
3. **调研结论附来源**，查不到来源的说「未核实」。
4. **不确定显式标注**：推测性内容写明「这是推测/建议，需要验证」。
5. **峰谷铁律**：工作日 09-12/14-18 不调 DeepSeek（含流水线），峰时改走免费渠道；真机与重活排谷时。
6. **产物可追溯**：产物中不出现无法回溯的结论（R10 落地后由模型按证据等级 [T1]-[T5] 标记关键结论）。
