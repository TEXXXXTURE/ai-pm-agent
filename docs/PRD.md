## 一、项目定位

### 1.1 一句话定位

AI 产品经理工作流 Agent——帮助专业 PM 完成从需求探索到上线增长的全流程，架构上采用「最简 Agent 内核 + 前端可插拔组件」的一体化设计，为未来的 Agent 工作台预留扩展空间。

### 1.2 核心理念

1. **Agent 最简内核**：Agent 只负责「接收组件 → 调模型 → 循环」，所有可插拔内容（工具、限制、上下文、逻辑片段）外置到前端层
2. **同一条信息流**：前端 UI、可插拔组件、Agent 内核在同一个进程，信息直接流转，无序列化/反序列化转换
3. **可视化改动**：可插拔组件在前端窗口里直接改动，不经代码端
4. **CLI 优先，桌面预留**：先做 CLI 端跑通，前端层预留桌面 UI 扩展接口

### 1.3 与市面产品的区别

| 维度 | 市面架构 | 本项目 |
|---|---|---|
| 可插拔组件位置 | 后端（Agent 内部） | 前端（窗口里直接改动） |
| 改动方式 | 改代码/改配置文件 | 窗口里可视化改动 |
| 信息流 | 前端 → 后端 → API → 前端（多次转换） | 前端 + 组件 + 内核同进程，直接操作 |
| Agent 角色 | 主动（包含所有逻辑） | 被动（只执行，组件由前端注入） |

## 四、技术架构

> 详细技术设计见 [technical-design.md](technical-design.md)；节点级工作流见 [workflow-design.md](workflow-design.md) v2.0。

### 4.1 选型结论

| 组件 | 选型 | 理由 |
|---|---|---|
| Agent 内核 | LangGraph | 状态机 + 循环 + 人机中断（interrupt）+ MCP 内置，作为最简执行内核 |
| 原语层 | LangChain | 模型调用、工具封装、提示词模板、记忆系统，与 LangGraph 同公司无缝集成 |
| 结构化输出 | Pydantic v2 | 每个节点输出经 Pydantic Model 约束，校验失败带反馈重试 |
| 前端层 | CLI（优先），预留桌面 UI | 先跑通 CLI，前端层预留桌面扩展接口 |
| 模型路由 | LangChain ChatOpenAI（多 Provider 配置） | 国产模型均兼容 OpenAI 格式，一个 ChatOpenAI 换 base_url+model 即可切换 |
| 持久化 | SQLite（LangGraph Checkpointer） | HITL 中断后断点续跑，进程退出不丢状态 |
| 产物模板 | Jinja2 | HTML 产物模板渲染 |
| 知识库 | 本地检索（INDEX 路由）+ 飞书源同步 | G4: 全程横切，开工查家底 + 交付写回 |

**放弃 Dify**：Dify 是独立服务，无法实现同进程信息流一体化。

### 4.2 架构图

```
┌──────────────────────────────────────────────┐
│  前端桌面窗口（一体化，同一个进程）              │
│                                                │
│  ┌──────────────┐   ┌────────────────────┐   │
│  │ 可视化编辑器   │   │ 可插拔组件库（在前端）│   │
│  │ 拖拽/配置/改动 │   │ 工具/限制/上下文/逻辑 │   │
│  └──────┬───────┘   └─────────┬──────────┘   │
│         └──────────┬──────────┘              │
│                    ↓ 直接操作，同一条信息流     │
│  ┌────────────────────────────────────────┐  │
│  │  Agent 最简内核（LangGraph）             │  │
│  │  只负责：接收前端注入的组件 → 调模型 → 循环│  │
│  └────────────────────────────────────────┘  │
└──────────────────────────────────────────────┘
                      ↕
               [模型 API / 外部服务]
```

### 4.3 核心机制：Agent 如何按通路思考

| 机制 | 解决什么 | 技术载体 |
|---|---|---|
| **通路 = 确定性状态图** | 路由权在 State 字段 + 条件边（纯函数），模型不决定走向 | LangGraph StateGraph |
| **思考 = 节点内统一执行器** | 每个节点走同一模式：上下文装配→Pydantic 结构化输出→校验自检→写回 State | NodeRunner + 可插拔组件 |
| **HITL = 原生中断 + 持久化** | 人机门暂停等人决策，进程退出可断点续跑 | LangGraph interrupt() + SQLite Checkpointer |

### 4.4 分层职责

| 层 | 技术 | 职责 |
|---|---|---|
| 前端层 | CLI（优先）/ 未来桌面 UI | 可视化编辑器、可插拔组件管理、信息流展示 |
| 可插拔组件层 | LangChain Tools + MCP | 工具、限制、上下文源、逻辑片段（文件式，自动发现） |
| Agent 内核 | LangGraph | 状态机执行、模型调用、工具调用、循环（最简执行内核） |
| 模型层 | LangChain / LiteLLM | 统一调用各种 LLM |
| 工具层 | MCP / 自定义 Python 函数 | 可插拔的工具组件 |
| 知识库层 | 本地 INDEX 路由 + 飞书源 | G4: 全程横切的查家底 + 写回 |

### 4.5 关键设计原则

1. **同进程一体化**：前端层、可插拔组件、Agent 内核都在同一个 Python 进程，信息流无转换
2. **分层可插拔**：工具层、限制层做成文件式组件（.md/.py），未来工作台可可视化管理
3. **CLI 优先**：先做 CLI 端跑通，前端层预留桌面 UI 扩展接口
4. **LangChain + LangGraph 综合使用**：内核用 LangGraph，工具/限制/提示词用 LangChain
5. **业务零侵入内核**：PM 方法论全在可插拔组件（prompts/schemas/guards），内核零业务知识
6. **路由确定性**：模型不决定走向，条件边是纯函数读 State 字段 <!-- [MA 2026-09-08] -->

## 五、功能需求

### 5.1 CLI 交互

- 命令行启动 Agent
- 支持多轮对话
- 支持流式输出
- 支持产物保存为文件

### 5.2 可插拔组件

- 工具组件：可插拔的工具（搜索、文件读写、API 调用等）
- 限制组件：输出约束、Guardrails
- 上下文组件：知识源、历史记录
- 逻辑组件：工作流节点、条件分支

### 5.3 PM 工作流

- 22 节点工作流（5 阶段：探索→PRD→AI 专项→评估→产物管理）
- 4 个 HITL 中断点（需求确认门/策略决策门/章节确认门/红队审查）
- 支持从任意段开始（需提供已有 State）
- 红队审查修订循环上限 3 轮，超限上报用户

### 5.4 AI PM 专项功能（G1-G9）

> 首版已确认的功能清单，详见 [workflow-design.md](workflow-design.md) v2.0 第九节

| 工作阶段 | 功能 | 缺口 | 类型 |
|---|---|---|---|
| 流程开工 | 查家底：检索知识库中相关选型/评测/案例背景 | G4 | 新增 |
| 需求确认门 | 复述需求时同步讲清 Agent 能力边界（自动/工具/人工） | G8 | 增强 |
| 需求确认后 | 立即建初始考题集，全流程生长 | G2 | 新增 |
| 探索阶段 | 加"该不该用 AI 做"判断 | G5 | 新增 |
| 探索阶段 | 机会评分算成本账（cost_feasibility） | G7 | 增强 |
| 探索阶段 | 环节拆分表+可插拔组件候选；候选先查开源与 MCP 生态 | G8+G9 | 新增 |
| PRD 阶段 | AI 功能"异常与边界"章默认必出（兜底/降级/拒绝规则） | G6 | 规则 |
| AI 专项 | 模型选型改循环：查档案→实测→写回→出结论 | G1 | 改造 |
| 交付 | 结论写回知识库，闭环 | G4 | 增强 |
| 交付后 | bad case 回收、回归重跑 | G3 | **二期，留接口** |

### 5.5 产物输出

- 自包含 HTML（可打印、可浏览器勾选、可一键复制）
- 按需求名分文件夹
- 保存通知机制
