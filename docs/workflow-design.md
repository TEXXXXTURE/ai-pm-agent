## 一、设计原则

1. **PM 交付链不废弃，AI 内容融合嵌入**：AI PM 的工作包含通用 PM 全部交付内容（PRD、评审、工单、发布计划），AI 内容按正确顺序嵌入这条链，不另起炉灶。非 AI 需求走原轨道，行为与现状一致。
2. **双轨道分流**：需求在探索阶段判定是否为 AI 核心需求。AI 核心需求走全轨（含可行性、评测、选型、内循环、飞轮）；非 AI 需求走普通轨，跳过全部 AI 专属段。
3. **判断内嵌，执行外置**：需要产品判断的内容内嵌进流水线（prompt 与 schema 硬引导：分流、ai-native PRD 章节、评审 AI 维度、kill 阈值、及格线硬判）；批量真实模型调用外置给评测工具（首选 Promptfoo），流水线只负责生成配置、启用工具、解析报告、代码硬判结论。
4. **主干在内核，外置分两类（S031 用户定调）**：工作流主干（12 段顺序、判定节点、路由、判定、档案）必须存在原生 Agent 的 `src/` 内。外置只给两种内容——①**产物能力外置**：Agent 本体不具备的产物制作（PPT、图表、演示物，见演示工具包）；②**执行器外置**：别人做得成熟、自写属于重复造轮子（G9）的通用机械执行器（如 Promptfoo：批量调模型、跑断言、出报告）。执行器必须无状态：不存业务数据、不决定流程走向；评测配置生成、结果解析、及格线硬判全部写在 `src/` 内，执行器只等价于 pytest 那样的命令行工具。
5. **可行性只能实测，不能评估**：AI 能力边界、成本与延迟在 PRD 前用 PoL 探针一次性侦察实测，不靠主观判断回答"能不能做"。
6. **AI 的"完成"= 评测通过率达到可接受阈值**：阈值不是 100%，定多少是产品决策，由 PM 在设计评测体系时与用户共同确定并写入 PRD。
7. **两种模型测试严格区分**：PoL 探针回答"能不能做"（PRD 前，一次性侦察）；Evals 评测集回答"达不达上线标准"（拆工单前定稿，构建期持续生长，带及格线判定）。
8. **质量靠飞轮维持**：模型行为会漂移，构建期有内循环（离线评测），上线后有外循环（坏例回收→新考题→回归评测→模型月度复评）。选型不是一次性决策。
9. **产物一律 Markdown，演示物外置**：延续 S012/S018 决策，文档产物直出 Markdown；评测工具、演示工具均外置，经路由表登记调度。

## 三、双轨道分流规则

分流判定发生在**第 1 段**（挖需求并判断是否AI核心），由流水线在确认需求时给出判定建议，用户在确认节点一并确认。

**判定为 AI 核心需求的条件**（满足任一）：需求的核心价值由模型判断、生成、推荐、记忆承担；或核心功能存在人工确认/人工接管环节；或输出质量由模型行为决定。

**判定为非 AI 需求**：普通界面、规则引擎、权限配额、提示文案等，即使文案中出现"AI""智能"字样也不算（沿用 prd-ai-native 模板的适用边界）。

| 段 | AI 全轨 | 普通轨 |
|---|---|---|
| 0–1 | 全走，第 1 段产出 `ai_core=true` 判定与理由 | 全走，第 1 段产出 `ai_core=false` 判定与理由 |
| 2 验证AI可行性 | **走**：探针实测 + 风险扫描 + 成本粗估 | **跳过** |
| 3 写PRD | ai-native 模板（第四节） | 现有普通 Markdown PRD |
| 4 评审PRD | 五维 + AI 维度评审 | 现有五维评审，行为不变 |
| 5 设计评测体系 | **走**：四层考题 + rubric + 及格线 | **跳过** |
| 6 对比选型模型 | **条件触发**（见该段） | **跳过** |
| 7 拆研发工单 | 普通工单 + AI 特殊项（trace/兜底/评测接入） | 现有工单，行为不变 |
| 8 构建期跑评测 | **走**：L1 每次变更、L2 按节奏，及格线硬判定 | **跳过** |
| 9 写发布计划 | 增加量化 kill 阈值与 cohort 晋级 | 现有发布计划，行为不变 |
| 10 灰度发布与监控 | L3 在线 A/B、trace 回看、漂移监控 | 常规灰度与监控 |
| 11 运营数据回流 | **走**：坏例回收→回归评测→月度复评 | **跳过** |

## 四、各段定义与判定节点的出入条件

### 第 0 段：接收需求（已建）

- **活动**：开工前查知识库（`kb_lookup`，无匹配返回空、不阻塞）；接收原始需求，做信息完整度评估（`intake`）。
- **入口**：用户提交需求描述。
- **出口产物**：`kb_context`、信息完整度评估。

### 第 1 段：挖需求并判断是否AI核心（已建）

- **活动**：确认需求 HITL（`requirement_confirm`，不足则追问，充足则结构化复述）；需求修订整合（`requirement_refine`，用户提修订意见/改判带附言时模型整合为完整新需求草案，HITL 确认/改判/放弃/带新意见重整合，前 2 版自动，第 3 版升级暂停）；需求挖掘（`needs_discovery`）；AI 适用性判定建议（ai_core 三档建议：AI 核心 / 非 AI / 存疑，附理由），在确认节点向用户展示并由用户最终确认；存疑时按 AI 核心走（先过验证AI可行性，探针实测后可改判回普通轨）。
- **入口条件**：第 0 段完成。
- **确认需求（已建）出口**：用户确认/纯改判 → **两轨都先做需求挖掘（`needs_discovery`）** → 按 `ai_core` 分流：AI 轨走第 2 段验证AI可行性，普通轨直接第 3 段写 PRD；用户提修订意见/改判带附言 → 进 `requirement_refine` 整合节点，整合后确认再进 `needs_discovery`；用户拒绝 → 流程结束。
- **出口产物**：确认需求（含整合后的完整需求）、AI 适用性判定及理由。

### 第 2 段：验证AI可行性（待建）

回答"该不该用 AI、能不能做、成本能否承受"，发生在 PRD 之前。

- **活动（四项）**：
  1. **能力三色判断**：逐关键能力点标注——模型当前可稳定做到（绿）/ 需配合兜底或人工（黄）/ 做不到（红）；
  2. **PoL 探针**：流水线生成探针方案（5 个以内 prompt 链：核心任务样例、边界样例、失败诱导样例，含调用模型与步骤），**由人工/工程师执行实测，结论在本节点 HITL 录入**（S031 用户拍板：探针是一次性侦察，流水线不自动批量调用，省 token）；
  3. **风险扫描**：幻觉、提示注入、数据泄露、监管合规四类逐项给风险等级；
  4. **成本粗估**：按预估调用量、上下文长度、候选模型单价算月度成本区间。
- **入口条件**：AI 核心需求完成第 1 段需求挖掘之后进入本段。
- **确认AI可行性出口（四态，代码硬判辅助 + 人工拍板）**：
  - **通过**：无红色能力点、风险有缓解方案、成本可接受 → 进第 3 段 ai-native PRD；
  - **改判普通轨**：探针证实传统方案即可达成、AI 无净增益 → 第 1 段分流改判 ai_core=false，进第 3 段普通 PRD；
  - **重塑**：有红色能力点但缩小范围可规避 → 回第 1 段调整需求范围后重新过判定节点（限 1 次）；
  - **放弃**：红色能力点不可规避或成本不可接受 → 流程结束，产出可行性结论留档。
- **出口产物**：可行性报告（三色表、探针方案与实测结论、风险表、成本区间、结论）。

### 第 3 段：写PRD（已建）

AI 轨使用 ai-native 模板，来源为参考库 `apm/skills/prd-architect/references/templates/prd-ai-native.md`，结合业界 2026 做法（Product Compass 等）增补。必含内容：

1. 背景与目标：本期只解决什么、不做什么、成功标准（用户结果、AI 结果、可观察质量各 1 条）；
2. **AI 协作边界表**：人工负责 / AI 负责 / 系统反馈 / 必须停止转人工的条件；
3. 功能逻辑表：每个功能行写清条件状态、用户动作、AI 动作、系统反馈、**失败与接管方式**；
4. **上下文与记忆**：哪些信息跨轮携带、哪些经用户确认才沉淀、哪些不进长期上下文；
5. **负向验收标准**：明确"什么结果算失败、出现什么必须拒绝/转人工"，不只写正向期望；
6. **AI 风险登记册**：幻觉/注入/泄露/监管四类风险逐条登记触发条件与缓解措施；
7. **评测计划与可接受通过率**：引用第 5 段将定稿的评测集，写明可接受通过率是产品决策（非 100%）；
8. 量化 **kill 阈值**占位：在线阶段触发停用/回滚的指标数值（第 9 段发布计划细化）。

普通轨沿用现有 Markdown PRD prompt，行为不变。

### 第 4 段：评审PRD（五维已建，AI 维度待加）

- **现状**：五维评分（结构完整、SMART 可验证、逻辑一致、真人表达、信息缺口显式标注），代码硬判三档（均分 <3.5 打回；≥3.5 有维 ≤2 带警告通过；全部 ≥3.5 通过），打回回 PRD 重写，3 次上限强制放行。
- **AI 轨增补评审维度**：协作边界是否完整、失败接管是否每行可观察、负向标准是否可判、风险册四类是否齐全、可接受通过率是否写明。
- **出口规则不变**：分数由模型给，结论由代码按同一硬判机制给，模型不决定走向。

### 第 5 段：设计评测体系（待建）

回答"用什么题考、怎么判、多少分算及格"，在 PRD 评审通过后、拆工单前定稿。

- **四层考题集**：
  1. **典型题**：核心用户任务的正常路径；
  2. **边界题**：长尾、歧义、超长或异常输入；
  3. **对抗题（红队）**：提示注入、诱导泄露、诱导幻觉；
  4. **线上回放题**：上线后由第 11 段飞轮回收的真实坏例，持续注入本层。
- **评分方式（rubric）**：每题标注评分器类型——L1 确定性断言（规则/程序可判）或 L2 模型裁判（LLM-as-judge，配人工抽检比例）。
- **及格线**：整体通过率阈值 + 关键题（对抗题、核心典型题）单项阈值，两套数值都要写。
- **入口条件**：PRD 评审通过（含带警告通过）。
- **确认评测体系（HITL）出口**：用户确认考题集/rubric/及格线 → 落盘评测配置（Promptfoo YAML 草案）进第 6/7 段；提修改意见 → 重新起草（2 轮上限，第 3 版升级暂停，沿用已建三个确认节点的协议模式）。
- **出口产物**：评测集 YAML、rubric、及格线数值，写入评测档案（知识库）。

### 第 6 段：对比选型模型（已建，条件触发）

- **触发条件**：评测档案中无该类需求的有效选型记录，或记录超过月度复评周期，或需求方指定多模型对比。档案有效时直接引用结论，跳过本段。
- **活动**：用第 5 段同一批评测题，经 Promptfoo 对多个候选模型 provider 横跑；产出质量（通过率）、成本（千次调用单价）、延迟（P50/P95）三维对比；写回评测档案。
- **出口产物**：选型结论（推荐模型 + 三维数据 + 适用条件），供 PRD/工单引用。
- **渠道边界**：产品自身的模型调用固定走项目自有 DeepSeek；横跑的候选 provider 清单在开工前单独报批。

### 第 7 段：拆研发工单（已建，AI 特殊项待加）

- **现状**：纵切拆单 + 覆盖矩阵 + 结构硬校验，确认工单三选一（确认/意见重拆 2 轮/回 PRD 限 1 次，第 3 版升级暂停）。
- **AI 轨增补工单检查项**：trace 埋点工单（调用链可回看）、兜底与转人工工单（对应 PRD 失败接管每行）、评测接入工单（Promptfoo 配置与 CI 接入）、风险册缓解措施各有工单承接；覆盖矩阵相应增加校验。
- **出口规则不变**。

### 第 8 段：构建期跑评测（待建，内循环）

这是研发阶段的循环，不是一次性节点。PM Agent 在本段的职责是提供考题、启用工具、验收报告，不替代工程开发。

- **L1 离线断言**：每次代码/prompt 变更跑，Promptfoo 执行，退出码即结果；
- **L2 模型裁判 + 人工抽检**：按节奏（如提测前）跑，裁判分 + 人工标注汇总；
- **判定评测是否达标（新硬判定）**：构建完成申请进入发布计划时，流水线回收最近一次评测报告，**代码硬判**——整体通过率与关键题单项均达到第 5 段及格线 → 准入第 9 段；未达线 → 不进发布，报告退回工程师，不设自动放行；
- **出口产物**：带分数的评测报告 + 判定结论。

### 第 9 段：写发布计划（已建，AI 内容待加）

- **现状**：7 步骨架产发布计划，judge 硬校验 9 错误 4 警告，确认发布计划三选一，真机已验收。
- **AI 轨增补**：
  - **量化 kill 阈值**：在线准确率、人工接管率、延迟、成本等指标的停用/回滚触发数值，来自 PRD 占位并在此细化到可执行；
  - **cohort 晋级规则**：灰度分批比例与每批晋级的观测指标、观察时长；
  - 监控指标与第 10 段在线监控对齐。
- **出口规则不变**。

### 第 10 段：灰度发布与监控（二期）

- **L3 在线评测**：A/B 对比、trace 回看、模型漂移监控；工具拟选 Langfuse（需 Docker，二期安装验证）。
- 本期流水线只在发布计划中产出监控计划与 kill 阈值文档，不执行在线监控。

### 第 11 段：运营数据回流（二期，本期留接口）

坏例回收（线上失败/人工接管/用户负反馈）→ 转成新考题注入第 5 段评测集第四层 → 触发回归评测（第 8 段引擎）→ 不达标触发模型月度复评（回第 6 段）。本期在评测档案结构中预留坏例字段与回归触发接口。

## 五、判定节点清单汇总

| # | 判定节点 | 所在段 | 类型 | 判定方式 | 现状 |
|---|---|---|---|---|---|
| 1 | 确认需求 | 1 | HITL | 人工确认（含 AI 适用性判定） | ✅ 已建 |

## 七、现状节点映射（2026-09-14 代码实况）

```
kb_lookup → intake → requirement_confirm(HITL)
→（条件边：pending=True）requirement_refine(HITL 整合节点)
→（条件边：confirm/reclassify → needs_discovery / feedback → 自环 / abandon → END）
→（条件边：pending=False）needs_discovery → prd_generation → prd_review
→（reject 回 prd_generation，最多 3 轮）
→ issue_splitting → issue_confirm(HITL)
→（确认 / 重拆 2 轮 / 回 PRD 限 1 次，第 3 版升级暂停）
→ launch_plan → launch_confirm(HITL)
→（确认 / 重调 2 轮 / 回工单限 1 次，第 3 版升级暂停）
```

## 九、术语表

| 术语 | 含义 |
|---|---|
| AI 核心需求 | 核心价值由模型判断/生成/推荐/记忆承担的需求；第 1 段分流判定 |
| PoL 探针 | PRD 前的一次性能力侦察：用少量 prompt 链真实调模型，回答"能不能做"；本项目流水线出方案、人工执行、HITL 录结论 |
| Evals 评测集 | 回答"达不达上线标准"的考题集，第 5 段定稿、构建期持续生长、带及格线判定 |
| 四层考题 | 典型题 / 边界题 / 对抗题（红队）/ 线上回放题（飞轮注入） |
| L1 断言 | 确定性规则/程序可判的离线评分，每次变更跑 |
| L2 裁判 | LLM-as-judge 模型裁判 + 人工抽检，提测前按节奏跑 |
| L3 在线评测 | 灰度期 A/B、trace 回看、漂移监控（二期 Langfuse） |
| rubric | 每题的评分标准与评分器类型 |
| 及格线 | 整体通过率阈值 + 关键题单项阈值，产品决策，第 5 段人工确认 |
| 对比选型模型 | 同批评测题对多个候选模型横跑，比质量/成本/延迟 |
| 评测档案 | 知识库中持久化的选型与评测记录，对比选型查旧档、写新档 |
| kill 阈值 | 在线指标触发停用/回滚的量化数值，PRD 占位、发布计划细化 |
| cohort 晋级 | 灰度分批与按观测指标晋级下一批比例的规则 |
| 数据飞轮 | 坏例回收→新考题→回归评测→模型月度复评的外循环 |
| 能力三色表 | 逐能力点标注绿（可稳定做到）/黄（需兜底或人工）/红（做不到） |
| HITL / AFK | 人工确认节点 / 自动执行无需人工 |
| 判定节点 | 流程中需要人工或代码做出通过/打回/暂停结论的位置 |
