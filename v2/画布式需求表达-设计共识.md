# 画布式需求表达与改造（Canvas-as-Spec）设计共识

> 日期：2026-09-18（S054）
> 状态：**边界共识已定，尚未实现**（第一步 = 模块拓扑清单）
> 定位：本项目「外层可拓展」的进阶形态——用画布表达需求，Agent 据此改代码。

## 一、核心思路（用户定调，S054）

后端（流水线）做完后已可用，本质是「输入接口 → 解耦模块 → 输出接口」。要调整它内部状态，有两条路：

- **旧路**：用自然语言向 Agent 提需求 → Agent 理解 → 改代码。语言有歧义、Agent 要理解整体。
- **新路（本方案）**：**人在画布上摆节点/连线/用拓扑关系表达需求**（可附文字）→ 前端把画布翻译成 **Agent 能懂的明确结构图（节点+边+参数）** → Agent **读结构图 + 读对应源码模块** → 改单个小模块的代码。

**核心价值**：用「逻辑/拓扑/位置」代替「语言」提需求，文字只是补充。因为功能已解耦、单个模块代码量不大，**改单个小模块比改整体更轻松、错误更少、更容易验证**（改动面小、测试范围小、回归风险低）。

## 二、边界（三层架构中的位置）

```
┌─ 工作台（新外层，未建）───────────────┐
│  对话框（对话 agent UI）  │  画布（流水线 UI）│
│       ↑                        ↑         │
└───────┼────────────────────────┼─────────┘
        ▼                        ▼
┌─ 中层：综合 agent（Hermes/Pi）────────────┐
│  · 读画布结构图（JSON/拓扑文本）→ 理解需求   │
│  · 定位到对应源码模块                       │
│  · 改单个模块 / 派单改                     │
└───────▲────────────────────────▲─────────┘
        │ 输出                    │
┌─ 内层：流水线（确定性引擎，已可用、已解耦）─┐
│  20 节点 · 输入/输出接口 · 798 测试         │
└──────────────────────────────────────────┘
```

- **画布 = 编辑/设计工具**（表达需求、生成改造说明书），不是运行引擎。
- **综合 agent = 读图改代码的执行者**（已有）。
- **流水线 = 被改的目标**（已可用、已解耦）。
- 画布最终产出「改造说明书」，Agent 照它改 `src/` 里的代码；流水线跑的仍是代码，不是画布 JSON。

## 三、关键机制（避免走错方向）

1. **Agent 读的是结构图，不是像素**：画布对人是直觉（摆着看），对 Agent 要翻译成结构（谁连谁、顺序、条件）。画布序列化成 JSON/拓扑文本喂给 Agent。
2. **画布与源码的对应**：需要一份「模块拓扑清单」——哪个节点、输入输出、被谁依赖、对应哪块源码。没有它，画布和源码对不上，Agent 无法从图定位到代码。
3. **解耦是前提**：单模块代码量小，改动面小、测试范围小、回归风险低。现有流水线已模块化（LangGraph 节点天然解耦），是好底子。
4. **Agent 的角色**：读结构图 + 读对应源码 → 改单个模块（可参考 `tool_catalog` 的「结构化信息注入 prompt」先例）。

## 五、与现有体系的关系

- 不推翻流水线：流水线照跑，画布是「改它」的新入口。
- 与「拓展规则」（references/ 下告诉 Agent 怎么改文件）互补：拓展规则是文字版怎么改，画布是图形版怎么改。
- 与三层架构（workflow-design.md 第 0 条）一致：画布属外层（可生长），Agent 属中层（灵活），流水线属内层（稳定）。
