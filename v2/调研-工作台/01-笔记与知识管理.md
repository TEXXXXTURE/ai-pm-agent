# 调研 01｜笔记与个人知识管理类工作台

调研对象：Notion、Obsidian、Logseq、Heptabase、Tana、Craft、Capacities（共 7 款）。

调研目的：我们自己在做一个「个人工作台」（自用+朋友用，不售卖）。它是一套统一前端：可以接入不同的 Agent（对话型用对话框、流水线型用画布），可以挂不同技能与工具，按 VS Code 插件的方式加按钮入口；按钮打开后的界面用组件拖拽自定义，产物是结构化 JSON。因为工作台本身有自定义能力，所以要把别家工作台的功能一条条"翻译"成我们这边的一个「模式」。

说明：
- 本文所有结论优先取官方文档/官网原话的意思；官网没有的写「未找到一手来源」，不猜。
- 拿不到一手确认的写「未核实」。
- 每节末尾给来源 URL。功能频次表与启示部分基于前面各节的来源，不引入新来源。

## 一、逐个产品

### 1. Notion

**① 一句话定位**
官方帮助中心把 Notion 描述为：页面由「块」堆叠而成，而数据库是「页面的集合」——即"一切内容都是块，数据库里的每一行本身也是一个页面"。官方原话：*"Everything in Notion is a block"*；*"Databases in Notion are collections of pages"*。
（来源：https://www.notion.com/help/what-is-a-block ，https://www.notion.com/help/intro-to-databases ）

**② 核心功能清单**

| 功能 | 说明 | 解决用户什么需求 |
|---|---|---|
| 块（Block） | 文本、图片、表格等每一段内容都是一个可独立移动/复制的块，页面是块的堆叠 | 边写边调结构，不用先规划大纲 |
| 页面嵌套 | 块下可以有子页面，页面下可以放行内数据库 | 内容和内容之间能直接长在一起，不用另开文件 |
| 数据库（Database） | 页面集合，每一条（表格的行、看板的卡片）都是独立页面 | 同一批条目既能当清单又能当文档 |
| 数据库视图 | 同一数据库可建多个视图标签：表格、看板、时间轴、日历、列表、画廊、图表；另有表单 | 同一份数据按当下要做的判断换一种呈现 |
| 属性 + 筛选/排序/分组 | 视图级设置：布局、显示哪些属性、筛选条件、排序、分组 | 只看此刻该看的那几条 |
| 关联数据库视图（Linked database） | 把另一个数据库的视图嵌到当前页面 | 在项目页里直接管任务，不用来回跳 |
| 模板 | 数据库条目模板、模板库 | 重复性的页面不用每次从零搭 |
| 权限与协作 | "Can edit content"等权限层级，可编辑内容但不能改属性/视图 | 分享时能控制别人能动到什么程度 |
| API（Connections） | REST API，`https://api.notion.com`，读写页面/数据库/块，JSON 请求响应，带分页 | 把外部工具接进工作区，也能在 Notion 里嵌互动界面 |
| AI / Agents | 导航中存在 Notion AI、AI Connectors、Custom Agents、External Agents 等板块 | 让 AI 在内容库里干活 |

**③ 怎么做自定义/扩展**
- **API/Connections**：官方把第三方接入统一叫 "Connections"，用 API 访问 pages、databases、users，可"build interactive experiences for users within Notion"（来源：https://developers.notion.com/reference/intro.md ）。
- **数据库视图 + 属性 schema**：自定义主要以"建数据库、加属性、存视图配置"的方式完成，不是写代码。
- **模板**：官方帮助中心有模板库（Marketplace & templates）与数据库模板（来源：https://www.notion.com/help/database-templates ，https://www.notion.com/help/start-with-a-template ）。

**④ 可抽象成我们工作台的一个「模式」**
- **模式名**：数据表模式（Database mode）
- **界面形态**：左侧页面树 + 中间文档区 + 顶部视图标签（表格/看板/日历/列表/画廊/图表）；每个视图标签只保存"筛选/排序/分组/显示字段"。
- **要接的后端接口**：
  1. 页面/块 CRUD（按块 ID 读写、取子块列表、分页）；
  2. 数据源查询（传入筛选+排序+分组，返回记录数组）；
  3. 视图定义读写（一个视图 = 一份 JSON，正好对齐我们拖拽组件的产物）；
  4. 属性（字段）schema 读写。
- **和我们已有的能力对应**：视图定义 JSON ≈ 我们拖拽布局产出的结构化 JSON；Agent 可以作为一个"视图里的行操作"。

**⑤ 来源 URL**
- https://www.notion.com/help/what-is-a-block
- https://www.notion.com/help/intro-to-databases
- https://www.notion.com/help/views-filters-and-sorts
- https://www.notion.com/help/create-links-and-backlinks
- https://www.notion.com/help/database-templates
- https://developers.notion.com/reference/intro.md

### 2. Obsidian

**① 一句话定位**
官网首页：*"Sharpen your thinking. The free and flexible app for your private thoughts."*——本地优先、可插拔、数据长期属于自己（原话包括 *"It stores notes privately on your device"*、*"With thousands of plugins and themes, you can shape Obsidian to fit your way of thinking"*、*"Obsidian uses open file formats, so you're never locked in"*）。
（来源：https://obsidian.md/ ）

**② 核心功能清单**

| 功能 | 说明 | 解决用户什么需求 |
|---|---|---|
| 本地文件库（Vault） | 笔记以 Markdown 文件存在本机，离线可用 | 数据自己拿着，不怕服务商跑路 |
| 双向链接 | `[[链接]]` 互连笔记，官方原话 "Invent your own personal Wikipedia" | 想法之间建立关系，而不是靠文件夹 |
| 标签页（Tabs） | 官方帮助站说明"Tabs 像浏览器标签一样工作"，可开任意多标签、分组、拖拽排列，布局可保留 | 同时处理几份笔记而不丢位置 |
| 每日笔记（核心插件） | 官方帮助站：打开"今天"的笔记，没有就按 `YYYY-MM-DD` 新建；可从 ribbon 图标、命令面板、快捷键打开 | 每天有个固定入口先记下来 |
| 关系图谱（Graph） | 可视化笔记之间的连接，看隐藏的模式 | 一眼看出哪些主题是孤岛 |
| 属性（Properties） | 给笔记加结构化字段 | 让笔记能被筛选、被查询 |
| Bases（核心插件） | 给笔记做"数据库式视图"：表格、列表、卡片网格、地图，可筛选/排序/分组，支持公式；视图描述存在 `.base` 文件或 Markdown 代码块里 | 不迁移数据也能得到数据库体验 |
| 核心插件开关 | 内置功能可按需开/关 | 界面不被用不到的功能占满 |
| 社区插件（Community plugins） | 用 TypeScript 写插件扩展功能；插件可加命令（Command palette）和左侧 ribbon 图标 | 把工具改成自己顺手的样子 |
| 主题与 CSS | 用 CSS 改外观，主题目录 | 长时间看的东西要顺眼 |
| Web Clipper | 浏览器扩展，把网页高亮存进库 | 收集外部资料 |
| Obsidian CLI | 从终端控制 Obsidian | 让脚本/Agent 驱动它 |
| Sync / Publish | 端到端加密同步；一键把笔记发成在线 wiki/数字花园 | 多设备；对外分享 |
| Canvas（核心插件） | 无限画布，把笔记和卡片摆开、连线 | 做研究时看整体关系 |

**③ 怎么做自定义/扩展**
- **插件机制**：官方开发者文档首页写明"用 TypeScript 写插件来扩展 Obsidian 的既有功能"；插件放 `vault/.obsidian/plugins/`，有 manifest，能注册命令（Command palette）、左侧 ribbon 图标按钮（教程示例即 `this.addRibbonIcon('dice', 'Greet', ...)`）。来源：https://docs.obsidian.md/Home ，https://docs.obsidian.md/Plugins/Getting+started/Build+a+plugin/ 。
- **主题/CSS**：官方开发者文档独立一章 Themes（同源）。
- **社区插件目录**：官方有 community directory（浏览、安装、更新、上架）来源：https://help.obsidian.md/community-plugins 。
- **Bases**：视图用 `.base` 语法描述，可存文件也可嵌在 Markdown 代码块中（来源：https://help.obsidian.md/bases ）。
- **CLI**：官方帮助站列有 Obsidian CLI，"Control Obsidian from your terminal using the command line interface"（来源：https://help.obsidian.md/ ）。

**④ 可抽象成我们工作台的一个「模式」**
- **模式名**：插件按钮模式（Plugin button mode）＋ 本地库模式（Local vault mode）
- **界面形态**：左侧 ribbon 竖排图标按钮 + 命令面板（`Ctrl/Cmd+P` 输入命令名）+ 主区编辑器/画布/表格视图多标签。
- **要接的后端接口**：
  1. 扩展注册接口（注册一个按钮：图标+名字+命令 ID；注册一个命令：名字+回调）——这正好就是我们要的"按 VS Code 插件方式加按钮入口"；
  2. 本地文件读写与索引（目录列举、读文件、写文件、块级引用索引）；
  3. 视图引擎接口（一个视图 = 声明式 JSON/文本描述，交给渲染器）。
- **要点**：Obsidian 的 ribbon icon + command palette 是我们按钮入口最接近的现成范式；Bases 的"视图描述与数据分离"是我们组件拖拽 JSON 的直接参照。

- https://help.obsidian.md/
- https://help.obsidian.md/tabs
- https://help.obsidian.md/plugins/daily-notes
- https://help.obsidian.md/bases
- https://help.obsidian.md/community-plugins
- https://docs.obsidian.md/Home
- https://docs.obsidian.md/Plugins/Getting+started/Build+a+plugin/

### 3. Logseq

**① 一句话定位**
官网：*"Logseq is the open toolbox for workflows that deal with lots of information"*——面向信息量大的工作流（学生、研究者、写作者、项目经理、开发者）；开源、隐私优先、数据本地、Markdown 文件（官网要点栏原话：Open source / Privacy first / Mobile apps / Markdown files / 150+ Plugins / 30+ Themes）。
（来源：https://logseq.com/ ）

**② 核心功能清单**

| 功能 | 说明 | 解决用户什么需求 |
|---|---|---|
| 大纲编辑器与缩进块 | 内容是缩进的块，官方文档有专页解释 indentation | 想到哪写到哪，结构后补 |
| 页面引用与块引用 | 可以引用一整页，也可以引用某一个块 | 把一句话搬到别处不复制粘贴 |
| 页面嵌入/块嵌入 | 引用之外还能"嵌"进来，内容同步 | 一处修改到处一致 |
| 反向链接与未链接引用 | 每页自动列出"谁引用了我"、"谁提到了这个词但没做链接" | 找回丢失的上下文，避免"过去的自己踩坑" |
| 日记页（Journals） | 以日期为天然入口 | 每天先记下来，回头再整理 |
| 任务/待办 | 块级 TODO/DOING 状态 | 笔记和任务不分家 |
| 查询（Queries / Query Builder / 高级查询） | 规则化筛选内容，有查询构建器 | 自动列出"所有没做完的项目" |
| 模板 | Templates | 常用结构一键铺开 |
| 属性（Properties） | 给页面/块加字段 | 让查询有东西可筛 |
| 白板（Whiteboard） | 文档列出的可视化功能 | 把块摆开看关系 |
| 闪卡 / PDF 高亮 / Zotero | 记忆、读文献、抓引文 | 复习与学术工作流 |
| 插件（150+）与主题（30+） | 官网数字 | 按需长功能 |
| 本地 Markdown / Org 文件、开源 | 数据可被别的工具打开 | 长期可迁移 |

**③ 怎么做自定义/扩展**
- **插件体系**：官方文档目录有 "Customization → Plugins" 与 "Create a plugin! Start with Plugins 101"（来源：https://docs.logseq.com/#/page/plugins ）。
- **主题与用户配置**：同目录下有 User configuration、Custom theme。
- **模板与查询**：官方功能清单里 Templates、Queries 与 Query Builder、Advanced Queries 属内置能力（同源）。
- **本地文件格式**：Markdown 和 Org Mode 两种（同源）。
- 注：插件 API 的具体接口清单本文未取到一手页面，标注**未核实**。

**④ 可抽象成我们工作台的一个「模式」**
- **模式名**：大纲块模式（Outliner mode）＋ 日记模式（Journal mode）
- **界面形态**：单栏大纲（缩进块，回车即新建同级块、Tab 缩进）；右栏是"当前页的引用/反向链接"面板；顶部有日记/查询/白板三个入口。
- **要接的后端接口**：
  1. 块树 CRUD（父块/子块、块 ID、块状态位）；
  2. 引用与反链索引（谁引用了这个块/页）；
  3. 查询执行接口（查询定义 → 结果块列表）；
  4. 日期路由（按 `YYYY-MM-DD` 取当天页）。
- **要点**：日记模式是我们"每天打开工作台先看到一个当日面板"的最省事做法；反链面板可以直接复用成"Agent 引用来源"的展示位。

- https://logseq.com/
- https://docs.logseq.com/

### 4. Heptabase

**① 一句话定位**
官网首页标题：*"Master anything you learn."*（把学到的东西彻底掌握）。官方 Wiki 把产品解释成"像操作系统一样"：左侧是各个 App，所有 App 共享同一个卡片数据库；上方是 "Research a topic" 按钮，下面依次是各 App（Inbox / Journal / Whiteboard / Card Library / Tag Database / Highlight / Chat）。
（来源：https://heptabase.com/ ，https://wiki.heptabase.com/user-interface-logic ）

**② 核心功能清单**

| 功能 | 说明 | 解决用户什么需求 |
|---|---|---|
| 卡片（Card） | 笔记的基本单位，所有卡片存在 Card Library；除笔记卡外还有 Journal 卡、Highlight 卡，以及 PDF/视频/音频/图片卡 | 一份资料就是一个可摆放的对象 |
| 白板（Whiteboard） | 无限画布，把卡片摆上去做研究；可建子白板分层 | 复杂主题需要一个能摊开的地方 |
| 卡片与白板解耦 | 官方原话"Whiteboards do not own cards"，同一张卡可同时出现在多块白板上 | 同一个概念在不同主题下复用，不用复制 |
| 白板上的多种对象 | 右键可建卡片、文本、思维导图、日记、Section、子白板；可画箭头连线 | 想法、结构、计划在同一个面上 |
| 标签数据库 + 属性 | 标签集中管理、分组到集合，卡片的属性可读写 | 批量管理同类卡片 |
| Tab 系统 | 普通标签、网页标签、固定标签、标签文件夹、标签分组（如 Work / Life） | 同时开很多上下文而不乱 |
| 右侧栏 App | 标签页右上角可开 Chat、Card library、Insight、Task 等 | 写作时把要参考的东西放在手边 |
| AI Chat / AI Actions / Insight | 用卡片、白板、PDF、视频、日记当上下文提问，回答带出处；AI Actions 可翻译、总结、生成思维导图，也能自定义提示词动作；Insight 把长文按约 300 字切块、每块给一条要点并回链原文 | 基于自己的资料问答，而不是通用聊天 |
| Research a topic | 上传 PDF/YouTube/文档/图片 → 自动转成卡片并铺到新白板，解析 PDF、下载字幕，并打开右侧对话给出建议问题 | 从"一堆资料"到"可研究的白板"一步到位 |
| 离线访问 | 官网要点栏：无网络也能访问全部笔记与文件 | 飞机上也能看 |
| Zotero / Readwise 同步、网页剪藏 | 官方 Wiki 与帮助中心列有 | 学术与阅读工作流 |

**③ 怎么做自定义/扩展**
- **官方明确说没有插件 API**：帮助中心条目《Do you provide an API so I can create my own plugins?》回答大意是"还没有。我们计划未来提供面向终端用户的可编程能力，但这不是当前优先级；现在聚焦移动端与白板体验；加自定义选项需要小心设计，避免复杂度干扰核心体验"（来源：https://support.heptabase.com/en/articles/10447604-do-you-provide-an-api-so-i-can-create-my-own-plugins ）。
- **MCP**：让外部 AI 服务列出/搜索/读取/创建/编辑/整理空间内容（笔记、日记、标签、白板、图片、解析过的 PDF），工具如 `read_object`、`read_pdf`、`read_image` 等（来源：https://support.heptabase.com/en/articles/12679581-how-to-use-heptabase-mcp ）。
- **CLI**：官方 CLI 让 AI 编码代理在终端里创建/读/改笔记卡与日记、搜卡片库、管标签、列白板并增删卡片、读写标签数据库 schema 与卡片属性值、逐页读 PDF 文本、读音视频转写、读 AI Tutor 课程；所有命令返回 JSON。官方还提供了配套的 CLI skill 仓库供 Agent 安装（来源：https://support.heptabase.com/en/articles/14715462-how-to-use-heptabase-cli ）。
- AI Actions 支持自定义提示词动作（来源：https://wiki.heptabase.com/fundamental-elements ）。

**④ 可抽象成我们工作台的一个「模式」**
- **模式名**：画布卡片模式（Canvas card mode）
- **界面形态**：无限画布放卡片，卡片可连线、可分组（Section）、可进子画布；左侧竖栏是"卡片库/标签库/收件箱"这些资源 App；右侧栏可切换成对话框或卡片库；整个工作台是多标签页（含网页标签）。
- **要接的后端接口**：
  1. 卡片 CRUD（含卡片类型与属性）；
  2. 画布布局持久化（对象的位置/尺寸/连线/分组/所属画布）；
  3. 资源库检索（按标签、属性、全文搜卡片，返回可拖到画布的对象）；
  4. Agent 上下文注入（把当前画布/选中卡片/打开的标签页作为上下文传给 Agent）+ 回答带出处的位置回链。
- **要点**：这一款和我们的"流水线型 Agent 用画布"几乎是同一个形态；"白板不拥有卡片"这一条值得直接照抄——我们的产物也应该是库里的一张卡，而不是画布上的孤本。

- https://heptabase.com/
- https://wiki.heptabase.com/fundamental-elements
- https://wiki.heptabase.com/user-interface-logic
- https://wiki.heptabase.com/organize-knowledge-and-projects
- https://support.heptabase.com/en/articles/10447604-do-you-provide-an-api-so-i-can-create-my-own-plugins

### 5. Tana

**① 一句话定位**
官方把 Tana 定位成知识图谱 + 大纲编辑器：官网口号 *"Write information, not documents."*（写信息，而不是写文档）；官方解释是"大纲编辑器适合处理知识图谱，但一直缺少表达层级之外结构的方式，Tana 用 Supertags 与字段补上，用 Views 在编辑器里可视化信息"。
（来源：https://outliner.tana.inc/knowledge-graph ，https://outliner.tana.inc/outline-editor ）

**② 核心功能清单**

| 功能 | 说明 | 解决用户什么需求 |
|---|---|---|
| 大纲编辑器 | 像普通大纲一样写，无限缩放：放大只看一条，缩小看全貌 | 在大信息量下既看细节又看全局 |
| 超标签（Supertags） | 给节点一个"它是什么"的类型，官方原话"think of them as types or categories"；最简单的就是一个 `#idea` 标签，最复杂可以是一个完整工作流（如 `#post` 带状态、媒介、发布日字段） | 一件事在记录时就带上它的处理方式 |
| 字段（Fields） | 超标签订了的字段在写的时候直接出现在行内 | 结构化不用跳去别的表 |
| 节点复用 | 官方原话"Update it anywhere and it updates everywhere"，信息可以在多处同时生长 | 消灭复制粘贴造成的不一致 |
| 搜索节点（Search Node） | 把散落各处但带同一类型/字段的节点收集到一起 | 不用管节点放在哪，按类型捞回来 |
| 视图（Views） | 同一份数据可切成列表、表格、卡片、标签页、日历 | 同一份信息按当下目的看 |
| 知识图谱 | 关系在背后自动维护，官方强调"不需要懂图论"、不用写查询语言 | 不学数据建模也能拿到结构化好处 |
| 内联 AI | 在大纲里按空格就能在光标处唤起 AI，而不是另开聊天窗 | AI 在工作发生的地方出现 |
| 官方模板 | 官方有模板功能页与模板商店 | 常见工作流一键开始 |
| Tana Input API | 官方提供 Input API 示例代码仓库（tanainc/tana-input-api-samples） | 外部工具往里送数据 |

**③ 怎么做自定义/扩展**
- **超标签 + 字段**是主要自定义方式：自己定义类型与字段，等于自己定义一套轻量应用（来源：https://outliner.tana.inc/supertags ）。
- **视图**：官方称"所有应用其实都是数据库的某种投影，我们在卖这些好看的投影"，Tana 把投影权交回用户；目前已支持列表、表格、卡片、标签页、日历，官方称还有十几种视图在研发（来源：https://outliner.tana.inc/views ）。
- **API**：官方 GitHub 有 Tana Input API 示例仓库（来源：https://github.com/tanainc/tana-input-api-samples ）；官方完整 API 文档本文未取到一手页面，标注**未核实**。
- **模板**：官方模板功能页 https://outliner.tana.inc/learn/features/tana-templates ；另有模板商店（来源：https://outliner.tana.inc/blog/tana-template-store ）。

**④ 可抽象成我们工作台的一个「模式」**
- **模式名**：类型化节点模式（Typed node mode）
- **界面形态**：大纲是大本营（缩进节点，行内显示字段），每个节点可切换视图（列表/表格/卡片/日历），另有"搜索节点"作为虚拟文件夹。
- **要接的后端接口**：
  1. 节点 CRUD（含类型 ID 与字段值）；
  2. 类型与字段 schema 读写（一个类型 = 一份 JSON 定义）；
  3. 查询接口（按类型+字段条件收集节点）——对应我们的"按钮点开列出所有 X"；
  4. 视图渲染器注册表（视图名 → 渲染器，同一份数据换投影）。
- **要点**：Tana 的"视图是同一份数据的投影"与我们"拖拽自定义得到结构化 JSON"是同一件事的两种说法；我们的按钮入口可以理解为"一个超标签 + 一个视图"。

- https://outliner.tana.inc/outline-editor
- https://outliner.tana.inc/supertags
- https://outliner.tana.inc/views
- https://outliner.tana.inc/learn/features/tana-templates
- https://github.com/tanainc/tana-input-api-samples

### 6. Craft

**① 一句话定位**
官网首页：*"Your space for notes, tasks, and big ideas"*，并明说 Craft 不只做一件事——官网列出的能力块是 Docs / Tasks / Calendar / Whiteboards / Daily Notes。
（来源：https://www.craft.do/ ）

**② 核心功能清单**

| 功能 | 说明 | 解决用户什么需求 |
|---|---|---|
| 块（Block） | 官方帮助中心原话"everything you create is a block"，每一段、每张图、每个标题都是独立单元，可单独移动/复制/删除 | 内容颗粒度细，改起来不用整篇重排 |
| 页面（Page） | 任何"下方还有内容的块"就是一个页面，可点进去 | 写到一半发现该分节，直接就地变页面 |
| 文档（Document） | 侧边栏里的顶层容器 | 一个话题一个文档 |
| 页面样式（Page / Card 样式） | 给"里面还有东西"的块一个显眼外观 | 一眼看出哪里能点进去 |
| 空间（Spaces） | 每个空间是独立工作区，有自己的文档和空间级设置（模板、发布内容、标签规则、成员等） | 工作与生活分开，互不干扰 |
| 模板 | 空间设置里可查看/编辑该空间的所有模板 | 重复内容不用重搭 |
| 任务 / 日历 / 每日笔记 | 官网首页列为并列能力 | 笔记、待办、日程放一起 |
| 白板 | 官网首页列为并列能力（未找到一手功能细则页 → **未核实**具体形态） | 把内容摊开看 |
| 链接与反向链接 | 官方帮助中心有《Links and Backlinks》专页 | 找到"谁提到了这个" |
| 发布与分享 | 空间设置里可管理已发布页面并查看其分析数据 | 对内整理、对外发布 |
| API Connections | 在侧边栏 Connections 页创建"API 连接"，选择全部日报或指定文档，设置权限与可见性，Craft 生成该连接专属的 API endpoint；支持全空间级访问：跨文档搜索（可带文件夹/标签/日期过滤）、日报与任务、创建/更新/删除文档、集合（Collection）schema 管理、带正则的高级搜索 | 把工作区按需、可控地开放给外部工具 |
| MCP | 官方明确说可通过 MCP 连接 Claude、ChatGPT 等 AI 助手 | 让 AI 助手用到自己的文档 |
| Extension API | 官方 GitHub 组织有 `craftdocs/craft-extension-api` 仓库（该仓库正文只给了一个开发者文档入口链接：documentation.developer.craft.do；该文档站本次抓取失败，**未核实**具体能力清单） | 在 Craft 内嵌自建扩展 |

**③ 怎么做自定义/扩展**
- **API 连接模型**：不是给一把万能钥匙，而是"一个连接对应一批文档 + 一组权限"，每连接独立 endpoint（来源：https://support.craft.do/en/integrate/api ）。
- **MCP**：官方在 API 页直接给出"通过 MCP 或其他集成方式连接 Claude/ChatGPT"的说明（同源）。
- **模板**：空间级（来源：https://support.craft.do/en/introduction/account-setup/spaces ）。
- **Extension API 仓库**：https://github.com/craftdocs/craft-extension-api （内容极少，仅指向开发者文档站）。

**④ 可抽象成我们工作台的一个「模式」**
- **模式名**：空间与文档模式（Space & document mode）
- **界面形态**：顶部空间切换器 + 左侧文档树 + 主区块编辑器（块可直接变页面）+ 并列的任务/日历/每日笔记入口。
- **要接的后端接口**：
  1. 空间列表与切换；
  2. 文档/块 CRUD（含"块升级为页面"的操作）；
  3. **连接（Connection）接口**：创建"一个技能/Agent 可见的文档范围 + 权限"，返回专属 endpoint——这正是我们"给每个 Agent 挂不同技能与工具"最贴切的权限模型；
  4. 模板读写（空间级）。
- **要点**：Craft 的"按连接分配可见范围"值得直接抄成我们挂 Agent/技能时的默认权限粒度。

### 7. Capacities

**① 一句话定位**
官方文档把 Capacities 描述为一个"以对象为中心"的空间：*"An object is the fundamental unit of content in Capacities. Every object in Capacities has a type."*——内容基本单位是"对象"，每个对象都有类型；类型分内置的基础类型和自建的自定义类型，类型决定内容结构。
（来源：https://docs.capacities.io/reference/content-types ）

**② 核心功能清单**

| 功能 | 说明 | 解决用户什么需求 |
|---|---|---|
| 对象（Object） | 内容的基本单位，对象必然属于某个类型；所有类型列在左侧栏 | 不同类型的东西长得就不一样，而不是一堆同质页面 |
| 基础类型 | Page、Tag、Image、Weblink、Audio、PDF、Files、Tweet、AI Chat、Query、Table 等内置类型 | 常见东西开箱就有合适的样子和功能 |
| 自定义类型 + 属性 | 自己定义类型与属性，属性决定结构 | 按自己的工作方式建模，而不是迁就模板 |
| 页面布局（Page layouts） | 仅自定义类型可用：标准（可宽屏，适合做仪表盘）、索引卡（仿纸质卡片，限制长度、适合短内容与草稿）、档案/Profile（圆形头像+左侧属性区，适合人/公司/组织）、百科（目录+反链导航，高信息密度） | 人和书和会议，应该有不一样的长相 |
| 标签（Tags） | 跨类型连接主题，可打在对象和块上，还能作为对象选择属性的下拉来源 | 大范围的横向连接 |
| 标签（Labels，类型内） | 用于同一类型内的细分筛选 | 精确到"这个类型里的哪种" |
| 集合（Collections） | 手动组织的集合 | 需要人肉挑一遍的场合 |
| 查询（Queries，Pro） | 保存的规则化动态视图，内容不满足规则就不出现，无需人工维护 | 视图自己保持最新 |
| 日记笔记 / 会议笔记 / 任务 / 日历同步 | 官方参考文档的用例页：Daily notes、Meeting notes、Calendar sync、Tasks | 日常记录与会议流程有既定做法 |
| 对象类型仪表盘 | 类型设置里有仪表盘分区，可固定/取消固定某一节 | 打开一个类型就看到该看的东西 |
| AI 助手 | 可把 AI 对话保存成对象 | 有价值的问答不丢 |
| REST API | `https://api.capacities.io`，一个访问令牌对应一个空间，可读写对象、属性、块内容、日报等 | 外部程序接入 |
| MCP | 官方文档有 Model Context Protocol 页 | 让 AI 工具直连 |

**③ 怎么做自定义/扩展**
- **类型 + 属性 + 页面布局**是主要自定义路径：自定义类型可配属性、可选布局（Standard / Index card / Profile / Encyclopedia）、可宽屏（来源：https://docs.capacities.io/reference/page-layouts ）。
- **查询**：Pro 功能，规则化视图（来源：https://docs.capacities.io/reference/organizational-structures ）。
- **API**：REST，base URL `https://api.capacities.io`，一个 token 一个空间，读写对象/属性/块/日报（来源：https://developers.capacities.io/api/overview ）；另有 SDK 页与 MCP 页（同站）。
- **官方给了决策树**：按结构还是按主题组织 → 结构用类型/属性，主题用标签；一组笔记手动用集合（类型内）或标签（跨类型），按规则用查询；同一类型内的分类用 Label，跨类型用 Tag（来源：https://docs.capacities.io/reference/organizational-structures ）。

**④ 可抽象成我们工作台的一个「模式」**
- **模式名**：对象类型模式（Object type mode）
- **界面形态**：左侧竖排类型列表（今天、人物、会议、书……）+ 点击某类型进入该类型的仪表盘（分区卡片网格）+ 单个对象页按布局渲染（标准/索引卡/档案/百科四种）。
- **要接的后端接口**：
  1. 类型与属性 schema 读写；
  2. 对象 CRUD（含类型、属性、所属集合、当天日记）；
  3. 查询接口（保存的规则视图）；
  4. 页面布局配置（类型 → 布局 + 宽屏开关）→ 与我们"按钮打开后的界面用组件拖拽自定义"天然对接：一个类型配一个默认布局 JSON。
- **要点**：Capacities 的"同一类型可有不同布局"最贴近我们的组件拖拽产物；它的决策树也是一段很好的默认引导文案，可以照抄进我们的新建类型向导。

- https://docs.capacities.io/reference/content-types
- https://docs.capacities.io/reference/organizational-structures
- https://docs.capacities.io/reference/page-layouts
- https://developers.capacities.io/api/overview

## 三、本组启示

### 值得我们抄的界面形态设计

1. **左侧资源栏 + 右侧上下文栏的两栏夹一主区**（Heptabase 左侧是各 App、右侧栏可切 Chat/卡片库/Insight；Logseq 右栏放引用）。→ 我们的 Agent 对话框天生该是右栏里的一个可切换面板，而不是另开一个窗口。来源见 Heptabase ①、Logseq ②节。
2. **「视图」是同一份数据的投影，不是新页面**（Notion 视图标签；Tana 官方原话"所有应用其实都是数据库的某种投影"；Obsidian Bases 视图用 `.base` 描述；Capacities 查询是保存的规则视图）。→ 我们拖拽布局产出的 JSON 应该被定义为"视图定义"，数据不复制、只换渲染器。来源见各节 ③/⑤。
3. **块可直接变成页面 / 卡片与画布解耦**（Craft：任何下方有内容的块就是页面；Heptabase 官方原话"Whiteboards do not own cards"，同一张卡可出现在多块白板）。→ 按钮入口产生的东西应该是库里的一张卡，可以在任何画布/列表里被引用，而不是只长在某个画布里。来源见 Craft ②、Heptabase ②。
4. **命令面板 + 侧边图标按钮**（Obsidian 的 ribbon icon 与 Command palette；Logseq 的 Commands/Advanced commands）。→ 这就是"按 VS Code 插件方式加按钮入口"的现成范式：一个扩展同时注册"一个图标按钮 + 一个命令"。
5. **同一类型可配不同页面布局**（Capacities：标准 / 索引卡 / Profile / 百科，人、书、会议长得不一样）。→ 我们的组件拖拽结果可以按"类型"存一套默认布局，点开即有型。
6. **标签页系统带 固定 / 文件夹 / 分组**（Heptabase：普通标签、网页标签、固定标签、标签文件夹、标签分组 Work/Life）。→ Agent 会话、流水线画布、网页都可以是标签，且能固定住常用的那几个。

### 明确不适合我们的

1. **通用数据库引擎（关系、汇总、公式、复杂的查询语言）**。Notion 的关联视图与属性体系、Tana 的搜索节点、Capacities 的查询都是重装备。我们是自己人用，建元数据的成本大于收益——先只留"标签 + 少量固定字段 + 保存的筛选"。来源见 Notion/Tana/Capacities 各节 ②③。
2. **把「图谱」当主界面**。Obsidian 的关系图谱、Tana 的知识图谱都强调"看连接"，但节点少时图谱不能带来判断。我们的引用只做局部列表（像 Logseq 的反链面板那样），不做全局星图。来源见 Obsidian ②、Tana ②。
3. **建插件市场与上架审核流程**。Obsidian 有社区插件目录与开发者政策、Logseq 有 150+ 插件生态——那是面向海量陌生用户才需要的。我们走"本机文件夹里的脚本 + 一个 manifest"即可。来源见 Obsidian ③、Logseq ③。
4. **把 7 款全做成模式、追求功能齐全**。Heptabase 官方在回答"为什么不做插件 API"时给的理由很值得听：加自定义选项要小心设计，避免复杂度干扰核心体验（原文大意"Adding customization options requires careful design to avoid complexity that could distract from the core experience"）。→ 建议先落地 3 个模式（画布卡片、数据表、大纲块），其余做成可选。来源：https://support.heptabase.com/en/articles/10447604-do-you-provide-an-api-so-i-can-create-my-own-plugins
5. **重前置结构**。Notion 要先建数据库和属性、Tana 要先定超标签与字段、Capacities 要先定类型——都要先做设计再记录。我们要的是"点按钮就能开始用"，所以默认值必须由我们预置好，让用户后补结构。来源见各节 ③。
6. **云同步与多端在线服务**。Notion、Tana、Capacities 都是在线服务，Obsidian/Logseq 则把"本地优先"当卖点。自用产品不需要为多端账号体系付复杂度；先做本机（配合现有同步盘）。来源见各节 ①。
