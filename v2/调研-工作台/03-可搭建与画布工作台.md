# 03 可搭建平台与画布式工作台 · 调研

> 调研对象：Retool、Appsmith、Budibase、ToolJet、n8n、Dify、Coze、ComfyUI、Figma、墨刀
> 调研角度：它们怎么做「自定义 / 可扩展 / 画布」，哪些做法能搬进我们的「个人工作台」，哪些不能搬。
> 写作原则：每条结论都给了来源 URL；查不到一手资料的写「未找到一手来源」；拿不准的标「未核实」。

---

## 0. 先给结论：这批产品其实是三种东西

在动手看细节之前，先把这 10 款产品分成三类，不然后面会串味：

| 类别 | 产品 | 它们真正在解决的问题 |
|---|---|---|
| 低代码搭建（页面 + 数据源） | Retool、Appsmith、Budibase、ToolJet | 让我不写前端也能做出一个能连数据库、能点按钮的内部工具 |
| 画布式工作流（节点 + 连线） | n8n、Dify、Coze、ComfyUI | 让我把一串处理步骤画成图，然后这张图能被程序读走、被引擎跑起来 |
| 拖拽设计（界面定制） | Figma、墨刀 | 让界面本身变成可拖拽、可复用、可被代码消费的对象 |

对我们最重要的一条观察：**上面三类产品在「画布 → JSON → 引擎」这条链路上是同一套做法**——画布上摆的东西最终都被序列化成一份带节点、连线、位置的文本，人看得懂，程序也读得走。差别只在序列化格式是公开的、还是自家私有的。

## 一、逐个产品

### 1. Retool

**① 一句话定位**
面向企业内部的低代码应用搭建平台，把自己定位成「连数据库、拼组件、写一点 JS 就能上线一个内部工具」。

**② 核心功能清单**

| 功能 | 说明 | 解决什么需求 |
|---|---|---|
| 组件化画布 | 组件在平台上「功能上类似 React 组件」，模块化、可复用、各自有内部状态 | 不写前端也能搭界面 |
| 组件即 JS 对象 | 每个组件被表示成一个 JavaScript 对象，里面是它的全部属性和当前值（如 `pluginType`、`value`、`label`） | 组件的每个属性都能被别的组件读取，界面变成一份可寻址的数据 |
| `{{ }}` 表达式 | 用 `{{ textInput1.value }}` 这种写法在任何地方引用其它组件和查询的结果 | 组件之间互相联动不用写事件回调 |
| 查询（Query） | 把「取数/写数」抽象成一个个命名的查询对象，独立于组件 | 数据来源和界面解耦，换界面不用重写取数 |
| 自定义组件库（retool-ccl） | 用 TypeScript / React 写自定义组件，通过 `npx retool-ccl dev` 在 Retool 里实时热更 | 内置组件不够用时能自己造 |
| dev / published 双版本 | 每个开发者有自己的 `dev` 修订版，正式用要走发布版本 | 改组件不影响别人正在用的应用 |
| Toolscript 序列化 | 应用被序列化成 `.rsx`（Retool Scripting XML）文件，按目录组织 | 应用能被版本管理和代码评审 |
| 导入导出 | 应用可导出为单个 JSON 文件，或 Toolscript ZIP 归档；导出含查询、组件、模块，**不含数据源（resources）** | 跨环境迁移、批量改名 |

**③ 它的「可搭建 / 可扩展」机制到底怎么运作**

- **组件绑定数据源**：不靠「配置面板里选数据源」，靠 **表达式引用**。每个组件是一个 JS 对象，属性值可以是 `{{ }}` 表达式，表达式里能访问任何其它组件和查询的公开属性。所以「绑定」本质上是在属性里写一段表达式。
- **画布序列化成什么格式**：这是 Retool 最有价值的一点。它有两套序列化：
  - 老的：单个 JSON 文件（导入导出用）；
  - 新的：**Toolscript**，`.rsx` 扩展名的 JSX 风格标记语言，官方原话是「为 Source Control 场景序列化 Retool 应用而做的 JSX 风格标记语言，区别于它的 YAML 前身，Toolscript 的设计目标是**可供人评审（human reviewable）**」。
  - Toolscript 的目录结构是这样的（官方文档原文）：
    ```
    app-name
    ├── .defaults.json            # 组件默认值
    ├── .positions                # 桌面布局位置
    ├── .global_positions.json
    ├── .pageName1.positions.json
    ├── .pageName1.mobilePositions.json
    ├── lib/
    │   ├── sqlQueryName.sql      # 查询被拆成独立文件
    │   └── jsQueryName.js
    ├── src/
    │   ├── container1.rsx        # 复杂组件被拆成独立文件
    │   └── main.rsx
    ├── functions.rsx             # 函数与查询
    └── metadata.json
    ```
  - 关键设计：**逻辑（`main.rsx` / `functions.rsx` / `lib/`）和位置（`.positions` 这类 JSON 点文件）分开存**；组件的顺序按画布上的位置排（从上到下、从左到右），移动按钮的位置，文件里的顺序也跟着变。
- **插件模型**：自定义组件是通过 `retool-ccl` CLI 发布的组件库（Component Library），应用在设置里选择用哪个版本，可以选某个 `dev` 版本或已发布版本。
- **对 AI 的用法（很值得抄）**：Retool 官方博客明确写了他们怎么让 LLM 理解应用——**直接用 Toolscript 作为给模型的输入**，理由是「LLM 懂代码，Toolscript 看起来足够像代码，模型能自然解析」，而且「与其发明一种新的表示法，不如把我们已经信任的、用于版本控制的格式给 LLM」。文件结构把逻辑和坐标分开，也让模型不用被坐标干扰。

**④ 可抽象成我们工作台的一个「模式」**

- **模式名**：`应用搭建模式`（搭建一个「页面对 + 数据源 + 交互」的小工具）
- **界面形态**：左栏组件树 / 中间画布（拖拽落位）/ 右栏属性面板；属性面板里每个字段旁边有个「绑定」入口。
- **要接的后端接口**：
  - `GET /apps/:id/definition` → 返回应用定义（组件树 + 位置 + 查询）
  - `PUT /apps/:id/definition` → 整体保存（前端只提交这一份 JSON）
  - `POST /queries/:name/run` → 跑一个命名查询，返回结果集
  - `GET /components` → 可选组件清单（含我们自己的自定义组件）
  - `GET /resources` → 数据源列表（**故意和应用定义分开**，导出时不带密钥）
- **给我们的启发**：位置数据和逻辑数据分开存；导出格式不要塞密钥。

**⑤ 来源 URL**
- 组件：https://docs.retool.com/apps/concepts/components/
- Toolscript：https://docs.retool.com/source-control/concepts/toolscript
- 导入导出：https://docs.retool.com/apps/guides/app-management/import-export
- 自定义组件库：https://docs.retool.com/apps/guides/custom/custom-component-libraries/
- retool-ccl 使用：https://docs.retool.com/apps/guides/custom/custom-component-libraries/retool-ccl
- 官方博客（AI 如何读应用）：https://onretool.com/blog/how-we-built-ai-assisted-development

### 2. Appsmith

**① 一句话定位**
开源的低代码内部工具平台，特点是把「写代码」塞进了整个界面的每一个角落（`{{ }}` 到处能用）。

**② 核心功能清单**

| 功能 | 说明 | 解决什么需求 |
|---|---|---|
| 拖拽组件面板 | 大量内置组件（表格、表单、图表等）拖到画布上 | 快速搭界面 |
| 属性面板可写代码 | 组件的属性、事件监听、查询、其它设置里都能写 JS | 复杂逻辑不用绕弯 |
| 引用外部 JS 库 | 可以导入外部库 | 扩展内置能力 |
| Custom Widget（自定义组件） | 用 HTML / CSS / JS（或 React）写自己的组件 | 内置组件不够用时自己造 |
| Custom Widget 数据通道 | 通过 `appsmith.model.{property}` 在 JS 里读外部传进来的数据，CSS 里用 `var(--appsmith-model-{property})` | 自定义组件能吃到页面数据 |
| 自定义事件 | 在属性面板配好多条事件，组件里用 `appsmith.triggerEvent("事件名")` 触发 | 自定义组件的交互能接回页面的查询/JS |
| JS Object | 把可复用的 JS 逻辑打包成对象 | 逻辑复用 |
| 实体级导入导出 | 可导出/导入**选中的实体**：组件、数据源、查询、JS Object、自定义库，导出为 JSON 文件 | 跨页面、跨应用复用某几块 |
| 一键链接分享 / fork | 应用有公开分享链接，别人可以 fork 一份 | 复用别人的应用当起点 |

**③ 它的「可搭建 / 可扩展」机制到底怎么运作**

- **组件绑定数据源**：靠 `{{ }}` 双大括号表达式，和 Retool 几乎一样。区别在于 Appsmith 的表达式渗透得更彻底——不只是属性，连事件的参数、CSS 变量都能写表达式。
- **画布序列化成什么格式**：整个应用在平台内就是一棵 **widget 树 + 查询 + JS Object**。对外暴露的有两档：
  - **实体级导出 JSON**：官方文档说得很直白——「这个 JSON 文件是你选中实体的 blueprint（蓝图），目的是在页面之间共享实体，**这个 JSON 文件不能用来创建一个新应用**」。也就是说它导出的是「零件」，不是「整机」。
  - **整应用导出**（用于备份/fork 的完整应用 JSON）在文档里另有入口，本次只查到实体级导出的一手说明。
  - 导出时有一个刻意的设计：**数据源的连接配置（含密钥）永远不导出**，导入后必须手动重配。
- **插件模型**：Appsmith 走的是「自定义组件（Custom Widget）+ 自定义 JS 库」这条路，而不是「装一个插件包」。自定义组件是在应用里的一个代码编辑器页面上直接写，不是发一个独立包。

**④ 可抽象成我们工作台的一个「模式」**

- **模式名**：`绑定表达式模式`（让任何界面上显示的字段都能指向别处的一个值）
- **界面形态**：不单独占一个模式，而是作为所有模式的「底层能力」——每个属性输入框旁边一个 `ƒ` 按钮，点开写一段表达式，可引用其它组件/步骤的输出。
- **要接的后端接口**：
  - `GET /apps/:id/tree` → 拿 widget 树（用于表达式补全）
  - `POST /expressions/eval` → 可选：服务端求值（我们更倾向前端求值）
  - `POST /entities/export` / `POST /entities/import` → 支持「只导出几块」的实体级迁移
- **给我们的启发**：导出「零件」比导出「整机」更常用。

**⑤ 来源 URL**
- 代码编写：https://docs.appsmith.com/core-concepts/writing-code
- 实体导入导出：https://docs.appsmith.com/build-apps/how-to-guides/import-export-app-entities
- 自定义组件参考：https://docs.appsmith.com/reference/widgets/custom

### 3. Budibase

**① 一句话定位**
开源的「以数据为中心」的低代码平台——先把表和数据源搭好，界面和自动化都绑在数据上。

**② 核心功能清单**

| 功能 | 说明 | 解决什么需求 |
|---|---|---|
| 数据优先 | 内置数据库 + 外部数据源（SQL 等） | 数据模型先立起来，界面后画 |
| Handlebars 绑定 | 用 `{{ }}`（Handlebars 语法）把数据绑进任何设计元素或自动化步骤；属性右边有个「闪电」图标，点亮就能插绑定 | 数据到界面/自动化的通路 |
| Handlebars 助手函数 | 数组、比较、日期、数学、数字、字符串、URL 七类助手 | 绑定里能做格式化和计算，不用写代码 |
| JS 绑定 | 除了 Handlebars，也能用 JavaScript 做绑定 | 复杂逻辑 |
| 自定义组件插件 | 用 **Svelte** 写组件，`budi plugins --init component` 生成骨架 | 内置组件不够用时自己造 |
| 组件清单文件 `schema.json` | 声明组件名字、图标、设置项、数据绑定（context）、样式、是否可作容器 | 让平台知道「这个组件该怎么被配置」 |
| 自定义数据源插件 | 用代码接一个平台没内置的数据源 | 接私有系统 |
| 插件来源多样 | 支持从 URL（tar.gz）、NPM 包、GitHub release、本地文件上传四种方式导入插件 | 插件的分发和安装 |
| 自动化（Automations） | 触发器 + 步骤，步骤之间可以引用上一步的数据 | 无代码流程编排 |
| 母版/实例 | 复用的界面片段改一处、处处改 | 界面复用 |

**③ 它的「可搭建 / 可扩展」机制到底怎么运作**

- **组件绑定数据源**：两套并存——**Handlebars 模板语法**（主打）和 **JavaScript**。绑定点用 UI 上的「闪电」图标暴露出来。要注意一个限制：Handlebars 的**助手函数**能用在自动化、设计面板和数据表公式列里，但**不能**用在数据源查询里（查询里只能用单个 `{{ value }}` 这样的简单占位）。
- **画布序列化成什么格式**：Budibase 的**组件插件**有一个明确的清单文件 `schema.json`，字段是（官方文档）：
  - `name`（唯一名）、`friendlyName`（在搭建器里显示的名字）、`icon`（组件树里的图标）
  - `settings`（数组）：里面每个设置项有 `type`（控件类型）、`key`、`label`、`dependsOn`（依赖另一个设置项才显示）、`defaultValue`、`options`（select 类型的选项）、`min` / `max`、`showInBar`（是否在浮动设置条里显示）、`placeholder`、`section`（是否是一个分组）
  - `context`（数组）：**这个组件对外提供哪些数据绑定**。文档原话说「context 键是『这个组件将要提供哪些数据绑定』的承诺。搭建器会用这些信息生成可选的绑定项，但**组件本身要负责真的提供这些数据**」
  - `styles`：`margin` / `padding` / `size` / `background` / `border` 的简写
  - `hasChildren`：能不能当别的组件的容器
  - `showSettingsBar`：选中时是否浮出设置条
  - `info`：在设置面板底部显示的一段说明
  - 事件型设置项还可以带自己的 `context`，例如一个 `onChange` 事件可以对外暴露 `{{ Field Value }}`。
  - 官方还给了内置组件的清单文件作参考：`packages/client/manifest.json`。
- **插件模型**：插件是一个可以被导入的包（tar.gz）。导入后：
  - 自定义**组件** → 出现在搭建器的组件列表里，归在一个「Plugins」分组下；
  - 自定义**数据源** → 出现在「添加数据源」对话框底部，和内置数据源一样用。
  - 有一个明确的环境限制：**自定义组件在云端也能导入，但自定义数据源出于安全原因只能在自建（self-hosted）环境里用**。
  - 开发体验：组件里通过 `getContext("sdk")` 拿到平台内部的 SDK（`styleable`、`API`），配合 `budi hosting --watch-plugin-dir` 做热更新；`schema.json` 的改动**不热更新**，必须刷新搭建器。
  - 组件必须在自己最外层的 div 上带上 `use:styleable={$component.styles}`，否则样式会出问题。

**④ 可抽象成我们工作台的一个「模式」**

- **模式名**：`插件注册模式`（把自己的组件/数据源装进工作台，装完就在面板里出现）
- **界面形态**：设置里一个「插件」页——列出已装插件，一个「添加插件」按钮（支持 URL / NPM / GitHub / 本地文件四种来源）。
- **要接的后端接口**：
  - `GET /plugins` / `POST /plugins`（上传 tar.gz 或给 URL）/ `DELETE /plugins/:id`
  - `POST /plugins/:id/enable`、`POST /plugins/:id/disable`
  - `GET /registry/components` → 合并内置 + 插件组件，供画布左栏渲染（**这就是 `schema.json` 的消费端**）
- **给我们的启发**：插件清单文件是整个机制的关键——**只要清单格式定死，平台就能自动为任意第三方组件生成配置面板、组件树图标、可绑定的数据源列表**。这一步我们完全可以照抄。

**⑤ 来源 URL**
- 自定义组件：https://docs.budibase.com/docs/custom-component
- 组件 schema：https://docs.budibase.com/docs/component-schema
- 自定义插件（导入/热更）：https://docs.budibase.com/docs/custom-plugin
- 绑定（Handlebars）：https://docs.budibase.com/docs/bindings

### 4. ToolJet

**① 一句话定位**
开源的低代码平台，特点是「插件市场」式的扩展——AI、数据库、云服务、SaaS 都做成可安装的插件。

**② 核心功能清单**

| 功能 | 说明 | 解决什么需求 |
|---|---|---|
| 拖拽搭建器 | 组件拖到画布、右侧属性面板配置 | 快速出内部工具 |
| 插件市场（Marketplace） | 一批把 ToolJet 接到外部服务的插件：AI 提供商（OpenAI、Anthropic、Gemini、Bedrock、Cohere、Mistral、Hugging Face、Portkey）、数据库、向量库、物流、支付等 | 「接一个新的外部服务」不用等平台更新 |
| 插件安装与凭据 | 云端预装全部插件；自建环境要手动安装，再去「数据源」页配凭据，配好后插件出现在查询面板里 | 插件 = 连接器 |
| 卸载有连带影响 | 官方警告：移除一个插件会**删掉所有应用里跟它关联的查询**，必须先把那些查询删掉才能卸载 | 依赖关系的显式约束 |
| Custom Component | 内置组件不够用时，在组件里直接写 **React 代码** | 一次性的界面定制 |
| 自定义组件的三个通道 | 平台给自定义组件三个 props：`data`（和宿主应用共享的对象）、`updateData`（更新传进去的数据）、`runQuery`（按名字跑一个查询） | 自定义组件能双向和页面通信 |
| `Tooljet.connectComponent` | 文档写「它扮演 HOC 的角色，是拿到传进自定义组件的数据、以及跑查询所必需的」 | 把裸 React 组件接入平台上下文 |
| 依赖从 CDN 拉 | 自定义组件里的包从 Skypack 或 esm.sh 导入（如 `import React from 'https://cdn.skypack.dev/react'`） | 不用打包工具也能写组件 |
| 应用导出 | 可导出**全部版本**或**选中的单个版本**为 JSON；可勾选是否连带导出 ToolJet 自带数据库的表结构 | 迁移、备份、版本对比 |
| 组件特定动作 / 暴露变量 | 组件有 CSA 和 exposed variables 的概念，可在面板里被引用 | 跨组件驱动 |

**③ 它的「可搭建 / 可扩展」机制到底怎么运作**

- **组件绑定数据源**：三个层面——应用级的「数据源/插件」、查询面板里的查询、组件属性上的 `{{ }}` 绑定。自定义组件则通过 `data` / `updateData` / `runQuery` 三个 props 拿到数据、改数据、跑查询。
- **画布序列化成什么格式**：整个应用可导出为 **JSON**。导出粒度是「应用级」（全部版本或单版本），不像 Appsmith 那样只导「零件」。导出选项里还带一个「ToolJet 数据库表结构」的开关——勾上之后导入时会顺带把表建出来，这是很实用的一手：**应用定义和数据表结构可以打包在一起迁移**（但也因此埋了个隐患：表数据不在里面）。
- **插件模型**：**插件 = 数据源连接器**，不是 UI 组件。插件有「安装 / 已安装 / 移除」三个状态，装完之后要配凭据，配完出现在查询面板。开发插件有单独的《Plugin Development guide》（本次未深入，标**未核实**）。
- 与 Budibase 的对比很清楚：**Budibase 的插件主要是「加组件」，ToolJet 的插件主要是「加数据源」**。

**④ 可抽象成我们工作台的一个「模式」**

- **模式名**：`插件市场模式`（装一个插件 = 接一个外部服务）
- **界面形态**：设置 → 插件市场列表（卡片 + 安装按钮），装完引导到「数据源」配凭据；已装插件分组展示。
- **要接的后端接口**：
  - `GET /marketplace/plugins`、`POST /marketplace/plugins/:id/install`、`DELETE /marketplace/plugins/:id`
  - `GET /plugins/:id/dependents` → **卸载前先查出哪些东西依赖它**（ToolJet 的警告值得抄成一个强约束）
  - `POST /datasources` → 存凭据（和插件分开存）
  - `POST /queries/run`（带 datasource 类型）
- **给我们的启发**：卸载插件必须有「影响面预览」，否则用户的页面会静默烂掉。

### 5. n8n

**① 一句话定位**
开源的工作流自动化平台——画布上连节点，每个节点是一个 API 调用或一步处理，数据在节点之间以「条目（item）列表」的形式流动。

**② 核心功能清单**

| 功能 | 说明 | 解决什么需求 |
|---|---|---|
| 节点画布 | 拖节点、连线条，一次触发跑一条链 | 把「一串步骤」变成能看的东西 |
| 工作流 = 一份 JSON | 一个工作流被完整描述成 `{ name, nodes, connections, settings }` | 工作流能被程序读写，能被 API 管理 |
| 节点结构明确 | 每个节点有 `id`、`name`、`type`（如 `n8n-nodes-base.jira`）、`typeVersion`、`position`（`[x, y]`）、`parameters`（该节点的配置）、`credentials`、`disabled` 等 | 节点配置就是一份可校验的 JSON |
| 节点分组 | 画布上的「框」（frame）被存成 `nodeGroups` | 大画布的组织 |
| 自定义节点 | 用 `n8n-workflow` 写自己的节点类型：一个类 + 一个 `description` 对象（`INodeTypeDescription`） | 平台没内置的服务自己接 |
| 两种节点风格 | **声明式**（只写描述，用 `properties` 里的 `routing` 描述请求怎么发）和**编程式**（自己写 `execute()`，读入数据、拼请求、返回） | 简单接口用声明式，复杂逻辑用编程式 |
| 社区节点包 | API 里有独立的 CommunityPackage 资源，节点可以按包安装 | 第三方节点分发 |
| Public API | 一整套 REST API：工作流、执行、凭据、数据表、项目、文件夹、Git 连接等 | 工作流能被外部程序管起来 |
| 版本化执行记录 | 执行（Execution）作为独立资源可查 | 调试和追溯 |
| 数据表 | 内置 DataTable 资源 | 存一点中间数据 |

**③ 它的「可搭建 / 可扩展」机制到底怎么运作**

- **节点绑定数据源**：节点有两种「连」的方式：
  - `credentials`（对象，如 `{ jiraSoftwareCloudApi: { id: '35', name: 'jiraApi' } }`）——凭据是**引用**，不是明文，凭据本体在 Credential 资源里单独管；
  - `parameters`（自由对象）——节点自己的配置。节点的输入通常靠表达式引用上游节点的输出。
- **画布序列化成什么格式**：这是最干净的一份「画布 JSON」样本。官方 OpenAPI 里工作流对象的必填字段就是 `name`、`nodes`、`connections`、`settings`；节点对象的字段见上表。**位置 `position: [x, y]` 和逻辑 `parameters` 放在同一个节点对象里**（这点跟 Retool 把位置拆出去相反）——好处是单文件可迁移，坏处是 diff 容易被坐标噪声污染。
- **插件模型**：节点类型 = 一个实现了 `INodeType` 的类，类的 `description: INodeTypeDescription` 里写 `properties`（Resources & Operations）。声明式节点靠 `routing` 描述 HTTP 请求，编程式节点靠 `execute()` 方法。这是一个非常明确、非常薄的扩展点：**扩展 = 加一个类，平台的画布/连接/参数表单都从 description 里生成**。
- 和 Budibase 的 `schema.json` 是同一个思路，只是 n8n 直接用了 TypeScript 的类型定义代替单独的 JSON 清单。

**④ 可抽象成我们工作台的一个「模式」**

- **模式名**：`流水线画布模式`（就是我们计划里那个 20 步流程的可视化）
- **界面形态**：中间无限画布，节点可拖拽/连线/框选分组；右栏是选中节点的参数表单（**表单由节点的 description 自动生成**，不是手写的）。
- **要接的后端接口**：
  - `GET /workflows/:id` → 返回 `{ name, nodes, connections, settings, nodeGroups }`
  - `PUT /workflows/:id` → 整体保存（画布编辑完一次性提交）
  - `POST /workflows/:id/run` / `GET /executions/:id` → 跑和查执行
  - `GET /node-types` → 节点类型清单 + 每个类型的参数定义（**这份定义决定右栏表单长什么样**）
  - `GET /credentials`、`POST /credentials` → 凭据单独管理，节点里只存引用 ID
- **给我们的启发**：**「节点类型定义」是整套东西的地基**。只要每个节点类型能吐出「我有哪些参数、每个参数是什么控件」，画布、表单、连线校验、甚至文档都能自动生成——我们不用为 20 个步骤手写 20 个配置面板。

**⑤ 来源 URL**
- 工作流 API/字段：https://docs.n8n.io/connect/n8n-api/workflow
- 节点结构（官方 OpenAPI 源文件）：https://github.com/n8n-io/n8n/blob/master/packages/cli/src/public-api/v1/handlers/workflows/spec/schemas/node.yml
- 自定义节点结构：https://docs.n8n.io/connect/create-nodes/build-your-node/reference/base-files/structure.md
- 数据结构：https://docs.n8n.io/build/work-with-data/understand-n8ns-data-structure

### 6. Dify

**① 一句话定位**
开源的 AI 应用开发平台——把「对话型应用」和「工作流型应用」都建在同一个工作流引擎上，拖拽连线搭好再发布成应用/API/MCP 服务。

**② 核心功能清单**

| 功能 | 说明 | 解决什么需求 |
|---|---|---|
| 两种主应用类型 | **Workflow**（单轮任务，适合批处理）和 **Chatflow**（每一轮对话都触发一次流程，能存对话变量、有记忆、能流式输出） | 一次任务 vs 多轮对话，分开建模 |
| 同一套引擎 | 官方说 Chatbot / Agent / Text Generator 这三种「基础类型」**跑在同一个工作流引擎上**，只是配了更简单的旧界面 | 不用维护两套运行时 |
| 拖拽式工作流编辑器 | Studio 里拖拽搭流程 | 编排 AI 步骤 |
| 统一入口节点 | 每个工作流都以一个 start 节点开始：**User Input**（用户/API 触发）或 **Trigger**（定时或外部事件） | 触发方式显式建模 |
| Dify DSL | **所有 Dify 应用都能导出成 YAML 文件**（Dify 自己的领域特定语言），也能直接从 DSL 文件创建应用 | 跨实例迁移、分享给别人 |
| 变量系统 | 变量是有名字的容器；输入节点可以定义任意多个输入变量；还有系统变量（`sys.user_id`、`sys.app_id`、`sys.query`、`sys.files`、`sys.conversation_id`、`sys.timestamp`） | 流程里到处引用数据 |
| 变量命名空间前缀 | 变量节点 ID 有前缀区分来源：`sys`（系统）、`env`（环境变量）、`conversation`（对话变量）、`rag`（RAG 管道变量） | 一眼看出这个变量从哪来 |
| 发布形态多 | 发布后可以通过 API、网页、或作为 **MCP server** 访问 | 建好的东西能被别的系统当工具用 |
| 插件 | 通过插件连接外部 API、处理不同数据类型、做专门的计算、执行真实世界的动作 | 扩展能力边界 |

**③ 它的「可搭建 / 可扩展」机制到底怎么运作**

- **节点/画布序列化成什么格式**：**YAML DSL**，结构（据社区对 Dify 源码整理的格式说明，当前 DSL 版本 `0.6.0`）：
  ```yaml
  version: "0.6.0"   # 必填，DSL 版本
  kind: "app"        # 必填
  app: { ... }       # 应用元数据
  workflow:
    graph:
      nodes: []      # 节点列表
      edges: []      # 连线列表
      viewport:      # 画布视角状态
        x: 0
        y: 0
        zoom: 0.7
    features: {}                 # 应用功能开关
    environment_variables: []    # 环境变量
    conversation_variables: []   # 对话变量
  ```
  - 节点类型（BlockEnum）包括：`start`（入口，定义输入变量）、`end`（workflow 模式的出口，定义输出变量）、`answer`（advanced-chat 模式的出口，流式输出文本）、`llm`（大模型调用）、`code`（执行 Python/JavaScript）等。
  - 值得注意：**连线和节点是分开的两个数组（`nodes` / `edges`），视角（`viewport`）单独一个对象**。这跟 n8n 把位置塞进节点里不一样，比 n8n 更干净。
- **可移植性设计**：DSL 的首要目的是「把应用移植到别的 Dify 实例、分享给别人」，所以它天然是**一份可直接读写的单文件**。
- **插件模型**：插件是独立的能力包（连外部 API / 做动作）。本次只查到插件的介绍页，插件包的内部清单格式**未找到一手来源**，标**未核实**。
- **来源可靠性说明**：Dify DSL 的顶层结构与字段，官方 Key Concepts 页只说了「所有应用可导出为 YAML 格式的 Dify DSL，也能从这些 DSL 文件直接创建应用」；上面那份详细字段表来自社区整理的《Dify Workflow DSL Format Reference》，该文件自称「从 Dify 源码提取」。**字段细节属于二手整理，实施前需以实际导出的 DSL 文件为准。**

**④ 可抽象成我们工作台的一个「模式」**

- **模式名**：`AI 编排模式`（对话型 Agent 与流水线型 Agent 共用同一个画布）
- **界面形态**：与 n8n 模式共用一个画布内核，但节点类型换成 AI 语义（输入、大模型、代码、判断、知识库检索、输出）；对话型 Agent 额外在画布右侧挂一个对话预览窗。
- **要接的后端接口**：
  - `POST /workflows/:id/export` → 吐一份 YAML（顶层 `version` / `kind` / `graph`）
  - `POST /workflows/import` → 吃一份 YAML 建应用
  - `POST /apps/:id/run`（流式）→ Chatflow 用
  - `GET /variables?scope=sys|env|conversation|rag` → 变量命名空间
- **给我们的启发**：**`nodes` 和 `edges` 分成两个数组、`viewport` 单独放**，是我们应该采用的画布 JSON 形状——比 n8n 那种「位置混在节点里」更容易做 diff 和自动生成。

**⑤ 来源 URL**
- Key Concepts（含 Dify DSL 与变量）：https://docs.dify.ai/en/learn/key-concepts
- 插件介绍：https://docs.dify.ai/en/plugins/introduction
- DSL 详细字段（社区整理，二手）：https://github.com/lingyichen-ai/workflow-skill/blob/main/skills/dify-workflow/references/dsl-format.md

### 7. Coze（Coze Studio 开源版）

**① 一句话定位**
字节的 AI Agent 开发平台——模型、提示词、插件、知识库、数据库、工作流、应用，全都在一个界面里配置；开源版是完整的"一体机"框架。

**② 核心功能清单**

| 功能 | 说明 | 解决什么需求 |
|---|---|---|
| 模型服务 | 管理模型列表，接入 OpenAI、火山引擎等服务 | 统一管理模型 |

| 资源体系 | 官方 README 列的四类资源：**插件（Plugins）、知识库（Knowledge bases）、数据库（Databases）、提示词（Prompts）** | Agent 的能力来自这四样 |
| 画布定义（Canvas） | 源码里 `Canvas` 结构体的注释原话是：**「Canvas is the definition of FRONTEND schema for a workflow.」**（画布是工作流的**前端 schema** 定义） | 前端和引擎共用一份定义 |
| 节点输入引用 | 节点输入可以是字面值，也可以是对别的节点输出的引用：`{"type":"ref","content":{"source":"block-output","blockID":"...","name":"..."}}` | 节点之间传递数据靠引用而不是复制 |
| 插件多样式创建 | 可以直接导入一个已有的 API 服务、可以用 Coze IDE 写、可以**导入 JSON 或 YAML 文件**创建插件、可以用代码解析器 | 接外部能力的门槛低 |
| 插件直接用 | 插件可以直接在 Agent 里用，扩展 Agent 能力 | 插件 = Agent 的手脚 |
| 前后端分离的节点包 | 前端有独立的 `frontend/packages/workflow/nodes` 目录，节点类型可按文档扩展（wiki 里有《Add new workflow node types》两篇：前端篇和后端篇） | 加节点类型有明确流程 |
| API 与 Chat SDK | 社区版用 Personal Access Token 认证，提供对话和工作流 API；还有 Chat SDK 可以嵌进业务系统 | 建好的 Agent 能被集成 |
| 可配置的基础组件 | 图片上传器等基础组件可配置（wiki 有《Basic Component Configuration》） | 开源版可裁剪 |

**③ 它的「可搭建 / 可扩展」机制到底怎么运作**

- **画布序列化成什么格式**：Coze 开源版的源码里有一份非常直白的答案——`backend/domain/workflow/entity/vo/canvas.go`，`Canvas` 被注释为「工作流的**前端 schema**」。也就是说：**画布不是前端自己的一套私有状态，而是由后端定义并返回给前端的 schema**。前端负责画，后端负责定义"能画什么"。这个分工比"前端自己存一份画布 JSON、提交给后端"要清楚。
- **节点之间怎么传递数据**：靠**引用对象**，形状是
  ```json
  { "type": "ref", "content": { "source": "block-output", "blockID": "<上游节点 ID>", "name": "<上游输出名>" } }
  ```
  输入值统一是 `BlockInput`：有 `type`（值类型），`content`（要么是文本等字面量，要么是一个 `BlockInputReference`）。同一种"输入"结构同时用于配置和运行，**没有第二套格式**。
- **插件模型**：插件最特别的地方是**创建方式**——导入已有 API 服务、Coze IDE 手写、**导入 JSON/YAML 文件**。最后一种意味着插件定义本身是一份结构化文档，不是只能手点出来的东西。
- **扩展点**：官方 wiki 有《Add new workflow node types (frontend)》和对应的后端篇，说明"加一个节点类型"是一个被认可、被文档化的扩展动作（要前后端各加一处）。

**④ 可抽象成我们工作台的一个「模式」**

- **模式名**：`Agent 工作台模式`（对话型 Agent 的完整配置面）
- **界面形态**：左侧资源栏（插件 / 知识库 / 数据库 / 提示词），中间画布或配置区，右侧实时预览（对话、调试、发布）。
- **要接的后端接口**：
  - `GET /workflows/:id/canvas` → **返回画布 schema（前端渲染的唯一依据）**
  - `GET /canvas/schema` → 画布结构定义本身（版本化）
  - `GET /resources?type=plugin|knowledge|database|prompt`
  - `POST /plugins/import` → 吃 JSON / YAML 建插件
  - `POST /apps/:id/publish`（Coze 有显式的"发布"动作）
- **给我们的启发**：**把"画布长什么样"的定义放在后端**，前端只做一个渲染器。这样以后要加节点类型，改的是定义，不是前端代码。另外，"导入 JSON/YAML 建插件"这个入口，让 Agent 也能帮人写插件。

**⑤ 来源 URL**
- 官方仓库 README（模块与资源清单）：https://github.com/coze-dev/coze-studio
- 画布定义源码（含注释与引用结构）：https://github.com/coze-dev/coze-studio/blob/e18f830111dfb40de1fd5e5855557da73bf44cd2/backend/domain/workflow/entity/vo/canvas.go

### 8. ComfyUI

**① 一句话定位**
节点式 AI 生成工作台（最初是 Stable Diffusion 前端）——把推理过程拆成一个个节点，用连线决定数据往哪流。

**② 核心功能清单**

| 功能 | 说明 | 解决什么需求 |
|---|---|---|
| 节点画布 | 每个节点是一步计算（加载模型、编码文本、采样、解码、保存图片） | 把黑箱推理过程摊开 |
| 节点有输入输出槽 | 节点定义里带 `inputs` / `outputs`，每项有 `name` / `type` / `slot_index` | 类型化连线 |
| 连线是独立对象 | `links` 数组，每条线有 `id`、`origin_id`、`origin_slot`、`target_id`、`target_slot`、`type`、`parentId` | 图结构可被程序遍历 |
| 分组（groups） | 画布上的框：`title`、`bounding`（4 个数）、`color`、`font_size`、`locked` | 大图组织 |

| 画布配置 | `config`：`links_ontop`、`align_to_grid` | 画布行为可配 |
| **两种保存格式** | **Save Format**（File → Save，给前端重新打开用）和 **API Format**（File → Export Workflow (API)，给程序调用用） | **编辑用的和人跑的，故意分成两份** |
| 公开的 JSON Schema | 工作流 JSON 用 JSON Schema 定义，有版本号（当前 Version 1.0），改动走 RFC 仓库 | 格式是合约，不是内部实现 |
| 重路由点（reroutes） | 连线的中转点也是数据 | 复杂连线可读 |
| 节点可折叠/钉住 | `flags`：`collapsed`、`pinned`、`allow_interaction`、`horizontal`、`skip_repeated_outputs` | 画布可读性 |

**③ 它的「可搭建 / 可扩展」机制到底怎么运作**

这是本组里**机制最干净、最值得直接参考**的一份。

- **两种格式的差别（官方原文对照表）**：

  | | Save Format | API Format |
  |---|---|---|
  | 入口 | File → Save / Ctrl+S | File → Export Workflow (API) |
  | 节点键 | 节点标题或标签 | **数字节点 ID** |
  | 控件值 | 有 | 有 |
  | 位置/布局数据（x, y, width） | 有 | **没有** |
  | 颜色/分组 | 有 | **没有** |
  | 用途 | 在前端里重新打开 | 提交给 API |
  | 能在界面里加载 | 能 | 能，但**没有布局** |

- **Save Format 的形状**（由公开 JSON Schema 定义）：
  ```
  {
    version: 1,
    config: { links_ontop, align_to_grid },
    state:  { lastGroupid, lastNodeId, lastLinkId, lastRerouteId },
    groups: [ { title, bounding: [x,y,w,h], color, font_size, locked } ],
    nodes:  [ { id, type, pos:[x,y], size:[w,h], flags:{...}, order, mode,
                inputs:[{name,type,link,slot_index}],
                outputs:[{name,type,links,slot_index}],
                properties:{ "Node name for S&R": ... },
                widgets_values, color, bgcolor } ],
    links:  [ { id, origin_id, origin_slot, target_id, target_slot, type, parentId } ],
    reroutes: [ { id, parentId, pos, linkIds } ]
  }
  ```
- **API Format 的形状**（无布局，按节点 ID 为键）：
  ```json
  {
    "3": {
      "inputs": { "seed": 156680208700286, "steps": 20,
                  "model": ["4", 0], "positive": ["6", 0], "negative": ["7", 0] },
      "class_type": "KSampler",
      "_meta": { "title": "KSampler" }
    },
    "4": { "inputs": { "ckpt_name": "v1-5-pruned-emaonly-fp16.safetensors" },
           "class_type": "CheckpointLoaderSimple",
           "_meta": { "title": "Load Checkpoint" } }
  }
  ```
  - 注意这里的连线表示法：**`inputs` 里直接写 `[上游节点ID, 输出槽序号]`**，没有单独的连线数组——连线被"内联"到输入值里了。
- **把「编辑态」和「执行态」分成两份产物**，这是 ComfyUI 最重要的一招：
  - 编辑态要"重"，因为它承载人的操作（位置、颜色、分组、折叠状态）；
  - 执行态要"轻"，因为它只承载机器要的东西。
  - 官方也说 API 格式「能在界面里加载，但没有布局」——也就是**执行态是编辑态的子集，两者可以互相转换**（转换方法官方给的是：在界面里 File → Load 打开，再 File → Export Workflow (API)）。

**④ 可抽象成我们工作台的一个「模式」**

- **模式名**：`执行图模式`（把我们的流水线从"给人看的图"变成"给引擎跑的图"）
- **界面形态**：和"流水线画布模式"共用同一张画布，但多一个「导出为执行格式」和「导入执行格式」的入口。
- **要接的后端接口**：
  - `GET /workflows/:id` → 编辑态（带 `pos` / `size` / `flags` / `groups` / `links`）
  - `POST /workflows/:id/compile` → **服务端把编辑态编译成执行态**（去掉布局、把连线内联成 `[上游ID, 槽位]`）
  - `POST /run` → 接收执行态 JSON 直接跑
  - `GET /node-classes` → 节点类型清单（对应 `class_type`）
- **给我们的启发**：**不要用一份 JSON 既存画布又喂引擎。** 编辑态和执行态分开，执行态可以小到只有"节点 ID → { 类型, 输入 }"。这样 Agent 读执行态时不用被坐标干扰，人读编辑态时又能看到布局。

**⑤ 来源 URL**
- 工作流 JSON Schema（公开标准）：https://docs.comfy.org/specs/workflow_json
- Save Format vs API Format：https://docs.comfy.org/development/api-development/workflow-api-format

### 9. Figma（只取「界面可定制」的机制）

**① 一句话定位**
浏览器里的界面设计工具——它对本调研的价值不在"画界面"，而在于它**把界面本身变成了一棵可被程序读写的树**。

**② 核心功能清单（只列与"界面可定制"相关的）**

| 功能 | 说明 | 解决什么需求 |
|---|---|---|
| 文件即一棵节点树 | 官方原话：「每个 Figma 文件都由一棵节点树组成，树的根是 `DocumentNode`，`DocumentNode` 是你访问和探索文件内容的入口」 | 界面变成可遍历的数据结构 |
| Plugin API 可读可写 | 「Plugin API 同时支持对 Figma 编辑器的**读**和**写**访问，可以查看、创建、修改文件内容」，通过全局对象 `figma` 访问 | 程序能改界面 |
| 插件操作的是节点属性 | 「插件首先与文件内容交互……插件可以查看和修改这些图层（或节点）的方面，例如颜色、位置、层级、文字等」 | 改界面 = 改节点属性 |
| 按需加载 | 「Figma 文件是**动态加载**的，页面只在编辑器需要时（例如用户导航到某个页面）才加载」 | 大文件不卡 |
| 插件清单 | 插件有自己的清单，并有 `documentAccess: "dynamic-page"` 这类开关（影响用同步还是异步 API） | 插件的权限/访问模式显式声明 |
| Variables（变量） | 有整套 `figma.variables` API：按 ID 找变量、找变量集合、取本文件的全部变量、`createVariable`、`createVariableCollection`，以及 `createVariableAlias`「用于把组件属性分配给变量」 | **设计令牌变成一份可编程的数据** |
| 跨库继承 | `extendLibraryCollectionByKeyAsync` 能从库或本地变量集合扩展出一个新的变量集合 | 设计系统跨文件复用 |
| Widgets | 交互式对象，和插件不同——「插件是为某个人运行的，而每个人都能看到并与同一个 widget 交互」，用 TypeScript + JSX 渲染，widget 组件「类似 React 组件」 | 界面里能塞进可交互的小程序 |
| Widget 可用 Plugin API | 「Widgets 也能访问 Plugin API 的功能」，包括拉外部数据、开 iframe 显示更多 UI、编辑文件里的其它对象 | 从只读展示到真正改文件 |
| REST API（服务端读） | `GET /v1/files/:key` 返回文件 JSON：`document` 是一个 `DOCUMENT` 类型的 Node；`components` 是「节点 ID → 组件元数据」的映射；还有 `componentSets`、`styles`、`schemaVersion` | 服务端也能拿到整棵界面树 |
| 按需取子树 | REST 支持 `ids`（只取关心的节点，连同它们的祖先链）、`depth`（只取到第几层）、`geometry=paths`、`plugin_data`（把插件写进文档的数据也带出来） | 不用拉整个文件 |

**③ 它的「可搭建 / 可扩展」机制到底怎么运作**

- **界面 = 一棵节点树**。这是 Figma 一切扩展机制的前提。节点有类型、有层级（父子），属性就是"面板上那堆东西"（颜色、位置、文字……）。
- **扩展模型有两条路，而且方向相反**：
  - **Plugin**：为**某个人**运行——他点了插件，插件替他改文件。适合"批处理一把"。
  - **Widget**：为**所有人**存在——它是一个躺在文件里的对象，谁都能看见、都能点。适合"界面上放一块活的区域"。
  - 官方对这条区别的原话是：「不像插件是为某个特定的人运行的，每个人都能看到并与同一个 widget 交互」。
  - **对我们的直接映射**：我们的工作台里，"按钮入口"更像 Widget（常驻、所有人可见），"点一下批量处理"更像 Plugin（一次性）。这两种东西的生命周期完全不同，界面上应该分开处理。
- **设计令牌是一等公民**：`figma.variables` 把颜色/尺寸这类东西做成了有 ID、能跨文件继承、能被组件属性引用的对象。这跟"在样式面板里手填一个色值"是两回事——前者可以被程序改名、替换、批量迁移。
- **服务端可读**：REST API 的 `GET /v1/files/:key` 让"读一个界面长什么样"变成一个普通的 HTTP 请求，而且支持只取子树（`ids` / `depth`），不用把整个文件搬过来。

**④ 可抽象成我们工作台的一个「模式」**

- **模式名**：`界面即数据模式`（Puck / MUI Toolpad / OpenPage 那层要用的东西）
- **界面形态**：不是一个新的界面模式，而是"自定义界面"功能的**数据层约定**——拖出来的每个组件是一棵节点树里的一个节点，节点有稳定的 ID 和一组属性。
- **要接的后端接口**：
  - `GET /ui/:id/tree?depth=2` → 只取前两层（借鉴 Figma 的 `depth`）
  - `GET /ui/:id/tree?ids=a,b` → 只取指定子树的祖先链（借鉴 Figma 的 `ids`）
  - `GET /ui/:id/tokens`、`PUT /ui/:id/tokens` → 设计令牌（颜色/间距/圆角）单独一份数据
  - `PUT /ui/:id/tree` → 整棵树的保存
  - `GET /ui/:id/tree?include_plugin_data=1` → 第三方组件塞进树里的私有数据也能带出来
- **给我们的启发**：**"按需取子树"和"设计令牌独立成一份数据"**这两点直接决定我们能不能撑住一个大界面；以及把"常驻入口（Widget 型）"和"一次性动作（Plugin 型）"在模型层就分开。

**⑤ 来源 URL**
- 插件总览（节点树 / DocumentNode / 动态加载）：https://developers.figma.com/docs/plugins/
- Plugin API – figma 全局对象：https://developers.figma.com/docs/plugins/api/figma
- Variables API：https://developers.figma.com/docs/plugins/api/figma-variables/
- Widgets（与插件的区别）：https://developers.figma.com/docs/widgets/
- REST 文件接口（document / components / ids / depth）：https://developers.figma.com/docs/rest-api/file-endpoints/

**① 一句话定位**
中文在线原型与协作工具——拖组件画界面、拉连线做交互、团队实时协同评审。

**② 核心功能清单**

| 批量操作 | 「支持组件属性复制，批量操作，智能调整」 | 改一堆同类组件不用逐个点 |

| 自动化出口 | 官方页面写「提供 REST API 和 CLI」 | 能被程序调用 |

**③ 它的「可搭建 / 可扩展」机制到底怎么运作**

- **组件面板 → 画布 → 属性面板**：这是墨刀最基本的机制，也是所有拖拽式搭建产品的通用三件套。墨刀的特殊点在于「高级组件」这一档——**高级组件不是"一个画好的静态组件"，而是"一个带属性面板和事件的半成品控件"**（下拉菜单能配下拉项的点击跳转、导航菜单能配多级结构）。用户双击它，改的是属性，不是拆开重画。
- **复用的机制名是「母版 / 实例」**：和 Figma 的 component / instance 是同一个东西——母版改一次，用它的地方全改。
- **交互靠连线**：墨刀的交互是在两个界面元素/页面之间**拉一条线**。这跟我们打算做的"流水线节点连线"在交互形式上是同一类操作，值得注意：**用户对"连线=建立关系"这件事是熟悉的**。
- **和代码的连接**：墨刀提供了两个方向的口子——**导入**（Sketch / Figma / Axure 文件）和**导出**（CSS / React / Vue / Tailwind 代码、REST API、CLI）。特别是「设计-代码组件映射」，它把"设计里的组件"和"代码库里的组件"建立对应关系，设计改动会提示哪些代码组件要同步——这是一个**双向对应表**，不是单向导出。
- **扩展模型的边界**：墨刀不像 Retool / Budibase / Figma 那样提供"写代码自定义组件"的公开机制。官方产品页列出的扩展口子是「插件（对接 Sketch / XD / PS / Axure）」「素材广场（组件包 / 图标 / 模板）」「REST API 和 CLI」。**"用代码写一个自定义组件并装进墨刀"这条路，未找到一手来源说明其存在。**
- **来源说明**：上面引用的原话分别来自墨刀官方的产品功能页、开发者页、以及功能更新页。**其中「高级组件」那一页是功能更新记录，页面自身注明"本文记录的墨刀新功能属于特定版本或历史场景……涉及现行功能、套餐或兼容性时，以墨刀当前官方页面和实际账号界面为准"**——所以"高级组件"的细节标注为**可能已随版本变化**。
- 墨刀导航里出现过「MCP 服务」，但本次**未找到其说明页的一手资料**，标**未核实**。

**④ 可抽象成我们工作台的一个「模式」**

- **模式名**：`组件复用模式`（界面定制的"可复用"那一层）
- **界面形态**：设计器里区分两类对象——**母版**（定义）和**实例**（引用）；实例的属性面板里能"脱离母版单独改"。组件来源分三档：内置组件、组件包里装的组件、母版。
- **要接的后端接口**：
  - `GET /components`（内置 + 已装组件包）
  - `GET /masters` / `POST /masters` / `PUT /masters/:id` → 母版增删改
  - `GET /masters/:id/usages` → "改这个母版会影响哪些页面"（"一处改处处改"的**前提是能算出影响面**）
  - `GET /design-tokens` / `PUT /design-tokens` → 对应墨刀的"设计-代码组件映射"里的那层对应关系
  - `POST /export/code`（→ CSS / React / Vue / Tailwind）
- **给我们的启发**：① 母版机制必须有"影响面查询"，否则用户不敢改；② "设计里的组件 ↔ 代码里的组件"这张映射表，对我们这些**既要做界面、又要生成产物**的产品来说，是一个很值得抄的中间层。

**⑤ 来源 URL**
- 产品功能页（组件/拖拽/连线/母版/预览/分享）：https://modao.cc/feature/prototype/
- 开发者页（标注、代码导出、组件映射、REST API 和 CLI）：https://modao.cc/ad/developer

| **拖拽三件套：左组件面板 / 中画布 / 右属性面板** | 6 | Retool、Appsmith、Budibase、ToolJet、墨刀、Figma | ★ 必抄 |
| **设计令牌 / 变量独立成一份数据** | 3 | Figma（Variables，有独立 ID 和库继承）、墨刀（设计-代码组件映射）、Dify（环境变量/对话变量独立成数组） | ★ 值得抄 |
| **连线即建立关系**（用户已形成的操作直觉） | 3 | n8n、ComfyUI、墨刀（连线加交互） | 参考，交互形式可复用 |
| **卸载扩展时显式给出影响面** | 2 | ToolJet（移除插件会删掉关联查询，官方警告在先）、墨刀（母版"一处改处处改"隐含影响面） | ★ 建议抄 |
| **导入 JSON / YAML 文件创建扩展**（让 Agent 能写扩展） | 2 | Coze（插件可导入 JSON/YAML）、Appsmith（实体 JSON 导入） | ★ 对"Agent 帮我们建东西"很关键 |
| **同一个引擎支撑多种前端形态** | 2 | Dify（Workflow / Chatflow / Chatbot / Agent 跑在同一个工作流引擎上）、ComfyUI（两种格式同源） | ★★ 正是我们"多模式一套引擎"的参照 |
| **服务端可只取子树**（`depth` / `ids`） | 1 | Figma（REST `ids` / `depth`） | 只有 1 款，但很实用 |

### 2.2 「产物是不是结构化 JSON」这一栏（本题重点）

这一栏直接回答：**哪些机制产出的东西人和 Agent 都能读，哪些锁死在私有格式里。**

**A. 产物是结构化 JSON / YAML，人和 Agent 都能读（可直接抄）**

| 产物 | 产品 | 格式 | 说明 |
|---|---|---|---|
| 画布/工作流定义 | **ComfyUI** | JSON，**有公开的 JSON Schema 且带版本号（Version 1.0）**，改动走 RFC | 最规范的一家。Schema 公开 = 谁都能写工具读它 |
| 执行态工作流 | **ComfyUI** | JSON（API Format） | 轻量、无布局、连线内联为 `[上游ID, 槽位]`，**天生适合给 Agent 看** |
| 工作流定义 | **n8n** | JSON | `{ name, nodes, connections, settings }`，节点字段有完整 OpenAPI 定义 |
| 工作流定义 | **Dify** | YAML（DSL，带 `version` 字段） | 设计目的就是"跨实例迁移和分享" |
| 画布定义 | **Coze** | JSON（源码里 `Canvas` 注释为"前端 schema"） | 由后端定义 schema、前端渲染 |
| 应用定义 | **Retool** | **Toolscript（`.rsx`）**，JSX 风格标记语言 | **官方明确说它是为了"可供人评审"而设计的，并且官方博客说 LLM 用的就是这个格式** |
| 应用定义 | **Appsmith / ToolJet** | JSON | 都是单文件可导出 |
| 界面树 | **Figma** | JSON（`document` 是 `DOCUMENT` 类型 Node；`components` 是 ID→元数据映射） | 有公开 REST 规范 |
| 扩展的类型定义 | **Budibase** | JSON（`schema.json`） | 组件能做哪些事**写在文件里**，人和 Agent 都读得到 |
| 扩展的类型定义 | **n8n** | TypeScript 类型（`INodeTypeDescription`） | 也是文本、也是结构化的，但需要会 TS 才能读 |

**B. 产物锁死在私有格式里（要抄机制，别抄格式）**

| 情况 | 产品 | 说明 |
|---|---|---|
| 格式没有公开规范，只能靠导出文件反推 | Appsmith、ToolJet、Budibase、Retool（JSON 版） | 都能导出 JSON，但**没找到公开的 schema 定义**；字段含义要自己试 |
| 老格式被废弃、新格式还在演进 | Retool | YAML 序列化已在 Q2 2025 稳定版中被移除，要求迁移到 Toolscript。**这说明"自定义序列化格式"是有维护成本的** |
| 官方只描述了能力，没给格式 | Coze（插件包的内部格式、工作流导出格式）、Dify（插件的包格式）、墨刀（原型文件格式） | 这几处标**未核实 / 未找到一手来源** |
| 界面/原型不带结构化出口 | 墨刀 | 有"设计-代码组件映射"和代码导出，但**原型文件本身**有没有可读的结构化格式，未找到一手来源 |
| 必须登录+私有 API 才能拿到数据 | Coze 商业版的部分能力（如语气定制限商业版） | 开源版能力是子集 |

**C. 一句话总结**

> 想让人和 Agent 都能读，关键不是"用 JSON"——上面每一家都在用 JSON。关键是三件事：
> 1. **格式有没有公开的 schema**（ComfyUI 有，别人基本没有）；
> 2. **格式是不是稳定**（Retool 从 YAML 迁到 Toolscript，说明会变）；
> 3. **有没有把"给人看的"和"给机器跑的"分开**（只有 ComfyUI 分得很彻底）。
>
> 我们如果只做对一件事，就做第三件。

## 三、本组启示

### 3.1 值得抄的（5 条）

**1. 【必抄】节点/组件的「类型定义」驱动整个界面生成机制**
Budibase 的 `schema.json`、n8n 的 `INodeTypeDescription`、Figma 的插件清单，是同一个思路的三种实现：**扩展方只提供一份声明，平台自动生成组件树图标、配置面板、可绑定的数据源列表、事件列表**。
对我们的价值最直接：我们的流水线有 20 个步骤，如果每个步骤的配置面板都手写前端，那是 20 份重复劳动，而且加第 21 个步骤还要改前端。**改成"每个步骤类型给一份定义，右栏表单自动生成"**，画布、表单、连线校验、甚至步骤文档都能一份定义全出来。
- 来源：https://docs.budibase.com/docs/component-schema 、https://docs.n8n.io/connect/create-nodes/build-your-node/reference/base-files/structure.md

**2. 【必抄】编辑态和执行态分成两份产物（ComfyUI 的做法）**
ComfyUI 的 Save Format 带位置/颜色/分组，API Format 只有 `{ 节点ID: { 类型, 输入 } }`，连线内联成 `[上游ID, 槽位]`。好处是三重的：
- 人读编辑态时信息够（能看见布局和组织）；
- 引擎读执行态时没噪声；
- **Agent 读执行态时 token 少、歧义小**——如果让 Agent 去理解一张带坐标和颜色的 JSON，它会把注意力浪费在没用的数字上。
我们的流水线正好需要这个：画布给人看，编译后的执行态喂引擎、也喂 Agent。
- 来源：https://docs.comfy.org/development/api-development/workflow-api-format

**3. 【必抄】把"给人读"当成序列化格式的第一设计目标（Retool 的 Toolscript）**
Retool 做了一件很少见的事：**先承认 YAML 不可读，于是做了一个专门为"人评审"设计的格式**（`.rsx`），并且明确把「逻辑」和「位置」拆成不同文件（`main.rsx` / `functions.rsx` / `lib/` vs `.positions` 这类 JSON 点文件）。更关键的是官方博客里那句：给 LLM 用的就是这个已经被版本控制信任的格式，**不另发明一套给 AI 的表示法**。
对我们的价值：我们同时要给"人"和"Agent"看，那就**不要造两套格式**——造一套人和模型都能读的，用它同时管版本管理和喂模型。
- 来源：https://docs.retool.com/source-control/concepts/toolscript 、https://onretool.com/blog/how-we-built-ai-assisted-development

**4. 【必抄】凭据（密钥）和定义物理分离**
三家都这么做，而且都写进了文档：Retool「导出含查询、组件、模块，**不含数据源**」；Appsmith「出于安全考虑，导出导入都不带任何数据源连接配置，导入后必须手动重配」；n8n 节点里只存 `credentials: { 某凭据类型: { id, name } }` 这样的**引用**。
对我们：我们要导出/分享工作台配置给朋友，这一步做错就是把 API key 一起送出去了。**定义里只允许出现凭据 ID。**
- 来源：https://docs.retool.com/apps/guides/app-management/import-export 、https://docs.appsmith.com/build-apps/how-to-guides/import-export-app-entities

**5. 【建议抄】"加节点类型"要是一条被文档化的路径（Coze 的做法）**
Coze 开源版的 wiki 里有《Add new workflow node types (frontend)》这样的条目，说明"加一个节点类型"是被认可的扩展动作，有标准流程（前后端各加一处）。配合它的 `Canvas` 结构体注释——**"Canvas 是工作流的前端 schema 定义"**——整个体系是这样的：**后端定义"能画什么"，前端只负责画。**
对我们的价值：我们的"把别的工作台的功能一条条变成我们工作台上的一个模式"，本质上就是**不断加节点类型/加模式**。如果加一个模式要改五处代码，这件事做几次就会停。
- 来源：https://github.com/coze-dev/coze-studio/blob/e18f830111dfb40de1fd5e5855557da73bf44cd2/backend/domain/workflow/entity/vo/canvas.go 、https://github.com/coze-dev/coze-studio/wiki/10.-Add-new-workflow-node-types-%28frontend%29

### 3.2 明确不适合我们的（5 条）

**1. 插件/组件市场（ToolJet Marketplace）——我们是自用，市场是纯负担**
ToolJet 那套「安装 → 配凭据 → 出现在查询面板」的市场机制，是为了让**成千上万个陌生用户**接**几百个外部服务**而存在的，代价是一整套版本兼容、凭据管理、卸载回滚的复杂度（官方文档专门警告"移除插件会删掉所有关联查询"）。
我们只有自己和朋友用。**应该抄的是"安装"这个动作，而不是"市场"这个基建**——本地目录里放一个 tarball 或一个 git 仓库路径就够了。
- 来源：https://docs.tooljet.com/docs/marketplace/marketplace-overview

**2. 把位置数据混在逻辑数据里（n8n 的做法）——我们不抄这个**
n8n 把 `position: [x, y]` 直接放进节点对象里。好处是单文件可迁移；但坏处是**每挪一下节点，逻辑定义的 diff 就变一行**，对版本管理不友好，对喂给 Agent 也不友好（噪声）。
**我们应该采用 Dify / ComfyUI 的形状**：`nodes` / `edges` / `viewport` 分开，位置单独一块。ComfyUI 更是直接把它拆成了两份产物。
- 来源（n8n 节点 schema）：https://github.com/n8n-io/n8n/blob/master/packages/cli/src/public-api/v1/handlers/workflows/spec/schemas/node.yml

**3. 云端插件与自建插件的安全分裂（Budibase）——我们不学这个"分裂"，只学"边界"**
Budibase 有一条规定：自定义组件在云端也能用，但**自定义数据源只能在自建环境用**。这是因为它是卖给别人的多租户 SaaS，必须防用户拿插件在别人的服务器上乱来。
我们是单机自用，**没有这个威胁模型**——所有插件都上，不用做这种区分。但"数据源和界面组件是两个不同的风险等级"这个判断是对的，值得作为我们内部设计的常识保留下来。
- 来源：https://docs.budibase.com/docs/custom-plugin

**4. 为 AI 单独造一套表示法——不抄**
Retool 明确拒绝了这条路（"与其发明一种新的表示法，不如把我们已经信任的、用于版本控制的格式给 LLM"）。我们要跟着拒绝：**不要再为 Agent 产出第二份"给模型看的摘要格式"**。一份格式，两种读者。
- 来源：https://onretool.com/blog/how-we-built-ai-assisted-development

**5. 自定义序列化格式（特别是自造标记语言）——成本高，我们不从这起步**
Retool 从 YAML 迁到 Toolscript，Q2 2025 稳定版里直接把 YAML 支持移除、要求用户迁移。这说明**一旦自造一种格式，就要长期维护它，还要承担迁移用户的成本**。
我们应该起步于**最普通的 JSON**（像 ComfyUI 那样配一份公开 JSON Schema + `version` 字段），而不是一上来就设计一门"像代码的标记语言"。等 JSON 真的不够用了，再考虑换。
- 来源：https://docs.retool.com/source-control/concepts/toolscript （其中提到 YAML 序列化已被移除、需迁移至 Toolscript）
