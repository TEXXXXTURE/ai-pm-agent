## 一、逐个产品

### 1. ClickUp

**① 一句话定位**
把所有工作类型（任务、文档、目标、聊天、白板、报表）塞进一个工作区的「全包型」工作管理平台。

**② 核心功能清单**

| 功能名 | 一句说明 | 解决用户什么需求 |
|---|---|---|
| 层级结构（Workspace → Space → Folder → List → Task） | 任务按四层装进结构里，每层可以有自己的状态、字段、权限设置，并且逐层可继承也可覆盖 | 让不同团队、不同项目共用一套工具，又各自有自己的规则 |
| 15+ 视图 | 同一批任务可以换成列表、看板、日历、甘特、时间线、表格、工作量等多种看法；接口层面官方支持 list / board / calendar / gantt 四类 view type | 同一个人干不同活时，想用的呈现方式不一样 |
| 自定义字段 Custom Fields | 给任务加自己的字段（数字、日期、下拉等），可排序、筛选、用于报表 | 把「任务清单」变成「自己业务的数据表」 |
| 公式字段 Formula Fields | 用函数、运算符和字段引用算出新值，例如「逾期天数」「完成用了几天」，且可用 AI 生成公式 | 不想手工算衍生指标 |
| 自动化 Automations | 触发器 + 条件 + 动作三件套，100+ 预置模板，可以用 AI 用自然语言生成，也支持 webhook | 让重复的流转（改状态、通知、加任务）自己跑 |
| ClickApps（功能开关） | 把某些功能（自定义字段、多负责人、优先级、时间跟踪、Sprint、工时估算等）整体开关，可在整个工作区或单个 Space 上开 | 功能太多会淹没普通成员，按团队按需开 |
| Docs 与 Whiteboards | 文档、知识页、白板跟任务直接互链，内容块可编辑 | 知识不要和工作分家 |
| Dashboards 与 Goals | 报表由任务数据实时生成，目标可挂在下层工作上 | 想知道整体进度，又不想手工统计 |
| 模板中心（Template Center） | 预置 + 社区模板，可套用到 Space / Folder / List / 任务 / 视图 / 文档 | 从零搭一套流程太慢 |
| 集成与开放接口 | 1000+ 集成、App Center、REST API（含视图、任务等端点） | 把外面的工具接进来 |

**③ 它怎么做自定义 / 扩展**

- **ClickApps（功能开关）**：只能由工作区拥有者和管理员在为整个 Workspace 或某个 Space 打开/关闭，成员只能看；官方文档列出了可开关的清单（Custom Fields、Email、Multiple Assignees、Priority、Sprints、Sprint Points、Time Tracking、Work in Progress Limits 等）。来源：`https://help.clickup.com/hc/en-us/articles/6304327753111-Intro-to-ClickApps`
- **自定义字段 + 公式字段**：Formula Fields 有自己的函数库（日期时间、字符串、逻辑、数学），字段名区分大小写，可用 Brain AI 代写公式。来源：`https://help.clickup.com/hc/en-us/articles/15807110924567-Use-advanced-Formulas`
- **自动化 Automations**：触发器/条件/动作模型，有 100+ 模板、AI Automation Builder（用自然语言生成后还能改再发布）、动态负责人、邮箱自动化、审计日志、webhook。来源：`https://clickup.com/features/automations`
- **视图本身是对象**：API 里 view 有 `type`（list / board / calendar / gantt）、`parent`（层级位置）、`grouping`、`filters`、`sorting`、`columns`，可以增删改；文档和whiteboard这类 page view 不走公开 API。来源：`https://developer.clickup.com/docs/views.md`
- **层级设置逐层覆盖**：状态、隐私、自定义字段在 Space 层设默认，Folder / List 可再覆盖。来源：`https://help.clickup.com/hc/en-us/articles/6309390855319-Create-and-edit-Spaces`

**④ 可以抽象成我们工作台的一个「模式」**

- **模式名**：多视图任务台
- **界面形态**：顶部一条视图栏（列表 / 看板 / 日历 / 甘特），下面同一份数据；点某个视图进入它自己的筛选、分组、排序、列显示。
- **要接的后端接口**：
  - 任务读写：任务增删改查、子任务、任务与任务的关联与依赖
  - 视图读写：视图对象（类型、筛选、分组、排序、显示列）、视图的保存与共享
  - 字段定义：自定义字段（类型 + 选项）、公式字段（表达式 + 求值）
  - 自动化：规则读写（触发器 / 条件 / 动作），规则执行记录
  - 模板：模板列表与「按模板创建」

- https://help.clickup.com/hc/en-us/articles/6304327753111-Intro-to-ClickApps
- https://help.clickup.com/hc/en-us/articles/6309390855319-Create-and-edit-Spaces
- https://help.clickup.com/hc/en-us/articles/15807110924567-Use-advanced-Formulas

### 2. Linear

**① 一句话定位**
给软件团队做的问题跟踪与产品规划工具，主打快、键盘优先、界面干净。

**② 核心功能清单**

| 功能名 | 一句说明 | 解决用户什么需求 |
|---|---|---|
| Issues（问题） | 一条条可以被指派、分优先级、打标签、给预估的工作项 | 把活儿拆成能追的颗粒 |
| Projects（项目） | 有明确结果和计划完成日期的一团工作，可跨多个团队共享，有自己的进度图和里程碑 | 把散落的问题聚成一个能交付的整体 |
| Cycles（周期） | 按周期规划推进工作（官方在功能导航里和 issue tracking 并列提及「cycle planning」） | 有节奏地推进，而不是攒一堆待办 |
| Initiatives（倡议） | 把项目挂到公司目标上，带状态、优先级、标签、负责人、目标日期；有「倡议图」，每条曲线代表一个项目的完成速度 | 让人看清战略目标下的项目进展 |
| Custom Views（自定义视图） | 用筛选器建视图，可保存、共享、收藏，还能挂在团队或项目下当 tab | 每个人关心的那一小片工作，一眼可见 |
| 视图形态 | 项目和问题的视图可切列表、看板、时间线（Display 里切换） | 不同场景换不同看法 |
| Triage（分诊） | 团队专属收件箱：外部或非本团队创建的 issue 先进这里，可以接受 / 标重复 / 拒绝 / 稍后处理 | 新进来的东西不要直接污染正常流程 |
| Triage Rules / Triage Intelligence | 规则按条件自动改团队、状态、负责人、标签、项目、优先级；Intelligence 分析内容后路由 | 人工分诊太占时间 |
| Triage Responsibility（值班） | 轮值负责盯分诊队列，可对接 PagerDuty / OpsGenie / Rootly / Incident.io 排班 | 明确「今天谁收活」 |
| Insights（洞察） | 把 issue 变成可分析的数据集，选 Measure（问题数、工作量、周期时间、前置时间、分诊时间、问题年龄）和 Slice 出图，带表格，可导出 CSV | 想知道瓶颈在哪、估得准不准 |
| Asks / Customer Requests | 把 Slack 里的请求、客户反馈变成 issue | 非工程同事也能提需求 |
| 模板、标签、收藏、快捷键 | 团队可设默认模板；大量键盘操作（G T、O V、Shift P 等） | 熟手要快 |

**③ 它怎么做自定义 / 扩展**

- **GraphQL API + TypeScript SDK + OAuth 2.0 / 个人 API key**：官方开发者站点把「GraphQL API、认证、Agents、TypeScript SDK」列为一等内容。来源：`https://linear.app/developers`
- **Webhooks**：官方集成页明确写「API 和 Webhooks 一起，让你把 Linear 的能力扩展到开箱即用之外」。来源：`https://linear.app/docs/integrations`
- **Integration Directory（集成目录）**：Slack、GitHub、GitLab、Sentry、Zendesk、Intercom、Front、Figma、Notion、Google Sheets、Zapier、Airbyte、Asks、Discord 等。来源同上
- **Custom Views 作为一等对象**：筛选条件建好后可保存、可共享（工作区级 / 团队 / 项目 / 倡议级）、可收藏、可设为打开 Linear 时的默认页；视图链接可复制，但复制链接不等于给了权限。来源：`https://linear.app/docs/custom-views`
- **Triage Rules**：按可筛选属性触发，自上而下按顺序执行，跨团队转分诊时新团队规则也会跑；冲突会在界面上提示。来源：`https://linear.app/docs/triage`
- **模板**：团队设置里可设默认模板，会覆盖分诊默认状态。来源同上
- **没有找到的东西（不猜）**：
  - 没有找到 Linear 提供通用「自动化画布」的一手来源 —— 它的自动化是散在分诊规则、SLA、集成里的。
  - 没有找到 Linear 有公式字段的一手来源。
  - 这两条判为「Linear 不提供该机制」，标记为**未核实（以官方文档为限）**。

**④ 可以抽象成我们工作台的一个「模式」**

- **模式名**：分诊收件台
- **界面形态**：一个收件箱（新进项先落这里，四条动作：接受 / 重复 / 拒绝 / 稍后）+ 右侧属性面板 + 列表/看板/时间线切换；快捷键优先。
- **要接的后端接口**：
  - 事项读写：创建、改状态、改负责人、打标签、设优先级与预估
  - 收件箱：待分诊队列读写、四条动作（接受、合并为重复、拒绝、稍后）
  - 规则：条件 → 动作的规则读写与执行顺序、执行记录
  - 视图：筛选条件的保存与共享
  - 洞察：按维度聚合的统计查询（问题数、停留时间等）

**⑤ 来源 URL**

- https://linear.app/features
- https://linear.app/docs/projects
- https://linear.app/docs/custom-views
- https://linear.app/docs/initiatives
- https://linear.app/docs/triage
- https://linear.app/docs/insights
- https://linear.app/docs/integrations
- https://linear.app/developers

### 3. Asana

**① 一句话定位**
把人和 AI 同事放在同一份计划上的工作管理平台，官方叫法是「人类与 Agent 团队的操作系统」（Work Graph）。

**② 核心功能清单**

| 功能名 | 一句说明 | 解决用户什么需求 |
|---|---|---|
| Tasks（任务） | 把活拆成有负责人和截止日期的小块 | 谁在什么时候干什么，写得清楚 |
| Projects（项目） | 任务装进一个共享的容器里一起推进 | 一群人对着同一份计划干活 |
| Project views（项目视图） | 同一批任务能按列表、日历、时间线、甘特图、看板看 | 不同角色想看的粒度不一样 |
| Custom fields（自定义字段） | 给任务加标签式字段（单/多选有 16 色），可排序、筛选、自动进报表 | 按自己的口径归类任务 |
| Status updates（状态更新） | 快速写项目进展更新 | 向上同步不用另写邮件 |
| My Tasks / Inbox / Home | 我的所有指派在一处；自动更新只推跟我有关的；首页给概览 | 个人视角的入口 |
| Goals / Portfolios | 目标挂住各团队的工作；组合看多个项目 | 想把工作连到公司目标上 |
| Reporting dashboards（报表看板） | 用实时图表看团队工作状态 | 要数据不要手工统计 |
| Forms（表单） | 标准化收需求的入口，收来的信息一开始就齐 | 别让人提需求时缺东少西 |
| Rules（规则） | 触发 → 动作的自动化，有规则库推荐，可跨 Asana 和别的工具（Slack、Gmail、Outlook、Jira） | 例行流转自动做 |
| Bundles（流程包） | 把一套流程一次性地创建、套用、更新到多个项目 | 同一套规范要铺到很多项目上 |
| Templates（模板） | 项目和任务的现成模板 | 起步不用从零搭 |
| Time tracking（时间跟踪） | 记录花在工作上的时间，便于排预算 | 工时要有数 |

**③ 它怎么做自定义 / 扩展**

- **Custom fields**：单/多选字段可选 16 种颜色，用来做看板颜色标识、筛选、报表。来源：`https://asana.com/features`
- **Rules**：用规则生成器自定义「触发 → 动作」，有规则库推荐，可更新自定义字段、多动作、跨项目、可暂停不删除、可看触发记录；官方把 Rules 和 Bundles、Templates、Forms 一起归在「工作流与自动化」下。来源：`https://asana.com/features/workflow-automation/rules`
- **Bundles**：把流程一次套到多个项目，解决「每个项目都要重配一遍」。来源：`https://asana.com/features`
- **开发者扩展**：官方开发者站点写明 Asana app 用 **REST API、App Components、Webhooks** 三样东西，可发布到 App Directory（给所有人）或只在组织内用。来源：`https://developers.asana.com/docs`
- **AI 相关**：AI Teammates（把 AI 同事加进流程）、AI Studio（设计 AI 工作流）、Dash（个人 AI 助手）。来源：`https://asana.com/features`
- 备注：Asana 有「表单 + 规则 + 流程包」的组合，这是它比较典型的做法。**未找到** Asana 提供用户可写「公式字段」的一手来源，标**未核实**。

**④ 可以抽象成我们工作台的一个「模式」**

- **模式名**：流程套件模式
- **界面形态**：一块项目页，上方是视图切换（列表 / 看板 / 日历 / 甘特），右侧是规则列表（一行一条 if-then），外加一个「表单入口」和「流程包」。
- **要接的后端接口**：
  - 任务与项目读写
  - 自定义字段定义与值
  - 规则读写（触发 / 动作）、规则执行日志
  - 流程包（一组设置的集合）的创建、套用、批量更新
  - 表单定义与提交
  - 目标与报表聚合查询

**⑤ 来源 URL**

- https://asana.com/features
- https://asana.com/features/workflow-automation/rules
- https://developers.asana.com/docs

### 4. monday.com

**① 一句话定位**
以「板（board）」为核心数据形态的可视化工作平台，主张人和 Agent 在同一块板上干活。

**② 核心功能清单**

| 功能名 | 一句说明 | 解决用户什么需求 |
|---|---|---|
| 板 / 分组 / 条目（Board / Group / Item） | 板是容器，分组是阶段，条目是具体工作 | 让非技术的团队自己搭出流程表 |
| 多视图 | 同一份板上数据可切表格、看板、日历、时间线、甘特、工作量、图表、电量图、地图等；视图可锁定、固定、隐藏主表 | 不同人用不同方式看同一批数据 |
| 列类型 | 状态列、人员列、日期列、时间线列、公式列、镜像列、连接列等 | 把工作数据结构化 |
| Automations（自动化） | 触发器 + 条件 + 一个或多个动作；支持多步；有大量预置模板 | 让板子自己跑起来 |
| Integrations（集成） | 大量预置集成，触发和动作可以在外部工具之间串 | 不用写代码连工具 |
| Dashboards 与小组件 | 把多个板的数据聚成看板 | 跨板看整体 |
| Workdocs / WorkForms | 文档；表单收集 | 知识与收需求 |
| AI（Sidekick、Agent builder、Notetaker、vibe coding） | 说话生成视图、自动化、代理，会议记录 | 降低搭建成本 |
| MCP | 官方提供 MCP 入口 | 让 AI 客户端直接接进平台 |
| 权限与审计 | 账户级 / 列级 / 条目级权限，活动日志可追踪与筛选 | 谁能改什么可控 |
| 模板 | 大量解决方案模板（含 AI 模板中心） | 快速开工 |

**③ 它怎么做自定义 / 扩展**

- **monday apps framework（应用框架）**：开发者可以做 board views、item views、board menu features、dashboard widgets、custom objects、account settings views、doc actions、AI assistant、integrations、automations、workspace templates；应用由「一个或多个 app feature」组成。来源：`https://developer.monday.com/apps/docs/intro`
- **视图是嵌入的网页**：board view / item view / dashboard widget 用 React 之类的前端技术写，编译成 HTML/CSS/JS 上传到 monday 的 CDN（官方明确提示这个 CDN 没有鉴权，被知道 URL 就能访问，介意的话就用 iframe URL 自己托管）。来源：`https://developer.monday.com/apps/docs/quickstart-view`
- **列视图（Column views）**：可以给状态列、下拉列、公式列、人员列做自定义弹窗（点开、悬浮、列设置、附加设置四种触发），存储仍落在原生列上。来源：`https://developer.monday.com/apps/docs/column-views`
- **列扩展（board column extension）**：把一整列的自动化配置放进一个自定义 UI，靠 webhook 在后台创建与管理自动化。来源：`https://developer.monday.com/apps/docs/board-column-extension`
- **SDK**：`monday.api`（代为查询 API）、`monday.listen`（听客户端事件）、`monday.get`、`monday.execute`、`monday.storage`（键值存储）、`monday.set`。来源：`https://developer.monday.com/apps/docs/introduction-to-the-sdk`
- **公式列**：服务端计算，只能读和创建、不能通过 API 写值或清空，`display_value` 是主字段；每分钟最多读 10000 个公式值、单次请求最多 5 个公式列、不支持引用镜像列和连接列；公式列也不支持在 `items_page` 里做服务端筛选。来源：`https://developer.monday.com/api-reference/reference/formula`
- **一个重要的已知限制**：官方「API 覆盖缺口」文档写明，**目前 API 不提供创建、删除、更新、列出板级自动化（recipes）的能力，自动化只能在界面里管**，说在做了。来源：`https://developer.monday.com/api-reference/docs/coverage-gaps`
- **自动化配方模型**：每个自动化 = 触发器（trigger）+ 条件（condition）+ 一个或多个动作（action）；可从零建，也可用模板；支持多步。来源：`https://support.monday.com/hc/en-us/articles/360001222900-Get-started-with-monday-automations`

**④ 可以抽象成我们工作台的一个「模式」**

- **模式名**：数据板 + 配方
- **界面形态**：一张主表格（行是条目、列是各种类型）在上，下面或旁边是「视图条」；自动化用一行行的配方展示：`当…… → 如果…… → 就……`。
- **要接的后端接口**：
  - 板 / 分组 / 条目 / 列 的增删改查
  - 列类型元数据（含公式列的表达式，只读）
  - 视图定义（类型 + 配置）的增删改查
  - 自动化配方（触发器 / 条件 / 动作）的读写与执行日志
  - webhook 订阅

### 6. Coda（现已改名 Superhuman Docs）

**① 一句话定位**
把文档、表格和应用合成一块画布，用一套积木把团队的流程装进去。

**② 核心功能清单**

| 功能名 | 一句说明 | 解决用户什么需求 |
|---|---|---|
| 画布 + 文档 | 像写文档一样写内容，内容里可以嵌表格、控件、按钮 | 说明和要做的事放在同一页 |
| 表格 | 有列类型、可跨表引用和计算的行式数据 | 文档里也要有结构化数据 |
| 按钮 Button | 画布上的按钮或表格里的按钮列；点一下执行一个动作（原生动作或 Pack 动作）；可以用「Disable if」在条件不满足时禁用，可加角标、可自定义点击后的提示 | 把「下一步做什么」变成一步操作 |
| 控件 Controls | 页面上的可调参数，按钮和公式可以读它 | 做简单的交互式工具 |
| Automations（自动化） | 两段式：When（触发）+ Then（动作），可以加多个 And Then；支持行变化和按时间触发；可以在公式里用 Step 1 Result 引用触发行的数据 | 重复劳动自动做 |
| 公式语言 | 文档里到处可以写公式（按钮、自动化、字段、筛选都行） | 用一套语言描述计算和判断 |
| Packs（扩展系统） | Coda 的扩展与集成体系，装上以后给文档增加四类积木：同步表、按钮、列格式、公式 | 把外部工具的读写直接变成文档里的零件 |
| 发布 Publishing | 把文档发成一个可分发的网站 | 内部工具也能给别人用 |
| Coda AI / AI Views | 把重复任务交给 AI，出「AI 视图」 | 少写公式、少做表格 |
| 开放 API | 程序化读写 Coda 文档 | 别的系统能接进来 |

**③ 它怎么做自定义 / 扩展**

- **Buttons 是主要交互单元**：点击动作可以从下拉里选，也可以开公式编辑器写；「Disable if」用公式决定按钮是否禁用；还可以命名按钮以便后续用公式引用。来源：`https://help.coda.io/hc/en-us/articles/39555758072717-Button-basics`
- **Automations 的模型**：When 的触发器包含「行变化」（只对可编辑列生效，公式列不算；公式变化、画布列编辑、评论都不触发）、时间触发等；Then 可以增删改复制行、复制页、通知人、**推按钮**、改控件值、调用 Pack 动作；And Then 可以无限加；自动化可以选以「我自己」或「Automation Bot」身份执行。来源：`https://help.coda.io/hc/en-us/articles/39555778179853-Automations-in-Coda`
- **自动化 + 按钮组合**：典型玩法是「先做一个按钮（比如用 Gmail Pack 发邮件），再写一条自动化去推这个按钮」；按钮是 Private 模式时自动化必须以本人身份跑，Shared 模式才能用 Automation Bot。来源：`https://coda.io/resources/guides/combine-automations-and-packs`
- **Packs（扩展系统）**：Packs 补足 Coda 的核心积木，装上后可提供四类东西——Pack 同步表、Pack 按钮、Pack 列格式、Pack 公式；Pack 是装到「文档」级别，不是账号级。来源：`https://help.superhuman.com/hc/en-us/articles/46210216072717-Overview-Use-Packs-in-Coda` 与 `https://help.coda.io/hc/en-us/articles/39555953761549-Install-Packs-in-your-doc`
- **自己写 Pack**：Pack SDK 里，动作就是带 `isAction: true` 的公式；动作不会被缓存或自动重算，只在按钮被按或自动化触发时跑；动作有账号参数，可选「用户私有账号」，这样每个人按按钮时用自己的账号执行；动作可以返回结果并写回同一张表的另一列。来源：`https://coda.io/packs/build/latest/guides/blocks/actions/` 与 `.../blocks/formulas/`
- **改名的提示**：Coda 现已改名 Superhuman Docs，官方产品页第一段就写了这件事，同时提到「AI 视图」和「企业级数据库」。来源：`https://coda.io/product`

**④ 可以抽象成我们工作台的一个「模式」**

- **模式名**：按钮 + 规则
- **界面形态**：一块画布（可以写文字、贴表格），表格里有一列是按钮；旁边一个规则面板，每条规则写成 `When … → Then … → And Then …`。按钮点一下执行动作，结果可以落到某一列里。
- **要接的后端接口**：
  - 文档 / 页面的读写
  - 表 / 行 / 列的读写，以及公式求值
  - 按钮定义与执行（动作名 + 参数 + 禁用条件）
  - 自动化规则读写（触发 / 动作序列 / 执行身份）
  - 外部动作（Pack）调用：列出可用动作、传参、拿返回值
  - 通知（给人发消息）

### 7. Basecamp

**① 一句话定位**
一个项目一页，把待办、讨论、文件、日程、卡片都挂在这一页上的「够用就好」型协作工具。

**② 核心功能清单**

| 功能名 | 一句说明 | 解决用户什么需求 |
|---|---|---|
| 项目页（Project page） | 每个项目一个专属页面，可以自己往里加内置工具（待办、留言板、聊天室、日历、卡片表等） | 内容自动归位，不用到处找 |
| Message Boards（留言板） | 公告、讨论、演示都以帖子和回复的形式存在这里，替代邮件；后来进项目的人也能补上上下文 | 讨论集中，不用翻邮件串 |
| To-do Lists（待办清单） | 可指派、可设截止、可讨论、可传文件、可建子任务，清单之间能拖 | 小事也要能被追到 |
| Card Tables（卡片表） | Basecamp 版的看板，卡片过列推进，可设定新卡进表或进某列时通知谁 | 有阶段的工作用可视化方式推 |
| Hill Charts（山坡图） | 用一条山坡表示每件事处在「还在摸索爬坡」还是「已经清楚下坡」 | 光看百分比看不出「卡住了没有」 |
| Campfire（围炉聊天） | 项目内即时聊天，可以开多个聊天室 | 不用另开一个聊天工具 |
| Calendar（日历） | 项目日历；还有把各项目日历聚到一起的全局日历；可订阅到 Outlook / Google / HEY 等 | 重要日期集中看 |
| Automatic Check-ins（自动签到） | 定时向团队提问（例如每周一早上问「这周在做什么」），答案存进一条记录 | 少开会也能对齐 |
| Docs & Files（文档与文件） | 文档、PDF、外部网盘文件（Figma、Google Docs、Dropbox 等）按列表和文件夹整理，可按人 / 类型 / 关键词筛 | 素材和交付物有固定位置 |
| My Bar（我的栏） | 屏幕底部常驻我的任务、事件、今日、书签、笔记，可用键盘唤出 | 不用离开当前页就能看自己的事 |
| Reports（报表） | Lineup（项目时间线）、某人动态、某人的分派、Mission Control（所有项目状态）、Hilltop（所有项目的山坡图）、Added/Completed、Overdue、Unassigned | 想一眼看全局或看风险 |
| Client mode（客户模式） | 逐个决定客户能看到项目里的哪些东西 | 给外部人看的时候要能藏东西 |
| Latest Activity（活动流） | 行动按主题组织、标明是谁做的、带时间戳，空白时段也显示 | 回头看发生了什么 |

**③ 它怎么做自定义 / 扩展**

- 「多视图 + 表格」是 7 款全中，说明**「同一份数据、换着方式看」是这类工作台最底层的共同点**。
- 「自动化（触发 + 条件 + 动作）」5 款有，但只有 4 款同时有「公式 / 计算字段」，说明**自动化比公式更普遍**：不会写公式的人多，但谁都想让事自己跑。
- 「表单」4 款有，且都出现在偏团队的 Asana / monday.com / ClickUp，个人场景价值一般。

## 三、本组启示

### 值得我们抄的界面形态

1. **视图条（View bar）**
   同一份数据上面挂一排视图标签，每个视图存自己的筛选、分组、排序、显示列；可以收藏、可以共享、可以锁。
   出现在：ClickUp、Linear、Asana、monday.com、Airtable、Basecamp。
   对我们：我们的产物本来就是 JSON，**把「视图」也做成一个 JSON 一等对象**（类型 + 筛选 + 分组 + 排序 + 列），这样按钮打开后的界面既可以整屏拖拽自定义，也可以只是「同一份数据换个视图」，实现成本低很多。

2. **看板卡片**
   6 款产品都有，是最普及的一种形态。
   对我们：卡片 = 一条记录 + 一个状态列，拖一下改状态。这个形态足够简单，也最适合承接 Agent 刚产出的东西（待处理 / 处理中 / 已完成）。

3. **行式自动化配方：`当… → 如果… → 就…`**
   monday.com 的「When this happens / Then do this」、Coda 的 When / Then / And Then、Asana 的 Rules、Airtable 的 trigger / action，都是这个套路。
   对我们：背景里说「流水线型 Agent 用画布」，但**大多数规则根本不需要画布**——一行 if-then 更好读、更好做、更好查。建议：简单逻辑用行式配方，只有真正的多分支流水线才上画布。

4. **表格里的按钮列**
   Coda 的 Button column：一行一个按钮，点一下就执行一个动作（原生动作或外部动作），执行结果可以写回同一行的另一列，还能用「Disable if」防止重复执行。
   对我们：这几乎是「按 VS Code 插件的方式加按钮入口」的现成形态——**按钮就是一个可注册的动作 + 参数 + 结果落点**，直接对得上。

5. **收件箱 / 分诊台**
   Linear 的 Triage、Asana 的 Inbox：新东西先落进一个待分流队列，人（或 Agent）再决定接受 / 合并 / 拒绝 / 稍后。
   对我们：Agent 的输出不应该直接写进正式数据里，中间需要一个「待人看一眼」的队列。这也是我们把 Agent 接进工作台时最需要的一层。

6. **山坡图（Hill Chart）**
   Basecamp 独有：一条山坡区分「还在摸索」和「已经确定」，比百分比更能说明真实状态。
   对我们：如果以后要做「项目在爬坡还是在下坡」的轻量表达，这是最有信息量又最省地方的一种画法。

### 明确不适合我们的

1. **多级容器层级（ClickUp 的 Workspace → Space → Folder → Subfolder → List）**
   设置逐层继承、又可逐层覆盖，官方还专门为「哪些设置在哪一层生效」写了一整篇文章。我们只有自己和朋友用，没有组织层级，这套结构会直接变成负担。**我们要的是「工作台 → 视图/模式」，最多两层。**

2. **管理员权限模型与全局功能开关（ClickUp ClickApps 只能 owner/admin 开；monday.com 锁视图、隐藏主表也只能 board owner）**
   这些机制存在的前提是「一个人用不好别人的功能」。个人工作台不需要权限矩阵，**用「每人一份自己的配置」代替「管理员开关」**。

3. **整套给第三方开发者的平台（monday.com 的 iframe 应用 + CDN + webhook 鉴权，Airtable 的 Blocks SDK，Coda 的 Pack SDK）**
   我们只需要「按 VS Code 插件方式加按钮入口」，不需要给别人做开发者平台。抄它们的**动作注册模型**就够了，不要抄它们的**托管与发布体系**（monday.com 官方自己都提示：上传到它 CDN 的视图没有鉴权）。

4. **甘特图 / 工作量视图（monday.com Gantt、Workload）这类重图形交互**
   画一屏漂亮的大长条，实现成本很高，个人和两三个人的场景基本用不上。除非明确要做项目排期，否则先不碰。

5. **把自动化当纯界面功能、不给程序接口（monday.com 官方写明自动化配方目前不能通过 API 创建、删除、更新、列出，只能在界面里管）**
   这是个反面教材。对我们来说，Agent 要能读写我们的自动化规则，所以**规则必须一开始就存成结构化 JSON，可读可写**，不能只活在 UI 里。

6. **靠品牌叙事推动产品（Coda 改名为 Superhuman Docs，产品页第一段就是改名公告）**
   自用工具不需要这一层。此处列出来只是提醒：不要在这类事情上花时间。
