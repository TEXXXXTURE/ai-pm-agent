## 一、一句话结论

**「模式」这个词在 32 款里其实只有两种含义**：一种是**界面形态**（同一份东西怎么看：表格、看板、大纲、画布、文档、收件箱），另一种是**通用机制**（每个形态都要有的动作：换视图、加按钮、登记一个连接、套模板、跑自动化、批准工具调用）。前者决定我们要画几种界面，后者决定我们要定几套登记表和接口。32 款没有一款是自己发明新东西成功的——它们都在做同一件事的取舍。

三条最重要、且已经被多家反复验证的结论：

1. **界面从清单里长出来，不写死在代码里**。Budibase 的类型定义文件、n8n 的节点描述、VS Code 的贡献点、Raycast 的命令表、LobeChat 的清单文件，是同一个思路的五种写法：加一个功能 = 加一条声明，平台据此自动生成图标、配置面板、入口。我们流水线有 20 个步骤，如果每个步骤的配置面板都手写前端，第 21 个步骤就要再改一次前端。
2. **同一份数据换着看**：视图不是另一份数据，只是「筛选 + 排序 + 分组 + 显示哪些列」的一份配置（Notion 视图、Obsidian Bases、Tana 视图、ClickUp/monday 的视图条都是这个做法）。这份配置正好就是我们要的「按钮打开后拖拽自定义产出的结构化 JSON」。
3. **接入信息和界面信息分两层登记**：Open WebUI 分「连接 / 模型预设」，Jan 分「服务商 / 助手」，Cherry Studio 分「服务商 / 助手与 Agent」。八款一致——后端怎么连只登记一次，界面上的每个角色复用同一份接入信息。

## 二、模式总表（32 款 → 32 个模式）

「界面形态」是它长什么样，「要接的接口」是它背后必须有什么后端能力，最后一列是我们那边的判断。

| # | 模式名 | 来自 | 界面形态 | 要接的接口 | 我们的判断 |
|---|---|---|---|---|---|
| 1 | 数据表模式 | Notion | 左页面树 + 中文档区 + 顶部视图标签（表格/看板/日历/列表/画廊/图表） | 页面与块读写、数据源查询、视图定义读写、属性定义读写 | 模式名不必照抄，但「视图 = 一份 JSON」直接可用 |
| 2 | 插件按钮模式 + 本地库模式 | Obsidian | 左侧竖排图标按钮 + 命令面板 + 主区多标签 | 注册按钮（图标+名字+命令 ID）、注册命令、本地文件读写与索引、视图渲染 | 这是我们要的「按 VS Code 插件方式加按钮」最接近的现成范式 |
| 3 | 大纲块模式 + 日记模式 | Logseq | 单栏缩进大纲 + 右侧反链面板 + 日记/查询/白板入口 | 块树读写、引用与反链索引、查询执行、按日期取页 | 日记模式＝「每天打开先看到当日面板」；反链面板可当「Agent 的引用出处」展示位 |
| 4 | 画布卡片模式 | Heptabase | 无限画布放卡片，可连线可分组可进子画布，多标签页 | 卡片读写、画布布局持久化、资源库检索、把当前画布当上下文传给 Agent | 和「流水线 Agent 用画布」几乎是同一形态；「白板不拥有卡片」这条要抄 |
| 5 | 类型化节点模式 | Tana | 大纲为主，每个节点可切视图，另有「搜索节点」当虚拟文件夹 | 节点读写、类型与字段定义读写、按条件查询、视图渲染器注册表 | 「视图是同一份数据的投影」和我们拖拽产物是同一件事 |
| 6 | 空间与文档模式 | Craft | 顶部空间切换 + 左文档树 + 主区编辑器 + 任务/日历/日记并列 | 空间列表、文档与块读写、模板读写、**连接接口（给一段可见范围+权限，返回专属地址）** | 「按连接分配可见范围」直接抄成我们挂 Agent/技能时的默认权限粒度 |
| 7 | 对象类型模式 | Capacities | 左竖排类型列表 + 类型仪表盘 + 对象页按布局渲染 | 类型与属性定义读写、对象读写、保存的查询、**一个类型配一个默认布局** | 「同一类型可有不同布局」最贴近我们的拖拽产物 |
| 8 | 多视图任务台 | ClickUp | 顶部视图栏（列表/看板/日历/甘特），下面是同一份数据 | 任务读写、视图读写、自定义字段与公式字段、自动化规则、模板 | 视图条是我们最该先做的一条壳 |
| 9 | 分诊收件台 | Linear | 收件箱（接受/重复/拒绝/稍后四条动作）+ 右属性面板 + 视图切换，快捷键优先 | 事项读写、待分诊队列与四条动作、规则与执行记录、聚合统计 | 值得做一个：新东西先落到一个地方等你处理，而不是散在各处 |
| 10 | 流程套件模式 | Asana | 项目页 + 视图切换 + 一行一条 if-then 的规则列表 + 表单入口 | 任务与项目读写、字段定义、规则读写与日志、流程包（一组设置）、表单 | 「流程包」＝一堆设置的集合，可整包套用，和我们的规则文件同构 |
| 11 | 数据板 + 配方 | monday.com | 主表格在上、视图条在旁，自动化写成 `当……→ 如果……→ 就……` 的一行行配方 | 板/分组/条目/列读写、列类型元数据、视图定义、配方读写与日志、订阅回调 | 「当→如果→就」这种一行式表达比图形化流程更容易被人和 Agent 读 |
| 12 | 关系表 + 计算字段 | Airtable | 表格为主，字段类型决定单元格长什么样，顶部多个视图标签 | 表/字段/记录读写、跨表链接与汇总计算、视图定义 | 跨表链接与汇总先不做，单表 + 字段类型够用 |
| 13 | 按钮 + 规则 | Coda | 一块画布（可写文字、贴表格），表格里有一列是按钮，旁边规则面板 | 文档读写、表行列读写与公式求值、按钮定义与执行、规则读写、外部动作调用 | **「表格里一列是按钮」值得直接抄**：这也是我们「外置工具挂到某一格」的最短路径 |
| 14 | 项目页（工具箱式） | Basecamp | 一个项目一页，页面上按卡片挂工具（讨论板/待办/看板/日历/文件） | 项目容器与「挂了哪些工具」的清单、各工具读写、报表聚合、模板套用 | 我们的「模式」应该像它这样：一页挂几个卡片，卡片可增删 |
| 15 | 应用搭建模式 | Retool | 左组件面板 + 中画布 + 右属性面板，组件绑定查询结果 | 组件属性读写与引用表达式、数据源查询、页面与模块读写 | 我们不做完整低代码，只取「组件属性可引用别处的值」 |
| 16 | 绑定表达式模式 | Appsmith | 任意界面字段都能写成引用别处值的一段表达式 | 表达式求值、组件属性树、查询绑定 | 等价语法我们先用最简形式，不引入表达式语言 |
| 17 | 插件注册模式 | Budibase | 用自己的组件/数据源装进平台，装完出现在面板 | **类型定义文件驱动界面生成**（图标/配置面板/可绑定数据源/事件列表） | 【必抄】每类步骤给一份定义，右栏表单自动生成 |
| 18 | 插件市场模式 | ToolJet | 安装 → 配凭据 → 出现在查询面板 | 插件包安装、凭据绑定、卸载回滚 | 【不抄】只抄「安装」这个动作，市场基建不要 |
| 19 | 流水线画布模式 | n8n | 节点 + 连线的画布，节点里带位置坐标 | 节点数组 + 连线数组、执行记录、凭据引用 | 形状要抄，但位置坐标不要混进节点对象（见第五节） |
| 20 | AI 编排模式 | Dify | 同一块画布上放对话型与流程型两种节点 | 图定义（nodes/edges/viewport 分开）、对话与流程运行时、日志 | 【直接采用】我们画布就按 nodes/edges/viewport 三块存 |
| 21 | Agent 工作台模式 | Coze | 画布 + 后端定义的节点类型清单 | 后端定义「能画什么」，前端只负责画；加节点类型有文档化路径 | 【必抄】「加一个模式」必须是一条被写下来的路径，不然加几次就停 |
| 22 | 执行图模式 | ComfyUI | 编辑态与执行态是两份产物，执行态只有「节点 ID → 类型与输入」，连线内联 | 带版本号的公开 JSON Schema、执行态序列化、执行接口 | 【必抄】画布给人看，编译后的执行态喂引擎、也喂 Agent（token 少、噪声小） |
| 23 | 界面即数据模式 | Figma | 设计文件本身就是可被代码消费的结构（组件、变量、样式） | 组件与变量定义、插件清单、增量读取 | 只取「界面产物是结构化数据」这条，不碰设计文件格式 |
| 24 | 组件复用模式 | 墨刀 | 拖拽原型 + 组件复用 + 分享 | 原型文件读写、组件库、分享链接 | 只取「组件可复用」，格式细节未拿到一手资料 |
| 25 | Agent 工作区 | Cherry Studio | 对话为主，右侧是 Agent 的状态面板，可挂技能/知识库/工具 | 服务商登记（地址+密钥+协议+模型 ID）、Agent 四步清单绑定、技能与工具挂载、五档权限 | 它的「服务商登记 + 助手绑定」就是我们两层登记的原型 |
| 26 | 插件清单模式（清单即界面） | LobeChat | 对话内嵌一块界面 + 插件清单决定的配置表单 | 清单文件（标识/接口/界面形态/设置表单定义）+ 网关 | 只抄「用一份 JSON Schema 描述要填什么」，不嵌网页 |
| 27 | 模型预设模式 | Open WebUI | 连接（地址+密钥）之外，把基础模型包成有提示词/工具/知识库的预设 | 连接读写、预设读写、消息上的工具审批、按需加载的技能文件 | 「连接 vs 预设」的分层直接采用 |
| 28 | 工作台项目模式 | AnythingLLM | 一个工作区 = 一份配置单 + 一个对外可见的 id | 工作区字段读写、一份配置 + 一个 id + 三层回落（本工作区 → 全局） | 【直接采用】这就是我们「模式」的骨架 |
| 29 | 服务商与密钥管理台 | Jan | 添加服务商弹窗四格：名称 / 协议格式 / 接口地址 / 密钥，逐模型标能力 | 服务商读写、模型能力标记、工具审批内联在工具卡片里 | 四格表单就是我们的最小登记面 |
| 30 | 声明式工作台模式 | VS Code | 侧栏图标 + 视图 + 命令面板 | 三张表：命令表、视图（面板）表、菜单挂点表（其余 35 个贡献点先不做） | 【必抄但只抄三个】先做命令、视图、菜单挂点 |
| 31 | 全局命令面板模式 | Raycast | 一个搜索框里跑所有命令 | 命令表（id + 标题 + 图标 + 说明 + 触发方式 + 参数） | 值得做：所有按钮/模式都能从一处搜到并触发 |
| 32 | 可拖拽面板工作台模式（视图 + 缎带按钮） | Obsidian | 左侧图标按钮 + 右侧可停靠面板，面板可换位置 | 注册视图（工厂函数）、注册图标按钮、把面板放到指定位置 | 「视图」和「按钮」是两个独立注册项，这个切法我们要照做 |

## 四、模式归并：我们要画几种界面、定几套登记表

把上表 32 个模式去重后，实际要做的只有下面这些（左边是要画的界面，右边是每个界面都共用的动作）。

**A. 要画的界面形态（8 种，前 3 种是我们已有规划的，后 5 种是这次调研补上的）**

| 界面形态 | 抄谁 | 说明 |
|---|---|---|
| 对话框 | Cherry / Open WebUI / Jan | 对话型 Agent 的界面（规划书已有） |
| 画布 | n8n / Dify / ComfyUI | 流水线型 Agent 的界面（规划书已有） |
| 面板（侧栏可停靠） | Obsidian / VS Code | 挂工具的常驻区（规划书已有按钮，缺面板这一层） |
| 表格 | Airtable / monday / Coda | 数据为主的模式（我们自己的产物清单、工单、考题都能用） |
| 看板 | ClickUp / Linear | 按状态分列 |
| 大纲 / 列表 | Logseq / Tana | 逐条缩进，最省事的记录形态 |
| 收件箱 / 分诊台 | Linear | 新东西先落到一处，四条动作处理 |
| 项目页（工具箱） | Basecamp | 一页挂几个卡片，卡片可增删 |

**B. 每个界面都共用的动作（登记表）**

1. **连接登记**（一个后端服务：协议类型 + 地址 + 密钥 + 模型 ID 列表，逐模型标能力）——八款一致的第一层。
2. **角色登记**（一个模式或 Agent：名字 + 图标 + 说明 + 系统提示词 + 挂哪些技能/工具/资料 + 从哪触发 + 是否启用）——八款一致的第二层。
3. **入口登记**（按钮/命令/面板三张表）——VS Code 的贡献点、Raycast 的命令表、Obsidian 的视图与图标按钮都是这个。
4. **视图定义**（筛选 + 排序 + 分组 + 显示哪些列，存成一份 JSON）——保证同一份数据换着看不用另存数据。
5. **模板**（一份可套用的设置集）——Asana 的「流程包」、monday/Airtable 的模板。
6. **规则**（触发 + 条件 + 动作，一行一条）——ClickUp/Asana/monday/Airtable/Coda。
7. **审批**（工具或动作调用前要人点一下，且这个提示长在调用点上，不要只做总开关）——Cherry 五档、Open WebUI 挂在消息上、Jan 内联在工具卡片里。

**C. 一份「模式」的最小字段（照 AnythingLLM 的做法）**：一份配置 + 一个对外可见的 id + 三层回落（模式自己的设置 → 上层默认 → 全局默认）。这样「模式」本身是可以被复制、分享、被 Agent 读写的一件东西。

**D. 关于「接入不同 Agent」的现成答案**：外部 Agent 一律先按一个 OpenAI 兼容端点接进来（Open WebUI 官方原话：加一个地址和密钥就行，不用插件不用中间件）；不能暴露端点的命令行 Agent（如 Claude Code 这类），走 Cherry Studio 的「编码搭档」形状——界面负责选模型、选工作目录、登记启动参数，点一下在终端里启动。

**E. 一个 Agent / 模型登记进界面的最小信息**（八款字段并排比出来的，逐项能追到官方字段名）：唯一标识 + 名称 + 图标 + 协议类型 + 接口地址 + 密钥 + 模型 ID 列表（每项标能力：工具/视觉/音频）+ 启用开关；可选的第二层是「角色层」（系统提示词、挂哪些技能/工具/资料）与「入口层」（从哪触发）。详见 `04-AI客户端与可扩展工作台.md` 第 3.3 节。

## 五、明确不做（四组一致指向）

| 不做 | 依据 | 原因 |
|---|---|---|
| 插件市场 / 社区一键导入 | ToolJet Marketplace、Open WebUI 社区列表 | 市场是给成千上万陌生用户 + 几百个外部服务准备的；我们自用，只抄「安装」这个动作 |
| 服务端执行任意代码的插件模型 | Open WebUI 用 Python 源码直接加载 | 安全与调试成本，自用不划算 |
| 在对话里嵌网页做插件界面 | LobeChat 的网页嵌入模式 | 要和宿主的主题、快捷键、状态同步，成本高 |
| 自造一种标记语言 / 自定义格式 | Retool 从 YAML 迁到 Toolscript 的代价 | 起步用最普通的 JSON + 公开的字段说明 + 版本号 |
| 为 Agent 单独造一份「给模型看的摘要格式」 | Retool 明确拒绝这条路 | 一份格式，两种读者（人评审、模型读） |
| 把位置坐标混进逻辑定义 | n8n 把坐标放进节点对象 | 挪一下节点逻辑定义的差异就变一行，喂给模型也是噪声 |

| 把检索参数塞进通用配置 | AnythingLLM 工作区字段 | 我们的模式不都是检索型，做成通用必填会让所有模式都变重 |
| 一上来抄全套贡献点 | VS Code 有 38 个贡献点 | 先做三个：命令、视图（面板）、菜单挂点 |
| 常驻菜单栏与后台定时任务 | Raycast 的菜单栏模式与定时命令 | 依赖「宿主常驻」，我们不是常驻类应用 |

## 六、对现有规划书要动的三处（只记录，不动手）

按这次调研，`docs/统一前端工作台规划书.md` 里三处需要改口径，等动工时一起改：

1. **画布的存放格式**（规划书第三节）：采用 `nodes` / `edges` / `viewport` 三块分开，并分成两份产物——给人看的编辑态（带位置、分组、颜色）和给引擎与 Agent 读的执行态（只有「节点 → 类型 + 输入」，连线内联）。依据：Dify 的三块结构 + ComfyUI 的两份产物。
2. **按钮入口的定义方式**（规划书第二·补节）：落地成三张表——命令表、视图（面板）表、菜单挂点表；「加一个模式」本身要写成一条被文档化的路径（前后端各加一处），不然加几次就会停。依据：VS Code 的贡献点、Coze 的「加节点类型」文档化流程。
3. **接入协议分两层**（规划书第四节）：先「连接登记」（协议 + 地址 + 密钥 + 模型 ID 列表），再「角色登记」（名字 + 图标 + 提示词 + 挂哪些技能/工具 + 入口 + 启用开关）；外部 Agent 统一先按 OpenAI 兼容端点进来，命令行型的走「登记启动参数 + 工作目录 + 启动」。
4. 补充一条规划书里没有的：**每个模式都应有一份可复制的配置单 + 对外可见的 id + 三层回落**（AnythingLLM 的做法），这样模式才能被复制、分享，也能被 Agent 读写。

## 八、方向修正（2026-09-19，用户说明）

> 用户澄清：目标**不是**上面这些知名厂商的工作台。要的是**个人自己给自己做的工作台**——按自己的工作习惯搭出来的流程、看板、行程安排、会议纪要、复盘。上面 32 款的调研不算白做（界面形态与登记表那两层还能当积木用），但「模式」的定义要改。

**用户给的两个真实例子：**

1. 一个外包用户每天用某个 AI 处理大量信息、产出很多内容，实际需要复盘，但翻聊天记录很费钱也很费精力 → 给他做了一个「截取屏幕上的信息 → 总结拆解」的功能，实测好用；产出固定三样：**解决了什么问题、学了什么新东西、有什么待办**。
2. 另一个用户：把 HuggingFace 上的模型信息做成「大批模型总结」＋「新模型发布提示」。

**由此得到的定义**（用户原话的意思）：**工作台就是一个帮人处理信息的工作站**。同一件事会反复出现，只是进来的信息不一样、连接的端点不一样——**处理的方式、传递的方式、呈现结果的方式是一样的**；具体问题用具体工具和方案解决，但「收进来 → 处理 → 固定几样产出」这个形状不变。

**对我们要做的东西的三点影响：**

1. 「模式」的正确定义不是「一种界面」，而是**一种固定的信息处理产出**（例如「回复盘」＝ 解决了什么问题 / 学到什么 / 待办 三栏；「模型动态」＝ 新模型发布提示 + 本期汇总）。表格、看板、收件箱、画布这些界面形态，是同一套产出可以换的呈现方式。
2. **输入端可以换**（屏幕文字、聊天记录、网页、订阅源、本地文件），处理流程与产出结构不变——这正好对应三层架构里的「输入接口 + 输出接口」。
3. 我们项目里已经有同款：行业追踪那条线（每天从订阅源收 → 定期提炼 → 出一篇）就是第 2 个例子；第 1 个例子的截屏总结，是给它换一个输入端。

**下一步**：等用户提供个人工作台的实际案例，按「他原来怎么处理 → 固定产出是什么 → 我们这边对应哪个模式」整理，再与前面 32 款的界面形态对接。

## 九、为什么要留这么大的自定义空间（2026-09-19，用户给的答案）

> 用户原话的意思：AI Agent 确实能帮人提效，**但只要还在坚持用公共方案，这个提效就是建立在「先学会一个应用」的基础上，这已经是绕远路了**。工作台留这么大的自定义空间，是为了鼓励用户**主动把自己的需求说出来**，把困难**落实成一条条现实的边界**——他们的需求远没有那么难对付，而且网上大把现成的解决方案；**怎么把这些轮子拼起来，Agent 是最好的使用者**。

**三点设计含义：**

1. **工作台的第一件事不是「提供功能」，而是「让用户把需求说出来、并被变成可拼的东西」。** 用户不该为了用功能先去学一套操作；表达入口（对话、画布上摆、附一段文字）比功能目录重要。
2. **「网上大把现成方案」就是我们已有的外置工具路由表那套做法**：工具登记在表上，Agent 按表去调，是引用不是装进来。Agent 的活是**挑轮子和拼装**，不是自己造轮子；具体问题用具体工具解决，只有「收进来 → 处理 → 固定产出」这套形状由我们自己定。
3. **模式库是用户自己攒出来的，不是我们预置的。** 一个模式 = 用户某次把需求说清、Agent 把现成轮子拼好、跑出固定结构产出之后**存下来的那一份**，下次同类需求直接套。厂商的工作台是预置模式让人去学；我们的空间是留给用户表达的，不是留给用户配置的。

**由此确定的验证目标（下一步）**：拿一个真实需求走完这条链——用户用自己的话说需求 → Agent 把它拆成几条现实的边界 → 找网上或工具包里现成的轮子 → 拼起来跑 → 出固定结构的产出 → 存成一个模式。用户举的「截屏总结」可以当第一个例子。
