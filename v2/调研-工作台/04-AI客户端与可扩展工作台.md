# 甲、桌面/本地 AI 客户端与多 Agent 前端

## 1. Cherry Studio

### ① 一句话定位
一个支持多家模型服务商的桌面客户端（Windows/macOS/Linux），在「对话助手」之外又做了独立的「工作（智能体）」区，能读写文件、挂技能与 MCP、装小程序，并且内置了「编码搭档」用来安装和启动命令行编码工具。

### ② 核心功能清单

| 功能 | 说明 | 解决什么需求 |
|---|---|---|
| 多家模型服务商接入 | 内置 OpenAI、Anthropic、Gemini、DeepSeek、Ollama、LM Studio 等，另可加「自定义服务商」 | 想用一个界面同时用云端和本地模型 |
| 对话-助手 | 预置 300+ 助手，可自建助手（角色预设） | 不同任务不用每次重写提示词 |
| 工作-智能体 | 左侧导航【工作】：自主调用工具、读写文件、跨多步完成任务；与「助手」明确区分 | 需要真正干活的 Agent，而不只是聊天角色 |
| 工作目录 + 任务 | 选一个工作目录，Agent 在里面读改生成文件；左侧面板管理任务与工作目录 | 让 Agent 的操作范围可控、可回看 |
| 内置工具分类 | 按上下文/文件/多媒体/编排/搜索/终端分组：生成图片、知识库检索与管理、联网搜索与抓取、记忆、定时任务、通知、子任务、工作流、文件转 Markdown、Bash、会话协调 | 常见操作不用自己接 |
| 知识库绑定 | 绑定的知识库即该 Agent 的检索边界；不绑则不加载知识库工具 | 限定「只能查这些资料」 |
| 技能（Skills） | 可复用的工作说明与配套资源，用 `SKILL.md` 约定；支持在线注册表、GitHub 单个 `SKILL.md` 链接、ZIP、含 `SKILL.md` 的文件夹四种安装来源 | 把重复流程固化成方法 |
| MCP 外部工具 | 在【设置】→【MCP】添加服务器（本地 stdio 命令+参数+环境变量，或远程 SSE / 可流式 HTTP），再绑定给某个 Agent | 接数据库、浏览器、业务系统 |
| 权限模式 | 逐次确认 / 自动接受编辑 / 智能批准 / 仅规划 / 完全访问 五档 | 先保安全，稳定后再放手 |
| 生成式小程序 | 本地 Web 应用，打包成 `.miniapp` 安装，界面自定，可调 `window.cherry` 使用已配置的 AI 能力；安装时审阅权限，用户为它选【默认模型】【快速模型】两个模型槽位 | 想做只有自己用的专用小工具 |
| 编码搭档（Code CLI） | 安装/检测/启动常见编程命令行工具（页面列出 Claude Code、OpenAI Codex、Gemini CLI、OpenCode、Qwen Code、Kimi Code、Qoder CLI、GitHub Copilot CLI 等），需要模型服务的 CLI 可选择服务商与模型，可选工作目录与终端后启动 | **把外部命令行 Agent 接进图形界面**（与我们「将来要接 Claude Code、CodeBuddy」的需求同构） |

### ③ 「接入 Agent / 加按钮 / 加扩展」的机制怎么运作

Cherry Studio 在这一组里是**扩展点最多**的一个，而且几个扩展点分工清楚：

1. **模型服务商登记（接入模型的最小机制）**
   - 路径：设置 → 模型服务 → 「+ 添加服务商」。
   - 填：**提供商名称**、**API 密钥**、**端点设置**（默认可加 OpenAI 与 Anthropic 端点，「更多设置」里还能加 OpenAI Responses、Gemini、图像生成 Base URL、图像编辑 Base URL）；也可「从预设创建」。
   - 加完要**打开启用开关**，否则模型不进选择列表。
   - 模型列表：点「获取模型列表」从 `服务商` 拉取，或点 `+` 手动填模型 ID；**只有加入列表的模型**才出现在模型选择器里；模型可编辑名称、类型、价格。
   - API 地址规则：默认只填根地址（自动补 `/v1/chat/completions`）；若填的地址以 `#` 结尾，就不再自动拼接。
   - 密钥可配多个并轮询（英文逗号分隔，或钥匙图标进入密钥管理逐条启用/禁用）。
   - → 机制名（我方称呼）：**服务商注册表**；关键结构：`{名称, APIKey[], 端点类型→URL 映射, 模型ID[], 启用开关}`。
2. **Agent 登记**
   - 【工作】→【添加智能体】，按四步创建：**基础信息 / 人格 / 技能 / 知识库**；内置 Cherry Assistant 可直接用。
   - Agent 编辑窗口里有【内置工具】【知识库】【技能】【MCP】四组绑定开关，绑定关系随 Agent 配置保存，从下一条消息生效。
   - → 机制名：**四步式 Agent 清单**。
3. **技能（扩展点一）**：文件夹 + `SKILL.md` 约定，四种安装来源（在线注册表 / GitHub 单文件链接 / ZIP / 本地文件夹）；全局启用开关 + 每个 Agent 再单独启用。
4. **MCP 服务器（扩展点二）**：本地 stdio（命令/参数/环境变量）或远程（URL，部分需授权）；连上后其工具进入 Agent 工具列表，并继续受权限模式控制；还提供资源与提示词，可从输入区【+】面板选用。
5. **小程序（扩展点三，最接近「插件」）**：`.miniapp` 包（本质是打包的本地 Web 应用）+ **安装时权限审阅**（必需权限不可取消）+ **模型槽位**（用户指定【默认模型】【快速模型】，小程序**看不到服务商、模型名与 API Key**）。
6. **编码搭档（扩展点四，专接外部 CLI Agent）**：识别「Cherry 托管安装」与「系统 PATH 里已有」两种来源；需要模型的 CLI 由界面选服务商+模型（页面按 CLI 所需接口类型过滤，不兼容的不列出），自带账号登录的 CLI 走原生登录；再选工作目录与终端后【启动】。Claude Code 还支持【通用】/【详细】两档，详细模式下按角色（Fable/Opus/Sonnet/Haiku/Subagent）做模型映射。

> 注意：GitHub README 里 **Plugin System 仍在 Roadmap**（标注为进行中），所以「第三方 UI 插件」这件事在 Cherry Studio 尚未落地；已落地的扩展点是技能、MCP、小程序、编码搭档。

### ④ 可抽象成我们工作台的一个「模式」

- **模式名**：**Agent 工作区（Work）**
- **界面形态**：中间是对话框，顶部一行下拉依次选「Agent / 模型 / 工作目录」；左侧栏是任务列表与工作目录；右侧面板四个页签：状态、文件、子任务、消息流（开发者模式可在右侧面板追加「调用链」）。权限模式做成顶部一个下拉（五档）。
- **要接的后端接口**：
  1. `Agent 清单`：列出/创建/编辑 Agent（名称、说明、图标、人格/系统提示词、绑定的技能、绑定的知识库、启用的内置工具分类、绑定的 MCP 服务器）
  2. `会话与消息流`：发送任务、以流式返回消息与「子任务开始/结束」「状态变化」事件（SSE 或 WebSocket）
  3. `工作目录与文件`：列出目录、读文件、写文件（每次写操作上报给前端以便审批）
  4. `工具调用与授权`：工具名+参数→前端弹审批→回传 允许/拒绝/本次全部允许
  5. `技能与 MCP 注册表`：列出可用技能、列出可用 MCP 服务器（含它提供的工具、资源、提示词清单）
- **第二个可选模式**：**服务商登记台**——界面是一个列表 + 「+ 添加服务商」弹窗（名称 / API 密钥 / 端点类型 / 地址 / 获取模型列表 / 启用开关 / 连通性检测按钮）。后端要 `GET {base}/models` 探测 + 一次 `chat/completions` 试调用。

## 2. LobeChat

### ① 一句话定位
一个「可扩展（函数调用）的聊天框架」：把外部服务写成插件接进对话，插件用一份 `manifest.json` 描述自己的身份、能调用的 API 和要不要在对话里弹一块界面（iframe）。

### ② 核心功能清单

| 功能 | 说明 | 解决什么需求 |
|---|---|---|
| 插件机制 | 插件 = 一个 manifest + 一组 API 端点；用户在工作台里安装插件后，模型可调用其 API | 让模型调「外部服务」，而不是只能聊天 |
| 函数调用 | 插件 API 以「名称 + 描述 + 参数 JSON Schema」声明，模型按此发起调用 | 模型自己判断该调哪个工具、传什么参数 |
| 插件界面（UI） | manifest 的 `ui` 可声明 `url`、`width`、`height`、`mode`（`iframe` 或 `module`），结果可在对话里以自定义界面呈现 | 有些结果（表格、图形、按钮）用文字说不清 |
| 插件类型 | `type` 可取值 `default` / `markdown` / `standalone` | 决定插件结果怎么被渲染 |
| 插件设置表单 | manifest 的 `settings` 字段是 JSON Schema，工作台据此渲染设置表单 | 插件要 API Key / 参数时，不用写界面 |
| OpenAPI 兼容 | manifest 可只填 `openapi` 字段指向一份 OpenAPI 文档，把已有 REST 服务直接变成插件 | 已有服务的团队零改造接入 |
| 网关（gateway） | manifest 可声明 `gateway` 地址 | 统一转发/鉴权（具体用途未核实） |
| 系统角色 | manifest 的 `systemRole` 描述插件用途，注入给模型 | 帮模型「读懂」插件是干什么的 |
| 插件市场 / 技能市场 | 站点上有插件与技能市场页面（搜索结果出现 `lobehub.com/skills`），可安装他人做好的插件 | 不用自己写就能用 |
| MCP 与内置工具 | 源码索引显示存在 MCP 相关类型定义与桌面端 MCP 控制器、内置工具注册表、技能推荐常量 | 跟上 MCP 生态（细节未核实） |

### ③ 「接入 Agent / 加按钮 / 加扩展」的机制怎么运作

- **机制名**：**插件清单（Plugin Manifest）**，文件名固定为 `manifest.json`，是个 JSON 文件，充当插件的「身份证」。
- **关键结构**（来自 SDK 仓库文档源码，字段与注释原文）：
  ```
  {
    "identifier": String,        // 插件唯一标识（平台内区分不同插件）
    "api": Array<PluginApi>,     // 插件提供的 API 数组（每个含 url/name/description/parameters）
    "author": String,            // 可选
    "createAt": String,          // 可选
    "gateway": String,           // 可选，插件网关地址
    "homepage": String,          // 可选
    "meta": {                    // 界面展示用
      "avatar": String,          // 头像 URL
      "description": String,     // 描述
      "tags": Array<String>,     // 标签
      "title": String            // 标题
    },
    "openapi": String,           // 可选，OpenAPI 规范 URL
    "settings": JSONSchema,      // 可选，插件设置表单的 JSON Schema
    "systemRole": String,        // 可选，注入给模型的插件说明
    "type": "default|markdown|standalone",  // 可选
    "ui": {                      // 可选，界面配置
      "url": String, "width": Number, "height": Number,
      "mode": "iframe|module"
    }
  }
  ```
- **一个 API 条目的样子**（文档示例）：`{"url": "http://localhost:3400/api/clothes", "name": "recommendClothes", "description": "...", "parameters": {properties: {...}, required: [...], type: "object"}}`。
- **加「按钮/入口」的方式**：没有独立的按钮贡献点。入口是**插件本身**——安装后在界面里可被选择/触发的插件项，以及插件通过 `ui.url` 在对话里渲染的那块 iframe 区域（那块区域里放什么按钮由插件自己决定）。
- **把已有服务变成插件的三步**（OpenAPI 路径）：写 API → 写一份 OpenAPI 文档（YAML/JSON）→ 写 `manifest.json` 并把 OpenAPI 文档地址填进 `openapi` 字段。
- **从 DeepWiki 的源码索引能看到**：存在「连接器（connector）」的同步与执行逻辑（`services/connector/sync.ts`、`exec.ts`、`refresh.ts`）、Agent 工具引擎（`AgentToolsEngine`）、内置工具注册（`packages/builtin-tools/src/register.ts`）、桌面端 MCP 控制器（`apps/desktop/src/main/controllers/McpCtr.ts`）、MCP 类型定义（`packages/types/src/discover/mcp.ts`）、技能推荐常量（`packages/const/src/recommendedSkill.ts`）。**这些只有文件路径证据，具体机制未核实。**

### ④ 可抽象成我们工作台的一个「模式」

- **模式名**：**插件清单模式（清单即界面）**
- **界面形态**：对话页右侧或消息下方放一块「插件结果区」；顶部是工具/插件的选择器（开关式多选）；插件详情页用 JSON Schema 自动渲染出设置表单；工具调用过程在消息里以卡片展示（调用中/成功/失败 + 结果块）。
- **要接的后端接口**：
  1. `GET 插件清单`：给我一个 URL（或本地清单路径）→ 返回 manifest JSON（我方需要的字段子集：identifier、title、description、avatar、tags、api[]、ui、settings、openapi）
  2. `POST 工具执行`：`{插件ID, 工具名, 参数}` → 返回结果（文本或一份界面描述）
  3. `POST 设置校验`：按 settings 的 JSON Schema 校验用户填的参数
  4. `GET 插件市场列表`（可选，若要接公开清单）
- **要点**：我们只要实现「清单 → 自动生成界面 + 自动生成设置表单」这一条，就等于有了「按 VS Code 插件方式加按钮入口」的通用底座；`ui.mode=iframe` 那条可以不做（见第三部分）。

## 3. Open WebUI

### ① 一句话定位
一个可自托管的 LLM 前端：模型连接（Ollama / OpenAI 兼容 / Open Responses）与「模型预设（把基础模型包成专用 Agent）」分开做，平台自身的能力则用**服务端 Python 插件**扩展，其中一种插件（Action）就是「在消息上加一个按钮」。

### ② 核心功能清单

| 功能 | 说明 | 解决什么需求 |
|---|---|---|
| 多连接协议 | Ollama、OpenAI 兼容 API、Open Responses 三种协议；加一个 URL + API Key，模型就出现在下拉里 | 本地模型和云端 API 放在同一个界面 |
| 模型自动发现 | 「Open WebUI 会自动发现多数服务商的可用模型」 | 少手填配置 |
| 模型预设（Models） | 给任意基础模型绑系统提示词、工具、知识库、技能、参数覆盖，做成一个「专用 Agent」 | 同一个基础模型出多个角色，不用每次重新配置 |
| 预设的登记字段 | 头像、名称与 ID、基础模型、描述、标签、可见范围（私有/公开）、系统提示词、绑定的工具、挂载的知识库、技能、按模型的 TTS 声音、访问控制 | 一个 Agent 需要登记什么，这份清单可直接借用 |
| 动态变量 | 系统提示词里可用 `{{ USER_NAME }}`、`{{ CURRENT_DATE }}`、`{{ CURRENT_TIME }}` 之类变量 | 同一预设对不同人/不同时间给不同上下文 |
| 工具（Tools） | 让模型能取实时真实数据（天气、股价、抓网页等）；有原生内置工具（如 `fetch_url`、知识库系列 `list_knowledge`/`query_knowledge_files`/`view_knowledge_file`） | 模型不只能凭旧知识回答 |
| 工具审批 | 待批准的工具调用挂在 assistant 消息上，刷新页面仍在；有审批开关 | 让「自动执行」可控 |
| 函数（Functions） | 四类：**Pipe**（注册成一个新「模型」）、**Filter**（在请求/流/响应三段拦截）、**Action**（在消息上加按钮）、**Event**（响应系统事件） | 扩展平台本身的行为与界面 |
| 一键导入社区插件 | 从社区站一键导入 Tools / Functions | 不用写代码就用 |
| 外部 Agent 也能接 | 官方有「Connect an Agent」页：把自主 Agent（终端、读写文件、联网、记忆、技能）当模型接进来 | 图形界面 + 外部 Agent 分工 |

### ③ 「接入 Agent / 加按钮 / 加扩展」的机制怎么运作

**A. 接入模型/Agent 的机制：连接 + 预设两层**

1. **连接层**：`设置 → 管理员 → 连接`，填 **URL + API Key**，加一个连接对应一个服务商；模型自动发现。技能/工具文档也说「加一个 URL 和 API key，模型就出现在下拉里」。
2. **接外部自主 Agent**：官方明确写——因为 Agent 框架大多暴露 OpenAI 兼容 API，所以「加一个 URL 和 API key 就行，**不需要插件、管道或中间件**」。官方列出的可接 Agent 有 Open WebUI Computer、Hermes Agent（Nous Research）、OpenClaw。
3. **预设层**：Workspace → Models → Create，登记字段如②表所列；预设是「薄包装」，底层模型不变。

**B. 加按钮的机制：Action 函数（这是这一组里最直接对应「加按钮」的机制）**

- 插件类型**由代码里的类名**决定，无需手工配置：类名 `Pipe` / `Filter` / `Action` / `Event` 匹配到什么就是什么。
- `Action`：**在消息的消息工具栏上加一个自定义按钮**；点击后执行 `action()` 方法，方法里可以调用事件系统做实时界面反馈、向用户提问、要求确认。
- 源码以 Python 字符串存在数据库里，运行时 `exec()` 动态加载，模块缓存在 `request.app.state.FUNCTIONS`，代码变了才重载。
- 存放位置分工：**Tools 在 Workspace 标签页**（可与用户共享、受权限控制）；**Functions 在 Admin Panel**（仅管理员，为全体用户改平台行为）。

**C. 安全前提（官方用整页警告写死了）**

- Tools / Functions / Pipes / Filters / Pipelines **都在服务器上执行任意 Python 代码**；官方要求：只从可信来源安装、导入前看代码、限制 Workspace 权限、定期审计；并明确写「被推荐/热门/出现在社区站 ≠ 审核过」，社区列表是用户提交且未审核。

### ④ 可抽象成我们工作台的一个「模式」

- **模式名**：**模型预设模式（把基础模型包成 Agent）**
- **界面形态**：顶部是模型下拉（预设与原始模型混列，用标签分组）；每个预设一张卡片，点开是编辑页：头像、名称、唯一 ID、基础模型、描述、标签、可见范围、系统提示词（带变量提示）、绑定的工具多选、挂载的知识库多选、参数覆盖。
- **要接的后端接口**：
  1. `预设 CRUD`：`{id, 名称, 头像, 基础模型ID, 描述, 标签[], 可见范围, 系统提示词, 工具ID[], 知识库ID[], 技能ID[], 参数覆盖}`
  2. `连接探测`：`GET {base}/models` + 一次最小对话调用
  3. `工具与技能注册表`：列出可用工具/技能及其参数说明（供绑定）
- **附带模式（值得单独抄一个）**：**消息按钮模式（Action）**——在每条消息的悬浮工具栏上，按「已启用的动作」动态渲染按钮；点按钮 → 前端 `POST /action/{id}`，后端流式回传进度与确认请求 → 前端弹确认框 → 回传用户选择。这是「加按钮」最省的一种实现形状。

## 4. AnythingLLM

### ① 一句话定位
自托管的「文档 + 对话 + Agent」一体化应用：以**工作区（workspace）**为隔离单位，每个工作区有自己的文档、提示词、模型覆盖与检索参数，Agent 用内部 aibitat 引擎把工具调用串起来。

### ② 核心功能清单

| 功能 | 说明 | 解决什么需求 |
|---|---|---|
| 工作区（Workspace） | 完全隔离的单元：自己的文档、聊天记录、系统提示词、可选模型覆盖 | 不同业务的资料互不串味 |
| 工作区字段化配置 | `name`、`slug`（自动生成、创建后不可改）、`openAiPrompt`、`openAiTemp`、`openAiHistory`、`similarityThreshold`、`topN`、`chatMode`、`chatProvider`/`chatModel`、`agentProvider`/`agentModel`、`vectorSearchMode`、`queryRefusalResponse` | 一个工作区就是一份可复制的配置单 |
| 三层设置优先级 | 工作区字段为 `null` 时回落到全局设置 | 全局换模型，未固定模型的工作区自动跟随 |
| 三种聊天模式 | `chat` / `query` / `automatic` 决定怎么用检索到的文档 | 有的场景只准照资料回答 |
| 工作区线索（Threads） | 继承父工作区的文档/设置/权限，但聊天记录独立 | 分支讨论不污染主记录 |
| 文档钉选（Pinning） | 被钉的文档每段都强制进上下文，跳过相似度检索 | 「必须一直带着」的风格指南类文档 |
| RAG 引用 | 上传 PDF/Word/URL 等并索引，回答里标来源 | 回答可追溯 |
| AI Agent（`@agent`） | 在工作区对话里输入 `@agent` 触发；或把工作区设为默认 Agent 模式 | 一处开关切换「聊天」与「干活」 |
| 内置技能库 | 网页搜索、网页抓取（`web-scraping`）、SQL 查询、文件创建、摘要、记忆等，每个技能是注册在 aibitat 引擎里的自包含插件 | 常见自动化开箱可用 |
| 技能重排序（Skill Reranker） | 用工作区的嵌入模型给每个工具描述与用户问题打分，只把最相关的子集（默认 `AGENT_SKILL_RERANKER_TOP_N=15`）给模型；官方称工具/MCP 多时可省最多 80% 提示词 token | 工具一多，提示词不炸 |
| 多用户与角色 | 管理员/经理/成员各自权限（来自文档首页镜像） | 多人共用一个实例 |
| 嵌入组件 | 可把某个工作区的聊天挂到网站（镜像首页所述） | 对外提供问答入口 |

### ③ 「接入 Agent / 加按钮 / 加扩展」的机制怎么运作

- **Agent 怎么被登记进界面**：**没有「Agent 清单 + 贡献点」这种机制**。Agent 是工作区的一个模式/开关（`@agent` 前缀或工作区默认 Agent 模式），Agent 用的模型由工作区字段 `agentProvider` / `agentModel` 覆盖。
- **工具怎么被登记**：技能 = **注册在 aibitat 引擎里的自包含插件**，文档给出的可核对证据是每个技能有**插件名**，例如网页抓取技能的插件名是 `web-scraping`。
- **调用链**：aibitat 引擎维护对话图 → 选择要加载的工具（插件）→ 通过 provider 相关 handler 执行 → 用 WebSocket 向浏览器推 `introspect` 消息（可实时看到 Agent 在想什么）；同一轮内相同函数+相同参数会被 `Deduplicator` 去重，MCP 工具另有冷却窗口防递归。
- **加按钮/面板的机制**：**未找到一手来源**说明 AnythingLLM 有「用户可自定义按钮/面板」的扩展点；本文只找到「工作区配置 + 技能 + MCP」三类扩展，没有第三方 UI 插件清单文件这类机制。
- **可被 API 驱动**：工作区的增改删都有 REST 接口，`slug` 是所有 API 路径里的标识（`/api/v1/workspace/{slug}/...`），也是浏览器 URL 与向量库命名空间的标识 —— **一个字符串 ID 打通界面与接口**。

### ④ 可抽象成我们工作台的一个「模式」

- **模式名**：**工作台项目模式（一个工作区 = 一份配置单）**
- **界面形态**：左侧工作区列表（每项显示名称 + 模型）；中间对话；右侧「资料与设置」抽屉：上传文档列表、钉选开关、系统提示词、模型覆盖下拉、检索模式下拉。Agent 开关做成输入框左侧的一个 `@` 按钮（点一下=下一条按 Agent 处理）。
- **要接的后端接口**：
  1. `工作区 CRUD`：`{name → slug, 系统提示词, 模型覆盖, 检索参数}`；`slug` 由后端生成
  2. `文档上传与索引状态`
  3. `会话`：发送消息；Agent 模式下额外推 `introspect` 事件流（WebSocket 或 SSE）用于「正在想什么」面板
  4. `技能开关 + 工具去重/冷却`由后端负责，前端只显示开关与用量
- **要抄的一点**：**设置三层回落**（工作区 → 全局）比「每个模式都要重填一遍」好用得多。

## 5. Jan

### ① 一句话定位
开源的本地优先桌面 AI 客户端：自带基础模型可离线跑，也能接云端；「助手指令」「服务商登记」「MCP 服务器」三件事分开做，并且把工具调用审批放在聊天里的工具卡片上。

### ② 核心功能清单

| 功能 | 说明 | 解决什么需求 |
|---|---|---|
| 本地模型 | 从 HuggingFace 下载并运行 Llama/Gemma/Qwen/GPT-oss 等 | 数据不出机器 |
| 云端接入 | OpenAI、Anthropic、Mistral、Groq、MiniMax 等 | 需要更强模型时随时切 |
| 自定义端点 | 任何说 OpenAI 或 Anthropic 协议的端点都能接（vLLM、Ollama、LocalAI、TGI、llama.cpp server、LiteLLM 网关、Bedrock/Vertex 代理） | 自建服务/内网网关不用改代码 |
| 服务商登记字段 | 服务商名称、API 格式（OpenAI 兼容 / Anthropic 兼容）、Base URL、API Key；保存时尝试 `{base_url}/models` 拉模型，拉不到就手动加模型 ID | 一个界面管所有模型来源 |
| 多密钥回落 | 一个服务商可配多个 Key，按 `#1` 主、`#2…` 备用，**仅在 401/403/429 时**自动重试下一个；有「Test keys」逐条测 | 限流/封号时不断线 |
| 逐模型能力标记 | 自定义服务商不会被自动探测能力，需逐个模型手动配置「工具 / 视觉 / 音频」等能力 | 让 MCP 只用在支持工具调用的模型上 |
| 采样参数 | 本地引擎（llama.cpp/MLX）与自定义服务商可调温度、top-K、top-P、min-P、重复惩罚等 | 本地调参 |
| 助手（Assistants） | 给模型一套固定指令并命名保存；可增/改/删；聊天输入框 `+ → Use Assistant` 直接切换；新建项目时可指定默认助手 | 不用重复写提示词 |
| 项目（Projects） | 项目可绑定助手，项目内所有对话自动用这套人设 | 长期任务有个容器 |
| MCP 支持 | 作为 MCP 宿主，添加 MCP 服务器后模型可调用其工具 | 接外部工具与数据源 |
| 工具调用审批 | 审批面板**在聊天里的工具卡片内联出现**，显示模型要传的确切参数，逐次允许/拒绝；可在设置里开「Allow All MCP Tool Permissions」预批准 | 让「自动执行」可控 |
| 联网工具 | 0.8.4 起有原生 web search 与 fetch 工具 | 本地模型也能上网取证 |

### ③ 「接入 Agent / 加按钮 / 加扩展」的机制怎么运作

- **接入模型（登记机制）**：设置 → Model Providers → 「Add Provider」→ 弹窗里选 **API 格式**（OpenAI 兼容 / Anthropic 兼容）→ 填 **Provider name / Base URL / API key** → Create。Base URL 必须带服务端期望的版本路径（如 `/v1`），否则 404；尾斜杠会自动去掉。无鉴权的本地服务**也必须填一个非空占位 Key**（例如 `sk-no-key`）。模型：保存时尝试 `{base_url}/models`，失败则在服务商的 Models 区点 `+` **按服务端期望的 ID 原样填**（如 `llama-3.1-8b-instruct`）。
- **Agent / 助手**：助手就是「模型 + 一套指令」的命名组合；登记信息在界面上体现为 名称、描述、指令。
- **MCP 服务器（这才是它的扩展机制）**：`Settings → MCP Servers` → `+` 添加，填 **Server Name / Command / Arguments / Environment Variables**（示例：`browsermcp` + `npx` + `@browsermcp/mcp`）；需要有 Node.js 或 Python。工具调用**逐个批准**，审批面板内联在工具卡片里；也可在设置里整体预批准。
- **加按钮/面板的机制**：**未找到一手来源**——Jan 官方文档里有「助手、服务商、MCP、设置」，但没有面向第三方的界面插件（按钮/面板/清单文件）机制。它的界面由官方自己迭代，第三方扩展只能走 MCP 与自定义端点两条路。

### ④ 可抽象成我们工作台的一个「模式」

- **模式名**：**服务商与密钥管理台**
- **界面形态**：列表页列出所有服务商（左侧名称 + 状态点）；「Add Provider」弹窗只有四格：名称、API 格式（下拉，两项）、Base URL、API Key；服务商详情页分两块：Models 列表（可 `+` 手填模型 ID、可「获取模型列表」）与 API keys 高级区（编号列表、逐条 Test keys、显示 401/403/429 的具体结果）。聊天里的工具调用卡片内联「批准/拒绝」。
- **要接的后端接口**：
  1. `服务商 CRUD`：`{name, apiFormat, baseURL, apiKey[]}`
  2. `GET {base}/models` 探测；`POST 最小对话请求` 做「检测」按钮
  3. `密钥校验`：逐 Key 探测并返回状态码分类（OK / 401 / 403 / 429 / 网络错误）
  4. `MCP 服务器 CRUD`：`{name, command, args[], env}`
  5. `工具审批`：前端弹卡片 → 回传 允许/拒绝/全部允许
- **要抄的一点**：**「API 格式」作为一个显式下拉**。这比让用户猜「我这个地址算不算 OpenAI 兼容」清楚得多，也直接告诉我们：接一个外部 Agent，最小登记项里应该有一个「协议类型」字段。

# 乙、可扩展的开发者工作台（重点：怎么加按钮 / 面板 / 命令）

## 6. VS Code

### ① 一句话定位
扩展式编辑器的事实标准：所有界面元素（命令、菜单、侧边栏图标、视图、面板）都**不是代码直接画出来的，而是在插件的 `package.json` 里「声明」出来的**（贡献点 Contribution Points），代码只负责在触发时被激活。

### ② 核心功能清单

| 功能 | 说明 | 解决什么需求 |
|---|---|---|
| 扩展清单 `package.json` | 每个扩展根目录必须有；含 `name`/`version`/`publisher`/`engines.vscode`（必填），`main`（入口）、`browser`（Web 入口）、`contributes`、`activationEvents` | 一份文件描述整个扩展 |
| 贡献点（contributes） | 文中列出 38 个贡献点，含 `commands`、`menus`、`submenus`、`keybindings`、`views`、`viewsContainers`、`viewsWelcome`、`configuration`、`icons`、`themes`、`walkthroughs`、`chatAgents`、`chatSkills`、`chatInstructions`、`chatPromptFiles`、`languageModelTools`、`languageModelChatProviders`、`authentication`、`taskDefinitions`、`customEditors`、`debuggers`、`snippets`、`languages` 等 | 加按钮、加面板、加语言支持都是「填声明」 |
| 视图容器 viewsContainers | 给侧边栏加一个自己的**图标+容器**（活动栏 activitybar 或面板 panel） | 我的功能要有固定入口 |
| 视图 views | 往容器里加视图；必须给 id 和 name；可加 `when` 条件、`icon`、`contextualTitle`；可贡献到内置容器 `explorer`/`scm`/`debug`/`test` 或自定义容器 | 侧边栏里的一块内容 |

| 菜单与子菜单 | `menus` 决定命令出现在命令面板之外还出现在哪（编辑器右键、资源管理器右键等）；`submenus` 分组 | 同一个命令放到最顺手的位置 |
| 命令 | `commands` 声明 id/标题/图标，用户在命令面板里搜索执行 | 可发现性 |
| AI 相关贡献点（与我们最相关） | `chatAgents`：把 `.agent.md` 文件打进扩展，扩展装好后**这些 Agent 出现在 Copilot 的 Agent 下拉里**；条目只需 `path`，可选 `when`、`sessionTypes`；名称/描述/工具/模型写在 `.agent.md` 的 frontmatter 里。另有 `chatSkills`、`chatInstructions`、`languageModelTools`、`languageModelChatProviders` | **扩展直接给界面贡献一个「Agent」**；也贡献「技能」与「工具」 |
| 工作台扩展能力 | 官方工作台扩展页列出的四类：Views Container、Tree View、Webview、Status Bar Item | 侧栏、树、自定义界面、状态栏 |

### ③ 「接入 Agent / 加按钮 / 加扩展」的机制怎么运作

- **机制名**：**贡献点（Contribution Points）** + **扩展清单（package.json）**。
- **关键结构（原文口径）**：贡献点是「你在扩展 `package.json` 的 `contributes` 字段里做的一组 JSON 声明」。
- **加一个侧边栏图标（活动栏容器）**：
  ```json
  { "contributes": { "viewsContainers": { "activitybar": [
    { "id": "...", "title": "...", "icon": "..." } ] } } }
  ```
  （必须给 id、title、icon；可贡献到 activitybar 或 panel。）
- **往容器里加视图**：
  ```json
  { "contributes": { "views": { "explorer": [
    { "id": "nodeDependencies", "name": "Node Dependencies",
      "when": "workspaceHasPackageJSON", "icon": "media/dep.svg",
      "contextualTitle": "Package Explorer" } ] } } }
  ```
  可贡献到 `explorer` / `scm` / `debug` / `test` 或自定义容器；`when` 控制可见性；`icon` 在标题显示不出来时用；`contextualTitle` 在被拖离原容器时补上下文。
- **视图内容**：TreeView（`registerTreeDataProvider` / `createTreeView`，适合层级数据和列表）或 WebviewView（`registerWebviewViewProvider`，可渲染任意 HTML）。
- **把 Agent 登记进界面**：
  ```json
  { "contributes": { "chatAgents": [ { "path": "./agents/planner.agent.md" } ] } }
  ```
  要求 `.agent.md` 在扩展目录内；**名称、描述、工具、模型写在 `.agent.md` 的 frontmatter，不写在贡献点里**；可选 `when`（条件启用）与 `sessionTypes`（在哪些会话类型里提供）。官方说明：这样打进去的自定义 Agent 会与用户自己定义的 Agent 一起出现在 Agent 下拉里。
- **模型提供方**：另有 `languageModelChatProviders` 贡献点（用于贡献模型提供方，细节本文未展开核实）。
- **一句话总结这套设计**：**界面是清单的子集**。扩展提供者只需描述「我有什么命令、什么视图、什么入口」，宿主负责渲染、放置、搜索、快捷键与生命周期。

### ④ 可抽象成我们工作台的一个「模式」

- **模式名**：**声明式工作台模式（清单里的界面）**
- **界面形态**：左侧一条「活动栏」图标带（每个已装扩展/模式一个图标）→ 点开是侧边栏容器 → 容器里是若干视图（树形列表或网页视图）；命令面板（`Ctrl/Cmd+Shift+P` 式）能搜到全部已注册命令；右键菜单按上下文出现相应命令；状态栏右下角可放一个项。
- **要接的后端接口**：
  1. `贡献注册表读取`：启动时汇总所有模式/扩展的 `contributes`，生成侧边栏、命令面板、菜单、快捷键三张表
  2. `视图数据提供`：按 viewId 拉数据（树形：`getChildren(节点)` 或一次性列表）
  3. `命令执行`：`POST 命令ID + 参数`（很多命令不需要参数）
  4. `激活事件匹配`：只有视图被打开/命令被调用时才启动对应后端
- **要抄的最小集**：只做三种贡献点就先够用——**commands（命令面板 + 按钮）、views + viewsContainers（图标 + 侧边栏面板）、menus（把命令挂到右键/工具栏）**。AI 那边再补一个 `agents` 贡献点，把「.agent.md 文件 → Agent 下拉项」这条路走通。

### ⑤ 来源 URL
- https://code.visualstudio.com/api/references/contribution-points （38 个贡献点全表；`views` 与 `viewsContainers` 的字段与示例；`chatAgents` 字段表与 `.agent.md` 约定）
- https://code.visualstudio.com/api/references/extension-manifest （`package.json` 字段表：name/version/publisher/engines/main/browser/contributes/activationEvents 等）
- https://code.visualstudio.com/api/extension-capabilities/extending-workbench （工作台扩展四类：Views Container、Tree View、Webview、Status Bar Item）

## 7. Raycast

### ① 一句话定位
以「全局输入框」为唯一入口的扩展宿主：扩展就是一份带 `commands` 数组的 `package.json`，每条命令对应一个入口文件，命令有明确的**模式**（开界面 / 不开界面 / 菜单栏），还有 `tools` 供 AI 调用。

### ② 核心功能清单

| 功能 | 说明 | 解决什么需求 |
|---|---|---|
| 单一入口 | 所有命令进同一个根搜索框（root search） | 不用记菜单在哪 |
| 清单即 npm 包 | `package.json` 是 npm `package.json` 的**超集**，「一个文件就能配置你的扩展」 | 不引入第二套构建体系 |
| 命令数组 | `commands` 声明扩展暴露的命令 | 扩展的可见功能 |
| 命令模式 mode | `view`（执行后推一个主视图）/ `no-view`（不开界面，例如直接打开 URL 或调 API）/ `menu-bar`（返回一个菜单栏常驻项） | 同一套机制覆盖三类交互 |
| 后台定时 | `interval`：`no-view` 或 `menu-bar` 命令可每 X 秒/分/时/天在后台跑（最低 1 分钟） | 常驻监控类功能 |
| 命令参数 | `arguments`：调用命令时向用户索取的参数 | 一条命令多用途 |
| 首选项 | `preferences`（扩展级/命令级，命令继承扩展并可覆盖同名项）：`textfield`/`password`/`checkbox`/`dropdown`/`appPicker` 等类型 | API Key、开关等配置不用自己画界面 |
| 命令间互调 | `launchCommand({name, type, context})` 可调本扩展或别的扩展的命令；调别的扩展会先弹权限确认 | 组合工作流；跨扩展调用受控 |
| 动态副标题 | `updateCommandMetadata({subtitle})` 可在运行时改命令副标题（如「未读通知：10」） | 入口本身能显示状态 |
| 图标 | 扩展级 `icon`（512×512 png，可加 `@dark` 后缀做深浅色）；命令级 `icon` 可选，不填用扩展图标 | 一眼认出 |
| AI 工具 | 清单里有 `tools` 数组「供 AI 用来与此扩展交互」，另有 `ai` 字段 | 扩展能力可为 AI 所用 |

### ③ 「接入 Agent / 加按钮 / 加扩展」的机制怎么运作

- **机制名**：**命令清单（package.json 的 `commands`）**。
- **关键结构**：扩展级必填 `name`（唯一、URL 友好）/ `title` / `description` / `icon` / `author` / `platforms` / `categories`；可选 `commands`、`tools`、`ai`、`preferences`、`keywords`、`owner`、`access`（`public`/`private`）、`contributors`、`external`。
- **一条命令的字段**：`name`（唯一 id，**直接映射到入口文件**：命令名叫 `index` 就对应 `src/index.ts`）、`title`（显示名，出现在商店/偏好设置/根搜索）、`subtitle`（副标题，可在运行时动态更新）、`description`（必填）、`icon`、`mode`（必填，三选一）、`interval`、`keywords`、`arguments`、`preferences`、`disabledByDefault`（默认全开，可让用户自己开）。
- **「加一个按钮/入口」到底落在哪里**：Raycast 没有「往别人界面上加按钮」的机制。扩展的入口是**根搜索里的一条命令**；要常驻显示，就用 `mode: menu-bar`（系统菜单栏上多一个项）。这就是它「加按钮」的全部形态。
- **示例清单**（官方给的典型文件）：
  ```json
  { "name": "my-extension", "title": "My Extension", "description": "...",
    "icon": "icon.png", "author": "thomas", "platforms": ["macOS","Windows"],
    "categories": ["Fun","Communication"], "license": "MIT",
    "commands": [ { "name": "index", "title": "Send Love",
      "description": "A command to send love to each other", "mode": "view" } ] }
  ```
- **命令间协作**：`launchCommand` 可按 `LaunchType.UserInitiated` 或 `LaunchType.Background` 启动命令并传 `arguments` 与 `context`；跨扩展会弹权限。

### ④ 可抽象成我们工作台的一个「模式」

- **模式名**：**全局命令面板模式**
- **界面形态**：一个输入框（`Ctrl/Cmd+空格` 唤起）→ 输入即过滤命令；选中一条命令后，如果需要参数就在同一块区域渲染参数表单（下拉/输入框），执行后把结果渲染成列表（每项一行：图标 + 标题 + 副标题）；不常驻的用 `no-view` 静默执行，需要常驻状态的在界面角落放一个「常驻项」显示动态副标题（如未读数）。
- **要接的后端接口**：
  1. `命令注册表`：`{name, title, subtitle, description, icon, mode, arguments[], preferences[]}`
  2. `命令执行`：`POST 命令name + {参数, 上下文}`；返回「打开某视图」或「结果列表」或「静默完成」
  3. `运行时元数据`：`PATCH 命令subtitle`（例如把未读数写回入口）
  4. `参数表单`：按 arguments 定义渲染，不写死界面
- **要抄的一点**：**用 `mode` 把「开界面 / 不开界面 / 常驻项」统一成同一个概念**。我们的按钮入口也可以照此分三类，避免为「只是想跑一下」的入口硬做一个面板。

### ⑤ 来源 URL
- https://developers.raycast.com/information/manifest （`package.json` 超集、扩展级字段表、命令字段表含 mode/interval/arguments/preferences/disabledByDefault、首选项类型表）
- https://developers.raycast.com/api-reference/command （`launchCommand`、`updateCommandMetadata`、LaunchType 与 LaunchOptions）

## 8. Obsidian

### ① 一句话定位
以「工作区（workspace）+ 面板叶子（leaf）」为骨架的笔记工具：插件通过注册**视图类型**往左右侧栏加面板，通过 `addRibbonIcon` 往最左侧的「缎带（ribbon）」加按钮，两者都在插件启用时注册、禁用时清理。

### ② 核心功能清单

| 功能 | 说明 | 解决什么需求 |
|---|---|---|
| 视图（View） | 文件列表、关系图、Markdown 视图都是视图；插件可自定义视图类 | 内容怎么显示由插件定 |
| `ItemView` 基类 | 自定义视图继承 `ItemView`，必须实现 `getViewType()`（唯一字符串 id）、`getDisplayText()`（人读名字）、`onOpen()`（构建内容）、`onClose()`（清理） | 面板内容的四件事写清 |
| 视图注册 | 插件 `onload()` 里 `this.registerView(VIEW_TYPE, (leaf) => new MyView(leaf))`；第二个参数是**工厂函数** | 懒创建，宿主可多次调用 |
| 面板放置 | `workspace.getRightLeaf(false)` 拿一个右侧的新 leaf → `leaf.setViewState({type, active:true})` → `workspace.revealLeaf(leaf)`（侧栏折叠时要 reveal） | 面板放右/左栏、并自动展开 |
| 已有视图复用 | `workspace.getLeavesOfType(VIEW_TYPE)` 找已存在的同类型面板，有就复用 | 不重复开面板 |
| 官方警告 | **不要在插件里自己持有视图引用**；宿主可能多次调用工厂函数；访问实例一律走 `getLeavesOfType()` | 少一类难查的状态 bug |
| 缎带按钮（ribbon） | 左侧 ribbon 的唯一用途就是「承载插件定义的动作」；`this.addRibbonIcon('dice', 'Print to console', () => {...})`（图标名、提示文字、回调） | 给功能一个固定按钮位 |
| 图标 | 参数一指定图标名；可自定义图标（见官方 Icons 文档） | 视觉识别 |
| 按钮的最佳实践 | 官方：**用户可以把你的图标从 ribbon 移除，甚至整条 ribbon 隐藏**，所以应同时提供别的入口（例如命令） | 入口不能只有一种 |
| 插件加载方式 | 放到 vault 的 `.obsidian/plugins/<插件目录>`，目录里有编译产物 `main.js`；在 设置 → 社区插件 打开开关才加载 | 本地开发/自装插件 |
| 插件清单 | `manifest.json`：`id`、`name`、`version`、`minAppVersion`、`description`、`author`、`authorUrl`、`fundingUrl`、`isDesktopOnly` | 一份小清单描述插件 |
| 命令 | ribbon 页提示「应创建命令作为替代入口」；**官方 Commands 文档页当日返回「页面不存在」**，命令 API 名本文未核实（见⑤） | 命令面板式入口 |

### ③ 「接入 Agent / 加按钮 / 加扩展」的机制怎么运作

- **机制名**：**插件（Plugin）+ 视图注册（registerView）+ 缎带动作（addRibbonIcon）**。
- **加一个面板**：定义 `VIEW_TYPE = 'example-view'` 常量 → `class ExampleView extends ItemView` 实现四个方法 → 在 `onload()` 里 `registerView(VIEW_TYPE, factory)` → 需要显示时 `getRightLeaf` / `setViewState` / `revealLeaf`。视图在 `onOpen()` 里用 `this.contentEl` 构建内容（示例用 `container.createEl('h4', {text: 'Example view'})`）。
- **加一个按钮**：`this.addRibbonIcon('dice', 'Print to console', () => { ... })`，一行搞定；但官方明确要求**同时提供命令等替代入口**，因为用户可以移除图标或隐藏整条 ribbon。
- **注册/清理生命周期**：面板与按钮都在插件 `onload()` 注册、`onunload()` 时清理由宿主统一处理（示例 `onClose()` 留空表示无需清理）。
- **面板是「叶子」不是「页面」**：同一视图类型可以同时存在多个 leaf，也可以被拖到任意分栏；插件不能假设只有一份。
- **接入 Agent**：**未找到一手来源**表明 Obsidian 有「把 Agent 登记进界面」的机制。它只提供了「视图 + 按钮 + 命令」这套 UI 扩展点；要接 Agent 得自己在插件里实现。

### ④ 可抽象成我们工作台的一个「模式」

- **模式名**：**可拖拽面板工作台模式（视图 + 缎带按钮）**
- **界面形态**：最左一条窄按钮带（每个功能一个图标，可被用户隐藏）；中间是可左右分栏、可拖拽的工作区；每个面板是一个「视图实例」，可放左栏、右栏或中栏，可并列多个；点缎带按钮 = 打开/聚焦对应面板（没有就新建，有就 `reveal`）。
- **要接的后端接口**：
  1. `视图类型注册表`：`{viewType 唯一字符串, 显示名, 图标, 工厂函数}`
  2. `面板打开`：`openPanel(viewType, 目标位置)` → 返回 leaf id；已存在同类型则激活
  3. `面板内容`：视图挂载时向后端请求数据（按 viewType + 参数）
  4. `动作回调`：缎带按钮/命令 → 前端调后端动作 → 后端返回「打开哪个面板」或数据
- **要抄的一点**：**注册的是「视图类型 + 工厂函数」，不是「视图实例」**，并且访问实例一律通过宿主查询。我们做拖拽自定义界面时，直接照抄这条能省掉一整类同步问题。

### ⑤ 来源 URL
- https://docs.obsidian.md/Plugins/User+interface/Views （`ItemView` 四个方法、`registerView` 工厂、`getRightLeaf`/`setViewState`/`revealLeaf`、`getLeavesOfType`、「不要持有视图引用」警告）
- https://docs.obsidian.md/Plugins/User+interface/Ribbon+actions （`addRibbonIcon(图标, 提示, 回调)`、ribbon 的用途是承载插件动作、用户可移除图标或隐藏 ribbon、建议同时提供命令）
- https://docs.obsidian.md/Plugins/Getting+started/Build+a+plugin （插件放 `.obsidian/plugins/`、编译产物 `main.js`、在社区插件里开启才加载）
- https://raw.githubusercontent.com/obsidianmd/obsidian-sample-plugin/master/manifest.json （清单字段：id/name/version/minAppVersion/description/author/authorUrl/fundingUrl/isDesktopOnly）

# 三、本组启示

## 3.1 值得抄的（5 条）

1. **界面从清单里长出来，不要写死在代码里。**
   VS Code 的 38 个贡献点、Raycast 的 `commands`、Obsidian 的 `registerView` + `addRibbonIcon`、LobeChat 的 `manifest.json` 是四种写法、同一个思路：**「加按钮/加面板」= 加一条声明**。我们做「按 VS Code 插件方式加按钮入口」时，最小可用集就是三张表：命令表、视图（面板）表、菜单/入口挂点表。来源：VS Code 贡献点文档、Raycast 清单文档、Obsidian Views/Ribbon 文档、LobeChat 插件清单文档。

2. **「连接」与「角色」分成两层登记。**
   Open WebUI 是「连接（URL + Key）+ 模型预设」；Jan 是「服务商 + 助手」；Cherry Studio 是「服务商 + 助手/Agent」。三家都做了同一个切分：**接入信息只登记一次，界面上的每个角色复用同一份接入信息**。我们的工作台也应把「Agent 后端怎么连」与「这个模式叫什么、用什么提示词、挂哪些技能」彻底分开。来源：Open WebUI Connecting / Workspace Models、Jan custom-endpoint / assistants、Cherry 自定义服务商 / Agent。

3. **外部 Agent 一律先按「一个 OpenAI 兼容端点」进来。**
   Open WebUI 官方原话：因为 Agent 框架大多暴露 OpenAI 兼容 API，所以「加一个 URL 和 API key 就行，**不需要插件、管道或中间件**」，并已列出 Open WebUI Computer、Hermes Agent、OpenClaw 三个样板；Cherry Studio 的编码搭档则提供了另一种形状：**界面负责安装/选模型/选目录，点一下在终端里启动 CLI**。我们的「将来接 Claude Code、CodeBuddy」两条路都有人走过：能暴露端点的走端点，不能的走「登记启动参数 + 选工作目录 + 启动」。来源：Open WebUI Connect an Agent、Cherry 编码搭档。

4. **审批先于自动化，而且审批要长在调用点上。**
   Cherry Studio 给了五档权限（逐次确认/自动接受编辑/智能批准/仅规划/完全访问）；Open WebUI 把待批准的工具调用挂在消息上（刷新页面仍在）；Jan 把审批面板**内联在工具卡片里**，显示模型要传的确切参数。三家都不是在设置页做一个总开关了事。来源：Cherry 权限模式、Open WebUI Tools 审批、Jan MCP。

5. **工作区 = 一份可复制的配置单，且带一个对外可见的 id。**
   AnythingLLM 的 workspace 把「系统提示词 / 模型覆盖 / 检索参数 / 文件」打包成一份结构化配置，`slug` 同时是 API 路径、浏览器 URL、向量库命名空间；设置优先级是「工作区字段非空则用，空则回落全局」。这套「一份配置 + 一个 id + 三层回落」正好可以当我们「模式」的骨架。来源：AnythingLLM 工作区文档、Jan 的 Projects、Cherry 的任务与工作目录。

## 3.2 明确不适合我们的（5 条）

1. **不做插件市场 / 社区一键导入。**
   Open WebUI 用整页警告写死了：Tools/Functions 是任意 Python 代码在服务器上执行，**社区列表是用户提交且未经审核**，官方直接说「被推荐/热门 ≠ 审核过」，并要求导入前逐行看代码。我们只给自己和朋友用，做市场 + 审核的成本完全收不回来。来源：Open WebUI 插件页安全警告。

2. **不做「服务端执行任意代码」的插件模型，也不做 iframe 插件界面。**
   Open WebUI 的插件是 `exec()` 加载 Python 源码到服务器内存；LobeChat 支持 `ui.mode = iframe` 在对话里嵌一块网页。前者是安全与调试成本，后者是与宿主主题/快捷键/状态同步的成本。我们的扩展点用「清单 + 本地进程/HTTP 接口」就够，不需要宿主执行任意代码。来源：Open WebUI 函数加载机制、LobeChat manifest 的 `ui` 字段。

3. **不要照抄 Open WebUI 的四类函数抽象（Pipe/Filter/Action/Event）。**
   四类里我们真正需要的只有一类：**Action = 在消息/面板上加一个按钮**。Filter（在请求前后拦截）和 Pipe（把任意 Python 变成"模型"）是平台方为兼容各家协议才需要的。来源：Open WebUI 函数页四类分工。

4. **不要把 RAG 参数塞进通用的「模式」配置。**
   AnythingLLM 的工作区有 `similarityThreshold`、`topN`、`chatMode`、`vectorSearchMode` 等字段——因为它的每个工作区都是检索型场景。我们的「模式」不都是 RAG（还有画布型、命令行型），把这些参数做成通用必填会让所有模式都变重。做法：只保留「挂了哪些资料」这一个通用字段，检索参数下放到具体模式自己的配置区。来源：AnythingLLM 工作区字段表。

5. **不要一上来就抄 VS Code 的全套贡献点。**
   官方列了 38 个贡献点（从 `languages` 到 `semanticTokenTypes`）。多数是编辑器/语言生态专用（`grammars`、`debuggers`、`breakpoints`、`problemMatchers`、`typescriptServerPlugins`…）。先做三个：**命令、视图容器+视图、菜单**；AI 相关只做**一个「Agent 贡献点」**（对应 `.agent.md` 那条路）。来源：VS Code 贡献点全表。

（补充注意项，不算「不适合」但需先决定：Raycast 的 `menu-bar` 模式与 `interval` 后台命令依赖「宿主常驻」这一形态；如果我们不是常驻类应用，先不做常驻项与后台定时。来源：Raycast 清单文档的 `mode` 与 `interval`。）

## 3.3 特别关注：一个 Agent / 模型「被登记进界面」的最小信息是什么

把八款产品的登记字段并排看，能提炼出一个最小集合。**来源逐项可查**：

| 我们要的字段 | 各产品里的对应字段（原文） | 来源 |
|---|---|---|
| 名称（给人看） | Cherry 助手：名称；Open WebUI：Name；Jan 助手：name；Raycast 命令：`title`；VS Code 扩展：`displayName`；LobeChat：`meta.title` | 各产品文档（见下） |
| 唯一标识（给代码用） | Open WebUI：ID；AnythingLLM workspace：`slug`；Raycast 命令：`name`「唯一 id…直接映射到入口文件」；VS Code 扩展：`name`（必须唯一）；Obsidian：`id`；LobeChat：`identifier`；Cherry 技能/小程序：包内 id | 同上 |
| 图标 | Open WebUI：Avatar（支持 GIF/WebP）；Raycast：`icon`（512×512 png，`@dark` 支持深浅色）；Cherry 助手：图标；LobeChat：`meta.avatar`；VS Code：贡献点里的 `icon`（容器与视图各有） | 同上 |
| 说明文字 | Cherry 助手：描述；Open WebUI：Description；Raycast：`description`（必填）；LobeChat：`meta.description`；Jan 助手：description | 同上 |
| **接口地址** | Jan：`Base URL`；Cherry：API 地址（默认根地址，自动补 `/v1/chat/completions`）；Open WebUI：连接里的 URL | Jan custom-endpoint、Cherry providers、Open WebUI Connecting |
| **鉴权** | Jan：`API key`（本地无鉴权也要填非空占位）；Cherry：API 密钥（可多把轮询）；Open WebUI：API Key；Raycast：`preferences` 的 `password` 类型 | 同上 |
| **协议类型** | Jan：`API 格式`（OpenAI 兼容 / Anthropic 兼容）；Open WebUI：连接协议（Ollama / OpenAI 兼容 / Open Responses）；Cherry：端点设置（OpenAI / Anthropic / OpenAI Responses / Gemini / 图像 Base URL） | 同上 |
| **模型 ID** | Jan：按服务端期望的 ID 原样填（`llama-3.1-8b-instruct`），并**逐模型标能力**（工具/视觉/音频）；Cherry：模型 ID + 名称/类型/价格，且「只有加入列表的模型才出现在选择器里」；Open WebUI：Base Model | 同上 |
| 参数 | Jan：温度、top-K、top-P、min-P、重复惩罚（本地与自定义服务商可见）；Open WebUI：参数覆盖；LobeChat 插件：`settings` 用 JSON Schema 描述要填什么 | 同上 |
| 入口 / 触发方式 | Raycast 命令：`mode`（view/no-view/menu-bar）+ `arguments`；VS Code：`commands` + `menus` + `activationEvents`；Obsidian：`addRibbonIcon` 的回调；LobeChat：`ui.url`；Cherry 小程序：安装后的网格图标 | 同上 |
| 可见范围 / 开关 | Open WebUI：Visibility（私有到指定用户/组，或公开）+ 启用；Cherry：服务商启用开关；Raycast：`disabledByDefault`、`access`（public/private） | 同上 |
| 可选的「能力清单」 | AnythingLLM 技能：插件名（如 `web-scraping`）；Open WebUI 工具：名称 + 参数 schema + 说明；Cherry Agent：内置工具分类开关 + 知识库 + 技能 + MCP 四组绑定 | AnythingLLM skills、Open WebUI Tools、Cherry tools-knowledge-skills-mcp |

**最小可落地结论（我们的登记模型）**：
一条「Agent/模型登记」至少要有 **唯一标识 + 名称 + 图标 + 协议类型 + 接口地址 + 密钥 + 模型 ID 列表（每项可标能力：工具/视觉/音频）+ 启用开关**；再加上两层可选的「角色层」（系统提示词、挂哪些技能/工具/知识库）与「入口层」（从哪触发：命令面板/面板/按钮）。前 8 项是接入信息，后两层是界面信息——**这正是本组所有产品共同的切法**（Open WebUI 的「连接 vs 预设」、Jan 的「服务商 vs 助手」、Cherry 的「服务商 vs Agent」）。

**注**：上表每个字段名都取自对应产品的官方文档或官方仓库（Raycast/VS Code/Obsidian 为官方开发者文档；LobeChat 为官方仓库文档源码；Open WebUI / Jan / Cherry 为官方文档站；AnythingLLM 为官方文档镜像站的正文原文）。凡未能指认字段名的项目，本文没有列入。
