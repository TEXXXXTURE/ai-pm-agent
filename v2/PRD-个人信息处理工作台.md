## 一、背景与问题

使用公共软件（Notion、ClickUp 等）处理个人工作的前提，是先学会那个软件本身，这已经是绕路。不同的人反复处理的是同类信息，真正需要的不是某一款现成应用，而是**按自己的工作习惯固定下来的信息处理方式**：信息从哪来都行，处理过程和产出结构不变。

## 二、产品定位与目标

**一句话定位**：个人信息处理工作台——一个帮人处理信息的工作站：把信息收进来，按固定方式处理，产出固定结构的几样东西。

- 「模式」不是一种界面样式，而是**一种固定的信息产出结构**。例如「回复盘」模式，无论输入是什么，产出永远是三栏：解决了什么问题、学到了什么、有什么待办；
- **输入端可以换**（屏幕上的文字、聊天记录、网页、订阅源、本地文件），处理方式和呈现方式不变；
- 产品不售卖，供自己、朋友和社区使用，自定义空间优先。

## 三、目标用户

- 有固定信息处理习惯、想把这套习惯固化下来的个人；
- 典型场景：流程、看板、行程安排、会议纪要、复盘。

## 四、真实案例（需求来源）

1. **截屏复盘**：一名外包从业者每天用 AI 处理大量信息、产出大量内容，需要复盘，但翻聊天记录又费钱又费精力。实际做法是「截取屏幕上的信息 → 总结拆解」，实测好用，产出固定三样：解决了什么问题、学到了什么、有什么待办；
2. **模型动态**：另一名用户把 HuggingFace 上的模型信息做成「大批模型总结」加「新模型发布提示」。

两个案例的共同形状：**信息收进来 → 按固定方式处理 → 产出固定几样**，换输入不换结构。

## 五、产品范围

### 5.1 做

1. 预设方案：以普通文件夹为载体的完整信息处理方案；
2. 工作台内置的两件基础能力：格式翻译器、文件解释器（渲染器）；
3. 界面声明：给普通文件夹加一份声明即可得到能看能点的极简界面；
4. 模式的保存、复制与分享机制；
5. 从 32 款现成产品调研中提炼的积木：8 种界面形态、7 张登记表（按需取用，不照搬产品）。

### 5.2 不做

1. 不做 Notion、ClickUp 那类厂商式工作台，不预置一套模式让用户学；
2. 模式库不由我们预先制作，由用户在实际使用中自己攒出来；
3. 不自己造工具轮子：格式转换、文件渲染、视频制作等全部使用现成工具，我们只做登记和拼装；
4. 不提前设计「翻译不了的格式」怎么处理，登记为「需要 Agent 出面」即可。

## 六、产品方案

### 6.1 预设方案 = 一个普通文件夹

文件夹内包含四样：

| 内容 | 说明 |
|---|---|
| 说明书 | 这是什么、输入是什么、每步做什么、产出是什么、缺什么就停下来问（人和 Agent 都能读） |
| 每步的做法 | 提示词或脚本 |
| 产出模板 | 固定结构的产出样式 |
| 入口 | 启动处理的方式 |

方案对外只通过两样打交道：**输入**（一份需求描述，可附一个素材文件夹）和**输出**（固定结构的几份文件）。中间怎么实现，外部不需要知道。

### 6.2 独立可搬运的三个条件

1. **接口薄**：对外只有输入和输出，中间实现可随时替换；
2. **依赖是引用，不是内容**：方案里只写「这一步需要什么能力的工具」，不把工具打包进来，谁运行谁按登记去取（先例：Docker 引用镜像名、GitHub Actions 的 `uses:`、本项目外置工具路由表）；
3. **一份人和 Agent 都能读的说明书**：Agent 读完即可执行。

### 6.3 工作台唯一内置的两件能力

#### （1）格式翻译器

把各种格式互相转换（文件 → 能显示的结构）。

- 现实工具不用自己写：Pandoc（文档格式互转）、ffmpeg（音视频）、ImageMagick（图片），工作台只登记「什么类型 → 用哪个工具」并做调度；
- 只做**规则明确、可以机械验证**的转换（有公开格式规范的）；
- 做不到的不硬做：显示原件并说明缺什么，需要判断的交给 Agent 处理，不塞进翻译器。

#### （2）文件解释器（渲染器）

把文件按类型画出来给人看：Markdown、JSON、表格、图表、流程图/思维导图、图片、音视频、PDF。

- 全部使用现成渲染库（Markdown 渲染、JSON 树、表格、ECharts、Mermaid、PDF.js、播放器等），工作台只登记；
- 缺少渲染器时降级为「显示原文 + 提示缺什么」，不假装能渲染。

两件能力与外置工具路由表是同一个套路：登记「有什么、装没装、怎么调」，翻译器和渲染器只是在这张表上多两栏。

### 6.4 界面声明（「简单加工」）

- 给文件夹加一份**界面声明**：哪个文件用什么方式显示、有哪几个按钮、按什么顺序看；
- 工作台读到声明，就能把这个文件夹画成一个能看能点的极简工作台；
- 不加声明，文件夹仍是一个能独立运行的方案；
- 声明跟随方案文件夹一起走，不是工作台私有的东西。

### 6.5 模式的保存、复制与分享

- 一个模式 = 用户某次把需求说清、Agent 把现成工具拼好、跑出固定结构产出之后，**存下来的那一份**。下次同类需求直接套用；
- 模式的最小字段（参照 AnythingLLM 做法）：一份可复制的配置单 + 一个对外可见的 id + 三层回落（模式自己的设置 → 上层默认 → 全局默认）；
- 模式可以复制、分享，也可以被 Agent 读写；挂进工作台 = 登记一条，搬走 = 拷走文件夹，两种用法互不影响。

### 6.6 Agent 的角色

Agent 负责划边界、挑选网上现成的轮子并拼装，不自己造轮子。用户用自己的话说需求，Agent 把需求拆成几条现实的边界，找现成工具拼起来跑出固定产出。具体问题用具体工具解决，只有「收进来 → 处理 → 固定产出」这个形状由产品自己定。

### 6.7 第一个候选样板：自媒体六步

| 步 | 做什么 | 输入 | 产出 | 承担 | 工具 |
|---|---|---|---|---|---|
| 1 | 信息收集 | 话题或关键词 | 素材清单（标题 + 链接 + 摘要） | 检索脚本 + 摘要提示词 | web_search.py、page_fetch.py（已有） |
| 2 | 选题收集 | 素材清单 | 选题表（选题 + 理由 + 目标读者 + 预判热度） | Agent + 提示词 | 无 |
| 3 | 文案撰写 | 选中的选题 | 文案稿（Markdown） | Agent + 提示词 | 无 |
| 4 | 视频制作 | 文案稿 | 分镜/脚本 + 视频成品占位 | Agent 出分镜，成片靠外部工具 | 待选 |
| 5 | 配音 | 文案稿或分镜 | 音轨文件 | 外部工具 | 待选 |
| 6 | 剪辑 | 视频素材 + 音轨 + 分镜 | 成片 | 外部工具 | 待选 |

第 4–6 步的工具尚未选择，方案里先只写「要什么产出」。

## 七、三条硬边界

1. **界面声明必须是最普通的格式**：JSON 或 YAML + 一份公开说明 + 版本号。不允许各方案各造一套声明格式；
2. **原件永远是第一真相源**：翻译和渲染都只是「看」的副本，翻译有损耗，改内容必须改原件，不能拿翻译结果当原件；
3. **翻译范围不提前设计**：先把规则明确的做掉，其余登记成「需要 Agent 出面」。

## 八、调研积木（32 款现成产品的提炼）

- **8 种界面形态**：对话框、画布、可停靠面板、表格、看板、大纲/列表、收件箱/分诊台、项目页（一页挂几个卡片）；
- **7 张登记表**：连接、角色、入口、视图定义、模板、规则、审批；
- 这两层只当积木使用：同一套固定产出可以换不同界面呈现，不照搬任何一款产品；
- 调研同时明确了 11 条不做（插件市场、自造格式、把位置坐标混进逻辑定义、多租户等）。

## 九、验收标准

1. 任一模式 = 一个普通文件夹，把文件夹拷给一个**未安装本工作台**的命令行 Agent，它读完说明书能跑出同样结构的产出；
2. 每个方案对外只有输入和输出，中间实现可替换；
3. 所需工具以引用方式登记，不打包进方案；
4. 工作台内置只有格式翻译器和文件解释器，且只处理规则明确的转换和渲染；处理不了时显示原件并说明缺什么；
5. 界面声明为普通 JSON/YAML 并带公开说明和版本号，跟随方案文件夹；不加声明的文件夹仍可独立运行；
6. 原件是唯一可编辑的真相源，翻译和渲染产物不能作为编辑源；
7. 模式可复制、可分享（配置单 + 对外 id + 三层回落）。

## 十、下一步与待确认问题

### 10.1 下一步

等用户提供个人工作台的实际案例（截图、链接、当时的做法均可），按「原来怎么处理 → 固定产出是什么 → 对应哪个模式」整理，再与界面形态积木对接。验证目标是拿一个真实需求走完整条链：用户说需求 → Agent 拆边界 → 找现成工具拼装 → 跑出固定产出 → 存成模式。「截屏复盘」可作为第一个例子。

### 10.2 待用户拍板

1. 自媒体第 4–6 步：方案里只写产出要求，还是连具体工具一起选定？
2. 自媒体六步是否就作为第一个样板先填满？
3. 说明书沿用现有技能文件的写法，还是另定一份更短的模板？

## 十一、与「统一前端工作台」的关系

两个产品独立。本产品不依赖统一前端工作台动工：文件夹本身可独立运行。若未来有统一前端一类的外壳，可通过本产品的界面声明获得可视化，方案文件夹不需要为此改动一个字。
