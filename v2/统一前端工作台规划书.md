# 统一前端工作台规划书（Workbench）

> 日期：2026-09-18（S054）
> 状态：**规划阶段，未动工**。启动时机=流水线 Agent 完结 + 内部优化（Pi/对话 Agent 层）完成之后。
> 性质：本项目「外层可拓展」的最终形态——**一套前端，接入所有 Agent**。

## 一、背景与目标

### 1.1 为什么做
- 后端（流水线 Agent + 综合对话 Agent）做完后，各自只有 CLI/内部接口，**没有一个统一的、面向人的操作界面**。
- 现状：对话 Agent 用对话框、流水线 Agent 用命令行——**每加一个 Agent 就要配一个前端**，重复且割裂。
- 目标：**一套统一前端工作台**，以后任何 Agent（流水线 / 对话 / 外部新 Agent）**只需接入，不再单独做前端**。

### 1.2 核心思想（S054 用户定调）
- **两个 Agent 只是内部不同的「输入接口 + 输出接口」**：用户把问题/信息放输入接口，Agent 处理完从输出接口给出。内部是什么形态（有没有循环、有没有内核）不重要。
- **前端按 Agent 功能用不同 UI 展示**：对话式 Agent → 对话框；流水线 Agent → **画布式**（每个步骤可看、可调）。

## 二、工作台形态

```
┌─ 工作台（统一前端）────────────────────────┐
│                                            │
│  [对话框]（对话 Agent）   [画布]（流水线 Agent）│
│   · 聊天输入/输出         · 节点+连线可视化     │
│   · 接入对话型 Agent      · 每步可看可调        │
│                                            │
└────────────────────────────────────────────┘
        │                        │
        ▼                        ▼
  综合对话 Agent            流水线 Agent（20 节点）
  （中层，灵活）            （内层，确定性）
```

- **对话框**：对话式 Agent 的 UI（聊天交互）。
- **画布**：流水线 Agent 的 UI（节点 + 连线，拓扑可视化）。
- **一套前端，两种形态**，按 Agent 类型适配；**新增 Agent = 接入这套前端**，不做新前端。

## 二·补、按钮可插拔（VS Code 插件模式，S054 定调）

- **不是整个前端可定制**：工作台是**固定壳**（对话框 + 画布 + 侧边栏等，我们设计好）。
- **可拓展的是「按钮/入口」**：像 VS Code 装插件后左侧出现新图标——工作台可**添加按钮**，每个按钮 = 一个功能/Agent/工具的入口 = **前后端接口**。
- **按钮不是手动绘制、不是画原型生成**：是**预定义的、可插拔的入口**——登记一个按钮定义（图标/名称/连哪个接口/什么语义）→ 出现在工作台。
- **加按钮 = 登记一个新入口**，与「外置工具路由表加一行」（references/外置工具路由.md）同构：加工具=路由表加行，加按钮=工作台入口定义加一条。
- **给 Agent 的规则**：操作者大概率是 agent → 写规则告诉 agent「加按钮 = 在入口定义文件加一条」，不用画界面、不用改前端壳。

## 三、画布式可视化（流水线 Agent 的 UI）

### 3.1 画布是什么
- 流水线 20 节点（见 `references/流水线模块拓扑清单.md`）= 画布上的**节点块**。
- 节点间边（线性/条件）= 画布**连线**；条件边标注路由条件（如「ai_core → AI 轨」）。
- 节点可调参数（prompt/阈值/及格线/config）= 画布节点上的**可调旋钮**。

### 3.2 画布的两种用途
1. **查看**：运行时可看当前走到哪个节点、每步输入输出（状态可视化）。
2. **调整**：改参数（旋钮）、改拓扑（连线）、**挂外部模块（skill/工具）到节点**——见 3.3。

### 3.3 核心价值：解耦 → 模块可中途插入
- 现有节点通过 `deps`（节点依赖容器）拿一切（registry 提示词 / runner / tool_catalog 工具），**节点结构不关心提示词从哪来、工具是谁装的**。
- 因此**换/增强某个节点的能力 = 换它的 prompt 或往 deps 挂外部 skill/工具，不动其他节点**。
- 例：评审需求（prd_review）节点 → 找一个**外部 skill 增强评审能力** → 在画布上把该 skill 挂到评审节点 → 评审变强，**其余 19 个节点零改动**。
- **这就是解耦的回报**：改动面小、测试范围小、回归风险低，Agent 改单个小模块远比改整体轻松。

### 3.4 画布与 Agent 的分工（关键机制）
- **人不直接改代码**：人在画布上摆/连/调（或用文字附注）→ 前端把画布翻译成**结构图（节点+边+参数，序列化 JSON/拓扑文本）**。
- **Agent 读结构图**（不是读像素）→ 定位对应源码模块（靠 `references/流水线模块拓扑清单.md`）→ **改单个模块**（或派单改）。
- 画布最终产出的是一份**改造说明书**，Agent 照它改 `src/`；流水线跑的仍是代码（不是画布 JSON）。
- 参考先例：`tool_catalog` 把工具表注入 prompt（结构化信息喂 Agent）；n8n/Dify/ComfyUI 的画布→JSON→引擎（业界标准）。

## 四、多 Agent 接入（工作台的扩展性）

- 工作台 = **前端壳**，不绑定具体 Agent。
- **接入协议**（规划）：每个 Agent 暴露「输入接口 + 输出接口」→ 工作台按类型选 UI（对话/画布）→ 内部实现细节对用户透明。
- 新增 Agent（外部新 skill / 新对话 Agent / 集群里的 Agent）= 接输入输出接口，**复用这套前端**。
- 与「外置工具路由表」（references/外置工具路由.md）配合：工具/技能登记后，工作台可发现、可挂到画布节点。

## 七、与现有体系的关系

- 不推翻流水线：画布是「看它/改它」的新入口，流水线照跑。
- 与「拓展规则」（references/ 告诉 Agent 怎么改文件）互补：文字版 vs 图形版怎么改。
- 与三层架构（workflow-design.md 第 0 条）一致：工作台属**外层（可生长）**，Agent 属**中层（灵活）**，流水线属**内层（稳定）**。
- 与演示外置不冲突：工作台是开发/运维界面，演示物仍走外置工具包。

## 八、调研取证（2026-09-18，web 实查）

> 本概念（前端=可视化发需求/展示返回，后端=计算推理，接口匹配即换；按钮=前后端接口）有现实趋势支撑，不是空想。以下是实查到的业界现状与对本项目的启示。

### 8.1 「画原型 → 生成代码」：成熟，但**不是本项目路径**

- **工具现状**：Figma → code（Builder.io Visual Copilot、Locofy、Anima）、prompt → code（v0 by Vercel、Bolt、Lovable）、AI coding agent + Figma MCP。
- **硬边界（Reddit/design engineer 共识）**：**没有工具能产出生产级干净代码**。原因是「Figma 文件缺结构/规则（无设计 token、无组件命名、absolute positioning）→ 输出是 div soup，不是组件架构」。**修复不是更好的插件，而是更好的设计契约**（design contract：token + 规则 + 组件映射）。
- **对本项目的启示（修正）**：本项目**不走「画原型 → 生成整个前端」**——工作台是固定壳，只加按钮（见 8.2）。但「设计契约」教训仍适用：**加按钮 = 定义一个接口契约**（按钮连哪个接口、什么语义），否则按钮只是装饰。

### 8.2 「按钮 = 前后端接口」：低代码平台已验证 + **VS Code 插件模式是正解**

- **Retool / Appsmith / Budibase / ToolJet**：拖组件（按钮/表格/表单）→ **绑定数据源/查询**（REST API、DB、JS 表达式）→ 组件即接口。Appsmith「widget 绑定 queries 和 JS」、Budibase「按钮触发查询」。
- **VS Code 插件模式（用户定调，S054）**：**不是整个前端可定制**——工作台是固定壳，可拓展的是「**添加按钮/入口**」，像 VS Code 装插件后左侧出现新图标。每个按钮 = 一个功能/Agent/工具的入口 = 前后端接口。
- **对本项目的启示（修正）**：我们的「按钮 = 联通前后端的接口」** = 低代码的「组件绑定」+ VS Code 的「插件加入口」**。按钮**不是手动绘制**，是**预定义的、可插拔的入口**（登记一个按钮定义 → 出现在工作台）——**加按钮 = 登记一个新入口**，与「外置工具路由表加一行」同构（见第五节）。接的是 Agent/流水线节点（不只 REST/DB），这是我们的差异点。

### 8.3 「画布/结构图喂给 Agent」：graph-as-context 先例

- n8n/Dify/ComfyUI：画布（节点+连线）→ **序列化成 JSON/API format** → 后端引擎按图执行；**Agent/引擎读的是结构图（JSON），不是像素**。
- ComfyUI 的「Save Format vs API Format」：UI 元数据（位置/颜色）不进执行 JSON，只留结构（节点 id + class_type + inputs 连线）。
- 对本项目的启示：我们的「画布 → 结构图 → Agent 读图改代码」**完全可行**，Agent 读的是图的结构描述（节点+边+参数），不是渲染的图。

### 8.5 「按钮打开后的界面原型可自由定制」（用户需求，S054）：有现成方案，难度中低

> 用户：按钮打开后的界面原型要像 Figma/墨刀那样**靠组件拖拽实现**，可自由定制。不知道难度与现成方案。以下为 web 实查（2026-09-18）。

**现成方案（开源、自托管、MIT）：**

| 方案 | 是什么 | 匹配度 |
|---|---|---|
| **Puck** | 开源可视化页面编辑器，React 组件，**嵌入你的应用**；拖组件到画布、侧边栏配字段、发布。MIT | **最贴**——「嵌入工作台，让用户拖组件做页面」，正是 Figma/墨刀式 |
| **MUI Toolpad Studio** | 开源内部工具构建器，拖组件（表格/表单/图表）→ 绑 API → 发布页面；MIT | 贴——「拖组件 + 绑后端」，接近「按钮=接口」 |
| **OpenPage** | 开源 AI 网站构建器，拖拽编辑 + AI 生成；**JSON-first**（每次编辑产出可 diff 的 JSON） | 特别贴「Agent 读结构图」——JSON 是唯一真相，AI 和人都能读 |

**关键洞察（OpenPage 理念）**：*「Code generation is fragile... Visual editors lock you into proprietary formats that AI agents can't read. OpenPage gives both humans and AI agents a shared, predictable interface」*——**好的可视化编辑器应该是 JSON-first**：拖拽产生结构化 JSON，不是脆弱代码、不是锁死私有格式。**这印证「画布 → 结构图喂 Agent」**：界面编辑器的产物也应是 JSON（结构），人拖、Agent 读 JSON 改。

**难度判断**：
- **要做的**：选现成方案（Puck/Toolpad/OpenPage）嵌入工作台 → 定义「组件库」（按钮/表单/结果展示组件）→ 组件拖拽生成界面（JSON）→ Agent 读 JSON 定位后端接口。
- **不用做的**：不造拖拽引擎（Puck 已有）、不造界面运行时（React 已有）、不处理布局算法（现成）。
- **难度：中低**——比从零写可视化编辑器低一个量级，主要是「选型 + 适配 + 定义组件库」。

**「交给 vibecoding 工具定制」判断**：可行且有依据。Lovable/Bolt/v0 正是做这类界面（内部工具/仪表盘/页面）的强项——Lovable 全栈生成、v0 前端 UI 最干净、Bolt 浏览器 IDE。工作台界面（含按钮打开的页面）可交给它们生成（描述 → 生成 React 界面 → 对接），我们定义好接口契约（按钮连哪个后端接口）。
**坑（调研共识）**：vibecoding 生成代码「能看能跑、离生产级有距离」，且「私有格式锁定」——**最好用 JSON-first 方案（OpenPage 这类）或让 vibecoding 生成「标准 React + 组件库」**，别生成自创格式，否则 Agent 读不了、改不动。

**结论**：按钮打开界面的可定制（组件拖拽）**有成熟开源方案、难度中低、可交给 vibecoding 生成**；关键是「产物 JSON-first + 接口契约先定义」。

### 8.4 综合结论（对本项目的三条硬要求）

1. **先定义接口契约**（每个节点/Agent 的输入输出口：数量 + 意义）——没有契约，按钮/画布接不上后端。← `references/流水线模块拓扑清单.md` 是雏形，要升级。
2. **按钮的「语义」必须在定义时显式声明**（这个按钮=提交需求/显示评审结果），不能靠 AI 猜——意义对齐是人工定义点。
3. **Agent 读结构图（JSON/拓扑），不是读像素**——画布 UI 是给人编辑的，喂给 Agent 的是序列化结构；按钮同理，登记的是「入口定义」（连哪个接口、什么语义），不是画的图。
