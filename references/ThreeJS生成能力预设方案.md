# Three.js / WebGPU 生成能力 · 预设计划（v0.1，仅计划未实施）

> 性质：下版本能力预设方案。**本文件只写计划，不动代码。**
> 协议正本：《Three.js / WebGPU 视觉内容生成的工程化方法 v1.0》（用户与 Agent 讨论产出，暂存 `D:\AgentHub\Hermes\output\ai-pm-agent实测\新建文本文档 (2).txt`，含 phase-gates / state-contract / judgment-ladder / param-schema / critic-spec / failure-modes 基准版条目）。
> 计划要回答的三件事：**RAG 怎么建怎么调、提示词怎么改、Agent 拿到什么执行方案**。

## 一、问题与目标

**问题**：用大模型生成 Three.js / WebGPU 页面，稳定失败形态是「代码能跑但画面不对、黑屏无报错、切场景显存泄漏、帧率不达标、反复改却定位不了」。根因不是模型弱，是工作模式错配：一次性输出 = 零反馈走长链路 = 错误全累积到最后。另一重问题是**资料新旧混杂**——模型把往年写法和新 API 混在一起，产出被拉向平均线（r160–r185 之间 WebGPURenderer / TSL / NodeMaterial / 异步初始化变动多轮，旧代码粘进来是静默错误）。

**目标**：靠三件套把「可量化的质感」收编为显式约束，让 Agent 在收窄的空间里执行——
1. **design 固定**：风格与参数固化成规格（硬约束 + 区间旋钮 + 排除项），审美从生成层搬到选择层；
2. **RAG 正/负参照**：官方资料 + 社区正确源码（正向）与错误源码 / 失败模式（负向）入库，检索时先过阶段与版本两道硬过滤；
3. **阶段协议**：分阶段门禁 + 状态外置 + 自检协议，替代一次性输出。

**边界（诚实）**：着色器数学推导、审美生成层的先验、长链路状态管理三处差距本方案不承诺解决——前者靠参照与人工，后两者靠协议补偿。没有任何公开基准测 Three.js 生成能力，效果验收只能自建（参考截图 + 参数区间 + 人工盲评）。

## 二、RAG 侧：建库与调用

### 2.1 两类来源，四种资产

| 资产 | 来源（用户点名的两类参照） | 性质 | RAG 能补多少 |
|---|---|---|---|
| 数学 / 着色器 / API 硬知识 | **官方资料**：docs、manual、examples、migration guide、release notes | 硬知识，有唯一正确答案 | 几乎全补，投入产出比最高 |
| 正向参照源码 | **社区正确源码**：官方 examples、精选项目片段（必须带版本与上下文） | 可运行范式 | 补大半 |
| 负向参照（负面知识） | **社区错误源码 / 旧写法** + 失败模式库（现象→可能原因→证伪→修复） | 反例 | 补大半；且**折旧最慢**（黑屏原因就那几十种，五年不变） |
| 可量化审美 | 参数表、取值区间、排除项、失败模式对照 | 软约束 | 能；不可量化部分用参考物替代，不存形容词 |

**采集分工**：官方资料走抓取管线（信源对接/monid 取数通道）；社区正/负源码**人工策管为主**（正例要求「完成度高 + 版本可溯」，负例要求「有证伪方法」——没有证伪方法的条目只算猜测，不准入库）。

### 2.2 元数据扩展（对齐现有 17 键契约与切片 v4）

现有 chunk 契约（chunk_type / parent_id / heading_path / quality 权重）之上新增：

```
phase_tags: [基建, 材质, 后处理, ...]      # 适用阶段（阶段路由用）
valid_for_versions: [r183, r184]           # 版本有效性（治新旧混杂的根）
invalid_after: rXXX                        # 过期线
constraint_type: hard | soft | negative    # 硬约束 / 软旋钮 / 负面知识
entity_type: api | param | pattern | failure | script
evidence: { source, url, date, level }     # 证据等级 + 核实日期
last_verified: YYYY-MM-DD                  # 90 天刷新
why_not_the_obvious_way: <正例挂载>         # 为何不采更直观写法——含金量常高于代码
```

**切片补两条规则**（协议 8.3 三个坑）：代码片段必须附最小可运行上下文或前置依赖清单（防「语法正确但全局不兼容」）；正例尽量成对挂反例（防「以为这模式永远成立」）。

### 2.3 检索调用（对齐双路 RRF + 质量乘数，改两处）

1. **硬过滤前置**：阶段过滤（phase_tags ∩ 当前阶段）+ 版本过滤（valid_for_versions / invalid_after）——**宁可少召回，不可召回来错的**；之后才走向量 ∥ 词法双路 + RRF；
2. **去冲突**：同一参数多条命中取值区间冲突时，按 evidence level 与 last_verified 取舍，并在返回里标注冲突供人工介入（对应现有质量乘数的扩展位）。

**负向参照的调用时机**：生成前做「排除项注入」（负提示），生成后进 L2 规则比对（failure-modes 按现象匹配）；不与正向混在同一段上下文里混灌。

## 三、提示词侧改动

### 3.1 design 固定块（风格与参数固化）

- **param-schema 两层**：硬约束写死（Three.js 版本、导入路径、`await renderer.init()`、DPR cap≤2、dispose 配对、prefers-reduced-motion、性能预算）；可调旋钮**给区间与优先级不给单点**（`bloom.threshold ∈ [0.7, 1.0]，优先偏保守`），每个旋钮带硬约束边界；
- **排除项清单**：明确「不要什么」（比说明「要什么」更稳定）；每条必须可二值判定，禁止「不要不好看」式表述；
- **参考资产索引**：参考图/参考站 → 参数快照映射；不存描述性审美形容词。

### 3.2 阶段协议块（反一次性输出）

- 八阶段门禁（Phase 0 规格化 → 7 收口，见执行方案），**交付物必须是文件**（spec.md / state.md / 代码文件），状态外置不靠对话记忆；
- 每轮强制回读顺序：memory-bank（不变契约）→ spec → state → 磁盘实际文件 → RAG 最小充分集；对话历史可丢弃；
- **变更白名单**：每轮带 allowed_files，列表外改动一律失败回滚（禁「顺手优化」）；防假装回读（轮首状态摘要 + 轮尾变更日志，与 diff 不符视为未回读）。

### 3.3 自检协议块（防归因幻觉）

判断前必须取外部信号（截图/控制台/包围盒/FPS/显存）；归因必须可证伪（「若是 bias 问题，调大应改善，否则排除」）；每次只改一个变量；改完重跑同一组检查。**此块写入知识库的收益高于任何审美规则。**

## 四、给 Agent 的执行方案（本计划的最终产出物形态）

**任务路由先行**：有运行时反馈、会反复迭代、多文件的走 pipeline；孤立、有唯一答案的（转换脚本/校验工具）可一 shot；拿不准先走 pipeline，降级单向。知识库内置 task-routing 条目。

**Pipeline 八阶段**（每阶段：交付物文件 → 自动化门禁 → 拍板方 → 失败回退）：

| 阶段 | 交付物 | 门禁 | 拍板 |
|---|---|---|---|
| 0 规格化 | spec.md / 参考资产索引 / 排除项 | 无代码；参考资产≥3 | 人 |
| 1 工程基建 | 目录/构建/renderer 初始化 | 白页可开、控制台零错、降级生效 | 脚本 |
| 2 最小可见闭环 | 相机+占位体+一盏光 | 不黑屏、包围盒在视锥内、FPS 达标 | 脚本 |
| 3 资源管线 | glTF/Draco/KTX2、dispose 配对表 | 模型出现、切场景 N 次内存不增 | 脚本 |
| 4 材质与光照 | 材质映射、光照、N 个差异化候选 | L3 与参考图比占幅/明暗/直方图 | 视觉+人 |
| 5 动画与交互 | easing 表（表达式）、scroll-driven | 表达式可解析、delta clamp、reduced-motion | 脚本+人 |
| 6 后处理调优 | pass 管线、降级路径 | 性能预算、bloom 不溢出 | 脚本+人 |
| 7 收口 | 体积/兼容矩阵/错误态 | 全量回归 | 脚本 |

**判断权四层**：L1 静态检查（脚本，不问模型）→ L2 规则比对（RAG+规则）→ L3 视觉比对（小模型，问「和参考图差在哪」不问「好看吗」）→ L4 人（仅两种情况升级）。**收敛阶段把选中候选反写回 spec 成新锚点**——这是产出靠近自身品味而非通用品味的唯一机制。

## 五、落地清单（分三批，本计划批准后启动）

1. **批 1 · RAG 建库**：官方资料采集 + 社区正/负参照策管（含 failure-modes 十条基准版入库）+ 元数据扩展 + 检索两道硬过滤改造；同步落 L1 验证脚本（成本最低收益最确定）；
2. **批 2 · 提示词模板**：design 固定块 + 阶段协议块 + 自检协议块（param-schema / exclusions 用真实项目填）；用一个真页面跑通 Phase 0–3；
3. **批 3 · 裁判层**：L3 视觉比对（差异定位不打分）+ critic-spec 阈值（从参考资产首轮人工标注得出，不用现成美学评分 API）。

## 六、待拍板（写计划时尚不能代填的）

1. **版本基线五项需人实测**：three_version、webgpu 导入路径、init 签名、toneMapping/outputColorSpace 默认值、shadow bias 安全下限——决定一半硬约束的真假；
2. **项目变量**：性能预算（draw calls/显存/FPS）、目标设备矩阵、排除项、参考资产——填错整份 schema 反向用力；
3. **社区正/负源码的采集范围与版权口径**（只存片段与出处 vs 存全文）；
4. **第一个试跑项目**选哪个页面（建议挑一个带材质光照+后处理的中等复杂度页，覆盖 Phase 0–6）。
