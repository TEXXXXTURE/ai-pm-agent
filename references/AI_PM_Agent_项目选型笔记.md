# AI PM Agent 项目选型笔记

> 本文档记录项目每个关键设计决策的选型过程：面对什么问题、有哪些可选方案、为什么选了这个、放弃了什么。不是结果的罗列，是决策过程的留档。

---

## 选型一：整体架构范式——Workflow 还是 Agent？

### 问题

做一个 PM 工作助手，应该用自主 Agent 架构（模型决定每一步做什么），还是 Workflow 架构（代码定义固定流程）？

### 可选方案

| 方案 | 代表 | 特点 |
|------|------|------|
| 纯自主 Agent | AutoGPT、早期 Agent 实验 | 模型完全自主决定下一步，灵活性最高 |
| Workflow + 模型节点 | Anthropic Workflow 范式、LangGraph | 代码定流程，模型只在特定节点工作 |
| 混合：外层 Workflow + 内层 mini-agent | Anthropic Evaluator-Optimizer 模式 | 外层流程固定，内层节点有自主循环 |

### 我们的判断

**选 Workflow 范式，并且明确说自己是 Workflow，不蹭"Agent"这个词。**

原因：

1. **PM 工作是流程敏感、合规导向的**——交付物需要可验收、可审计、可回溯。纯自主 Agent 的不确定性和业务场景的确定性要求之间有根本矛盾。

2. **固定流程的效率和可靠性远高于自主决策**——PM 日常工作大部分是重复性的、有明确步骤的，枚举流程比让模型自己想更快、更稳、更便宜。

3. **"不够 Agent"不是劣势，是优势**——在业务场景里，"不够自主"意味着"更可控、更可预期、更容易落地"。这不是能力不足，是有意的设计选择。

### 放弃了什么

- 放弃了"开箱即用的灵活性"——纯 Agent 可以不加修改地应对新任务，Workflow 需要为每个新任务写流程
- 放弃了"前沿感"——说自己是 Workflow 不如说自己是 Agent 听上去酷
- 但我们换来了：确定性、可验收性、可审计性、更低的出错成本

### 未来的跨越条件

什么时候值得让模型来决定下一步：**当问题空间的分支变异速度超过了在代码里枚举分支的能力时。**

具体到 PM 场景：
- 需求分类路由 → 类型是有限集，不该跨
- 状态机流转、格式校验 → 刚性判断的天然领地，不该跨
- Pi 承担的柔性任务 → 如果任务本身需要"根据中间结果调整下一步"，可以在节点内嵌 mini-agent，但外层仍保持 Workflow
- 多方协调协商、开放式调研 → 中长期才值得真正跨越

**演进路径**：外层流水线长期保持 Workflow，把自主性收缩到特定节点内部，而不是把整个系统翻成 Agent。

## 选型二：刚性判断和柔性任务的分工

### 问题

工作流里的每一步判断，哪些交给代码，哪些交给模型？

### 可选方案

| 方案 | 做法 | 问题 |
|------|------|------|
| 全模型 | 所有判断都让模型做 | 不确定性高、成本高、不可审计 |
| 全代码 | 所有判断都写死规则 | 无法处理开放式任务，扩展性差 |
| 混合但边界模糊 | 有些地方代码有些地方模型，凭感觉分 | 维护混乱，出了问题不知道是谁的锅 |

### 我们的判断

**按"判断性质"分工，边界清晰：刚性判断交代码，柔性任务交模型。**

| 判断类型 | 执行者 | 判定标准 |
|---------|--------|---------|
| 刚性判断 | 代码 | 规则可以穷举、结果有唯一正确答案、必须 100% 准确 |
| 柔性任务 | 模型（Pi） | 没有唯一正确答案、需要理解和创造、规则无法穷举 |

具体分工：
- **代码管**：流程路由、格式校验、状态守卫、交付物合规检查、数据提取和转换
- **模型管**：调研、起草、总结、创意类工作、开放式问题分析

### 为什么这么分

1. **可审计**——代码判断 100% 可复现，出了问题可以精确复现和调试
2. **成本低**——代码判断零成本，模型判断按 token 计费
3. **边界清晰**——出了问题立刻知道是代码层还是模型层，不会互相甩锅
4. **渐进式优化**——代码规则可以逐步细化，模型能力可以逐步提升，互不干扰

### 这条线怎么画

一个简单的检验标准：**如果这个判断的规则可以写成 if-else 或者正则表达式，就交给代码。如果写完之后发现规则越来越复杂、边界 case 越来越多、多到写不动了，再考虑让模型做。**

而且即使让模型做，也应该是"代码调用模型，代码校验结果"——代码仍然是守门员。

## 选型三：分类体系的选择

### 问题

对外表达（文档、汇报、团队沟通）时，用哪套 Agent 分类术语体系？

### 背景事实

先澄清一个误区：社区流行的"单轮工具调用 → ReAct → Plan-and-Solve → Multi-Agent"四级阶梯，**不是某篇论文或标准定的**，是教程/课程圈把几篇不同论文的名词按"复杂度递增"拼成的叙事。它暗示"越往后越高级"，这对 Workflow 项目会造成不必要的压力。

真正有影响力的权威体系各说各话：

| 体系 | 提出者 | 分类维度 | 对我们的友好度 |
|------|--------|---------|--------------|
| 四大 Agentic 设计模式 | Andrew Ng 2024 | Reflection / Tool Use / Planning / Multi-Agent | 中——把 Tool Use 和 Planning 当模式，不贬低 Workflow |
| Workflows vs Agents + 五种模式 | Anthropic 2024.12 | 谁决定下一步（代码 vs 模型） | 高——明确把 Workflow 当一等公民 |
| 按组件拆分 | Lilian Weng 2023.6 | 规划 / 记忆 / 工具 | 中——偏组件视角，不太涉及架构定位 |
| 推理范式进化链 | 学术圈 | CoT → ReAct → ReWOO → ... | 低——暗示进化=进步，对 Workflow 不友好 |

### 我们的判断

**不选一套通吃，按受众分层使用，但技术上以 Anthropic 为锚。**

| 受众 | 推荐体系 | 为什么 |
|------|---------|--------|
| 技术文档 / 架构设计 | Anthropic 2024.12 | 最精确、可追溯，直接映射 LangGraph 流水线结构 |
| 向上汇报 / 跨部门宣讲 | Andrew Ng 四模式 | 国内认知度最高，听众能秒懂"Tool Use + Planning" |
| 团队内部对齐 | Anthropic 骨架 + Ng 词汇 | 精确度和共识兼得 |
| 社区科普 / 对外写文章 | "自主程度"轴 | 自己习惯的轴，比"四级阶梯"更诚实，更容易引发有质量的讨论 |

### 为什么 Anthropic 是锚

Anthropic 体系最大的优势是：**它不贬低 Workflow，反而把"代码定流程"当作一种有意的、有价值的设计选择。**

这意味着在技术文档里写"我们是 Workflow 范式"，天然就把定位从"弱"变成"强"——不是做不到 Agent，而是选择了 Workflow，因为它更适合这个场景。

### 回应"你们这个不算 Agent"的策略

按对方是谁选策略：

- **工程师/研究者质疑**：直接用 Anthropic 术语接住——"对，它是 Workflow 不是 Agent，这是有意选择。PM 工作是流程敏感的，确定性 > 自主性。"主动承认 + 反转价值。
- **管理层/利益相关方**：别陷入术语之争，用结果说话——"它自动化了 PM 工作流中 X% 的环节，交付物可审计、可追溯。" 如果对方确实想要"Agent"这个词，用 **Agentic Workflow** 折中。
- **社区/同行**：可以贡献自己的角度——"'四级阶梯'是教程圈拼接的叙事，Plan-and-Solve 原文是提示词技巧不是架构范式。我更倾向于用'自主程度'这个轴来分类。"把质疑转化成话题资产。

### 不造自定义称谓

不造"流程型 Agent"这类词。原因：
- 造词增加沟通成本
- 加限定词反而暗示"我也知道它不完全是 Agent"——比直接叫 Workflow 更心虚
- Agentic Workflow 是行业已经在流通的术语，不是自造的

## 选型四：状态机驱动的工作流

### 问题

PM 工作流程怎么组织？是自由组合的节点图，还是固定顺序的状态机？

### 可选方案

| 方案 | 特点 | 适合场景 |
|------|------|---------|
| 自由 DAG（有向无环图） | 节点之间任意连接，灵活度高 | 通用型、多路径的复杂工作流 |
| 固定顺序状态机 | 状态按固定顺序排列，每个状态有明确的进入/退出条件 | 流程明确、步骤固定的业务场景 |
| 规则引擎 + 动态路由 | 根据规则动态决定下一步 | 分支多、条件复杂的场景 |

### 我们的判断

**固定顺序的状态机，每个状态有明确的进入条件、退出条件和检查点。**

原因：

1. **PM 工作流程本身就是固定顺序的**——从 intake 到分析到方案到交付，步骤是线性的，不需要复杂的动态路由
2. **可验收性**——每个状态的退出条件和检查点就是这个阶段的验收标准，质量有保障
3. **可调试性**——出了问题立刻知道卡在哪个状态，排查方便
4. **和"代码做刚性判断"的原则一致**——状态流转就是刚性判断的一部分

### 状态的结构

每个状态都有：
- **进入条件**：满足什么条件才能进入这个状态
- **执行内容**：这个状态做什么（代码判断 or 模型生成）
- **退出条件**：满足什么条件才能离开这个状态
- **检查点**：必过的质量门禁

## 选型五：参考库外置

### 问题

项目的参考资料、模板、示例代码，放在项目仓库里还是外面？

### 可选方案

| 方案 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| 放进仓库 | reference/ 目录，和代码一起版本管理 | 方便查找、版本一致 | 仓库膨胀、大量非代码文件 |
| 外置 + 路由文件 | 参考库存外部，项目里只有路由索引文件 | 仓库干净、参考库可复用 | 多一步跳转 |

### 我们的判断

**参考库外置，项目内通过路由文件引用。**

原因：
- PM 项目的参考资料量很大（框架文档、论文、案例、模板），放进仓库会严重膨胀
- 参考库可以被多个项目复用，不局限于这一个 PM Agent
- 路由文件是轻量级的索引，开发新功能时先查路由 → 定位参考 → 进入实现，流程清晰

## 选型六：两套知识库并存

### 问题

项目里的知识怎么存？一套大而全的知识库，还是按用途分开？

### 可选方案

| 方案 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| 一套知识库 | 所有内容都进同一个 RAG 库 | 简单、统一检索 | 不同类型内容混在一起，检索质量下降，技术选型无法差异化 |
| 按用途分开 | 业务档案一套，领域知识一套，各自用适合的技术 | 各取所需，技术选型精准 | 多一套系统要维护 |

### 我们的判断

**两套独立的知识库，技术栈不同，用途不同。**

| 知识库 | 用途 | 技术 | 为什么选这个技术 |
|--------|------|------|---------------|
| PM 业务档案库 | 存决策、评估、案例等业务记录 | 纯关键词打分，零依赖 | 业务档案是结构化的、有明确字段的，关键词检索足够准确；零依赖、纯本地，和业务数据的稳定性要求匹配 |
| AI Agent 领域知识库 | 存论文、概念、框架等领域知识 | 向量检索 + 混合加权 | 领域知识是开放式的、语义丰富的，关键词检索覆盖不够；需要语义匹配才能找到相关但不包含精确关键词的内容 |

### 为什么不合在一起

1. **内容性质完全不同**——业务档案是"我们自己的记录"，领域知识是"外部的参考资料"
2. **检索模式不同**——业务档案查的是"有没有某个决策记录"，精确匹配就行；领域知识查的是"有什么相关的知识"，需要语义联想
3. **更新频率不同**——业务档案随项目持续写入，领域知识是批量导入 + 定期更新
4. **技术选型无法兼顾**——关键词检索对结构化档案又快又准，向量检索对开放式知识效果好，一套技术不可能两头都最优

### 领域知识库的三层结构

AI Agent 领域知识库不是扁平的一堆文档，而是**三层互补结构**，各层内容性质、质量、更新节奏都不同：

| 层 | 来源 | 内容形式 | 数量 | 检索权重 | 更新频率 | 分块方式 |
|----|------|---------|------|---------|---------|---------|
| 概念解读层 | agentic-ai-knowledge-base | Markdown 深度解读（人写的） | 209 篇，32 分类 | ×2.0 | 每季度手动 | Section-aware 分块 |
| 精选论文层 | awesome-llm-agent-papers | 论文元数据 + abstract | 514 篇，10 分类 | ×1.5 | 每月 diff | 整篇一块 |
| 新论文追踪层 | arXiv API + LLM 过滤 | 论文元数据 + abstract | 约 3000-5000 篇 | ×1.0 | 每周自动 | 整篇一块 |

三层用一套**统一分类体系**（~25 个分类）对齐，ChromaDB 里通过 metadata 的 `layer` + `category` 字段区分，检索时可按层过滤、按层加权。

### 领域知识库的持续更新策略

知识库不是死的，三层各有更新节奏和处理方式：

- **概念层（每季度）**：整篇文档删了重写。因为量小、频率低，整篇重建简单可靠，不用搞增量 diff
- **精选层（每月）**：纯追加。awesome 列表新增的论文直接入库，旧的不动
- **追踪层（每周）**：批量追加。arXiv 拉新 → LLM 过滤 → 直接入库

更新时内容"放到合适的位置"靠 metadata 标签（`category` 字段），不是物理位置——向量数据库里内容是打乱存的，检索时靠标签过滤 + 内容相似度匹配。

### 怎么共存

- 共用查询入口（kb_query.py 扩展 `--domain` 参数），上层统一
- 底层两个独立实例，各自维护
- 飞书知识地图作为统一的导航层，指向两套知识库的不同条目

### 技术选型速览（领域知识库）

| 组件 | 选型 | 理由 |
|------|------|------|
| 向量数据库 | ChromaDB（嵌入式） | 规模匹配（几千个 chunk）、零运维、Python 原生、支持 metadata 过滤 |
| 嵌入模型 | Doubao-embedding（火山引擎 API） | 已有账户、中英文混合效果好、零部署、成本极低 |
| 分块策略 | 按层差异化 | 概念层 section-aware / 论文层整篇，各适配内容性质 |
| 检索策略 | 分层加权混合检索 | 兼顾语义和精确，高质量内容优先 |

完整选型细节见《AI Agent 知识库 RAG 选型笔记》。

## 选型总览

| 决策项 | 选定方案 | 核心理由 | 放弃了什么 |
|--------|---------|---------|-----------|
| 整体架构范式 | Workflow（Anthropic） | 业务场景确定性 > 自主性 | 纯 Agent 的灵活性和"前沿感" |
| 刚性/柔性分工 | 代码管刚性，模型管柔性 | 可审计、低成本、边界清晰 | 全模型的简单统一感 |
| 分类术语体系 | 按受众分层，技术锚定 Anthropic | 精确度和传播效率兼得 | 一套术语通吃的简洁性 |
| 工作流组织 | 固定顺序状态机 | PM 流程线性、可验收、可调试 | 自由 DAG 的灵活度 |
| 参考库管理 | 外置 + 路由文件 | 避免仓库膨胀、可复用 | 一步直达的便利性 |
| 知识库架构 | 两套独立（业务档案 + 领域知识） | 内容性质不同，技术选型差异化 | 一套系统的简单性 |
