# AI Agent 知识库 RAG 选型笔记

> 本文档记录 AI Agent 领域知识库 RAG 系统的每个选型决策：面对什么问题、调研了哪些方案、为什么这么选、放弃了什么、有什么trade-off。

---

## 选型一：知识库的定位——内容源还是导航层？

### 问题

飞书知识库和外部 RAG 库，各自承担什么角色？是把所有内容都放进飞书，还是飞书只做目录？

### 可选方案

| 方案 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| 飞书全量内容 | 所有知识内容都写在飞书里，RAG 直接索引飞书文档 | 一站式、人读和机读统一 | 飞书编辑成本高、批量导入困难、自动更新难做 |
| 飞书纯目录 + 外部全量内容 | 飞书只放目录和路由，详细内容全在外部 RAG 库 | 飞书轻量、外部内容易批量处理和自动更新 | 人读需要跳转 |
| 飞书有内容但精简 | 飞书有简要说明 + 笔记 + 路由，详细内容在外部 | 飞书可以独立阅读，外部提供深度 | 需要维护两份，有同步成本 |

### 我们的判断

**方案三：飞书做知识地图（目录 + 笔记 + 路由），外部 RAG 库存详细内容。**

原因：

1. **飞书的优势是"人读"，不是"机读"**——飞书的分级标题、评论、@人这些功能都是为人与人协作设计的，不是为批量数据处理设计的。把大量论文和技术文档塞进飞书，维护成本很高。

2. **外部 RAG 库的优势是"批量 + 自动更新"**——论文可以从 arXiv 批量拉取，向量索引可以自动构建，新内容可以自动追踪入库。这些在飞书里做都很别扭。

3. **飞书做导航层是最高效的分工**——你在飞书里系统性学习（有你的笔记、判断、标注），需要深度内容时跳去 RAG 库看原文。Agent 也一样：先读飞书地图定位领域，再去 RAG 库做深度检索。这是一种"分层检索"，反而比全量无差别检索更准。

### 飞书的两个核心功能

1. **人主动阅读的入口**：在飞书里看知识地图，知道知识点在 KB 的哪个位置，需要时调出原文细读
2. **Agent 的有目的检索引导**：Agent 先读飞书的知识地图（顶层结构 + 路由信息），再定向到具体 KB 条目

### 放弃了什么

- 放弃了"一站式"的便利性——人看深度内容需要从飞书跳转到 RAG 库
- 放弃了"单份维护"的简洁性——飞书的结构和 RAG 库的结构需要保持对应，有同步成本
- 但我们换来了：飞书的轻量和可编辑性 + RAG 库的批量处理和自动更新能力

## 选型二：知识源的选择——用哪些外部知识库？

### 问题

社区里有大量 AI Agent 相关的知识库、论文列表、awesome 项目，我们选哪些作为知识源？怎么组合？

### 调研结果

调研了 6 大类共 18 个项目，按内容性质分类：

| 类别 | 代表项目 | 内容类型 | 质量 | 自动更新 | 规模 |
|------|---------|---------|------|---------|------|
| 全景知识库 | agentic-ai-knowledge-base | 概念+框架+最佳实践，人写的深度文档 | 高 | 半自动 | 170+ 文档 |
| 论文索引（人工精选） | awesome-llm-agent-papers | 517 篇 must-read 论文 + 注释 + taxonomy | 很高 | 人工（约每月） | 517 篇 |
| 结构化元数据 | llmpapers (sinankprn) | 4.8 万篇论文元数据 + abstract | 参差 | 全自动（每日） | 48,616 篇 |
| Awesome 列表 | awesome-ai-agents | 框架/工具/资源索引 | 中 | 人工 | 条目级 |
| RAG 基础设施 | arxiv-rag, doc-watch-rag 等 | RAG 系统的参考实现 | 参考用 | N/A | N/A |
| 论文追踪工具 | arxiv-tracker-agent 等 | 论文发现/筛选/推送工具 | 参考用 | N/A | N/A |

### 三层知识的互补关系

这三个主要数据源的内容层次完全不同，**重合度很低，是互补关系不是替代关系**：

```
第一层：解读层（agentic-ai-knowledge-base）
  人写的深度文档，有组织、有观点、有框架对比
        │ 引用关系（提到论文名，但不是论文本身）
        ▼
第二层：精选论文层（awesome-llm-agent-papers）
  人工精选的 517 篇 must-read 论文 + 注释 + 清晰分类
        │ 子集关系（517 篇基本都在 4.8 万篇里）
        ▼
第三层：全量数据层（llmpapers）
  4.8 万篇论文元数据 + abstract，自动采集
```

- 第一层和第二层几乎不重合——第一层是"解读"，第二层是"索引"
- 第二层和第三层条目重合但用途不同——第二层是"精选+注释+高质量分类"，第三层是"全量+自动更新"
- 三层加起来实际入库约 90-160 万词，向量检索规模完全没问题

### 我们的判断

**三层都用，但用法不同、权重不同、更新策略不同。**

| 知识层 | 来源 | 用途 | 权重 | 更新策略 |
|--------|------|------|------|---------|
| 概念解读层 | agentic-ai-knowledge-base | 回答"是什么、怎么分类、有什么区别"，质量最高 | ×2.0 | 每季度手动检查，选择性吸收新章节 |
| 精选论文层 | awesome-llm-agent-papers + 补全 abstract | 论文溯源、准确出处、高质量分类 | ×1.5 | 每月检查 diff，选择性入库新论文 |
| 新论文追踪层 | llmpapers 过滤后（只留 agent 相关约 3000-5000 篇） | 覆盖前沿、查最新进展 | ×1.0 | 每周自动增量，LLM 过滤相关性后入库 |

### 为什么不全量导入 llmpapers

4.8 万篇看起来很多，但：
1. **质量参差**——里面灌水论文也不少，全量导入会拉低检索质量
2. **我们只关心 agent 领域**——过滤后大概几千篇，不需要全量
3. **精选层已经覆盖了经典论文**——追踪层只补最新的、精选层还没收录的

### 为什么不只用精选层

只有 517 篇的话：
1. **覆盖不够广**——很多子领域、边缘方向没有覆盖
2. **没有时效性**——人工精选永远滞后于最新研究
3. **缺少原始 abstract**——只有一行注释，深度不够做 RAG

## 选型三：向量数据库选什么？

### 问题

用什么向量数据库？有哪些选项？我们的场景适合哪个？

### 可选方案

| 方案 | 类型 | 部署方式 | 规模上限 | metadata 过滤 | 生态 |
|------|------|---------|---------|--------------|------|
| ChromaDB | 向量数据库 | 嵌入式（Python 库） | 百万级 | 支持 | 好，RAG 教程里用得多 |
| LanceDB | 向量数据库 | 嵌入式 | 千万级 | 支持 SQL-like | 中，较新 |
| FAISS | 向量搜索库 | 嵌入式库 | 千万级 | 不支持 | 好，Facebook 出品 |
| Qdrant | 向量数据库 | 独立服务 | 亿级 | 支持 | 好，Rust 写的性能好 |
| Weaviate | 向量数据库 | 独立服务 | 亿级 | 支持 | 好，功能最全 |
| pgvector | Postgres 插件 | 依附 Postgres | 亿级 | 支持（SQL） | 中 |

### 我们的判断

**选 ChromaDB，嵌入式 Python 库。**

原因：

1. **规模匹配**——我们的知识库大约几百到几千个 chunk，嵌入式数据库完全够用，不需要独立服务
2. **零运维**——`pip install` 就用，不需要启动服务器、不需要配置、不需要维护
3. **和项目架构一致**——你项目是纯 Python 的，ChromaDB 作为 Python 库集成最自然
4. **metadata 过滤支持**——我们的分层加权检索需要按 layer/category/curated 等字段过滤，FAISS 没有这个能力
5. **生态成熟**——多个参考项目（arxiv-rag、doc-watch-rag 等）都用 ChromaDB，有问题好查

### 为什么不选其他的

- **不选 Qdrant / Weaviate**：需要独立部署服务，我们这个规模完全没必要，徒增运维成本
- **不选 FAISS**：只有向量搜索能力，没有 metadata 过滤，我们的分层加权策略需要过滤支持
- **不选 pgvector**：你项目没有 Postgres 部署，为这个单独起一个数据库太重了
- **不选 LanceDB**：也可以，但生态比 ChromaDB 小一点，踩坑了资料少。作为备选，以后规模大了可以迁移

### 放弃了什么

- 放弃了独立向量数据库的高性能和可扩展性——但我们短期内用不到
- 放弃了 SQL 查询能力（LanceDB/pgvector）——但我们的查询模式不需要 SQL
- 如果以后知识库规模涨到几万篇以上，可以考虑迁移到 Qdrant 或 LanceDB

## 选型四：嵌入模型选什么？

### 问题

用什么嵌入模型？本地部署还是 API 调用？中英文混合场景下哪个效果好？

### 可选方案

| 方案 | 部署方式 | 维度 | 中文效果 | 多语言 | 成本 |
|------|---------|------|---------|--------|------|
| Doubao-embedding（火山引擎） | API | 最高 2560 维 | 好 | 是 | 按 token 计费 |
| BGE-M3 | 本地 | 1024 维 | 很好 | 是（100+语言） | 免费，需 GPU/CPU 推理 |
| m3e-base | 本地 | 768 维 | 好 | 中 | 免费 |
| text-embedding-3-large (OpenAI) | API | 3072 维 | 一般 | 是 | 按 token 计费 |

### 我们的判断

**选 Doubao-embedding（火山引擎 API）。**

原因：

1. **已有账户**——你项目已经在用火山引擎的模型服务，复用同一套密钥和配置，零额外接入成本
2. **中英文混合效果好**——我们的知识库中英文混合（论文英文、概念文档英文、你的笔记中文），Doubao 嵌入在混合场景下表现稳定
3. **高质量**——2560 维，语义表示能力强
4. **零部署成本**——不需要下载模型、不需要本地 GPU、不需要管理模型版本
5. **成本极低**——嵌入模型的计费比生成模型便宜很多，我们每周才更新一次库，调用量很小

### 为什么不选本地模型

- **BGE-M3 确实好**，但需要下载 ~1GB 模型文件，增加项目体积和首次启动时间
- 本地推理需要考虑 CPU/GPU 兼容性、模型更新、性能调优等问题
- 对于我们这种"写入少、读取多"的场景（每周写入一次，平时只读），API 方式的总成本反而更低

### 备选方案

如果以后有这些情况，可以切换到 BGE-M3 本地部署：
- 知识库规模大幅增长（几万篇以上），API 成本变高
- 有离线运行需求
- 对数据隐私有更高要求，不想把文本发到外部 API

## 选型五：分块策略——怎么切？

### 问题

文档怎么分块？切多大？一刀切还是按文档类型差异化？

### 可选方案

| 方案 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| 固定大小分块（RecursiveCharacterTextSplitter） | 按字符数切，比如 1000 字符一块，有重叠 | 简单通用，什么文档都能切 | 破坏语义边界，可能把一段完整意思切碎 |
| Section-aware 分块 | 按标题层级（#/##/###）切 | 保持语义完整性，每块对应一个小节 | 需要文档有清晰的标题结构 |
| 整篇一个 chunk | 不切，整篇文档一个块 | 语义最完整 | 文档太大的话检索精度下降 |
| 语义分块 | 用模型判断语义边界，自动切 | 最精准 | 成本高、速度慢、不确定 |

### 我们的判断

**按知识层差异化，不搞一刀切。**

| 知识层 | 分块策略 | chunk 大小 | 理由 |
|--------|---------|-----------|------|
| 概念解读层 | Section-aware splitter（按标题切） | 500-800 字，overlap 100 | 这些文档（agentic-ai-knowledge-base）本身有清晰的章节结构，按标题切保持语义完整性 |
| 精选论文层 | 整篇为一个 chunk | 每篇约 300-500 词 | 单篇论文的 abstract 本身就短，拆开反而破坏语义完整性。整篇作为一个知识单元 |
| 新论文追踪层 | 整篇为一个 chunk | 同上 | 理由同上 |

### 为什么不做更细的分块

1. **规模小**——总共几千个 chunk，不需要靠细粒度来提升召回
2. **论文 abstract 本身是完整摘要**——拆开没有意义
3. **概念文档按章节切已经足够细**——一节一个 chunk，粒度合适

### 元数据设计

每个 chunk 必带的元数据字段，这些是分层加权和过滤的基础：

```
id, layer (concept|curated-paper|tracked-paper), category, source,
title, authors, year, arxiv_id, url, tags, curated (true/false), feishu_ref
```

## 选型六：检索策略——怎么搜？

### 问题

用什么检索方式？纯向量？关键词？还是混合？要不要加权？怎么加权？

### 可选方案

| 方案 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| 纯向量检索 | 语义相似度匹配 | 能找到语义相关但不包含关键词的内容 | 精确匹配可能不如关键词，可能返回语义接近但不相关的内容 |
| 纯关键词检索 | BM25 / 关键词打分 | 精确匹配好，可解释性强 | 找不到同义词、语义相关但用词不同的内容 |
| 混合检索（无权重） | 向量 + 关键词，结果合并去重 | 兼顾两者 | 两层结果怎么融合没有区分度 |
| 混合检索 + 分层加权 | 混合检索 + 按知识层和质量加权 | 兼顾语义和精确，同时把高质量内容顶在前面 | 实现稍复杂，权重需要调 |

### 我们的判断

**分层加权混合检索：关键词 + 向量并行执行，合并后按知识层和质量标记加权重排序。**

完整流程：

```
查询
  ├── 关键词检索 → 结果集 A（按关键词分数排序）
  ├── 向量语义检索 → 结果集 B（按余弦相似度排序）
  └── 分类预过滤（从飞书地图预判 category，缩小搜索范围）
         ↓
   合并去重（同一个 chunk 只保留一次）
         ↓
   分层加权：
     - concept 层 → × 2.0（质量最高，人工组织）
     - curated-paper 层 → × 1.5（人工精选，有注释）
     - tracked-paper 层 → × 1.0（自动采集，质量参差）
     - curated 标记 → 额外 × 1.2
     - 飞书路由命中 → 额外 × 1.3
         ↓
   重排序，返回 Top-K（默认 5 个）
```

### 为什么要分层加权

这是解决"多源内容质量不均"问题的核心手段：

1. **避免低质量内容淹没高质量内容**——新论文追踪层有几千篇，全是自动采集的，如果不加权，检索结果里会充斥着质量一般的论文，把精选层和概念层的内容挤下去
2. **匹配不同问题的最佳答案来源**——
   - "什么是 ReAct？" → 概念解读层的解释最好懂，权重最高
   - "ReAct 是谁提出的？" → 精选论文层的出处最准确，权重高
   - "2026 年有什么新进展？" → 追踪层才能覆盖，但质量参差，权重低
3. **飞书路由命中加权是"人机对齐"**——飞书里有你标注的知识点，如果检索结果刚好命中你标记过的内容，说明这条结果和你的认知体系对齐，应该优先返回

### 加权计算公式

1. 关键词分归一化到 0-1（除以最高分）
2. 向量分本来就是 0-1（余弦相似度）
3. 两者融合：`final_score = 0.4 × keyword_norm + 0.6 × vector_sim`
4. 乘层级权重和质量权重：`weighted_score = final_score × layer_weight × quality_bonus`
5. 排序取 Top-K

**向量权重 0.6 > 关键词权重 0.4**，因为语义匹配是 RAG 的核心价值；关键词作为补充，保证精确匹配的内容不会丢。

### 为什么不加重排器（reranker）

- 我们的规模小（几千个 chunk），Top-K 之后的结果量不大，基础排序已经够用
- 重排器（如 BGE-Reranker）需要额外的模型推理，增加延迟和成本
- 等以后规模大了、检索精度下降了，再加 reranker 也不迟

## 选型七：自动更新机制

### 问题

知识库怎么更新？手动还是自动？更新频率多高？

### 可选方案

| 方案 | 更新方式 | 频率 | 质量 | 成本 |
|------|---------|------|------|------|
| 纯手动 | 手动添加新内容 | 不定 | 最高 | 人力成本高 |
| 半自动 | 自动采集 + 人工审核后入库 | 每周/每月 | 高 | 中等 |
| 全自动 | 自动采集 → 自动过滤 → 自动入库 | 每日/每周 | 参差 | 低 |

### 我们的判断

**按知识层差异化更新策略，三层各有各的节奏。**

| 知识层 | 更新频率 | 更新方式 | 人工介入 |
|--------|---------|---------|---------|
| 概念解读层 | 每季度一次 | 手动检查 agentic-ai-knowledge-base 的新章节，选择性吸收 | 全程手动 |
| 精选论文层 | 每月一次 | 对比 awesome-llm-agent-papers 与上次版本的 diff，提取新增论文 → 补 abstract → 入库 | 人工审核新增的论文是否真的相关 |
| 新论文追踪层 | 每周一次 | arXiv API 拉取过去 7 天的新论文 → LLM 过滤相关性 → 写入追踪层 | LLM 自动过滤，偶尔人工抽查 |

### 为什么不是统一频率

- **概念层变化最慢**——概念体系和框架对比是相对稳定的，不需要频繁更新
- **精选层变化中等**——人工 curated 的论文列表大约每月有新增
- **追踪层变化最快**——arXiv 每天都有新论文，需要持续追踪

### 为什么追踪层用 LLM 过滤而不是人工

- 每周新增的 agent 相关论文可能有几十篇，人工审核成本太高
- LLM 过滤的准确率已经够用（大概 80-90%），即使有少量误判也没关系——追踪层权重最低，质量差点不影响整体效果
- 真的重要的论文，后续会被 awesome 列表收录，进入精选层（权重更高）

## 选型八：飞书知识地图的结构

### 问题

飞书知识地图怎么组织？和外部 KB 怎么对应？

### 我们的判断

**飞书的分级标题和外部 KB 的目录结构一一对应，结构对齐。**

```
飞书层级（目录）              外部 KB 层级（内容）
──────────────────────────────────────────────────
一、基础概念                   concepts/ 目录
  1.1 Agent 是什么              ├── agent-definition.md
  1.2 Agent 分类体系             ├── agent-types.md
  1.2.1 按自主程度分             │   └── (文档内的小节)
  1.2.2 Workflow vs Agent       │   └── (文档内的小节)
  1.3 核心范式演进              └── paradigm-evolution.md

二、架构与模式                  architecture/ 目录
  2.1 规划与推理                 ├── planning.md
  2.2 记忆系统                   ├── memory.md
  2.3 工具使用                   └── tool-use.md

三、框架与平台                  frameworks/ 目录
...
```

### 对应规则

- 飞书一级标题 → KB 顶层目录
- 飞书二级标题 → KB 单篇文档
- 飞书三级及以下标题 → 文档内小节（section-aware 分块时的 chunk 边界）
- 每篇飞书文档里有"KB 原文链接"，指向对应的 KB 文档

### 每个飞书知识点包含什么

1. **标题和简要说明**——一句话概括这个知识点
2. **你的笔记**——你自己的理解、判断、标注（这是飞书最有价值的部分，外部任何知识库替代不了）
3. **KB 路由**——指向 RAG 库里对应条目的 ID 和链接

### 为什么结构要对齐

1. **降低认知负担**——你在飞书里看到的分类和 KB 里的分类是一样的，不需要记两套体系
2. **方便路由映射**——结构对齐了，路由关系就是简单的一一对应，不需要复杂的映射逻辑
3. **Agent 检索更准**——Agent 从飞书地图里拿到 category，直接在 KB 的对应 category 里做定向检索，准确率更高

## 选型总览

| 决策项 | 选定方案 | 核心理由 | 放弃了什么 |
|--------|---------|---------|-----------|
| 知识库定位 | 飞书做地图，外部做内容 | 飞书擅长人读，外部擅长批量处理；分层检索更准 | 一站式的便利性 |
| 知识源选择 | 三层知识（概念/精选/追踪） | 层次互补，各有用途；重合度低 | 单一来源的简单性 |
| 向量数据库 | ChromaDB（嵌入式） | 规模匹配、零运维、Python 原生 | 独立向量库的高性能 |
| 嵌入模型 | Doubao-embedding（API） | 已有账户、中英文好、零部署 | 本地模型的离线能力和隐私性 |
| 分块策略 | 按层差异化（section-aware / 整篇） | 不同内容性质适配不同分块方式 | 一刀切的简单性 |
| 检索策略 | 分层加权混合检索 | 兼顾语义和精确，高质量内容优先 | 纯向量/纯关键词的简单性 |
| 更新机制 | 按层差异化频率（季/月/周） | 各层变化速度不同，节奏匹配 | 统一频率的简单性 |
| 飞书结构 | 与外部 KB 一一对应 | 降低认知负担，方便路由 | 自由组织的灵活性 |
