## 选型一：知识库的定位——内容源还是导航层？

### 问题

飞书知识库和外部 RAG 库，各自承担什么角色？是把所有内容都放进飞书，还是飞书只做目录？

### 可选方案

| 方案 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| 飞书全量内容 | 所有知识内容都写在飞书里，RAG 直接索引飞书文档 | 一站式、人读和机读统一 | 飞书编辑成本高、批量导入困难、自动更新难做 |
| 飞书纯目录 + 外部全量内容 | 飞书只放目录和路由，详细内容全在外部 RAG 库 | 飞书轻量、外部内容易批量处理和自动更新 | 人读需要跳转 |
| 飞书有内容但精简 | 飞书有简要说明 + 笔记 + 路由，详细内容在外部 | 飞书可以独立阅读，外部提供深度 | 需要维护两份，有同步成本 |

### 我们的判断

**方案三：飞书做知识地图（目录 + 笔记 + 路由），外部 RAG 库存详细内容。**

原因：

1. **飞书的优势是"人读"，不是"机读"**——飞书的分级标题、评论、@人这些功能都是为人与人协作设计的，不是为批量数据处理设计的。把大量论文和技术文档塞进飞书，维护成本很高。

2. **外部 RAG 库的优势是"批量 + 自动更新"**——论文可以从 arXiv 批量拉取，向量索引可以自动构建，新内容可以自动追踪入库。这些在飞书里做都很别扭。

3. **飞书做导航层是最高效的分工**——你在飞书里系统性学习（有你的笔记、判断、标注），需要深度内容时跳去 RAG 库看原文。Agent 也一样：先读飞书地图定位领域，再去 RAG 库做深度检索。这是一种"分层检索"，反而比全量无差别检索更准。

### 飞书的两个核心功能

1. **人主动阅读的入口**：在飞书里看知识地图，知道知识点在 KB 的哪个位置，需要时调出原文细读
2. **Agent 的有目的检索引导**：Agent 先读飞书的知识地图（顶层结构 + 路由信息），再定向到具体 KB 条目

### 放弃了什么

- 放弃了"一站式"的便利性——人看深度内容需要从飞书跳转到 RAG 库
- 放弃了"单份维护"的简洁性——飞书的结构和 RAG 库的结构需要保持对应，有同步成本
- 但我们换来了：飞书的轻量和可编辑性 + RAG 库的批量处理和自动更新能力

## 选型二：知识源的选择——用哪些外部知识库？

### 问题

社区里有大量 AI Agent 相关的知识库、论文列表、awesome 项目，我们选哪些作为知识源？怎么组合？

### 调研结果

调研了 6 大类共 18 个项目，按内容性质分类：

| 类别 | 代表项目 | 内容类型 | 质量 | 自动更新 | 规模 |
|------|---------|---------|------|---------|------|
| 全景知识库 | agentic-ai-knowledge-base | 概念+框架+最佳实践，人写的深度文档 | 高 | 半自动 | 170+ 文档 |
| 论文索引（人工精选） | awesome-llm-agent-papers | 517 篇 must-read 论文 + 注释 + taxonomy | 很高 | 人工（约每月） | 517 篇 |
| 结构化元数据 | llmpapers (sinankprn) | 4.8 万篇论文元数据 + abstract | 参差 | 全自动（每日） | 48,616 篇 |
| Awesome 列表 | awesome-ai-agents | 框架/工具/资源索引 | 中 | 人工 | 条目级 |
| RAG 基础设施 | arxiv-rag, doc-watch-rag 等 | RAG 系统的参考实现 | 参考用 | N/A | N/A |
| 论文追踪工具 | arxiv-tracker-agent 等 | 论文发现/筛选/推送工具 | 参考用 | N/A | N/A |

### 三层知识的互补关系

这三个主要数据源的内容层次完全不同，**重合度很低，是互补关系不是替代关系**：

```
第一层：解读层（agentic-ai-knowledge-base）
  人写的深度文档，有组织、有观点、有框架对比
        │ 引用关系（提到论文名，但不是论文本身）
        ▼
第二层：精选论文层（awesome-llm-agent-papers）
  人工精选的 517 篇 must-read 论文 + 注释 + 清晰分类
        │ 子集关系（517 篇基本都在 4.8 万篇里）
        ▼
第三层：全量数据层（llmpapers）
  4.8 万篇论文元数据 + abstract，自动采集
```

- 第一层和第二层几乎不重合——第一层是"解读"，第二层是"索引"
- 第二层和第三层条目重合但用途不同——第二层是"精选+注释+高质量分类"，第三层是"全量+自动更新"
- 三层加起来实际入库约 90-160 万词，向量检索规模完全没问题

### 我们的判断

**三层都用，但用法不同、权重不同、更新策略不同。**

| 知识层 | 来源 | 用途 | 权重 | 更新策略 |
|--------|------|------|------|---------|
| 概念解读层 | agentic-ai-knowledge-base | 回答"是什么、怎么分类、有什么区别"，质量最高 | ×2.0 | 每季度手动检查，选择性吸收新章节 |
| 精选论文层 | awesome-llm-agent-papers + 补全 abstract | 论文溯源、准确出处、高质量分类 | ×1.5 | 每月检查 diff，选择性入库新论文 |
| 新论文追踪层 | llmpapers 过滤后（只留 agent 相关约 3000-5000 篇） | 覆盖前沿、查最新进展 | ×1.0 | 每周自动增量，LLM 过滤相关性后入库 |

### 为什么不全量导入 llmpapers

4.8 万篇看起来很多，但：
1. **质量参差**——里面灌水论文也不少，全量导入会拉低检索质量
2. **我们只关心 agent 领域**——过滤后大概几千篇，不需要全量
3. **精选层已经覆盖了经典论文**——追踪层只补最新的、精选层还没收录的

### 为什么不只用精选层

只有 517 篇的话：
1. **覆盖不够广**——很多子领域、边缘方向没有覆盖
2. **没有时效性**——人工精选永远滞后于最新研究
3. **缺少原始 abstract**——只有一行注释，深度不够做 RAG

## 选型三：向量数据库选什么？

### 问题

用什么向量数据库？有哪些选项？我们的场景适合哪个？

### 可选方案

| 方案 | 类型 | 部署方式 | 规模上限 | metadata 过滤 | 生态 |
|------|------|---------|---------|--------------|------|
| ChromaDB | 向量数据库 | 嵌入式（Python 库） | 百万级 | 支持 | 好，RAG 教程里用得多 |
| LanceDB | 向量数据库 | 嵌入式 | 千万级 | 支持 SQL-like | 中，较新 |
| FAISS | 向量搜索库 | 嵌入式库 | 千万级 | 不支持 | 好，Facebook 出品 |
| Qdrant | 向量数据库 | 独立服务 | 亿级 | 支持 | 好，Rust 写的性能好 |
| Weaviate | 向量数据库 | 独立服务 | 亿级 | 支持 | 好，功能最全 |
| pgvector | Postgres 插件 | 依附 Postgres | 亿级 | 支持（SQL） | 中 |

### 我们的判断

**选 ChromaDB，嵌入式 Python 库。**

原因：

1. **规模匹配**——我们的知识库大约几百到几千个 chunk，嵌入式数据库完全够用，不需要独立服务
2. **零运维**——`pip install` 就用，不需要启动服务器、不需要配置、不需要维护
3. **和项目架构一致**——你项目是纯 Python 的，ChromaDB 作为 Python 库集成最自然
4. **metadata 过滤支持**——我们的分层加权检索需要按 layer/category/curated 等字段过滤，FAISS 没有这个能力
5. **生态成熟**——多个参考项目（arxiv-rag、doc-watch-rag 等）都用 ChromaDB，有问题好查

### 为什么不选其他的

- **不选 Qdrant / Weaviate**：需要独立部署服务，我们这个规模完全没必要，徒增运维成本
- **不选 FAISS**：只有向量搜索能力，没有 metadata 过滤，我们的分层加权策略需要过滤支持
- **不选 pgvector**：你项目没有 Postgres 部署，为这个单独起一个数据库太重了
- **不选 LanceDB**：也可以，但生态比 ChromaDB 小一点，踩坑了资料少。作为备选，以后规模大了可以迁移

### 放弃了什么

- 放弃了独立向量数据库的高性能和可扩展性——但我们短期内用不到
- 放弃了 SQL 查询能力（LanceDB/pgvector）——但我们的查询模式不需要 SQL
- 如果以后知识库规模涨到几万篇以上，可以考虑迁移到 Qdrant 或 LanceDB

## 选型四：嵌入模型选什么？

### 问题

用什么嵌入模型？本地部署还是 API 调用？中英文混合场景下哪个效果好？

### 可选方案

| 方案 | 部署方式 | 维度 | 中文效果 | 多语言 | 成本 |
|------|---------|------|---------|--------|------|
| Doubao-embedding（火山引擎） | API | 最高 2560 维 | 好 | 是 | 按 token 计费 |
| BGE-M3 | 本地 | 1024 维 | 很好 | 是（100+语言） | 免费，需 GPU/CPU 推理 |
| m3e-base | 本地 | 768 维 | 好 | 中 | 免费 |
| text-embedding-3-large (OpenAI) | API | 3072 维 | 一般 | 是 | 按 token 计费 |

### 我们的判断

**选 Doubao-embedding（火山引擎 API）。**

原因：

1. **已有账户**——你项目已经在用火山引擎的模型服务，复用同一套密钥和配置，零额外接入成本
2. **中英文混合效果好**——我们的知识库中英文混合（论文英文、概念文档英文、你的笔记中文），Doubao 嵌入在混合场景下表现稳定
3. **高质量**——2560 维，语义表示能力强
4. **零部署成本**——不需要下载模型、不需要本地 GPU、不需要管理模型版本
5. **成本极低**——嵌入模型的计费比生成模型便宜很多，我们每周才更新一次库，调用量很小

### 为什么不选本地模型

- **BGE-M3 确实好**，但需要下载 ~1GB 模型文件，增加项目体积和首次启动时间
- 本地推理需要考虑 CPU/GPU 兼容性、模型更新、性能调优等问题
- 对于我们这种"写入少、读取多"的场景（每周写入一次，平时只读），API 方式的总成本反而更低

### 备选方案

如果以后有这些情况，可以切换到 BGE-M3 本地部署：
- 知识库规模大幅增长（几万篇以上），API 成本变高
- 有离线运行需求
- 对数据隐私有更高要求，不想把文本发到外部 API

## 选型五：分块策略——怎么切？

### 问题

文档怎么分块？切多大？一刀切还是按文档类型差异化？

### 可选方案

| 方案 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| 固定大小分块（RecursiveCharacterTextSplitter） | 按字符数切，比如 1000 字符一块，有重叠 | 简单通用，什么文档都能切 | 破坏语义边界，可能把一段完整意思切碎 |
| Section-aware 分块 | 按标题层级（#/##/###）切 | 保持语义完整性，每块对应一个小节 | 需要文档有清晰的标题结构 |
| 整篇一个 chunk | 不切，整篇文档一个块 | 语义最完整 | 文档太大的话检索精度下降 |
| 语义分块 | 用模型判断语义边界，自动切 | 最精准 | 成本高、速度慢、不确定 |

### 我们的判断

**按知识层差异化，不搞一刀切。**

| 知识层 | 分块策略 | chunk 大小 | 理由 |
|--------|---------|-----------|------|
| 概念解读层 | Section-aware splitter（按标题切） | 500-800 字，overlap 100 | 这些文档（agentic-ai-knowledge-base）本身有清晰的章节结构，按标题切保持语义完整性 |
| 精选论文层 | 整篇为一个 chunk | 每篇约 300-500 词 | 单篇论文的 abstract 本身就短，拆开反而破坏语义完整性。整篇作为一个知识单元 |
| 新论文追踪层 | 整篇为一个 chunk | 同上 | 理由同上 |

### 为什么不做更细的分块

1. **规模小**——总共几千个 chunk，不需要靠细粒度来提升召回
2. **论文 abstract 本身是完整摘要**——拆开没有意义
3. **概念文档按章节切已经足够细**——一节一个 chunk，粒度合适

### 元数据设计

每个 chunk 必带的元数据字段，这些是分层加权和过滤的基础：

```
id, layer (concept|curated-paper|tracked-paper), category, source,
title, authors, year, arxiv_id, url, tags, curated (true/false), feishu_ref
```

## 选型六：检索策略——怎么搜？

### 问题

用什么检索方式？纯向量？关键词？还是混合？要不要加权？怎么加权？

### 可选方案

| 方案 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| 纯向量检索 | 语义相似度匹配 | 能找到语义相关但不包含关键词的内容 | 精确匹配可能不如关键词，可能返回语义接近但不相关的内容 |
| 纯关键词检索 | BM25 / 关键词打分 | 精确匹配好，可解释性强 | 找不到同义词、语义相关但用词不同的内容 |
| 混合检索（无权重） | 向量 + 关键词，结果合并去重 | 兼顾两者 | 两层结果怎么融合没有区分度 |
| 混合检索 + 分层加权 | 混合检索 + 按知识层和质量加权 | 兼顾语义和精确，同时把高质量内容顶在前面 | 实现稍复杂，权重需要调 |

### 我们的判断

**分层加权混合检索：关键词 + 向量并行执行，合并后按知识层和质量标记加权重排序。**

完整流程：

```
查询
  ├── 关键词检索 → 结果集 A（按关键词分数排序）
  ├── 向量语义检索 → 结果集 B（按余弦相似度排序）
  └── 分类预过滤（从飞书地图预判 category，缩小搜索范围）
         ↓
   合并去重（同一个 chunk 只保留一次）
         ↓
   分层加权：
     - concept 层 → × 2.0（质量最高，人工组织）
     - curated-paper 层 → × 1.5（人工精选，有注释）
     - tracked-paper 层 → × 1.0（自动采集，质量参差）
     - curated 标记 → 额外 × 1.2
     - 飞书路由命中 → 额外 × 1.3
         ↓
   重排序，返回 Top-K（默认 5 个）
```

### 为什么要分层加权

这是解决"多源内容质量不均"问题的核心手段：

1. **避免低质量内容淹没高质量内容**——新论文追踪层有几千篇，全是自动采集的，如果不加权，检索结果里会充斥着质量一般的论文，把精选层和概念层的内容挤下去
2. **匹配不同问题的最佳答案来源**——
   - "什么是 ReAct？" → 概念解读层的解释最好懂，权重最高
   - "ReAct 是谁提出的？" → 精选论文层的出处最准确，权重高
   - "2026 年有什么新进展？" → 追踪层才能覆盖，但质量参差，权重低
3. **飞书路由命中加权是"人机对齐"**——飞书里有你标注的知识点，如果检索结果刚好命中你标记过的内容，说明这条结果和你的认知体系对齐，应该优先返回

### 加权计算公式

1. 关键词分归一化到 0-1（除以最高分）
2. 向量分本来就是 0-1（余弦相似度）
3. 两者融合：`final_score = 0.4 × keyword_norm + 0.6 × vector_sim`
4. 乘层级权重和质量权重：`weighted_score = final_score × layer_weight × quality_bonus`
5. 排序取 Top-K

**向量权重 0.6 > 关键词权重 0.4**，因为语义匹配是 RAG 的核心价值；关键词作为补充，保证精确匹配的内容不会丢。

### 为什么不加重排器（reranker）

- 我们的规模小（几千个 chunk），Top-K 之后的结果量不大，基础排序已经够用
- 重排器（如 BGE-Reranker）需要额外的模型推理，增加延迟和成本
- 等以后规模大了、检索精度下降了，再加 reranker 也不迟

## 选型七：自动更新机制

### 问题

知识库怎么更新？手动还是自动？更新频率多高？

### 可选方案

| 方案 | 更新方式 | 频率 | 质量 | 成本 |
|------|---------|------|------|------|
| 纯手动 | 手动添加新内容 | 不定 | 最高 | 人力成本高 |
| 半自动 | 自动采集 + 人工审核后入库 | 每周/每月 | 高 | 中等 |
| 全自动 | 自动采集 → 自动过滤 → 自动入库 | 每日/每周 | 参差 | 低 |

### 我们的判断

**按知识层差异化更新策略，三层各有各的节奏。**

| 知识层 | 更新频率 | 更新方式 | 人工介入 |
|--------|---------|---------|---------|
| 概念解读层 | 每季度一次 | 手动检查 agentic-ai-knowledge-base 的新章节，选择性吸收 | 全程手动 |
| 精选论文层 | 每月一次 | 对比 awesome-llm-agent-papers 与上次版本的 diff，提取新增论文 → 补 abstract → 入库 | 人工审核新增的论文是否真的相关 |
| 新论文追踪层 | 每周一次 | arXiv API 拉取过去 7 天的新论文 → LLM 过滤相关性 → 写入追踪层 | LLM 自动过滤，偶尔人工抽查 |

### 为什么不是统一频率

- **概念层变化最慢**——概念体系和框架对比是相对稳定的，不需要频繁更新
- **精选层变化中等**——人工 curated 的论文列表大约每月有新增
- **追踪层变化最快**——arXiv 每天都有新论文，需要持续追踪

### 为什么追踪层用 LLM 过滤而不是人工

- 每周新增的 agent 相关论文可能有几十篇，人工审核成本太高
- LLM 过滤的准确率已经够用（大概 80-90%），即使有少量误判也没关系——追踪层权重最低，质量差点不影响整体效果
- 真的重要的论文，后续会被 awesome 列表收录，进入精选层（权重更高）

## 选型八：飞书知识地图的结构

### 问题

飞书知识地图怎么组织？和外部 KB 怎么对应？

### 我们的判断

**飞书的分级标题和外部 KB 的目录结构一一对应，结构对齐。**

```
飞书层级（目录）              外部 KB 层级（内容）
──────────────────────────────────────────────────
一、基础概念                   concepts/ 目录
  1.1 Agent 是什么              ├── agent-definition.md
  1.2 Agent 分类体系             ├── agent-types.md
  1.2.1 按自主程度分             │   └── (文档内的小节)
  1.2.2 Workflow vs Agent       │   └── (文档内的小节)
  1.3 核心范式演进              └── paradigm-evolution.md

二、架构与模式                  architecture/ 目录
  2.1 规划与推理                 ├── planning.md
  2.2 记忆系统                   ├── memory.md
  2.3 工具使用                   └── tool-use.md

三、框架与平台                  frameworks/ 目录
...
```

### 对应规则

- 飞书一级标题 → KB 顶层目录
- 飞书二级标题 → KB 单篇文档
- 飞书三级及以下标题 → 文档内小节（section-aware 分块时的 chunk 边界）
- 每篇飞书文档里有"KB 原文链接"，指向对应的 KB 文档

### 每个飞书知识点包含什么

1. **标题和简要说明**——一句话概括这个知识点
2. **你的笔记**——你自己的理解、判断、标注（这是飞书最有价值的部分，外部任何知识库替代不了）
3. **KB 路由**——指向 RAG 库里对应条目的 ID 和链接

### 为什么结构要对齐

1. **降低认知负担**——你在飞书里看到的分类和 KB 里的分类是一样的，不需要记两套体系
2. **方便路由映射**——结构对齐了，路由关系就是简单的一一对应，不需要复杂的映射逻辑
3. **Agent 检索更准**——Agent 从飞书地图里拿到 category，直接在 KB 的对应 category 里做定向检索，准确率更高

# 选型复审：从「三层知识」到「增量/存量」双域（2026-10-15）

> **复审动因**：产品定调更新——知识库重组为两部分：【增量部分】用户自己输入内容、或从信息源引入文档，规定文档格式，实时更新、可立即检索，切片要语义自包含（新增切片不破坏旧库）；【存量部分】大量文献、社区关于选型的讨论、模型信息，可提前批量制备，按最适合该类资料的切片方式处理，再进混合检索。混合检索按现实情况重新选型。
> **调研方式**：三路子任务并行多源调研（每路 ≥4 独立来源互相印证、剔孤证、冲突挂起不裁决），主 Agent 交叉终审。主要来源：Anthropic contextual retrieval 实验、Dense X 论文、Jina late chunking 论文与 Part II、Vectara NAACL2025 分块研究、Chroma/FloTorch 分块评测、bm25s/tantivy/whoosh 项目文档、Elasticsearch/Qdrant/Azure RRF 文档、BAAI/Qwen reranker 模型卡。
> **复审结论一句话**：语料组织从「三层」改「增量/存量双域」；切片从「分层差异化」升级为「结构优先 + 自包含 + 类型化」；检索从「向量候选内补关键词分」推翻重建为「双路召回 + RRF」；ChromaDB、嵌入模型、飞书导航层保留不动。

## 复审一：语料框架——三层知识 vs 增量/存量双域

### 问题
原三层（concept / curated-paper / tracked-paper）按「来源 + 质量」分层。新定调按「进入方式 + 处理时机」分增量/存量，且新增了社区讨论帖、模型信息两类语料。三层要不要保留？

### 判断
**改为增量/存量双域，「质量分层」降级为 metadata 质量标记，不丢。** 理由：

1. 社区讨论帖、模型信息在三层里没有位置——既非概念解读也非论文，硬塞进任何一层都会污染该层的切片策略和权重假设。
2. 增量内容（用户输入/信源引入）是实时进入的，与三层的季/月/周批量节奏是两种工程形态，混在一个「层」里更新机制没法写。
3. 三层里真正值钱的洞察是「质量不同的内容要区别加权」，这个保留：改为 `quality` 标记（`user_input` / `curated` / `auto`），与域解耦，继续参与检索加权。

### 旧三层 → 新双域映射
| 旧 | 新 | 说明 |
|----|----|------|
| concept 层（209 篇人写解读） | 存量 / 文献解读类 | 按存量切片 |
| curated-paper 层（514 篇论文） | 存量 / 论文类 | 按存量切片 |
| tracked-paper 层（arXiv 周更，未实现） | 增量 / 信源引入 | 归入增量的自动引入通道，实时性要求天然满足 |
| （新增）用户手输内容 | 增量 / 用户输入 | 新增 |
| （新增）社区选型讨论帖 | 存量 / 讨论帖类 | 新增 |
| （新增）模型信息 | 存量 / 结构化 | 新增 |

### 放弃了什么
- 三层层权重（concept×2.0 / curated×1.5 / tracked×1.0）作废，加权改为质量标记 × 域内外的乘数体系（见复审九）。

## 复审二：增量切片——什么切法能「加新切片不破坏库」

### 问题
增量部分的核心诉求：切片语义自包含，新增切片时不需要重切整个库。怎么切？

### 调研结论（要点）
| 方案 | 增量友好度 | 关键证据 |
|------|-----------|---------|
| 结构切片（Markdown 标题/段落边界 + 超长递归兜底） | 高：边界只由本文档决定，重复切片可复现 | 纯规则、0 LLM 成本（LangChain MarkdownHeaderTextSplitter 同构） |
| 语义分块 | 中高：文档内局部，但编辑一处改动其后全部断点 | **收益有争议**：Vectara NAACL2025 称固定分块常更优，Chroma 评测称语义切块 recall 91.9%，FloTorch 称仅 54%——三来源冲突，挂起 |
| 命题式分块（Dense X） | 中：LLM 生成原子命题，约 6× 膨胀、结果不稳 | 论文自述 GPT-4 造种 + 微调 Propositionizer，成本最高 |
| contextual retrieval（chunk 专属上下文前缀） | 高：上下文 = 本文档 + 本块的函数 | top-20 失败率 5.7%→3.7%，+BM25→2.9%，+rerank→1.9%（Anthropic 实测）；但**泛化文档摘要前缀收益「非常有限」**，只有 chunk 专属上下文有效 |
| 父子分块（small-to-big） | 高：父子都在文档内生成 | 小块检索、父块回填作答，仅存储冗余成本 |
| late chunking | — | **排除**：Qwen3-Embedding-8B 是 last-token pooling，late chunking 要求 mean pooling，硬约束不兼容 |

### 判断
**结构优先切片 + 轻量父子 + 可选 contextual header：**

1. **切片**：沿用并强化现有 section-aware 逻辑（标题/段落边界、800 字递归兜底、行边界重叠、表格保护——这些已在 `src/kb/rag/splitter.py` 落地）。切片是「单文档的纯函数」：边界只依赖本文档内容与固定参数 → 新增/编辑只触碰该源，这是「不重切全库」的充分条件。
2. **自包含（轻量父子）**：每个 chunk 前缀写 `heading_path`（标题路径）+ 必要时回填父块全文（存 metadata），500-800 字段落因此带上「我在哪篇文档的哪一节」，指代可解。0 额外模型成本，实时入库不拖慢。
3. **contextual header 作为可选增强**：只对批量入库的存量（尤其论文章节块）按需开启 LLM 生成 chunk 专属上下文（50-100 token）。**注意不是文档摘要前缀**（实测收益有限），是针对该 chunk 的定位上下文。

### 放弃了什么
- 命题式分块（成本最高、6× 膨胀、中文改写失真风险、生成不稳定）；
- late chunking（pooling 硬约束不兼容）；
- 语义分块默认化（收益三源冲突挂起，且边界不稳定，增量场景「编辑一处重切全文」与诉求相悖）。

## 复审三：增量文档格式契约

### 问题
用户手输/信源引入的文档要「规定大致格式」——规定到什么程度，才能确定性切片又不让用户负担过重？

### 判断
**最小 4 必填 + 渐进严格，纯文本自动包壳。** 文档头部 YAML frontmatter：

```yaml
---
title: 销售侧竞品分析            # 必填
source: "https://...|用户手输|文件路径"   # 必填，全局唯一来源键（幂等的锚点）
type: note|doc|snippet           # 必填
updated: 2026-10-15              # 必填
tags: [竞品]                     # 可选
---
```

- **系统字段用户不写、管道写入**：`doc_id`、`content_hash`、`strategy_version`、`chunk_index`、`heading_path`。
- **结构要求只一条**：用 `#/##/###` 分层，标题下避免超 800 字巨型段落（超长有递归兜底，不强制）。
- **手输纯文本零负担**：管道自动包一层 frontmatter（source 取内容 hash，type=note），不要求用户先学格式。
- 依据：frontmatter 把类型过滤前置到检索前（便宜验证先行），企业级 RAG 同样主张「显式固定 schema + 核心字段精简」。

---

## 复审四：实时入库的工程模式

### 判断
1. **按 source 先删后插**：Chroma `delete(where={"source": ...})` + `upsert`，只动被改的源（Chroma 官方能力，`ingest.py` 的 `delete_by_source` 已具备雏形）。
2. **确定性 chunk ID**：`{doc_id}:{strategy_version}:{chunk_index}`（或等价 hash）。邻居变化该块保留原 ID，写入是覆盖不是追加 → 重跑幂等、不产生重复。
3. **孤儿清理**：新版块数变少时仅 upsert 会残留旧块——必须按源记录 chunk ID 集合并删差集（工程坑，多来源明确指出）。
4. **幂等跳过**：每源记录 `content_hash + strategy_version`，均未变则整条流水线跳过（增量日更重嵌成本可降 80-95%）。
5. **全库重建的唯一触发**：`strategy_version` 变（切片策略升级）或嵌入模型/维度变。届时蓝绿重建（新库建好再切换），不是原地改。

## 复审五：存量论文的切片

### 判断
**abstract 摘要节点 + 章节 section chunk 双索引（同一 collection，metadata 区分），章节块可选 contextual header。**

- 摘要节点（chunk_type=abstract，每篇 1 块）答「这篇讲什么/哪几篇相关」；
- 章节块（chunk_type=section，300-600 字）答「具体方法/结论」；
- 只有 abstract 的论文维持「整篇一块」不变，等有全文再启用章节切。

依据：结构清晰文档上 structure-aware 切块检索与计算成本均优（工业域研究）；双索引兼顾总览与细节；contextual header 补回跨块语境。**放弃**：RAPTOR 全树（建树贵、约 4% 摘要轻幻觉）、late chunking（复审二已排除）。

---

## 复审六：存量社区讨论帖的切片

### 判断
**thread parent + 楼级子块（parent-child）**：OP + 高赞/被采纳回复组装为 thread parent（保留讨论脉络），每楼单独成子块，metadata 存 `parent_id / score / stance(支持|反对|中立)`。

依据：论坛回复脱离主帖语义不完整（「我反对」指向谁？多来源列为常见错误）；vote/采纳是现成的质量信号；正反立场保留下来才支撑「选型讨论」类问题。**放弃**：纯按楼切（丢脉络）、整帖一块（超长 + 签名/引用噪声主导嵌入）。旧技术讨论用时间戳过滤时效。

---

## 复审七：模型信息的存储

### 判断
**SQLite/JSON 结构化为准 + 模型卡叙述走向量，按问题类型路由。**

- 参数量/价格/上下文长度/能力边界等**事实字段进结构化表**——计数、比较、精确查值只有结构化查询做得了，向量做不到且会编数字；
- 模型卡的叙述文本（「适合做什么」）进向量，做语义匹配；
- 查询路由：比较/计数/精确值 → 结构化查询；场景匹配 → 向量。

**放弃**：纯向量存模型事实（数值幻觉风险）。

---

## 复审八：混合检索——真双路召回

### 问题
现实现（`store.py`：向量召回 top_k×5 → 候选内关键词打分 → 0.4/0.6 加权）是否算真混合检索？要不要重选？

### 判断
**现方案不是真混合检索，推翻重建。** 它是「单路向量召回 + 候选集内关键词 boost」：关键词精确命中但向量不在候选的结果（型号、人名、错误码、精确术语）永远出不来——密集向量会把稀有串「抹平」，这正是「模型信息/选型讨论」语料最常问的东西。业界共识：hybrid = 词法全库召回 ∥ 向量全库召回 → 融合。

**词法选型：jieba + bm25s。** 纯 Python/Numpy、免 Java/PyTorch、比 rank-bm25 快数个量级、支持自定义分词器，契合本机 Windows + 小语料（几千到几万 chunk）+ 中英混合。**放弃**：whoosh（曾两度弃坑）、tantivy-py（中文分词器注册未闭环）、SQLite FTS5（中文需自定义分词，兜底备选）、chroma-bm25（太新）。

**存储：ChromaDB 保留，旁路加 bm25s 词法索引。** 换 LanceDB（原生 BM25+向量+RRF 一体）是备选，但迁移成本对当前规模不值——规模涨到几十万 chunk 或 Chroma 稀疏能力成熟后再评估。

---

## 复审九：融合与重排

### 判断
1. **融合用 RRF（Reciprocal Rank Fusion，k=60 起步），替代 0.4/0.6 加权融合。** 理由：加权融合要归一化，而 BM25 分数无界、余弦 ∈[-1,1]，min-max 受离群值影响、α 难调；RRF 免归一化、单参数，是 ES/OpenSearch/Weaviate/Qdrant/Azure 的默认。
2. **层/质量/飞书权重保留，降级为 RRF 之后的乘数**：`最终分 = RRF分 × quality_weight(user_input 1.5 / curated 1.2 / auto 1.0) × feishu_ref_bonus 1.3`，同源去重、is_stale 过滤照旧。
3. **重排（reranker）在跨库合并之后做，模型可插拔**（2026-10-15 三轮修正，推翻本条原表述）：原「reranker 暂缓 + 本机跑不动」的推理作废——PMagent 是产品不是单机工具，使用者普遍经中转站接入各类模型，**选型不以单机硬件/成本为约束**。模型候选（bge-reranker-v2-m3 / Qwen3-Reranker 系列 / 托管 rerank API）按效果定，接入层做成可插拔；重排位置固定在合并去重之后。
4. **挂起冲突**：RRF k=60 在 top 段太平、会埋掉「单路决定性命中」（dev.to）vs k=60 可靠（app-lab/Elastic 默认）→ 不裁决，用少量标注 query 扫 k∈{10,30,60,100} 自测定档。

## 第二轮定调（2026-10-15，多域库网格与路由）

> 背景：资料库的总目标是帮项目以最好的方式完成需求——建成一个「行业、知识面极广的产品经理」，接近全知方向：跨领域需求不必去找两个领域的懂行者，由库替 Agent 补上判断力（Agent 本身缺判断能力；而 PM 在「找 + 判断」的过程中已经把好内容筛出来了，沉淀进库就是沉淀判断）。

1. **存量覆盖面泛化**：不只 AI 模型/范式，还包括代码相关方式、泛化方法、硬件（如单片机）、IT/PC 等——搜罗成网格，用自己筛过的内容替代网上中庸、质量不高的内容。
2. **多域库 + 路由机制（核心架构决策）**：存量按领域分库存在，单个域「总结完毕」即固定（frozen）；新内容**不强行叠进已完成库的切片**（明知向量切片无法完善叠加进已建成的库），而是由路由机制把注意力导向对应域的库，在那个库内检索切片后返回。
3. **增量库只收合规数据（清洗位置挪到库外）**：库侧零清洗——新规则写好（格式契约 = 准入标准），清洗在入库前完成；旧增量内容并入存量一起整理、固化。今后进增量库的只有「已按规则清洗过」的数据。（修正复审三/决策 2 中「管道自动包壳」的说法：包壳是入口侧动作，不是库内清洗。）
4. **旧版内容全部重置**：v1 的 5300 chunk 不做迁移兼容，随 strategy_version 升 v2 蓝绿重建；重置过程即一次性整理固化。缺口清单（实物）：缺 frontmatter 34 篇 + 缺 abstract 12 篇，见 `D:\AgentHub\Hermes\output\AI-PM-Agent-RAG\存量重置缺口清单.md`。
5. **contextual header**：先讨论后定。

## 第三轮定调（2026-10-15，切片定案 + 产品视角修正）

1. **切片定案（用户方案，替代复审二/五/六的粒度表述）**：
   - **断点优先级：标题 > 段落 > 约束词 > 字数上限**。宁可让某块只有 150 字，也**不能在条件句和结论之间切断**——流程分析类文本最大的坑就是条件/结论劈开后召回哪半都是错的。约束词（必须/不得/仅当/前提/假设/适用/不适用/除非…）做成词表规则，零成本。
   - **每块带 Contextual Header**：格式 `[领域] > [章节] > [条目]`，**参与嵌入与词法索引**（不只是 metadata）。这是小块不丢上下文的唯一保障，收益远高于把 overlap 从 0 提到 15%；结构化内容 overlap=0，仅叙事长文留约 10%。
   - **父子块必须上**：子块参与检索，父块进入上下文——检索打得准（小块）+ 答案说得全（大块）。父块/摘要块承接宽泛提问。
   - 与上一轮「大块切分」的关系：**不是推翻是细化**——大块降级为父块层，块内粒度此轮才定。
2. **产品视角修正（全局）**：选型**不考虑单机硬件、型号、成本性价比**——PMagent 是产品，使用者走中转站接入各类模型；文档中「本机跑不动」「CPU 只能跑 0.6B」类表述作废。
3. **检索默认定案（本轮补定）**：①引导外查询（kb_lookup/脚本/信源梯度）走保守通道——不做术语翻译与路由，双路直搜全库；②术语映射表 + 元数据打标归「入库前清洗」环节：Agent 按规则打、人只审；③摘要块进索引但排在子块之后；④词法+向量双路 + RRF 基座保留，「术语归一化/跨库并行/需求要素转元数据」是叠加层。
4. **暂放待议**：需求要素补全的元数据字段清单（「成本量级/合规敏感度」等需求侧字段 vs 内容侧字段的对齐问题）。

## 第四轮定调（2026-10-15，两层结构与原文归档）

1. **原文归档是一等公民（硬规矩）**：任何入库通道（CLI / inbox / 飞书）必须先把原文落 `domain_kb/source/` 归档，**再**切片入库——切片只是索引产物，永远可重切重建。已核查：v1 原文俱在（concept 209 篇原始 md + 514 篇论文 JSON），chunk 带 source + chunk_index 可完整溯源。**现存缺口**：飞书入口拉取文本直接切片未落原文归档，需补。
2. **两层结构（用户定调）**：
   - **存量层 = 复合嵌套多库**；检索层 = 混合检索 + **库级标签信息**参与检索决策（效果要测试）。嵌套深度按「域库 → 子域/类型」两级封顶理解（待确认）。测试要求：固定评测查询集（每库若干条 + 跨库若干条）作为调参标尺。
   - **增量库 = 对接用户信息源的随时入库通道**：(a) 格式契约硬闸门，不合规不入库——但不静默丢弃，顺序为「信源 → Agent 按规则清洗整理 → 格式校验 → 不合规退回 + 缺项清单」；(b) 数据一致性靠统一数据结构（切片=单文档纯函数 + 统一 schema/ID/strategy_version），且**跨库一致**：子库切法可不同，元数据必须同构，否则路由层无法统一工作。
3. **路线取舍（二选一，取 b）**：先用现有资料重建一个库 + 立好分层架构骨架，再按域补新库内容。理由：原文俱在恢复成本低；先跑通「切片→入库→路由→检索」全链路；新域搜罗是持续运营不是一次性工程；现有语料正好当新切片规则的试验田。顺序：现有库重建（v1 归档保留）→ 架构骨架定稿 → 按域补新库 → 信源对接增量。

## 第五轮定调（2026-10-15，存量更新 = 低频「整理→重切」）

1. **重切存量不禁止（用户变更）**：存量内容的重新切片不是禁区——只是相对于增量内容，它的更新间隔更长（增量随时进、进即检索；存量按季/月批量节奏）。据此**作废**复审四「全库重建的唯一触发 = strategy_version 变更或嵌入变更」的排他口径，扩为：**策略版本变、嵌入模型变、以及存量的周期性整理，都可以触发重切**。
2. **存量更新动作 = 两步**：①对库中需要切片的自然语言内容做一次**整理**（源层修订/归并/补缺，落在 `domain_kb/source/` 原文层——语料是本体）；②整理完**重新切片入库**（蓝绿重建，旧库归档不删）。切片始终是索引产物，永远可重切。
3. **frozen 语义收窄（对第二轮「不叠加原则」的精确化）**：域库 frozen 冻结的是「把新切片硬叠进已建索引」，**不是冻结库本身**。新内容不往旧索引上打补丁，而是进语料层、随下一次整理→重切成建制入库。不叠加原则保留原义，库本体可低频迭代。
